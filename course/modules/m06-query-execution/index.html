From SQL text to a running plan

Everything you built through Milestone 3 was preparation for this moment. The parser turns a SQL string into an abstract syntax tree; the binder resolves every table and column name against the catalog and attaches types (see M05). What comes out is still a description of a question. This module is about the machinery that turns that description into an answer: the planner, which produces an executable plan, and the executor, which runs it.

The classic survey by Hellerstein, Stonebraker, and Hamilton describes the whole arc in one sentence: a relational query processor takes a declarative SQL statement, validates it, optimizes it into a procedural dataflow execution plan, and executes that plan on behalf of a client, which then pulls result tuples, typically one at a time or in small batches.1 Two words there deserve emphasis. Dataflow: the plan is a graph whose nodes are operators and whose edges carry tuples. Pulls: the consumer asks for rows; nothing runs until someone asks.

PostgreSQL is the cleanest real-world illustration of the staging. A query passes through five subsystems: the parser builds a parse tree (rooted in a SelectStmt node) checking syntax only; the analyzer performs semantic analysis and produces a query tree (a Query structure recording the command type, target list, range table, and join tree); the rewriter transforms the query tree according to stored rules — this is how views are expanded into their defining subqueries; the planner produces a plan tree using purely cost-based optimization (PostgreSQL supports neither rule-based optimization nor hints); and the executor runs the plan tree, accessing tables and indexes in the order the plan nodes dictate.5 View expansion in the rewriter is an old idea with a long pedigree — the survey traces it back to INGRES, and lists it alongside constant folding and predicate rewrites as the standard rewriter duties.1

FerricDB collapses this into four stages, which is a course choice to keep Milestone 4 small: parse (MS3) → bind (MS3) → plan → execute. There is no separate rewriter; the few rewrites we ever do (constant folding, predicate pushdown) arrive in Milestone 7 as optimizer rules, mirroring where SQL Server hosts its rewriter — inside the optimizer — rather than DB2's stand-alone component.1 The public seam in course/ferricdb/crates/exec is three calls:

let plan = planner.plan(bound_statement)?;      // BoundStatement -> LogicalPlan
let plan = planner.optimize(plan)?;             // identity until Milestone 7
let mut exec = planner.create_executor(&plan)?; // LogicalPlan -> Box<dyn Executor>

Logical plans vs physical plans

A logical plan says what relational operation to perform: "filter these rows", "keep these columns", "order by this expression". A physical plan says how: which access path fetches the rows, which algorithm sorts them. The survey frames the optimizer's whole job as converting the internal query representation into an efficient plan — a dataflow diagram piping table data through a graph of operators — and its example plan is explicitly physical: HeapScan and IndexScan leaves feeding an IndexJoin, not the abstract "scan" and "join" of relational algebra.1 The distinction matters because one logical plan usually has several physical realizations with wildly different costs, and choosing among them is the optimizer's business (M08).

toyDB, the Rust engine we lean on throughout the course, represents a plan as a Plan enum whose variant names the statement kind (SELECT, INSERT, UPDATE, DELETE) and whose body is a tree of Node values; each node emits a stream of rows and may consume the row streams of its children, with rows flowing from the leaves to the root.3 For a SELECT with a join, filter, projection, and ORDER BY, toyDB's tree stacks Order over Projection over Filter over a join of two Scan leaves.3 FerricDB's plan::LogicalPlan enum is the same shape:

pub enum LogicalPlan {
    SeqScan    { table_idx: usize, table: TableInfo, filter: Option<BoundExpr> },
    Filter     { input: Box<LogicalPlan>, predicate: BoundExpr },
    Projection { input: Box<LogicalPlan>, exprs: Vec<BoundExpr>, schema: Schema },
    Sort       { input: Box<LogicalPlan>, keys: Vec<(BoundExpr, bool)> },
    Limit      { input: Box<LogicalPlan>, limit: u64 },
    Values     { rows: Vec<Vec<BoundExpr>>, schema: Schema },
    Insert     { table: TableInfo, input: Box<LogicalPlan> },
    Update     { table: TableInfo, set: Vec<(usize, BoundExpr)>, input: Box<LogicalPlan> },
    Delete     { table: TableInfo, input: Box<LogicalPlan> },
    // IndexScan (MS5), joins and Aggregate (MS6) join the enum later
}

Notice the name: LogicalPlan, even though Milestone 4 executes it directly. This is a deliberate course choice. Until Milestone 5 there is exactly one access path (the sequential scan) and one sort algorithm (in memory), so every logical node has exactly one physical realization and a separate physical tree would be pure ceremony. toyDB makes the same simplification — a single node tree serves as both.3 When index scans (MS5) and cost-based choices (MS7) arrive, create_executor becomes the place where physical decisions get made.

How do real systems represent the executable plan? The survey notes that every major DBMS now compiles queries into some interpretable data structure, but the abstraction level varies: some systems use a lightweight, relational-algebra-like tree annotated with access method and algorithm names, while others lower plans into op-codes closer in spirit to Java bytecode.1 PostgreSQL and SQLite sit at opposite ends of that spectrum, and it is worth seeing both because FerricDB copies one and your intuition from sqlite3 may come from the other.

PostgreSQL's planner emits a tree of plan nodes; the executor walks it, with control flowing top-down (a Sort node invokes the Seq Scan below it) while tuples flow bottom-up, one at a time, in classic Volcano style.5 EXPLAIN prints the tree directly — for a single-table query with an ORDER BY you see a two-node plan (costs elided here):5

Sort  (cost=… rows=… width=…)
  Sort Key: data
  ->  Seq Scan on tbl_1  (cost=… rows=… width=…)
        Filter: (id < 300)

The executor reads and writes tables through the buffer manager (M03), works within memory areas such as work_mem and temp_buffers, and spills to temporary files when a sort or hash exceeds them.5 The tree-of-objects design has structural advantages: a running plan stays mutable, and independent nodes are natural units to hand to separate threads.6 FerricDB is squarely in this camp.

SQLite compiles a SQL statement into bytecode: a prepared statement is literally a small program, executed by a virtual machine (the VDBE), with high-level opcodes like OP_Next (advance a B-tree cursor) and OP_Column (extract a column value).6 SQLite's own documentation contrasts this with MySQL and PostgreSQL, which compile SQL into "a tree of objects that represent the processing to be done" and execute by walking that tree.6 Bytecode's advantages: EXPLAIN renders the whole program as a flat, readable table of instructions; execution pauses naturally after each produced row (incremental evaluation is trivial); the program is compact; and the inner loop makes fewer decisions per step, so it runs fast.6 The costs: a bytecode program is hard to restructure once running, and harder to parallelize than a dataflow tree whose nodes are independent.6

The Volcano iterator model: open, next, close

Now the heart of the module. Most query executors, from the earliest relational systems to toyDB, use the iterator model (also called the Volcano model or pipeline model). The survey sketches the whole idea as a tiny superclass: an iterator has an array of input iterators and three methods — initialize, get the next tuple, and close — and every operator in the plan is a subclass of it.1 A typical system's subclass roster reads like our milestone list: file scan, index scan, sort, nested-loops join, merge join, hash join, duplicate elimination, grouped aggregation.1 FerricDB's version is the trait you will implement nine times in Milestone 4:

/// One row flowing between Volcano operators, carrying an optional RecordId
/// from base scans/filters so Update and Delete compose cleanly.
pub struct ExecRow { pub values: Vec<Value>, pub rid: Option<RecordId> }

/// Volcano iterator contract. next() returns Ok(None) at end of stream.
pub trait Executor {
    fn schema(&self) -> &Schema;
    fn open(&mut self) -> Result<()>;
    fn next(&mut self) -> Result<Option<ExecRow>>;
    fn close(&mut self) -> Result<()>;
}

(Naming is cosmetic and varies by system: the survey writes init/get_next/close,1 BusTub writes Init/Next and returns each tuple alongside its RID,2 toyDB reuses Rust's own Iterator::next.4 FerricDB's open/next/close returning ExecRow { values, rid } is a course choice: base scans attach rid: Some(rid) and Filter forwards it unchanged so Update and Delete know which slot to modify, while operators that synthesize rows — Projection, Values, joins, Aggregate — set rid: None.) The lifecycle:

  • open() — acquire resources and initialize state: look up the table's first page, allocate the sort buffer, reset counters. Each operator opens its children, so one call at the root cascades to the leaves.
  • next() — do the smallest amount of work needed to produce one output row, calling children's next() as needed; return Ok(None) when the stream is exhausted.
  • close() — release everything, again cascading down. After close, no more next() calls are legal.

Pull-based dataflow

The deep property of this design is that dataflow is coupled with control flow: a call to get_next() is an ordinary procedure call, and the tuple travels to the parent as its return value — a row moves up the tree exactly when control returns.1 Three big consequences follow, all from the survey.1

  • One thread suffices. A single thread executes the entire plan; there are no queues between operators and no rate-matching problem where a fast producer floods a slow consumer — contrast network dataflow systems, which need explicit feedback protocols between concurrent producers and consumers.1
  • Composability is total. Any iterator can be the input of any other; each operator's logic is independent of what sits above or below it, so no special-case code is needed for particular combinations.1 Your Limit will not know whether its child is a scan, a filter, or (from Milestone 6) a hash join — and must not care.
  • Resources stay busy, and first rows come early. Since some iterator is always active, a single-processor plan keeps resources fully utilized; and because rows stream out as soon as they are produced, the model also serves time-to-first-row, the metric interactive applications care about, not just time-to-completion.1

The model even survives parallelism: exchange operators encapsulate threading and network "push" behind the same pull-style get_next() interface, so the other operators never notice.1 You will not build exchange operators in this course, but it explains why the 1990-vintage design still runs inside nearly every SQL engine you can name.

In Rust the model is almost embarrassingly natural. toyDB's executor takes the plan, recursively calls execute_node() on each node, and has every node return a boxed row iterator that the parent consumes; pulling on the root iterator drives the entire pipeline by recursively calling next() on the children's iterators.4 FerricDB keeps an explicit Executor trait instead of bare Box<dyn Iterator> (a course choice: we need schema() for wire results and an explicit close() to unpin buffer pages deterministically), but the driver loop is the same four lines you will write in the REPL:

let mut exec = planner.create_executor(&plan)?;
exec.open()?;
while let Some(row) = exec.next()? {
    print_row(&row);
}
exec.close()?;
Where does the tuple's memory live?

The survey distinguishes BP-tuples — tuple references pointing into buffer-pool pages, which force the page to stay pinned as long as the reference lives — from M-tuples, copies materialized on the heap (by copying columns out of a page or by evaluating expressions).1 Always copying into M-tuples simplifies the executor and eliminates a classic bug — forgetting to unpin a page, a "buffer leak" — but the copies themselves can become the bottleneck, so high-performance engines support both.1 FerricDB always copies: a row is an owned ExecRow holding values: Vec<Value> (plus an optional RecordId), decoded from the page inside SeqScan. That is a course choice, trading memory bandwidth for never having a dangling page reference — the borrow checker would fight us on BP-tuples, and it would be right to.

Watch a plan run: the pull stepper

Time to make the cascade concrete. Take this table and query — the same fixed data the widget below uses:

SELECT name, balance FROM accounts WHERE balance >= 100 LIMIT 2;

Limit 2
└─ Projection: name, balance
   └─ Filter: balance >= 100
      └─ SeqScan: accounts        -- 8 rows in heap order

Worked example. The client's first next() on Limit cascades down — Limit asks Projection, Projection asks Filter, Filter asks SeqScan — and SeqScan reads row 1, (1, ada, 120). The predicate 120 ≥ 100 holds, so the row rides the return values back up and the client has its first result after exactly one heap read. The second pull is more interesting: SeqScan yields (2, bob, 45) — Filter rejects it and, without returning to its parent, calls SeqScan.next() again; (3, cat, 80) is rejected too; (4, dan, 200) passes and flows up. Filter's single next() invocation consumed three child rows. On the third pull, Limit has already emitted 2 rows, so it returns None immediately — it never calls Projection at all. The final tally:

Operatornext() calls receivedrows returned upward
Limit 232, then None
Projection22
Filter22
SeqScan44

SeqScan read 4 of 8 rows; rows 5–8 were never touched. Nothing in the Limit code "knows" about scans — the early exit falls out of the pull discipline: work happens only when a parent asks, and Limit stops asking.1 Scale the intuition up: if accounts had a million rows and the first two matches still sat in rows 1 and 4, the query would still perform exactly 4 heap reads. BusTub's spec states the operator's contract dryly — Limit constrains the number of output tuples, and has no effect if the child produces fewer than the limit2 — but the performance consequence is this short-circuit.

The gap between "calls received" and "rows returned" is where execution cost hides. When you implement EXPLAIN ANALYZE-style counters in FerricDB, these are exactly the numbers to expose.

Streaming vs blocking, and rival execution models

Streaming operators and pipeline breakers

Filter, Projection, and Limit are streaming operators: each output row needs only a bounded amount of input, so rows flow through with O(1) state and the first result reaches the client while the scan is still cold. Blocking operators break the pipe. A sort cannot emit its first output row until it has seen its last input row — the minimum of the sort order might be the final tuple the scan produces. toyDB's Order node therefore buffers all input rows in memory before sorting them,4 and PostgreSQL's executor sorts within work_mem, spilling to temporary files when the data exceeds it.5 The BusTub spec names the phenomenon: aggregation is a pipeline breaker, as is the build side of a hash join — which is why those executors do their heavy lifting in Init() rather than Next().2

Inside the iterator contract, "blocking" is not a different interface — it is just an operator whose first next() call is expensive. Your Milestone 4 Sort will drain its child completely on the first pull, sort the buffered rows, then stream them out one per call. The contract is preserved; only the latency profile changes. That means everything downstream of a Sort loses the time-to-first-row benefit, and a LIMIT above a Sort cannot save the scan — though production engines can save comparisons via a bounded top-k heap instead of sorting the entire stream.

Materialization and vectorization, surveyed

Tuple-at-a-time pulling is not the only way to run a plan tree. Two alternatives matter, and you should be able to place any engine you meet on this axis.

  • Full materialization. Each operator consumes its entire input, computes its entire output, and hands the finished intermediate table to its parent. This is the natural model if you think of relational algebra as set functions, and it is effectively what a blocking operator does locally. As a whole-engine strategy it forfeits early results and can allocate intermediate results as large as the base tables — our LIMIT query above would read all 8 rows (or all million) before Limit discarded the surplus. Its virtue is simplicity and tight loops per operator.
  • Vectorized (batch-at-a-time) execution. Keep the pull-based tree, but let each next() return a batch of tuples instead of one. This is not exotic: the current BusTub is built this way — every executor's Next returns a batch of up to BUSTUB_BATCH_SIZE tuples (plus their record IDs), or an indicator that no tuples remain.2 Even the classic survey's client interface anticipates it: results are pulled "typically one at a time, or in small batches".1 The point is to amortize per-call overhead — one virtual dispatch per few thousand values rather than per value — the same "fewer decisions per step" argument SQLite makes for its bytecode inner loop.6 The price is more in-flight memory and more bookkeeping at operators like Limit that must split batches.

FerricDB stays tuple-at-a-time for the whole course. The reasoning is pedagogical: every operator's state machine is visible in a page of Rust, and correctness bugs surface as a single wrong row rather than a corrupted batch boundary. If you later want the vectorized flavor, the refactor is mechanical — change next() to return Vec<ExecRow> and teach each operator to loop.

Evaluating expressions over tuples

Operators move rows; expressions compute over them. A Filter carries a predicate expression, a Projection carries one expression per output column, an Update carries one per assignment. BusTub's planner models them the same way: expression trees of column references, constants, and arithmetic nodes attached to plan nodes.2

The single most important design decision is when names die. In the AST, a column reference is a name ("balance"); ambiguity is everywhere — after a join, two tables may both have a released column, aliases rename things, and an ORDER BY may reference a column the projection does not even output. toyDB resolves all of this at plan time: the planner threads a Scope that tracks which column names are visible at each node and which index each occupies, and build_expression() converts every by-name reference into a by-index reference — its docs show a join predicate movies.genre_id = genres.id compiling down to the positional form #3 = #4 against the joined row layout.3 FerricDB does the same one milestone earlier: the binder (M05) produces BoundExpr trees whose column references are already (table, column-index) pairs, so by the time an executor sees an expression, evaluation is a recursive walk in which a column reference is a plain row[i] array access — no string comparison, no catalog lookup, no failure path.

Types were settled even earlier, and the catalog is what settled them. The survey's example is worth internalizing: in (EMP.salary * 1.15) < 75000, which multiplication routine runs and how the literals are represented depends entirely on the declared type of EMP.salary — integer, float, or "money" — information the parser pulled from the catalog when it validated attribute references.1 FerricDB's Value::sql_cmp handles the last subtlety at runtime: it returns None when either side is NULL, mirroring SQL's three-valued comparison logic from M01 — and your Filter must treat a NULL predicate result as "do not pass", not as an error.

Note also what expression evaluation produces: fresh values that belong to no page. In the survey's vocabulary, evaluating EMP.sal * 0.1 constructs an M-tuple on the heap.1 This is why our Projection returns a new Vec<Value> rather than a slice of its input — some of its outputs never existed in storage at all.

The catalog: the executor's map of the world

Every stage of the query processor consults the catalog, each asking a different question. The parser asks "does this table exist, and what are its columns' types?" — the survey describes the parser canonicalizing each table name, invoking the catalog manager to verify the table is registered, caching its metadata, and then using the catalog to validate every attribute reference.1 The planner asks "what does the row layout look like, and what access paths exist?" — toyDB's Planner holds a catalog handle precisely to fetch table schemas while building Scan nodes.3 The executor asks the bluntest question of all: "where are the bytes?" BusTub's executors call Catalog::GetTable() and Catalog::GetIndex() during Init() to locate the physical table and any indexes that must be maintained.2

In FerricDB the answers live in two structs you defined in Milestone 3: TableInfo (oid, name, schema, first_page, indexes) and IndexInfo (oid, name, column, root_page). A SeqScan's open() is little more than catalog.table("accounts")? followed by HeapFile::open(store, info.first_page); an Insert uses the same TableInfo to find where new tuples go, plus the schema to type-check what it writes. The catalog is itself stored in heap pages and reads itself at startup from fixed bootstrap page ids — a course choice from MS3 that pays off here: the executor needs no special path for system tables, because .tables in the REPL is just a scan over the catalog's own heap.

One contract deserves its own paragraph, because our test harness enforces it from Milestone 4 on: every executor must know its output schema, and its rows must match it exactly. BusTub warns that executors "must produce tuples with schema exactly as specified in the plan node" or fail the tests;2 FerricDB surfaces the same rule as Executor::schema(), which the REPL uses for column headers today and the wire protocol will use for RowDescription messages in Milestone 10. The planner computes schemas bottom-up: SeqScan's schema is the table's; Filter's is its child's, unchanged; Projection's is derived from its expression list. If your Projection reorders columns, its schema must say so.

Operator semantics: the Milestone 4 zoo

Here is the executor roster for Milestone 4, operator by operator. For each: what next() must do, and where the traps are. Throughout, remember the composability rule — each operator may assume nothing about its child except the iterator contract.1

Reading: SeqScan, Filter, Projection, Values, Limit, Sort

SeqScan walks the table's heap pages in physical order, decoding one tuple per next(). It sits directly on HeapFile::scan() from Milestone 1 (M02). The subtlety is dead tuples: a heap slot may hold a deleted or invalid tuple, and the scan must skip it silently — BusTub's SeqScan likewise checks each tuple's metadata (is_deleted_) and skips deleted entries.2 FerricDB's SeqScan plan node also carries an Option<BoundExpr> filter, so a pushed-down predicate can be applied during the scan without a separate Filter node — the same shape as toyDB's Scan, which passes an optional predicate straight into the storage engine's scan call.4 At MS4 your planner may leave that field None and rely on an explicit Filter; the optimizer starts filling it in Milestone 7.

Filter holds a predicate and one child.2 Its next() is a loop: pull a child row, evaluate the predicate, return the row if the result is true, otherwise pull again; propagate None. It is stateless beyond the child handle. Treat a NULL predicate result as false-for-filtering, per three-valued logic.

Projection evaluates its expression list against each input row and emits the results as a new row — toyDB's projection node does exactly this per joined row.4 It never filters and never reorders rows; count in must equal count out.

Values is a leaf that yields literal rows from the plan itself — BusTub uses it as the child of Insert for INSERT INTO t VALUES (...).2 Note the expressions still need evaluation (a literal row may contain 1 + 2), just with no input row to reference.

Limit keeps a counter; after emitting limit rows, it answers None forever without touching its child — the short-circuit you watched in the stepper. If the child ends first, Limit passes the None straight through; a limit larger than the input has no effect.2

Sort is Milestone 4's only blocking operator. On the first next() (or in open(), your choice — BusTub frames the same decision for its pipeline breakers2), drain the child into a Vec, sort with a comparator built from the plan's (expression, descending) key list and Value::sql_cmp, then stream from the buffer. Because Value::sql_cmp returns None when either operand is NULL, your comparator must impose a total order on NULLs: FerricDB's course convention is NULLS LAST for both ASC and DESC (verified by ms4_order_by_limit_and_null_ordering). Buffering in memory is precisely toyDB's approach — its Order node buffers everything in memory4 — and it is a labeled course choice: real engines cannot assume the input fits, which is why PostgreSQL spills sorts to temp files beyond work_mem5 and CMU's project builds a two-way external merge sort with multi-column keys, ASC/DESC directions, and NULLS FIRST/LAST handling.2 FerricDB defers external sorting to Milestone 6 (ExternalSorter, with a fixed page budget); Milestone 4's sort is allowed to be a Vec and a comparator.

Writing: Insert, Update, Delete

DML plans are shaped differently from queries: the survey describes them as simple straight-line plans — one access method as the source, and a data modification operator at the top of the pipeline.1 An INSERT's source is usually a Values node; UPDATE and DELETE sit above a scan (plus Filter) that finds the victim rows. All three are executors like any other, but their observable output is tiny: BusTub's Insert, Update, and Delete each emit a single tuple containing one integer — the number of rows affected.2 FerricDB surfaces the same number as QueryResult::affected (course choice, matching that convention), which the REPL prints as INSERT 3.

Insert pulls each row from its child, validates it against the table schema from the catalog, encodes it, and calls HeapFile::insert. From Milestone 5 onward it must also insert into every index on the table — BusTub requires exactly this index maintenance.2

Delete needs to know which physical tuple to kill, which a bare Vec<Value> row does not say. BusTub solves this by having every executor's Next return record identifiers (RIDs) alongside tuples, so a Delete can address the exact slot its child produced.2 FerricDB adopts the same idea via ExecRow { values, rid }: base scans populate rid: Some(RecordId) (page id + slot — the analog of Postgres's ctid) and Filter preserves it unchanged, so Delete and Update compose cleanly over any scan/filter pipeline. Deletion itself is a logical mark, not immediate physical compaction: in Milestone 4, Delete tombstones the slot's line pointer via HeapFile::delete(rid) (analogous to BusTub setting is_deleted_ on the tuple header rather than removing bytes in place2), while TupleMeta stays zeroed until M09 / Milestone 8 switches DELETE to stamping TupleMeta::xmax for MVCC visibility and defers slot tombstoning plus space reclamation to VACUUM.

Update is read-modify-write: pull a row and its RID, evaluate the SET expressions (each assignment in FerricDB's plan is a (column-index, expression) pair), and write the result back. The simplest correct implementation is the one BusTub prescribes: delete the old tuple, insert the new one.2 That choice — updates may move tuples — is also the door to one of the oldest bugs in the field.

Pitfall: the Halloween problem

Discovered by the System R group on October 31st, hence the name. Take "give every employee earning under $20K a 10% raise" and run it as a pipeline: an index scan over EMP.salary feeding an Update operator. Each raise rewrites the tuple, which — because the scan's index is on the updated column — can reinsert it ahead of the scan cursor. The scan rediscovers the tuple, raises it again, and again, until every victim earns more than $20K. SQL semantics forbid this: a statement must not see its own updates. Standard fixes: have the planner refuse index scans on the updated column, or split the pipeline — materialize the full list of victim RIDs first, then fetch and update them in a second pass.1

Do not assume a sequential scan is immune. In Milestone 4, Update tombstones the old tuple and writes the new version via HeapFile::insert, which appends the replacement at a higher slot on the same page or on an appended page at the tail of the heap chain. A live SeqScan walking (page_id, slot) in ascending order can therefore encounter its own newly inserted tuples later in the very same scan — even with zero indexes — and update qualifying rows repeatedly (for example, UPDATE n SET x = x + 1 WHERE x < 100 re-incrementing rows 95–98 all the way to 100). Milestone 4 therefore adopts Figure 3's batch fix: Update drains its child completely first, materializing every matching (RecordId, new_values) pair using the rid on each ExecRow returned by Executor::next, closes the scan, and only then applies the deletes and inserts — verified directly by the provided test ms4_halloween_guard. When Milestone 5 adds IndexScan, the same materialization step shields index-driven updates as well.1
