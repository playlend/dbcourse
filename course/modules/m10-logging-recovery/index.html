Milestone 8 gave FerricDB isolation; this module is about the other half of the ACID contract: durability (a committed transaction is never lost) and atomicity (a half-finished one never survives) — maintained across the most hostile event a database faces, the crash.4 The algorithm is ARIES, published by Mohan et al. in 1992 after a decade of hard lessons inside IBM, and still the reference design for every disk-based engine, Postgres included.1

What we promise to survive

Three failure classes, three answers. A transaction failure (one transaction aborts — a conflict, a constraint, a user Ctrl-C) needs rollback of just that transaction while everyone else proceeds. A system failure (process crash, power loss) wipes everything volatile — buffer pool, transaction table — but leaves the disk intact; this is the one recovery machinery exists for. A media failure (the disk dies) needs backups plus log archives — Postgres's point-in-time recovery, a survey topic here.3 The tricky part of a system failure is what the disk looks like afterward: some pages new, some old, in no useful order — a state that reflects buffer-pool eviction timing, not transaction boundaries.

Steal and no-force: the bargain

Two policy questions determine how hard recovery is, and CS186's recovery notes frame them crisply.4 Force: must a transaction's dirty pages be flushed to disk before it commits? Forcing makes durability trivial and performance terrible — a commit becomes many random writes. Steal: may the buffer pool evict (and thus write) a page dirtied by a transaction that hasn't committed? Forbidding it makes atomicity trivial — uncommitted data never reaches disk — and memory management miserable, because pinning entire write sets in RAM bounds transaction size by pool size.

Every serious system picks steal + no-force: the best-performing pair and the worst for recovery — uncommitted data can be on disk (needs undo), and committed data can be missing from disk (needs redo).4 The entire rest of this module is the price of that choice, and it is worth paying: with no-force, a commit costs one sequential log flush, and one fsync of the log can commit many small transactions at once.2

The write-ahead rule

The mechanism that makes steal/no-force safe is the log: an append-only record of every change, written ahead of the data. The PostgreSQL documentation states the central concept exactly: changes to data files must be written only after those changes have been logged — after the WAL records describing them have been flushed to permanent storage.2 Two inequalities, then, define the discipline:4

  • Before flushing page P: pageLSN(P) ≤ flushedLSN — the log describing P's changes reaches disk before P does. Your Milestone 2 buffer pool's LogFlusher hook exists to enforce exactly this.
  • Before acknowledging commit: lastLSN(T) ≤ flushedLSN — including the commit record itself. Nothing else needs flushing: that is no-force.

LSNs everywhere

Every log record gets a log sequence number — monotonically increasing, in practice the record's byte offset in the log. Three derived quantities do all the work:4 pageLSN — stored in each page's header (your Milestone 1 reserved those 8 bytes), the LSN of the last record that modified the page: recovery's way of knowing exactly how much of history a disk page already reflects. flushedLSN — in memory, the last log record safely on disk. prevLSN — in each log record, the same transaction's previous record, chaining each transaction's history backward through the shared log so rollback can walk just its own records.

The bookkeeping: ATT and DPT

Recovery reconstructs two in-memory tables, so know them before the algorithm:4

Active Transaction Table (ATT)

One row per in-flight transaction: txid, status (running / committing / aborting), and lastLSN — its most recent log record, the entry point into its prevLSN chain.

Dirty Page Table (DPT)

One row per page that is dirty in memory: page id and recLSN — the LSN of the first record that dirtied it since it was last clean. recLSN is the earliest point at which disk might be missing changes to this page — which is why redo starts at the DPT's minimum recLSN.

ARIES: analysis, redo, undo

After a crash, ARIES makes three passes over the log:1

  1. Analysis — start at the last checkpoint and scan forward, rebuilding the ATT and DPT as of the crash: updates add transactions (tracking each one's lastLSN) and add pages to the DPT with their recLSN; commits remove transactions. Analysis determines the RedoLSN — where the redo scan must begin — and the list of loser transactions to roll back.1
  2. Redo — "repeating history." Scan forward from the minimum recLSN and re-apply logged updates whose effects didn't reach disk — including the losers' updates. ARIES reestablishes the exact state as of the failure, uncommitted mess and all, before cleaning any of it up. A record is redone iff the affected page's pageLSN is less than the record's LSN; no logging happens during redo.1 Re-applying to a page that already has the change would double-apply it; the pageLSN comparison is what makes redo idempotent — crash during recovery, recover again, same result.
  3. Undo. Roll back all losers' updates in reverse chronological order in a single backward sweep: repeatedly take the maximum lastLSN among not-yet-finished losers, undo that record, follow its prevLSN. Unlike redo, undo is not conditional — no pageLSN comparison — because history was just repeated, so every loser update is known to be present.1 Each undo writes a compensation log record (CLR) describing the compensating change, whose UndoNxtLSN pointer names the next record of that transaction still to undo — precisely tracking rollback progress, so a crash mid-undo resumes where it left off instead of undoing twice. CLRs are redo-only: they are never themselves undone.1

Fuzzy checkpoints

Without checkpoints, analysis and redo would scan from the beginning of time. A naive checkpoint — freeze everything, flush everything — is a availability disaster. ARIES instead takes fuzzy checkpoints: write a record capturing the current ATT and DPT, without stopping transactions or flushing pages.1 The checkpoint is a photograph of the bookkeeping, not a sync point: analysis starts from it (loading the saved tables) and scans forward, and redo can still reach back before it, to the oldest recLSN in the saved DPT. Cheap to take, so you take them often, bounding recovery time by checkpoint frequency.

How Postgres does it

PostgreSQL's WAL (the "xlog") implements the same discipline with its own vocabulary: practical systems write transaction logs precisely because logging changes is dramatically cheaper than synchronously writing whole pages per change, and the server recovers by replaying the log after a crash.3 Its recovery is redo-focused (roll-forward), with MVCC playing the role of undo — aborted transactions' tuples are simply invisible, Milestone 8's gift.2 Two production refinements worth knowing: full-page writes (the first change to a page after a checkpoint logs the whole page, defending against torn writes), and WAL archiving, which turns the log into a time machine — restore a base backup, replay archived WAL to any instant: point-in-time recovery.2 FerricDB follows ARIES more faithfully than Postgres does — you log before-images and write CLRs — because implementing undo is where the algorithm's deepest ideas live.
