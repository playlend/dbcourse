Module 9 and Milestone 8 gave FerricDB isolation across concurrent transactions. This module builds the other half of the ACID contract: durability (once COMMIT returns, the transaction's effects are never lost) and atomicity (a half-finished or aborted transaction never leaves partial effects on disk) — even when the server loses power at the worst possible microsecond.4 The algorithm is ARIES (Algorithms for Recovery and Isolation Exploiting Semantics), published by Mohan et al. in 1992 after a decade of hard production lessons inside IBM, and still the architectural foundation for virtually every disk-based transactional engine, including PostgreSQL and your Milestone 9 course/ferricdb/crates/wal.1

What we promise to survive

Database recovery distinguishes three failure classes, each demanding a different mechanism:

  1. Transaction failure: A single transaction aborts during normal execution — an explicit ROLLBACK, a serialization conflict (Error::Serialization), a constraint violation, or a dropped client connection. Only that transaction's writes must be undone while every other transaction continues uninterrupted.
  2. System failure (crash): The database process dies (SIGKILL, panic, kernel crash, or power cut). Every volatile in-memory structure — buffer pool frames, dirty page table, active transaction table, and in-memory commit statuses — disappears instantly, while previously synced disk blocks remain intact. After a system crash, the on-disk data files contain an arbitrary mix of stale pages (whose recent committed writes never reached disk) and dirty pages (whose uncommitted writes were evicted early to make room in RAM). ARIES exists to turn that arbitrary disk state back into the exact committed state.
  3. Media failure: The storage device itself is destroyed or corrupted beyond repair. Local logs cannot survive a dead drive; survival requires off-host base backups plus continuous log archiving (PostgreSQL's Point-In-Time Recovery, surveyed near the end of this module).23

Steal and no-force: the buffer-pool bargain

How hard crash recovery becomes depends directly on two buffer-pool policies framed crisply in Berkeley CS186's recovery notes:4

  • Force vs No-Force: Must the buffer pool flush all pages modified by a transaction to the data files before reporting COMMIT? A force policy makes durability trivial (committed pages are always on disk) at disastrous runtime cost: every small commit stalls on scattered random 8 KB page writes. Under no-force, a commit flushes zero data pages — only a single sequential append to the log file.
  • No-Steal vs Steal: May the buffer pool evict (and write back to disk) a dirty page touched by a transaction that has not yet committed? A no-steal policy makes atomicity trivial (uncommitted data never touches disk), but forces every in-flight transaction's entire write set to stay pinned in RAM — crashing with BufferPoolExhausted whenever a bulk UPDATE exceeds pool size. Under steal, the replacer can evict any unpinned page freely.

Every high-performance engine chooses steal + no-force: maximum runtime throughput in exchange for supporting both undo and redo at restart.4 The payoff is enormous: because log writes are strictly sequential, a single fsync of the log tail can durably commit dozens of concurrent transactions at once (group commit), turning dozens of random seeks into one sequential write.2

The write-ahead rule

The mechanism that makes steal/no-force safe is the write-ahead log (WAL): an append-only, durable sequence of records describing every change, written to disk ahead of the data pages it modifies. PostgreSQL's documentation states the central rule directly: changes to data files must be written only after those changes have been logged — after the WAL records describing them have been flushed to permanent storage.2

Two inequalities enforce this contract across the entire engine:4

  1. Steal safety (before writing dirty page P to disk): pageLSN(P) ≤ flushedLSN. Every log record describing mutations on P (including before-images needed to undo uncommitted writes!) must reach durable storage before P overwrites the data file. Your Milestone 2 BufferPoolManager already exposes set_log_flusher(Arc<dyn LogFlusher>) to invoke flush_until(page.lsn()) before any eviction or explicit flush.
  2. No-force durability (before acknowledging COMMIT of transaction T): lastLSN(T) ≤ flushedLSN, where lastLSN(T) is T's Commit log record. Because log flushing is a prefix operation, flushing through the commit record guarantees that every earlier update of T is durable too — while data pages stay lazily in the buffer pool.

LSNs everywhere

Every log record receives a strictly increasing 64-bit Log Sequence Number (LSN) — in ARIES and PostgreSQL, the record's byte address in the log stream (in FerricDB, Lsn = u64 with real records numbered ≥ 1 and 0 reserved for "none").14 Seven LSN quantities knit the entire storage engine, buffer pool, and recovery manager together:

One subtle concurrency invariant governs pageLSN: when a writer mutates a heap page, it must append the log record and stamp page.set_lsn(record_lsn) while still holding the page's exclusive write latch (WritePageGuard). That guarantees the order of mutations applied to a page matches their LSN order in the WAL, which physical redo relies on strictly.1

The bookkeeping: ATT and DPT

During normal execution the engine maintains two small volatile tables in RAM; after a crash they are gone, and ARIES's first pass exists specifically to reconstruct them:4

Active Transaction Table (ATT)

One entry per currently running transaction: txn_id, status (running / committing / aborting), and lastLSN — the head of its backward prevLSN chain. A transaction leaves the ATT only when its final Commit or Abort record is logged.

Dirty Page Table (DPT)

One entry per dirty page in the buffer pool: page_id and recLSN — the LSN of the first mutation that dirtied the page after it was loaded clean (never overwritten on subsequent updates to that same page until the page is flushed clean). recLSN marks the earliest log record whose effect on that page might be missing from disk.

ARIES: analysis, redo, undo

After a crash, ARIES restores the database in three deterministic passes over the durable WAL.1 Every pass has one crisp job, and together they achieve a remarkable property: idempotency under arbitrary crashes during recovery.

Pass 1 — Analysis (forward from the last complete checkpoint)

Load the latest complete checkpoint’s metadata from the master record — its CheckpointBegin LSN plus the cumulative pre-checkpoint committed_txns and max_txn_id (or start empty at LSN 1 if no checkpoint has been taken yet) — and scan forward to the end of the durable log (stopping cleanly at any torn trailing bytes):1

  • When passing CheckpointEnd, merge its photographed tables into ATT and DPT (skipping any active_txns entry already present in ATT or already seen as Commit/Abort since CheckpointBegin, and keeping the smaller recLSN if a page appears in both DPTs).
  • For any transaction record (Begin, Insert, Update, Delete, Clr), insert or update ATT[txn].lastLSN = record.lsn.
  • For any page-modifying record (PageInit, Insert, Update, Delete, Clr), if record.page is not already in the DPT, insert DPT[record.page] = record.lsn.
  • For Commit, remove txn from the ATT and add it to committed_txns (winner!). For Abort, remove txn from the ATT (already fully rolled back before the crash).

At the end of the log, whoever remains in the ATT is a loser transaction that must be undone, and RedoLSN = min(DPT.values()) tells Pass 2 where to begin (if the DPT is empty, Redo skips completely).1

Pass 2 — Redo: "repeating history" (forward from min recLSN)

ARIES's defining paradigm is repeating history: scan forward from min recLSN and re-apply every page-modifying record whose effect is missing from disk — for winners, for losers, and for CLRs alike — so the database first reconstructs the exact physical state as of the crash before rolling anything back.1

A page-modifying record (PageInit, Insert, Update, Delete, or Clr) must pass two distinct filters before Redo applies it:1

  1. Filter 1 — DPT pre-check (in-memory, zero disk I/O): Skip immediately if record.page ∉ DPT OR record.lsn < DPT[record.page].recLSN. Any record predating the page's recLSN was already flushed before the page first became dirty.
  2. Filter 2 — On-page pageLSN check (ground truth): Fetch the page through the buffer pool and read its header. Apply the record's redo action if and only if page.lsn() < record.lsn, then stamp page.set_lsn(record.lsn). If page.lsn() ≥ record.lsn, skip it — that mutation (or a newer one) already reached disk before the crash.

Both filters are mandatory and solve different jobs: Filter 1 avoids unnecessary page reads, while Filter 2 guarantees idempotency (re-applying an already-present slotted-page mutation would corrupt the page).13 Notice two crucial rules: CLRs are redone during Redo under the exact same two filters, and Redo writes zero new log records.

Pass 3 — Undo (single backward sweep over losers)

Now every loser's writes are guaranteed to be physically present on disk/buffer pages. Undo rolls back all losers in one reverse-chronological sweep across the log:1

  1. Maintain a priority set ToUndo seeded with ATT[t].lastLSN for every loser t.
  2. While ToUndo is non-empty, pop the maximum LSN across all losers and inspect that record:
    • If it is an undoable mutation (Insert, Update, Delete): apply its inverse unconditionally (no DPT check, no pageLSN check — repeating history guarantees the page matches!), append a Compensation Log Record (CLR) with undo_next = record.prev_lsn, stamp page.set_lsn(clr.lsn), and push record.prev_lsn into ToUndo (if non-zero).
    • If it is a CLR (left over from an interrupted rollback or an earlier crash during recovery): never undo a CLR! Jump straight to clr.undo_next.
    • When a loser's chain reaches 0 (or its Begin record), append LogRecord::Abort { txn } (ARIES's transaction-end record) and remove the loser from the ATT.

Why is the CLR + undo_next trick one of the most celebrated ideas in systems engineering? Because if the machine crashes halfway through Undo, the next restart runs Redo (which replays all CLRs already flushed!) and then Undo hits the latest CLR and hops directly via undo_next past every record already rolled back. Every original update is undone at most once, even across ten consecutive crashes during recovery — bounding log growth strictly.1

Two-record fuzzy checkpoints

Without checkpoints, Analysis and Redo would scan the entire WAL from LSN 1 on every restart. A naive sharp checkpoint — freeze all incoming transactions, flush every dirty page in the buffer pool to disk, then resume — is an availability disaster on a busy server. ARIES instead takes fuzzy checkpoints that photograph the bookkeeping without stopping writers or forcing dirty pages:1

  1. Append CheckpointBegin to the WAL (remembering its LSN).
  2. Snapshot the live tables without blocking traffic: read the current ATT ((TxnId, lastLSN)) and ask the buffer pool for its dirty pages via BufferPoolManager::dirty_pages() (Vec<(PageId, Lsn /*recLSN*/)>).
  3. Append CheckpointEnd { active_txns, dirty_pages } and flush the WAL through CheckpointEnd.
  4. Atomically update the master record (ARIES's durable checkpoint pointer; pg_control in PostgreSQL3) to point at this completed checkpoint.

Why two records instead of one? Because concurrent transactions keep logging updates and dirtying pages between Step 1 and Step 3 while the checkpointer gathers the ATT and DPT! If recovery started Analysis at CheckpointEnd, a mutation logged just before Step 3 might have been missed when Step 2 read the DPT. Starting Analysis at CheckpointBegin guarantees every record logged during checkpointing is scanned and reconciled with CheckpointEnd's tables.1 And updating the master record only after CheckpointEnd is durable ensures that a crash halfway through taking a checkpoint safely falls back to the previous complete checkpoint.

Remember the golden rule of fuzzy checkpoints: a checkpoint bounds where Analysis starts, not where Redo starts. Because no dirty pages were forced to disk, the DPT inside CheckpointEnd can still hold recLSN values strictly smaller than CheckpointBegin — so Redo still reaches back to min recLSN (Figure 2). In production, a background writer dribbles old dirty pages out asynchronously so min recLSN advances steadily without checkpoint I/O spikes.13

Physiological vs physical logging and MVCC recovery

What exactly goes inside the payload of a log record? Recovery designs pick among three granularities:1

  • Physical logging: Record raw byte ranges ("at page 7 offset 8120, old bytes = …, new bytes = …"). Simple to replay, but fragile: compacting a slotted page moves byte offsets, and two concurrent writers on different slots of the same page cannot safely undo out of order if byte offsets shifted.
  • Logical logging: Record high-level SQL or operator actions ("insert row (42, 'ada') into users"). Tiny log records, yet fatal on partial crashes: if a B+Tree split crashed halfway through touching two pages, re-running a logical operation sees an inconsistent tree.
  • Physiological logging (ARIES's compromise): Physical to a single page, logical within that page ("insert tuple payload into slot 3 of page 7"). Each log record names exactly one page so its pageLSN test is self-contained, while slot-level addressing tolerates intra-page compaction and supports fine-grained concurrency.1

In course/ferricdb/crates/wal/src/lib.rs, FerricDB uses clean tuple-physical / slot-addressed logging matching ARIES's structure without page-splitting complexity. Every mutation variant carries the exact data needed for redo and undo:

  • PageInit { page_id } — logs formatting a brand-new heap page (HeapPage::init) so Redo can re-initialize an unflushed newly allocated page before replaying Insert records onto it.
  • Begin { txn }, Commit { txn }, Abort { txn } — transaction lifecycle markers.
  • Insert { txn, rid, tuple, meta } — Redo places (meta, tuple) at the exact slot rid via HeapPage::put_at; Undo tombstones rid via HeapPage::delete.
  • Update { txn, rid, old_meta, old, new_meta, new } — carries both before-image (undo) and after-image (redo) for in-place metadata/tuple mutations such as stamping xmax.
  • Delete { txn, rid, old_meta, old } — Redo tombstones rid; Undo restores (old_meta, old) at rid via HeapPage::put_at.
  • Clr { txn, rid, action, undo_next } — carries an explicit ClrAction::Tombstone (compensating an Insert) or ClrAction::Restore { meta, tuple } (compensating an Update or Delete), replayed on Redo and skipped via undo_next on Undo.
  • CheckpointBegin and CheckpointEnd { active_txns, dirty_pages }.
Two bridges that make Milestone 8 + Milestone 9 truly ACID

1. Normal ROLLBACK reuses ARIES Undo. When a live transaction aborts during normal operation, FerricDB does not need a separate rollback code path: WalHook::rollback delegates to ferricdb_wal::rollback_txn, which walks that transaction's prevLSN chain backward (including any unflushed tail records), applies HeapPage::delete / HeapPage::put_at, writes a Clr for each undone mutation, and appends Abort — the exact same routine Pass 3 runs after a crash.1 (In production PostgreSQL, MVCC lets ROLLBACK skip physical undo and CLRs — its WAL is redo-only, leaving aborted tuple versions for VACUUM; FerricDB runs ARIES physical undo on live ROLLBACK too so you build the full Mohan et al. algorithm end to end.)

2. Post-recovery MVCC restoration. When FerricDB restarts after a crash, TransactionManager::new() starts with an empty commit map and next_txid = 1. If you stopped right after recover(wal, pool), every pre-crash committed tuple (say xmin = 7) would look uncommitted to Snapshot::is_visible, and the first new transaction would reuse TxnId = 1 and collide with old stamps! That is why WalManager::checkpoint persists cumulative committed_txns and max_txn_id in its checkpoint metadata (mirroring PostgreSQL's durable pg_xact + pg_control), recover() returns RecoveryReport { redone, undone, loser_txns, committed_txns, max_txn_id } without scanning before the last checkpoint, and startup immediately calls txn_manager.restore(report.max_txn_id, report.committed_txns) so pre-crash commits remain visible and new transaction ids resume cleanly above max_txn_id.

How PostgreSQL WAL works in production

PostgreSQL's WAL subsystem (historically called XLOG) builds on the exact same write-ahead discipline while tailoring recovery to its MVCC storage engine and real-world storage hardware:23

  • pg_wal 16 MB segment files: Instead of one unbounded log file, PostgreSQL partitions its 64-bit LSN space into sequential 16 MB segment files inside pg_wal/, recycling old segments once checkpoints pass them.3 Each XLOG record carries a header with its xl_prev back-pointer, resource-manager tag, and CRC-32C checksum to detect torn tails cleanly.3
  • pg_control and redo-focused recovery: The small control file global/pg_control serves as PostgreSQL's master record, storing the LSN of the latest completed checkpoint and its REDO location.3 On crash restart, PostgreSQL replays XLOG records forward from the REDO point whenever a record's LSN exceeds the page's pd_lsn — and stops without an ARIES Undo pass!23 Because PostgreSQL persists transaction commit status in pg_xact (logged to WAL as well), uncommitted or aborted transactions' tuple versions remain invisible under MVCC visibility rules until VACUUM reclaims them. FerricDB implements full ARIES Undo and CLRs by design so you master the complete canonical algorithm and keep WAL correctness independent of MVCC.
  • Full-Page Writes (full_page_writes = on): Hardware disks and OS filesystems typically commit 512-byte or 4 KB sectors atomically, not 8 KB database pages. If power fails halfway through writing an 8 KB data page, the disk holds a torn page (half old, half new) that a small delta log record cannot safely repair. PostgreSQL solves this by logging a complete snapshot of the entire 8 KB page image on the first modification to that page after each checkpoint; during recovery, replaying that full-page image overwrites any torn bytes completely before subsequent delta records apply.23
  • WAL archiving and Point-In-Time Recovery (PITR): Because the WAL captures every physical change in sequence, copying completed 16 MB pg_wal segments to durable archive storage turns the log into a time machine: take one physical base backup, restore it onto a new machine after a media failure (or an accidental DROP TABLE), and replay archived WAL segments forward up to the exact second or transaction id right before the disaster.23
