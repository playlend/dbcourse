M04 · Index Data Structures: B+Trees (and Friends)

The data structure that runs the database world: why high-fanout search trees beat hash maps for general queries, how composite (key, rid) B+Tree nodes live on 8 KB pages, what actually happens during leaf and internal splits — plus dynamic hash indexes and LSM-trees for perspective.

Your Milestone 4 executor currently answers SELECT * FROM users WHERE id = 42 the only way a heap file can: read every page in the table, deserialize every tuple, and evaluate the predicate. On a 10-million-row table that costs tens of thousands of page reads to retrieve one row. An index is an auxiliary on-disk data structure maintained alongside a table so the executor can jump straight to matching tuples in a handful of page reads — or walk a contiguous key interval in sorted order without touching the rest of the table. This module studies the data structure that won the relational database world — the B+Tree — in full implementation detail for Milestone 5, then surveys the two major alternatives (dynamic hash indexes and LSM-trees) so you know when a B+Tree is not the right answer.

Why a tree at all?

Start from the workload requirements rather than jumping straight to an algorithm. cstack's tutorial reduces what a general database index needs to three capabilities:1

  1. Logarithmic point lookup: locate the entry for a given key in O(log N) page reads rather than scanning all N rows.
  2. Cheap updates in place: insert or delete a key you have already located without rewriting the entire structure.
  3. Ordered range traversal: retrieve every key between lo and hi (WHERE age BETWEEN 20 AND 30, prefix queries like name LIKE 'Al%', or avoiding a sort for ORDER BY) in sorted order.19

Run the classic textbook structures against that checklist and every in-memory favorite fails on disk. A sorted array gives binary search and fast ranges, but inserting a key in the middle shifts O(N) bytes across thousands of pages. A hash map gives O(1) equality lookups, but hashing deliberately scrambles key order, making range queries and sorted scans impossible.19 A balanced binary search tree (AVL or red-black tree) satisfies all three requirements asymptotically, yet performs terribly on block storage: each node holds one key and two pointers, so a 10-million-key tree sits roughly 24 levels deep. Even if every node were packed into pages, chasing random pointers across 24 levels triggers up to 24 disk reads per lookup and wrecks CPU cache locality.

The fix is to raise the branching factor from 2 to hundreds. Let every node hold up to m child pointers — the tree's order — sized so one node fills one disk page, and require every node except the root to stay at least half full so the tree remains shallow and balanced.14 That is the core insight behind the B-tree family: a B+Tree is a balanced search tree whose node size is chosen for the disk page, not the CPU register.

B-Trees vs B+Trees, and clustered vs secondary indexes

Two structural choices separate production engines, and SQLite actually ships both inside a single file format:12

  • B-Tree vs B+Tree: In a classic B-Tree (used by SQLite for its index pages), keys and payloads live in both interior and leaf nodes; a lookup can terminate early at an upper level, but carrying payloads in interior nodes shrinks their branching factor and forces range scans to jump up and down the tree. In a B+Tree (used by SQLite for table pages, by PostgreSQL for its default index access method, and by FerricDB), interior nodes store routing separators only and every data entry lives in a leaf; PostgreSQL, FerricDB, and textbook B+Trees also link leaves sequentially with sibling pointers (SQLite omits leaf sibling links from its page headers and walks back through interior nodes).147 Higher interior fanout makes the tree shallower, and sibling links turn a range scan into one root-to-leaf descent followed by a sequential walk across the leaf chain.
  • Clustered (index-organized) vs secondary (unclustered) indexes: A clustered B+Tree stores the entire table tuple inside each leaf cell (SQLite tables keyed on rowid and InnoDB primary keys work this way). A secondary B+Tree stores only the indexed key plus a physical pointer — a RecordId (page_id, slot) in FerricDB, a 6-byte heap TID (ctid) in PostgreSQL — pointing into a separate unordered heap file.47 Secondary indexes let a table carry many independent indexes without duplicating whole rows, at the cost of an extra heap-page fetch per matching RecordId during an IndexScan.

The shape and math of a B+Tree

Formally, an order-m B+Tree is an m-way balanced search tree governed by four structural invariants:34

  1. Routing order (separator bounds): An internal node holding n strictly sorted separator keys k₁ < k₂ < … < kₙ owns n + 1 child pointers c₀, c₁, …, cₙ. Defining implicit sentinels k₀ = −∞ and kₙ₊₁ = +∞, every key x stored anywhere in subtree cᵢ (for 0 ≤ i ≤ n) must satisfy kᵢ ≤ x < kᵢ₊₁. (SQLite flips the tie boundary to kᵢ < x ≤ kᵢ₊₁;2 either half-open convention is equally valid provided search, split, and invariant checking agree.)
  2. Uniform leaf depth (balance): Every path from the root to any leaf crosses the exact same number of edges.
  3. Occupancy bounds: Every non-root internal node holds between ⌈m/2⌉ − 1 and m − 1 keys (⌈m/2⌉ to m children); every non-root leaf holds between ⌊(m − 1)/2⌋ and m − 1 entries. The root is exempt from the lower bound: an empty tree has a single empty leaf root, and a newly split root has 1 separator and 2 children. (As we will see under lazy deletion, production systems and Milestone 5 often relax the lower bound on deletes while strictly preserving the upper bound.)
  4. Sibling leaf chain: Every leaf carries a pointer to its immediate right sibling (and typically its left sibling too, as in PostgreSQL's doubly linked leaf level7), so walking the leaf chain from the leftmost leaf visits every entry in the entire tree in strictly ascending order.

Worked example: fanout arithmetic — idealized vs real pages

Why does high fanout dominate database storage? Run the numbers on FerricDB's page size — our course choice of 8,192 bytes (8 KB), matching PostgreSQL's default block size.8

First take a back-of-the-envelope idealized calculation ignoring page headers, cell pointers, and fill factor: an 8-byte INTEGER key paired with a 4-byte child PageId takes 12 bytes, yielding roughly 8192 / 12 ≈ 680 separators (fanout ≈ 680) per internal page; a leaf entry with an 8-byte key and a 6-byte RecordId (4-byte PageId + 2-byte slot) takes 14 bytes, yielding roughly 8192 / 14 ≈ 580 entries per leaf. At height 3 (root → one internal level → leaves), the tree reaches 680² = 462,400 leaves holding 680² × 580 ≈ 268 million entries. Adding one more internal level (height 4) multiplies by another 680, reaching 680³ × 580 ≈ 182 billion entries.

Now reconcile that rough bound with real page overhead and steady-state fill factor for FerricDB's Milestone 5 layout:4

  • Headers: Reserve 16 bytes for FerricDB's common page header (pageLSN, page_type, reserved) plus 16 bytes for the B+Tree node header (cell count, content-area start, sibling or right-most child pointers), leaving 8,192 − 32 = 8,160 usable bytes.
  • Cell pointers and composite separators: Each cell needs a 2-byte offset in the cell pointer array.2 Furthermore, as explained in the next section, FerricDB stores the full composite (key, rid) separator in internal nodes so duplicate keys route unambiguously: an INTEGER internal cell is 8 B key + 6 B RecordId + 4 B child PageId + 2 B ptr = 20 B, giving ⌊8,160 / 20⌋ = 408 separators (409 children) at 100% full. A leaf cell is 8 B key + 6 B RecordId + 2 B ptr = 16 B, giving ⌊8,160 / 16⌋ = 510 entries at 100% full.
  • Average fill factor (~69%): Under random insertions with standard 50/50 splits, classic analysis (Yao's theorem) shows a high-order B+Tree stabilizes around an average occupancy of ln(2) ≈ 69%.4 At 69% fill, each internal node averages 409 × 0.69 ≈ 282 children and each leaf averages 510 × 0.69 ≈ 352 entries.

Even after paying for real headers, cell pointers, composite tie-breakers, and 69% average occupancy, a height-3 B+Tree indexes nearly 28 million rows in three page reads, and a height-4 tree reaches almost 8 billion rows. Better still, the top two levels of a 28-million-row tree occupy only 1 + 282 = 283 pages (~2.2 MB), which your Milestone 2 buffer pool pins warm in RAM indefinitely. In steady state, a B+Tree point lookup usually triggers at most one physical disk read: the target leaf (plus the heap page if the tuple is not cached).

Composite (key, rid) entries and key ordering

Many introductory tutorials assume every indexed key is unique. A real relational engine cannot make that assumption, for two distinct reasons:

  1. Non-unique secondary indexes: Queries routinely index low-cardinality columns such as CREATE INDEX idx_items_grp ON items (grp) or foreign keys orders(customer_id), where hundreds or thousands of rows share the exact same key value.4
  2. MVCC out-of-place updates (Module 9 / Milestone 8): Even on a PRIMARY KEY column, updating a row under multi-version concurrency control writes a new tuple version at a new RecordId while leaving the old version in the heap for older snapshots. Until VACUUM reclaims the dead version, two live heap tuples legitimately share the same indexed key.7

CMU's lecture notes survey two ways to represent duplicate keys: append a unique tie-breaker to every key, or attach an overflow/value list per key.4 Since PostgreSQL 12, PostgreSQL has treated every B-tree entry as uniquely ordered by the composite key (indexed_key, heap_TID), sorting duplicate logical keys in ascending order of their 6-byte heap TID and carrying the heap TID as a tie-breaker when a run of duplicates splits across pages.7 (On top of that, PostgreSQL applies leaf-level deduplication, packing repeated keys into a single key followed by a sorted posting list of heap TIDs to save space.7)

FerricDB adopts PostgreSQL's composite tie-breaker directly in crates/index (leaving posting-list compression out to keep cell encoding clean): every entry in a leaf — and every routing separator in an internal node — is the composite pair (key, rid). Watch how cleanly this single design choice shapes the entire Milestone 5 BPlusTree API:

  • insert(&mut self, key: &Value, rid: RecordId) -> Result<()> permits multiple distinct RecordIds under the same key (both non-unique indexes and MVCC updates work out of the box) and returns Err(Error::Execution) only if the exact (key, rid) pair is already present.
  • get(&self, key: &Value) -> Result<Vec<RecordId>> descends to the first leaf that could hold (key, RecordId { page_id: 0, slot: 0 }) and walks forward — hopping across sibling leaves if a run of duplicates spans a page boundary — collecting every matching RecordId in ascending order.
  • delete(&mut self, key: &Value, rid: RecordId) -> Result<bool> targets one exact (key, rid) pair, so Milestone 8's VACUUM can excise a dead tuple version without touching a newer live version that shares the same key.

Key validation and strict total order

Binary search and separator routing break completely if key comparisons are not a strict total order (antisymmetric, transitive, and defined for every pair). Two SQL values threaten that contract in FerricDB's Value enum: Value::Null (where SQL three-valued logic makes Value::sql_cmp return None) and IEEE-754 Value::Float(NaN) (where NaN < x, NaN == x, and NaN > x are all false). Unlike PostgreSQL, which defines an explicit NULLS FIRST/LAST sort position and places NaN greater than all finite floats in its B-tree operator classes,9 FerricDB keeps index ordering clean by rejecting Value::Null, Value::Float(NaN), and any key whose DataType does not match the tree's declared key_type with Err(Error::Execution). (SQL rows whose indexed column is NULL are omitted from the index during backfill and write maintenance.) With Null and NaN excluded, Value::sql_cmp is a strict total order on keys, and pairing it with Rust's derived Ord on RecordId { page_id, slot } gives a strict total order on every (key, rid) entry.

A node is a page

"One tree node = one 8 KB page" is an architectural rule shared by PostgreSQL, SQLite, BusTub, and FerricDB.23 Because BPlusTree reads and writes nodes through the exact same Arc<dyn PageStore> trait as HeapFile, your Milestone 2 BufferPoolManager caches index pages and heap pages in the same frames with zero extra plumbing. Recall from Module 2 that the first 16 bytes of every FerricDB Page are reserved for pageLSN (u64), page_type (u32), and 4 reserved bytes: Milestone 5 stamps leaf pages with PAGE_TYPE_BTREE_LEAF = 2 and internal pages with PAGE_TYPE_BTREE_INTERNAL = 3 via Page::set_page_type.

Inside the remaining 8,176 bytes, FerricDB borrows SQLite's slotted b-tree cell layout (adding PostgreSQL-style sibling leaf links for fast range scans):2

  1. Node header: directly after the 16-byte reserved page header. Holds the cell count (u16), the start offset of the cell content area (u16), and link pointers — prev_leaf and next_leaf PageIds on leaf pages (as in PostgreSQL's nbtree; SQLite omits leaf sibling pointers), or the rightmost_child PageId on internal pages (as in SQLite, so K cells holding (separator, left_child) plus one header pointer represent all K + 1 children without a dummy cell).2
  2. Cell pointer array (grows forward): an array of 2-byte byte-offsets, strictly sorted in ascending (key, rid) order.2
  3. Free space: unallocated bytes between the end of the pointer array and the start of the cell content area.
  4. Cell content area (grows backward from byte 8191): the serialized cells themselves, written wherever free space was allocated — not physically sorted.2

Fixed-width INTEGER keys vs variable-length TEXT keys

If this page looks almost identical to your Milestone 1 slotted HeapPage, that is not a coincidence — a B+Tree page is a slotted page whose slot directory stays sorted by key. That slotted indirection becomes essential the moment a user creates an index on a TEXT column. Fixed-width keys (Boolean: 1 byte, Integer/Float: 8 bytes) have a constant cell size, so every page holds a predictable count of entries. Variable-length TEXT keys (encoded as a 4-byte UTF-8 length prefix plus payload bytes) do not: a page storing 80-byte email addresses holds around 85 leaf cells, whereas a page storing 8-byte short codes holds around 400. Consequently, never hard-code a fixed MAX_KEYS constant in Milestone 5. A node is full when the incoming serialized cell plus its 2-byte pointer no longer fits in free_space (after optional intra-page compaction if tombstones or removed cells left holes), and a split divides entries by byte weight or midpoint count so both halves fit comfortably below 8 KB.24

Production optimization — suffix truncation and prefix compression

Internal separator keys only need to distinguish the largest entry of the left subtree from the smallest entry of the right subtree. PostgreSQL applies suffix truncation when copying a separator up from a leaf split: if the left leaf ends with ("apple", (3,1)) and the right leaf starts with ("banana", (9,4)), the internal separator does not need the 6-byte heap TID at all (and could even truncate "banana" to "b"), raising internal fanout further.47 In Milestone 5, keeping the full (key, rid) separator is cleaner and avoids subtle edge cases when duplicate keys span leaves.

Search, insert, split, and range scan

Every B+Tree operation begins with the same root-to-leaf descent. Inside each internal node, binary search over the sorted cell pointer array locates the child pointer in O(log K) comparisons (about 9 comparisons for a 400-key page — CMU's spec warns that linear scans inside 500-entry nodes blow your CPU budget3). Repeating until page_type == PAGE_TYPE_BTREE_LEAF takes exactly H page fetches.

  • Point lookup (get): Validate the key (non-Null, non-NaN, matching DataType), descend searching for the lower bound (key, RecordId { page_id: 0, slot: 0 }), then read forward across entries whose key equals key, stepping through next_leaf if the run crosses a leaf boundary. Return the collected Vec<RecordId>.
  • Range scan (range): Validate any bounded endpoints. For Bound::Unbounded on the lower side, descend along child 0 to the leftmost leaf; for Included(v), seek to (v, min RecordId); for Excluded(v), seek past (v, max RecordId). From there, RangeIter::next advances slot by slot and follows next_leaf across page boundaries — skipping any empty leaves created by lazy deletion — until a key violates the upper bound or next_leaf == INVALID_PAGE_ID.3 The iterator stores only (current_page, current_slot) and re-fetches each page through PageStore::with_page so it never holds a buffer-pool pin across an entire query.

Insert and the three split rules

Insertion descends to the target leaf while recording the descent path as a stack of (PageId, child_index) pairs (avoiding brittle parent pointers stored on disk, which would have to be rewritten in every child whenever an internal node splits3). If the exact (key, rid) already exists in the leaf, return an error without mutating the tree. If the leaf has free space, append the cell, shift the 2-byte pointers, and finish. When the page cannot fit the new cell, the tree grows by splitting — and leaves, internal nodes, and the root follow three distinct rules (Figure 2):13

  1. Leaf split — the separator is copied up: Allocate a fresh leaf page, move the upper half of entries to the new right sibling, splice the sibling pointers (new_right.next = left.next; left.next = new_right, plus prev links if doubly linked), and insert the right sibling's first (key, rid) into the parent. That entry is copied, not removed from the leaf, because in a B+Tree every indexed entry must remain findable at the leaf level.
  2. Internal split — the separator is pushed up: If inserting the separator overflows the parent internal node, allocate a new internal page, move the upper half of separators and child pointers into it, and push (move) the middle separator up to the grandparent so it remains in neither half. Internal keys are pure routers; leaving a duplicate copy behind would create a phantom routing interval with one too many pointers.
  3. Root split — height grows at the top: If a split propagates all the way out of the root, allocate a new root page containing the single promoted separator and two child pointers (old root and new right sibling), and update self.root. Because height increases only by adding a new root above the old one, every leaf's depth increases by 1 simultaneously, preserving uniform depth automatically.1 Remember to persist the new root page id to the catalog via Catalog::set_index_root — a B+Tree is identified on disk strictly by its root PageId.2

One practical workload detail: inserting keys in strictly ascending order (such as an auto-increment primary key) hits the rightmost leaf every time, leaving every split left sibling exactly 50% empty forever under a naive midpoint split. Production systems solve this with two techniques: when building an index on existing rows (CREATE INDEX), bulk-load by sorting all (key, rid) pairs first and packing leaves sequentially to a target fill factor (PostgreSQL defaults to 90% fill on B-tree leaves); during online appends to the rightmost page, split asymmetrically (e.g., 90/10) so historical pages stay nearly full.47 Milestone 5 asks for plain midpoint splits — straightforward to verify and cleanly covered by your invariant checker.

Deletion: lazy vs merge

Textbook B+Tree deletion mirrors insertion: if removing an entry drops a node below its minimum occupancy (half full), the tree tries to redistribute (borrow) an entry from an adjacent sibling and update the separating key in the parent; if neither sibling can spare an entry, the tree merges (coalesces) the two siblings into one node and deletes the parent's separator, recursing upward until the parent stays legal or the root loses its last key and shrinks the tree by one level.34

In practice, many database engines deliberately relax eager merging, for two operational reasons:4

  • Split/merge thrashing: If a workload alternates inserts and deletes right at the 50% boundary, eager merging triggers expensive page merges followed immediately by page splits, generating write amplification and latching contention.
  • Concurrency and complexity: Merging touches three pages simultaneously (left sibling, right sibling, parent) and can cascade to the root, dramatically multiplying latch-crabbing corner cases and WAL recovery paths.

Two pragmatic alternatives dominate production and teaching systems. CMU's Fall 2025 project specifies a tombstone buffer inside leaves: deleted keys are marked dead and only physically compacted once enough tombstones accumulate.3 PostgreSQL performs bottom-up index deletion when a leaf page is about to split (pruning dead MVCC versions before allocating a new page) and lets background VACUUM reclaim dead tuples and unlink completely empty pages rather than eagerly merging half-full ones.7 FerricDB's Milestone 5 takes the clean lazy-delete school: delete(key, rid) removes that exact cell from its leaf (the visualizer above marks it struck through so you can see where tombstones sit) and leaves underfull nodes intact. Two consequences follow directly: your Milestone 5 check_invariants does not enforce minimum occupancy, and RangeIter must skip over empty leaves cleanly rather than stopping early. Full redistribution and merging remain a rewarding stretch exercise once splits are rock-solid.

Latch crabbing and concurrency (survey)

A single global mutex around the entire B+Tree serializes every reader behind every writer, destroying multi-core throughput. Locking individual pages naively without a protocol causes deadlocks the moment two threads traverse overlapping paths in opposite directions. Recall from Module 3 that pages are protected by short-lived latches (RwLock<Page> in FerricDB's buffer pool), not transaction-duration locks.5

Pessimistic latch crabbing and the safe-node rule

The classic protocol is latch coupling, better known as latch crabbing: acquire the parent's latch, acquire the child's latch, and release the parent's latch as soon as the child is proven safe.5 A node is safe for an operation if modifying it cannot cause a structural change that propagates back up to its parent:5

  • Search (read): Acquire shared (read) latch on parent → acquire shared latch on child → immediately release parent latch (every child is safe for a read).
  • Insert (pessimistic write): Acquire exclusive (write) latch on parent → acquire exclusive latch on child. The child is safe if it is not full (it has room for one more key without splitting). Once a safe child is latched, release all held ancestor latches in top-down order.
  • Delete (pessimistic write): Same protocol, except a child is safe if it is strictly more than half full (removing one entry cannot trigger a merge or redistribution).

Optimistic latch crabbing

Pessimistic crabbing has a glaring bottleneck: every single insert or delete grabs an exclusive latch on the root page first, serializing all writers even though on a 400-way fanout tree over 99% of writes touch only a leaf and never split!5 CMU's project and notes prescribe optimistic latch crabbing:35 writers descend taking shared read latches crab-style all the way down to the leaf's parent, then acquire an exclusive write latch on the leaf itself. If the leaf turns out to be safe (has room for an insert, or stays above minimum on a delete), the writer modifies the leaf and finishes without ever holding an exclusive latch on the root! Only on the rare unsafe leaf does the thread drop its latches and restart from the root using the pessimistic write-latch protocol.

Production engines push concurrency even further. PostgreSQL implements the Lehman–Yao B-link tree: every page stores a high key (upper bound of keys on that page) alongside its right-sibling pointer.7 If a split happens right after a reader releases a parent latch and before it latches the child, the reader notices its target key exceeds the child's high key and hops rightward along the sibling link until it catches up — searches never need latch coupling at all. Even deeper lies ARIES/IM, Mohan and Levine's algorithm uniting B+Tree concurrency with write-ahead log recovery so a crash landing mid-split never corrupts the tree.11 In FerricDB, Milestone 5 runs single-writer via &mut self; latch crabbing is the optional stretch goal once the core tree passes its fuzz tests.

The friends: hash indexes and LSM-trees

B+Trees win the general relational workload, not every specialized workload. Two alternative index families appear throughout modern storage engines.

Dynamic hash indexes: extendible and linear hashing

A disk-based static hash table allocates a fixed array of N bucket pages and maps key k to bucket h(k) mod N. When the table outgrows N, static hashing stalls to rehash every key into a larger file. Two classic dynamic hashing schemes grow incrementally one bucket at a time:6

  • Extendible hashing: Maintains an in-memory/paged directory of 2^G bucket pointers indexed by the first G bits of h(k) (the global depth), while each bucket records its own local depth L ≤ G (multiple directory slots may share one bucket). When a bucket overflows: if L < G, split only that bucket, increment its local depth, and redirect half its directory pointers using bit L + 1; if L == G, double the directory array (G ← G + 1) and then split the single overflowing bucket.6 Data movement stays local to one bucket, and lookups need at most one bucket read after checking the directory.
  • Linear hashing: Eliminates abrupt directory-doubling spikes altogether. No directory exists; instead the table tracks a round-robin split_pointer and uses two hash functions h_level(k) = h(k) mod (N · 2^level) and h_{level+1}(k) = h(k) mod (N · 2^{level+1}).6 Whenever any bucket overflows (attaching an overflow page), the table splits the bucket currently addressed by split_pointer, appends a new bucket at the end, and advances split_pointer — resetting it to 0 and incrementing level once a full round completes.

PostgreSQL ships crash-recoverable on-disk hash indexes that store only a 4-byte 32-bit hash code per entry (compact for long URLs or UUIDs), but its planner can only consider them for strict equality (=) — never <, >, BETWEEN, or ORDER BY.9 FerricDB skips dedicated hash indexes because an equality lookup on a B+Tree is just a point range of width one.

LSM-trees: optimizing for writes

Every random insert into a B+Tree dirties an entire 8 KB page to change 16 bytes — a large write amplification factor that wears SSDs and caps write-heavy ingest throughput. Log-Structured Merge-Trees (LSM-trees) invert the trade-off by turning random writes into sequential appends:10

  • Write path: Every insert, update, or delete appends sequentially to a WAL and inserts into an in-memory sorted memtable (such as a skip list or in-memory B-tree). Once the memtable hits a size threshold, it freezes and flushes sequentially as an immutable Level-0 Sorted String Table (SST) file.10
  • Deletes and background compaction: Because SSTs are immutable, updates write a newer value and deletes write a tombstone marker. A background compaction job periodically merge-sorts overlapping SSTs into deeper levels (L0 → L1 → L2 …), discarding superseded versions and dropping tombstones once they reach the bottom level.10
  • Read path and Bloom filters: A point lookup searches the active memtable, immutable memtables, and SST levels from newest to oldest, stopping at the first match. To avoid touching every level on misses, each SST carries an in-memory Bloom filter (a compact bitset that definitively rules out absent keys with zero false negatives) and block fence pointers.410

Immutability makes crash recovery and multi-threaded reads clean, at the cost of higher read amplification (consulting multiple levels on a miss or range scan) and space amplification (holding stale versions until compaction catches up). RocksDB (descended from LevelDB) powers storage beneath distributed SQL engines like TiDB and CockroachDB;10 stretch milestone S3 lets you swap FerricDB's storage backend for an LSM engine following the Mini-LSM design.
