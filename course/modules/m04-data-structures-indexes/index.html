Your executor currently answers WHERE id = 42 the only way it can: read every tuple and check. That is O(N) disk pages for one row. This module is about the data structure that turns point lookups and range scans into a handful of page reads, and it is the single most consequential data structure in database history — every major relational engine keeps its tables or indexes in some variant of it.

Why a tree at all?

The requirements come first. An index must make three things fast, and cstack's tutorial states them crisply: searching for a particular value (logarithmic, not linear), inserting or deleting a value you have already found (cheap rebalancing), and — the one that eliminates most alternatives — traversing a range of values in order, which a hash map cannot do at all.1 A sorted array gives log-time search and ranges but O(N) insertion; a binary search tree gives all three asymptotically but is a disaster on disk: a million-key balanced binary tree is ~20 levels deep, and each level is a separate page read.

The fix is to let each node have many children — up to m, the tree's order — with every node except the root required to stay at least half full so the tree stays shallow and balanced.1 Make m big enough that one node fills one disk page, and the tree's height collapses. That is the whole insight: a B+Tree is a search tree whose node size is chosen for the disk, not the CPU.

Two flavors matter, and SQLite ships both. In its file format, indexes use B-trees (interior nodes store values too) while tables use B+Trees, where interior nodes hold only keys for routing, all data lives in the leaves, and interior nodes consequently fit more children per page.1 FerricDB builds the B+Tree: data in leaves, and the leaves chained left-to-right so a range scan is one descent plus a linked-list walk.3

The shape of a B+Tree

A B+Tree is a balanced search tree in which internal pages direct the search and leaf pages contain the actual entries.3 An internal node with keys k₁ … kₙ has n+1 children: the i-th subtree holds keys in [kᵢ₋₁, kᵢ). Every leaf sits at the same depth — the balance invariant — and each node (root excepted) stays at least half full.3

Now the arithmetic that makes it magic. Take FerricDB's numbers — our course choice of 8 KB pages, matching PostgreSQL's default block size6 — with 8-byte integer keys, 4-byte child pointers, and 6-byte record ids. An internal page holds roughly 8192 / 12 ≈ 680 separator keys; a leaf holds roughly 8192 / 14 ≈ 580 entries. Then:

Any key among hundreds of millions in three page reads — and the top two levels are a few hundred pages, which your Milestone 2 buffer pool will keep resident essentially forever. In practice a warm B+Tree lookup costs about one disk read: the leaf.

A node is a page

"Node = one page" is a design rule, and SQLite's file format shows exactly how to lay one out. A SQLite b-tree page is divided into regions in a fixed order: the page header, the cell pointer array growing from the front, unallocated space, and the cell content area growing backward from the end — with each cell holding one key (plus payload in leaves, plus a child pointer in interiors).2 The header packs a type byte, the first-freeblock offset, the cell count, the content-area start, and — on interior pages only — the right-most child pointer.2 If this sounds familiar, it should: it is your Milestone 1 slotted page with a sort order. The cell pointer array is kept in key order so binary search works over the pointers, while the cells themselves sit wherever they landed.

Search, insert, split

Search is a descent: binary-search the internal node's keys to pick a child, repeat until a leaf, binary-search the leaf. Height page reads, full stop.

Insert is a search followed by a leaf insertion — until the leaf is full. Then the tree grows by splitting, and this is where implementations are won and lost, because leaves and internals split differently:

  • Leaf split — the separator is copied up. Half the entries move to a new right sibling; the first key of the right sibling is copied into the parent as a router. Copied, not moved: the key still lives in the leaf, because in a B+Tree every entry must be findable in a leaf.
  • Internal split — the separator is pushed up. The middle key moves up to the parent and does not remain in either half — internal keys are pure routers, and keeping a copy would leave a phantom route with no subtree between the halves.
  • Root split — the tree grows. When a split propagates to the root, a new root is allocated with one key and two children. This is the only way a B+Tree gains height, which is why every leaf always sits at the same depth: growth happens at the top, never the bottom.

Splitting versus redistributing into a sibling with spare room is a legitimate design choice — CMU's project spec calls both out as acceptable, along with merge-vs-redistribute on the delete side.3 FerricDB's Milestone 5 asks for plain splits; they are simpler and the invariant checker doesn't care which you chose.

Deletion: lazy vs merge

Textbook deletion mirrors insertion: removing a key that underflows a node (below half full) triggers borrowing from a sibling or merging two half-empty nodes — potentially cascading to the root, shrinking the tree.3 Real systems very often don't bother. The pragmatic alternative is lazy deletion: mark the entry dead (a tombstone) and reclaim space later — the current CMU project even specifies a tombstone buffer design, where deleted entries are only physically removed once enough of them accumulate in a leaf.3 The tree may carry some dead weight, but every invariant still holds and no rebalancing code path exists to get wrong. FerricDB's Milestone 5 follows this school — lazy delete required, merges as stretch — and the visualizer above does the same (struck-through keys).

Latch crabbing (survey)

A single latch around the whole tree serializes every lookup; per-node latches deadlock the moment writers meet. The classic protocol is latch coupling, or crabbing: latch the parent, latch the child, and release the parent as soon as it is safe — where "safe" means the child cannot split or merge in a way that would touch the parent (for an insert: the child has room; for a delete: the child is above minimum). The current CMU project prescribes the optimistic variant: descend taking read latches as if only the leaf will change, and restart with pessimistic write latches on the rare unsafe path.3 The name is the image: a crab moving claw by claw, never letting go of both at once. Deeper still lies ARIES/IM, which works out index concurrency and recovery together — the optional deep dive in Go deeper.5 In FerricDB, crabbing is the stretch goal of Milestone 5; the core milestone runs the tree single-threaded.

The friends: hash indexes and LSM-trees

Hash indexes

A hash table on disk gives O(1) point lookups and nothing else: no ranges, no ordered scans, no prefix queries — the exact trade cstack's requirements list rules out for a general index.1 They shine where equality is the only question (join build sides, key-value stores). Postgres ships hash indexes; its planner uses them for = and nothing more. FerricDB skips them — once you have a B+Tree, equality is just a range of size one.

LSM-trees

The write-optimized school: buffer writes in a memtable, flush batches to immutable sorted string table (SST) files, and let a background compaction merge files to apply updates and deletions lazily.4 Immutable files make concurrency and crash-safety simpler, at the price of read and space amplification — a read may consult many SSTs. RocksDB (after LevelDB) is the canonical implementation, and distributed systems like TiDB and CockroachDB build on it.4 Stretch milestone S3 swaps FerricDB's heap for one, following the Mini-LSM course.
