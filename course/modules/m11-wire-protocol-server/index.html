Why speak someone else's protocol

Through nine milestones, FerricDB has talked to exactly one client: your local REPL, across in-process Rust function calls. Module 11 turns that embedded engine into a networked server, and it rests on a deliberate architectural bet: instead of inventing a custom RPC format and maintaining client libraries in ten languages, FerricDB speaks the PostgreSQL frontend/backend protocol, version 3.0 (PROTOCOL_VERSION = 196608).1

The leverage is disproportionate. Once your byte codec in course/ferricdb/crates/server/src/protocol.rs matches the wire specification byte for byte, real psql, Rust's tokio-postgres, Python's psycopg, Go's pgx, JDBC drivers, and graphical SQL workbenches all connect immediately. None of those clients know or care that the server answering them is a ten-crate educational database written in Rust. A wire protocol carries no SQL execution semantics of its own — it moves framed commands, parameter values, typed result rows, and structured errors between a frontend (client) and a backend (server). The Rust ecosystem's pgwire crate is built around this exact separation, dividing the wire contract into three composable sub-protocols: startup, simple query, and extended query.2

Course choice: port 5433 and hand-rolled framing

ServerConfig::default() listens on 127.0.0.1:5433 — a course choice set one port above PostgreSQL's standard port 5432 so a real PostgreSQL installation and FerricDB can run side by side on the same laptop without colliding. In Milestone 10, you hand-roll the codec directly using bytes::BytesMut and big-endian integer parsing with no external protocol crate (pgwire is linked below as optional post-milestone reading to compare your codec against a production implementation).2

Framing over a TCP byte stream

Once a connection moves past its initial startup packet, every message in either direction shares one uniform envelope:3

+------------------+------------------------+----------------------------------+
| type byte (1 B)  | length (Int32, 4 B BE) | payload (length - 4 bytes)       |
+------------------+------------------------+----------------------------------+

Four rules govern every byte on the wire:3

  1. Self-inclusive length, excluding the type byte. The Int32 length field counts its own four bytes plus the payload, and does not count the leading type byte. An empty-body message such as Sync ('S'), Terminate ('X'), EmptyQueryResponse ('I'), ParseComplete ('1'), or BindComplete ('2') therefore carries length 4 and occupies 1 + 4 = 5 bytes on the wire. Getting this off by one desynchronizes every message that follows.
  2. Signed big-endian integers and validation. All wire integers (Int16, Int32) use network byte order (big-endian), and the length header is a signed 32-bit integer (i32 in Rust).3 Because the length must at least count itself, any value < 4 — including negative values such as -1 (0xFF_FF_FF_FF) — is malformed and must fail immediately with Error::Protocol. Never decode the header as an unsigned u32; casting -1i32 to u32 makes the server stall indefinitely waiting for 4 GiB of payload.
  3. NUL-terminated UTF-8 strings ("C strings"). Text fields such as SQL queries, column names, command tags, and error messages travel as UTF-8 bytes followed by a single 0x00 terminator.3 An interior NUL byte inside a string cannot be represented safely, so encoders reject it with Error::Protocol. Column values inside DataRow and parameter values inside Bind are the deliberate exception: they carry explicit Int32 byte lengths rather than NUL terminators so arbitrary text (or binary data) passes through unambiguously.
  4. Independent direction namespaces. Frontend and backend message type bytes are disjoint namespaces.3 ASCII 'D' means Describe when sent client-to-server and DataRow when sent server-to-client; 'E' means Execute from the client and ErrorResponse from the server; 'S' means Sync from the client and ParameterStatus from the server.

The one exception: typeless startup packets

Before startup finishes (startup = true in read_message), client packets omit the leading type byte:3

+------------------------+---------------------------+---------------------------+
| length (Int32, 4 B BE) | version / code (Int32 BE) | body (length - 8 bytes)   |
+------------------------+---------------------------+---------------------------+

Here the self-inclusive length counts the entire packet (minimum 8 bytes), and the second Int32 disambiguates what kind of startup packet arrived: protocol version 196608 = (3 << 16) | 0 for a normal StartupMessage, 80877103 = (1234 << 16) | 5679 for an SSLRequest, or 80877102 = (1234 << 16) | 5678 for an out-of-band CancelRequest.3 Any unrecognized startup code (for instance, obsolete protocol 2.0 = 0x00020000 or an unsupported CancelRequest) is rejected with Error::Protocol.

TCP is a byte stream, not message-framed

A common bug in first network servers is assuming one TCP read() returns one protocol message. TCP offers no message boundaries: the kernel can split a 15-byte Query("SELECT 1;") into a 7-byte segment followed by an 8-byte segment, or coalesce a pipelined Query and Terminate into a single 20-byte read. That is why crates/server/src/protocol.rs specifies an incremental, non-blocking codec over bytes::BytesMut:6

  • Partial frame → Ok(None) without consuming bytes. Peek the header first (4 bytes if startup, 5 bytes otherwise). If fewer header bytes are buffered, return Ok(None). Parse the signed Int32 length, verify len >= 4 (or >= 8 for startup) so invalid lengths fail immediately without waiting for more data, and compute the total frame size (len for startup, 1 + len for typed messages). If buf.len() < total, return Ok(None) with buf untouched; the caller performs another async socket read and calls read_message again.
  • Coalesced frames → drain in a loop. Only once a complete frame is present does the decoder consume those exact bytes (e.g., via buf.split_to(total)) and return Ok(Some(msg)). The server loop must therefore drain every buffered message with while let Some(msg) = read_message(&mut buf, false)? before issuing the next stream.read_buf(&mut buf).await — otherwise a second message already sitting in buf stalls waiting for network traffic that will never arrive.

SSL / TLS negotiation (SSLRequest)

Run psql -h 127.0.0.1 -p 5433 against a fresh server that expects StartupMessage first, and the connection dies immediately before authentication even starts. The reason is libpq's default sslmode=prefer: before sending a single credential or parameter, real PostgreSQL clients probe whether the server supports TLS using an in-band SSLRequest handshake.15

SSLRequest is an 8-byte typeless startup packet: Int32(8) followed by the magic code SSL_REQUEST_CODE = 80877103 = (1234 << 16) | 5679 (00 00 00 08 04 D2 16 2F).3 Placing 1234 in the major-version slot guarantees it can never collide with a real protocol version such as 3.0. Unlike every other backend message, the server's reply to SSLRequest has no length header — it is a single raw ASCII byte:1

  • 'N' (0x4E) — decline TLS. The server refuses encryption. Under sslmode=prefer or allow, the client keeps the same TCP socket open and immediately sends a cleartext StartupMessage. Under sslmode=require, verify-ca, or verify-full, the client closes the connection and reports an error to the user.5 Replying b'N' and looping back to read_message(&mut buf, true) is what FerricDB Milestone 10 implements by default so plain psql -h 127.0.0.1 -p 5433 connects without requiring sslmode=disable.
  • 'S' (0x53) — accept TLS. Both peers immediately perform a standard TLS 1.2 or TLS 1.3 handshake over that exact TCP stream.1 In Rust with Tokio, the server hands its TcpStream to tokio_rustls::TlsAcceptor::accept(stream).await, obtaining a TlsStream<TcpStream> that implements the same AsyncRead + AsyncWrite traits as the raw socket. Once the TLS handshake succeeds, the session code runs unmodified on top of the encrypted stream: the client sends StartupMessage, password challenges, SQL text, and result rows entirely inside TLS.

Direct TLS negotiation in PostgreSQL 17+

The classic SSLRequest dance acts like STARTTLS: it costs an extra network round trip before TLS begins and starts every TCP connection with 8 non-TLS bytes, which breaks standard SNI-routing proxies expecting a TLS ClientHello as byte 0. PostgreSQL 17 introduced direct TLS negotiation (sslnegotiation=direct): the client skips SSLRequest altogether and starts the TLS handshake immediately on TCP connect, advertising the mandatory ALPN (Application-Layer Protocol Negotiation, RFC 7301) protocol identifier "postgresql".15 The server distinguishes the two flows from the very first byte on the socket: a TLS record begins with 0x16 (handshake record), whereas a big-endian PostgreSQL startup packet length begins with 0x00 — and requiring the "postgresql" ALPN token defends against cross-protocol confusion attacks.1

Security boundary: cleartext passwords require TLS

When ServerConfig::password is set, Milestone 10 uses AuthenticationCleartextPassword so the codec stays concise. Sending a cleartext password over an unencrypted TCP socket exposes the secret to anyone able to sniff the link — acceptable only on loopback (127.0.0.1) for local development. Any server reachable over a network must combine TLS encryption (protecting the channel and authenticating the server certificate) with challenge-response authentication such as SCRAM-SHA-256 (AuthenticationSASL), where the plaintext password never crosses the wire at all.5

Startup, authentication, and parameters

Once TLS negotiation finishes (or is skipped by a client configured with sslmode=disable), the client sends StartupMessage containing PROTOCOL_VERSION = 196608 and a sequence of key\0value\0 pairs ending with an extra \0.3 Typical keys are user (required by PostgreSQL), database (defaults to the user name if omitted), application_name, and client_encoding. Because FerricDB hosts a single database per server process, your startup handler records the parameters for diagnostics and proceeds straight to authentication.

Authentication uses backend type byte 'R' with a 32-bit method code:3

  • Trust mode (ServerConfig::password = None): the server replies immediately with AuthenticationOk ('R', length 8, Int32(0)).
  • Cleartext password mode (ServerConfig::password = Some(pw)): the server sends AuthenticationCleartextPassword ('R', length 8, Int32(3)). The client prompts or reads PGPASSWORD and sends PasswordMessage — note the lowercase 'p' (0x70), not uppercase 'P' (which is Parse) — carrying the password as a C-string.3 If it matches, the server sends AuthenticationOk; if it fails, the server emits ErrorResponse with SQLSTATE 28P01 (invalid_password)4 and closes the TCP stream without sending ReadyForQuery.

Immediately after AuthenticationOk, the server emits its startup status burst and switches the connection from startup mode (startup = true) into normal framed mode (startup = false):1

  1. ParameterStatus ('S') × n: runtime configuration values that client libraries inspect during setup. FerricDB sends at least server_version (e.g., "16.0 (FerricDB)" so drivers recognize modern protocol capabilities) and client_encoding = "UTF8".
  2. BackendKeyData ('K'): two Int32 values — process_id and secret_key — that real PostgreSQL uses to authenticate out-of-band CancelRequest packets on a second TCP connection. FerricDB does not implement query cancellation, so a monotonic connection counter plus a constant or random secret keeps libpq happy.
  3. ReadyForQuery ('Z'): a 6-byte wire message (1-byte tag 'Z' + length 5, covering the 4-byte length field and 1-byte transaction status 'I' for idle). Only after receiving this message does psql draw its interactive prompt and wait for user input.1

The simple query cycle and value encoding

In the simple query sub-protocol, the frontend sends a single Query ('Q') message containing one or more semicolon-separated SQL statements as a C-string.1 The backend feeds the string into ferricdb_exec::execute(sql, &session_ctx), which returns Vec<QueryResult> — one result per statement — and translates each result onto the wire in order:1

  • Empty query string (whitespace or comments only): emit EmptyQueryResponse ('I') (length 4, empty body) followed by ReadyForQuery. Typing a bare ; in psql actually sends an empty query string; a server that silently skips it hangs the session waiting for a reply.1
  • Row-returning statements (SELECT, EXPLAIN): emit one RowDescription ('T'), zero or more DataRow ('D') messages, and one CommandComplete ('C').
  • Command-only statements (CREATE TABLE, INSERT, UPDATE, DELETE, BEGIN, COMMIT, ROLLBACK): emit only CommandComplete ('C') (no RowDescription).
  • Cycle terminator: after all statements in the Query string complete (or after the first error stops execution), emit exactly one ReadyForQuery ('Z'). Because one Query can produce several CommandComplete messages, ReadyForQuery is the single unambiguous signal that the backend is ready for the next frontend message.1

Exact wire format of RowDescription and type OIDs

RowDescription ('T') begins with Int16 field count, followed by one descriptor per output column. Each descriptor contains the column name C-string followed by exactly 18 fixed bytes:3

  • Int32 table OID (0 when not attributable to a specific table, which FerricDB always writes);
  • Int16 attribute number (0 in FerricDB);
  • Int32 PostgreSQL type OID;
  • Int16 fixed byte size of the type, or -1 for variable-length types;
  • Int32 type modifier (-1 = none, which FerricDB always writes);
  • Int16 format code (0 = text format, 1 = binary format; FerricDB writes 0).

Clients map each column's type OID to native host types and display formatting. FerricDB maps its four ferricdb_common::DataType variants onto standard PostgreSQL catalog OIDs as follows:3

DataRow text encoding and CommandComplete tags

Each DataRow ('D') begins with an Int16 column count (matching RowDescription), followed per column by a signed Int32 byte length and that many raw payload bytes.3 Two edge cases are mandatory to keep distinct on the wire:

  • Value::Null travels as length -1 (0xFF_FF_FF_FF) with zero value bytes following it.
  • Value::Text("") travels as length 0 (0x00_00_00_00) with zero value bytes following it. Conflating -1 and 0 corrupts SQL three-valued logic at the transport layer.

When all rows have been sent, CommandComplete ('C') carries the command tag string from QueryResult::tag: SELECT N, INSERT 0 N (the literal 0 is PostgreSQL's historical OID field), UPDATE N, DELETE N, CREATE TABLE, DROP TABLE, BEGIN, COMMIT, or ROLLBACK.3

The extended query protocol and pipelining

The simple query protocol re-lexes, re-parses, and re-plans every statement on every request, and forces applications to interpolate values into SQL strings — the root cause of SQL injection. Application drivers (tokio-postgres, pgx, JDBC) therefore default to the extended query protocol, which splits query execution into five reusable messages:1

  1. Parse ('P') → ParseComplete ('1'): ships a SQL template containing positional placeholders ($1, $2, …) plus optional parameter type OIDs and stores the parsed statement under a client-chosen name (empty string "" denotes the unnamed prepared statement, overwritten on the next unnamed Parse).
  2. Bind ('B') → BindComplete ('2'): supplies concrete parameter values (length-prefixed byte slices, -1 for NULL) and input/result format codes for a prepared statement, instantiating an executable portal (again, "" is the unnamed portal). Because parameter bytes never touch the SQL parser, SQL injection through parameter values is structurally impossible.
  3. Describe ('D') → RowDescription ('T') or NoData ('n'): unlike simple Query, Execute does not automatically send column metadata before streaming DataRow messages.1 Clients therefore issue Describe with kind 'P' (portal) to receive RowDescription (for queries returning rows) or NoData ('n') (for INSERT/UPDATE/DELETE), or kind 'S' (statement) to receive ParameterDescription ('t') followed by RowDescription or NoData.
  4. Execute ('E') → DataRow ('D') × N + CommandComplete ('C'): runs the named portal up to max_rows rows (0 means unlimited; a positive limit stops early with PortalSuspended ('s') so the client can fetch the next chunk later).
  5. Sync ('S') vs Flush ('H'): Flush ('H') tells the server to flush any buffered response bytes to the TCP socket immediately without ending the batch or sending ReadyForQuery — useful when a driver wants a Describe result before deciding how to Bind.1 Sync ('S') ends the extended-query batch, commits the implicit single-statement transaction (unless the session is inside an explicit BEGIN block), and emits ReadyForQuery ('Z').1

Pipelining and error-skipping resynchronization

Wait-for-each-reply execution would turn a single parameterized query into five sequential network round trips. PostgreSQL avoids that latency by supporting pipelining: a client writes Parse, Bind, Describe, Execute, and Sync back to back in one TCP send buffer, paying one round trip total, and reads the ordered stream of replies as they arrive.1

Pipelining creates a subtle failure mode: what happens if Parse fails while Bind, Describe, Execute, and Sync are already in flight on the wire? PostgreSQL solves this with error-skipping semantics: the moment any extended-protocol message fails, the server emits ErrorResponse and enters an ignore state, discarding every incoming frontend message until it reads Sync ('S').1 Upon seeing Sync, the server leaves the ignore state and sends ReadyForQuery (carrying status 'E' if inside an explicit transaction block, or 'I' otherwise). Both sides immediately regain lockstep synchronization without closing the connection. In Milestone 10, the extended-protocol messages are round-trip tested in crates/server/tests/protocol.rs; wiring them into the live server loop is an optional extension after simple queries work.

Errors, SQLSTATE codes, and transaction status

ErrorResponse ('E') is a structured key-value record, never an unstructured text blob.34 Its payload is a sequence of fields — each a single ASCII field-type byte followed by a NUL-terminated value — terminated by a final 0x00 byte. PostgreSQL mandates three fields on every error (plus optional fields such as 'D' Detail, 'H' Hint, and 'P' Position):4

  • 'S' (Severity): "ERROR" for recoverable statement failures, "FATAL" when the connection is terminating, or "PANIC".
  • 'C' (SQLSTATE code): a five-character standard error code that is never localized and lets drivers branch programmatically.4
  • 'M' (Message): the primary single-line human-readable explanation.

Every ReadyForQuery ('Z') carries the session's live transaction state in its single payload byte:3

  • 'I' (idle): not inside an explicit transaction block (psql prompt =>).
  • 'T' (in transaction): inside an active BEGIN block (psql prompt *=>).
  • 'E' (failed transaction): an error occurred inside an explicit transaction block (ExecContext::failed_txn = true; psql prompt !=>). PostgreSQL and FerricDB reject every subsequent statement until the client explicitly sends ROLLBACK, preventing an application from committing the second half of a broken transaction by accident.1
The classic wire-protocol hang: forgetting ReadyForQuery on error

When a statement fails inside the query loop, a common mistake is sending ErrorResponse and continuing or returning early without emitting ReadyForQuery. In PostgreSQL's state machine, ErrorResponse explains what failed while ReadyForQuery grants the client permission to speak again.1 Omit it after a syntax error or 40001 conflict, and psql hangs forever waiting for the end of the cycle.

Finally, clean shutdown arrives as Terminate ('X') (5 bytes: 58 00 00 00 04), after which the client closes its write half without expecting a reply.1 A robust server treats both Terminate and an unexpected TCP EOF identically on cleanup: close the socket and abort any open transaction owned by that session.

Server architecture: async I/O meets a blocking engine

PostgreSQL historically uses a process-per-connection model: the postmaster calls fork() for each TCP connection, isolating session state inside separate OS address spaces while sharing the buffer pool and lock table through shared memory. FerricDB takes the modern Rust approach in course/ferricdb/crates/server/src/lib.rs: a single process running a Tokio async accept loop that spawns one lightweight task per TCP connection.6

Three engineering invariants keep that server correct under concurrent clients:

  1. Per-connection session isolation via ExecContext::new_session. The Server holds one shared Arc<ExecContext> referencing the database's shared Catalog, PageStore (buffer pool), TransactionManager, and optional WalHook. When a new TCP socket is accepted, the task immediately calls ctx.new_session(), which clones those shared Arcs but allocates a brand-new current_txn: Mutex<Option<Arc<Transaction>>> and failed_txn: Mutex<bool> private to that connection. Sharing one ExecContext directly across connections would cause client A's BEGIN to hijack client B's queries.
  2. Abort-on-disconnect hygiene. Suppose client A runs BEGIN, updates a row, and then crashes or closes its terminal without sending COMMIT or ROLLBACK. When the session task observes Terminate ('X'), TCP EOF (read_buf returning 0), or a protocol error, it must inspect its session's current_txn and roll back any active transaction (by running ferricdb_exec::execute("ROLLBACK", &session) inside spawn_blocking, so both MVCC abort and WAL physical undo/CLRs run cleanly). Forgetting this leaks an active snapshot forever, pinning TransactionManager::oldest_visible_xid() and preventing VACUUM from reclaiming dead tuples across the entire database.
  3. Offloading synchronous work with tokio::task::spawn_blocking. Tokio's async executor multiplexes thousands of tasks across a small pool of worker threads using cooperative yielding.6 FerricDB's execute(), buffer-pool RwLocks, and DiskManager file I/O are synchronous blocking calls. Invoking execute() directly inside an async worker thread blocks that OS thread while disk reads or scans run, starving other clients' handshakes and socket reads. Wrapping each execute() call in tokio::task::spawn_blocking hands the CPU and disk work to Tokio's dedicated blocking thread pool while keeping the network reactors free.6
