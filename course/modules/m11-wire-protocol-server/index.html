Why speak someone else's protocol

Everything you have built so far talks to one client: your REPL, through function calls. Module 11 is about the moment FerricDB becomes a server — and about a strategic choice. Instead of inventing a protocol and writing clients for it, FerricDB speaks the PostgreSQL frontend/backend protocol, version 3.1 The payoff is disproportionate: psql, every language's Postgres driver, GUI tools, dashboards — none of them know or care that the thing on port 5433 is a teaching database. A protocol, after all, carries no SQL semantics — it moves strings and rows, and the Rust ecosystem's pgwire library is built around exactly that split: startup, simple query, extended query, as three separable sub-protocols.2

Framing: type byte + length

Once past startup, every message in either direction has the same skeleton: one type byte (an ASCII letter — 'Q' query, 'T' row description, 'D' data row, 'E' error, 'Z' ready), then an Int32 length, then the payload. The length counts the message contents including the length field itself but excluding the type byte — the single most bug-prone sentence in this module, so read it twice.3 Integers are big-endian; strings are NUL-terminated. That is the entire transport layer: a loop that reads one byte, reads four more, then reads exactly length − 4 payload bytes, forever.

Startup and authentication

The one message that breaks the framing rule is the first: StartupMessage has no type byte — just Int32 length, then Int32 protocol version (major 3 in the high 16 bits), then name/value parameter pairs (user, database, …) terminated by a zero byte.3 There is no type byte because at connection start there is nothing to disambiguate — and because the version field doubles as one (special values in it distinguish SSL and cancel requests).

The server answers with an authentication conversation — reject with ErrorResponse, demand a password, or accept with AuthenticationOk — and then, in the normal case, a burst of ParameterStatus messages (server settings the client should know), BackendKeyData (a secret for out-of-band query cancellation), and finally ReadyForQuery: the prompt.1 FerricDB's Milestone 10 implements trust auth (accept anyone) first, cleartext password as the optional upgrade.

The simple query cycle

The workhorse. The frontend sends Query with the SQL as text (it may contain several statements); the backend responds per statement and closes the cycle with ReadyForQuery — sent as its own message precisely because a query string can contain multiple statements, and the client needs one unambiguous "done with all of it".1 For a SELECT: RowDescription describing the columns (name, type OID, size per field), then one DataRow per row — each column as an Int32 length + bytes, with −1 meaning NULL — then CommandComplete with a command tag like SELECT 3 or INSERT 0 5.3 An empty query string gets its own answer, EmptyQueryResponse — psql actually sends this, and a server that doesn't handle it hangs the session.1

The extended query protocol

The simple protocol re-parses and re-plans every statement. The extended protocol splits the cycle into reusable steps: Parse ships the SQL once (with optional parameter types) and names a prepared statement; Bind supplies parameter values, turning the statement into a portal; Execute runs the portal (with an optional row limit — zero means all rows); and Sync ends the batch, closing the implicit transaction and triggering ReadyForQuery.1 The names matter: empty-string statement and portal names denote the unnamed ones, which drivers use constantly. Prepared statements are why parameterized queries (WHERE id = $1) are both faster and immune to SQL injection — the value never passes through the parser.

Errors and transaction status

ErrorResponse is structured, not a string: a sequence of fields, each one code byte plus a NUL-terminated value — Severity, SQLSTATE Code, Message, optionally position and detail — terminated by a zero byte.3 FerricDB maps its error enum onto SQLSTATEs (Error::Serialization → 40001, parse errors → 42601), which is what lets a Rust client's retry loop work unmodified against your server. And every ReadyForQuery carries the transaction status byte — 'I'dle, in-'T'ransaction, or 'E'rror (statements rejected until ROLLBACK) — which is how psql knows to change its prompt to =!>.3 The classic beginner mistake is forgetting to send ReadyForQuery after an error: the client waits politely, forever.1
