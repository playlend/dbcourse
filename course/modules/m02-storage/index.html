Why the disk dictates the design

Everything in this module — and most of what makes database internals interesting — follows from one asymmetry: computation happens in memory, but the data does not fit there and must survive power loss, so it lives on secondary storage that is orders of magnitude slower to reach.11 A spinning disk is a mechanical device: an arm assembly positions read/write heads over tracks on platters rotating at around 15,000 RPM.11 Reaching a byte therefore costs three things: a seek to move the arm to the right track (2–3 ms on average), a rotational delay waiting for the sector to swing under the head (0–4 ms at 15,000 RPM), and the transfer itself (about 0.25 ms per 64 KB).11

Cost componentBallparkPaid when
Seek time2–3 ms averageEvery jump to a different track
Rotational delay0–4 ms (15,000 RPM)Every non-adjacent read
Transfer time≈ 0.25 ms per 64 KBAlways — the only cost you pay for sequential streaming

Two consequences shape every storage engine. First, block granularity: the disk does not sell you single bytes. The unit of transfer between disk and memory is a fixed-size block (a multiple of the device's sector size); the database's page is sized to match, and it is the smallest thing you ever read or write.11 Asking for one 8-byte integer costs the same I/O as asking for the whole page around it, so the game is to make every page you touch earn its trip. Second, sequential beats random: if the next page you want is physically adjacent, you pay only transfer time; if it is somewhere else, you pay seek plus rotation again. Hard disks are therefore very bad at random reads, and laying data out with spatial locality makes sequential scans dramatically faster.11 SSDs remove the mechanical penalty and offer fast random reads,11 but they still transfer fixed-size blocks, and the classic page-oriented design — which FerricDB follows — remains how PostgreSQL, SQLite, and nearly every production engine is built.510

Where this goes next

Because pages are the unit of I/O, the database keeps a cache of recently used pages in memory and counts its costs in "pages touched", not "bytes read". That cache is the buffer pool — the whole subject of M03. This module is about what is inside the pages.

Files and fixed-size pages

Start from the top. A PostgreSQL server manages one database cluster — a collection of databases — and identifies every database object (tables, indexes, and the databases themselves) by an OID, an unsigned 4-byte integer recorded in system catalogs such as pg_database and pg_class.1 On disk, the cluster is a directory tree: each database is a subdirectory of base/ named after its OID, and each table or index within it is stored in its own file, named by a number called the relfilenode (usually, but not always, equal to the object's OID — operations like TRUNCATE, REINDEX, or CLUSTER assign a fresh filenode).26 When a relation grows past 1 GB it is split into gigabyte-sized segment files named relfilenode.1, relfilenode.2, and so on.6 Alongside the main file live auxiliary forks: a free space map (suffix _fsm) and a visibility map (suffix _vm).26

FerricDB's course choice: one file per database, managed by the DiskManager in course/ferricdb/crates/storage. A table is not a file of its own but a chain of pages inside the shared file — closer to SQLite's model, where the complete state of a database normally lives in a single "main database file",10 than to PostgreSQL's file-per-relation tree. You get the same lessons with far less filesystem bookkeeping.

Whatever the file layout, every engine here slices its files into fixed-size pages. PostgreSQL uses pages of 8,192 bytes by default;7 SQLite allows any power of two between 512 and 65,536 bytes, fixed per database and recorded in the file header.10 Why fixed sizes? Because they buy you random access by arithmetic: page N begins at byte N × PAGE_SIZE, so any page can be located with one multiplication and fetched with one read — PostgreSQL numbers the pages of a heap file sequentially from 0 and addresses them by block number this way.3 Fixed sizes also make free space interchangeable: a page freed anywhere can be reused for anything, with no external fragmentation between pages, and the buffer pool of M03 can manage memory as an array of identical frames. All reads and writes are page-aligned and whole pages — SQLite states this explicitly for its main database file.10

FerricDB fixes the page size at 8 KB

ferricdb-common declares pub const PAGE_SIZE: usize = 8192;. That is a course choice, made to match PostgreSQL's default block size of 8 kB7 so that every number you compute for FerricDB pages transfers directly to what you would observe in a real Postgres data directory.

The slotted page

Now zoom into one 8 KB heap page. If rows were fixed-size you could treat the page as an array and index records by position, using a count or a bitmap to track occupied slots.11 Real rows are variable-length — TEXT ruins everything — so pages need a smarter internal map. The near-universal answer is the slotted page. PostgreSQL's version has three moving parts inside each page:37

  • a fixed 24-byte page header at offset 0 (PageHeaderData);3
  • an array of 4-byte line pointers (ItemIdData) growing forward from the header, each holding the byte offset, length, and a few flag bits of one tuple;37
  • the tuple data itself, stacked backward from the end of the page toward the middle.3

The unallocated region between the end of the line-pointer array and the lowest-placed tuple is the free space, informally "the hole".3 Two header fields fence it: pd_lower points just past the last line pointer (the start of free space) and pd_upper points at the start of the most recently placed tuple (the end of free space).37 The full PostgreSQL page header, 24 bytes in all:7

FieldBytesWhat it stores
pd_lsn8WAL position of the last change to this page (M10 territory)
pd_checksum2Page checksum
pd_flags2Flag bits
pd_lower2Offset to the start of free space
pd_upper2Offset to the end of free space
pd_special2Offset to the "special space" — empty in ordinary tables, used by index pages
pd_pagesize_version2Page size and layout version
pd_prune_xid4Oldest unpruned XMAX on the page, or zero

FerricDB's heap page is a deliberate near-copy. The Page type in course/ferricdb/crates/storage reserves its first 16 bytes for a page LSN (u64), a page-type tag (u32), and a reserved word (u32); the HeapPage view adds lower, upper, a slot count, and flags, bringing the heap header to the same 24 bytes as Postgres:

Why this mirror-image arrangement? Because neither side knows in advance how many entries it will need. A page might hold three enormous tuples or three hundred tiny ones; letting the pointer array and the data area grow toward each other means neither has to be pre-sized, and the page is full exactly when they meet. CS186's notes describe the same design with the directory placed in a footer growing from the page's other end — a mirror image with identical properties.11

The indirection through line pointers is the quietly brilliant part. Everyone outside the page — most importantly indexes — refers to a tuple by its TID: the pair (block number, line pointer number).3 Because the reference names a slot rather than a byte offset, the page is free to shuffle tuple bytes around during compaction: it updates the offsets stored inside its own slots and every external reference remains valid — precisely the reason PostgreSQL gives for the ItemIdData layer.7 FerricDB's RecordId { page_id, slot } is the same idea; Postgres calls it the ctid. One numbering quirk to remember: PostgreSQL offset numbers count from 1,3 while FerricDB slots are ordinary Rust indices counting from 0 — a course choice you will thank us for when you write slots[rid.slot as usize].

Interactive: life inside one 8 KB slotted page

Insert tuples and watch the slot array grow forward while data stacks backward; delete to leave tombstones; compact to reclaim dead bytes. Green = live data, red = tombstoned, plain = free. Tiny regions are widened to stay visible — the printed byte offsets are exact.

Try: insert until the page fills, delete a few tuples, watch inserts still fail, then compact.

Play with the failure mode: fill the page, tombstone two tuples, and try to insert again. The insert still fails — deleting only marks slots dead; the bytes sit where they were, and the hole between lower and upper has not grown. Only compaction slides the survivors back against the end of the page and turns dead slots into reusable ones. PostgreSQL behaves the same way: space from deleted tuples is reclaimed lazily (by pruning and vacuum, guided by header fields like pd_prune_xid), not at DELETE time.7

Inside a tuple

A tuple on a page is not just the row's values; it carries a header that the engine uses for versioning and decoding. PostgreSQL's HeapTupleHeaderData occupies a fixed 23 bytes on most machines:7 t_xmin (4 B) records the ID of the inserting transaction, t_xmax (4 B) the deleting one, t_cid (4 B) a command counter within the transaction (sharing its bytes with t_xvac), t_ctid (6 B) the TID of this or a newer version of the row, two 2-byte flag words t_infomask2 (which also holds the attribute count) and t_infomask, and the 1-byte t_hoff giving the offset where user data begins.7 If any column is NULL, a null bitmap follows the fixed header, one bit per column, with 1 meaning not-null; if the HEAP_HASNULL flag is clear, there is no bitmap and every column is present.7 Finally, padding aligns t_hoff to a multiple of the platform's MAXALIGN, because Postgres reads fields in place through C pointers.7

FerricDB keeps the ideas and drops the ballast. A stored tuple is TupleMeta — xmin: u64, xmax: u64, 16 bytes — followed by the serialized payload: a null bitmap (one bit per column, rounded up to whole bytes), then the values in schema order, with TEXT encoded as a u32 length prefix plus UTF-8 bytes. Three simplifications, all course choices: 64-bit transaction IDs sidestep the wraparound machinery that 4-byte XIDs force on Postgres;7 there is no alignment padding because FerricDB decodes bytes into Values rather than casting pointers at them; and there is no ctid chain or command ID until you need them. The xmin/xmax fields are written as 0 from Milestone 1 onward and simply ride along — they come alive in M09, when Milestone 8 starts stamping them to decide which transactions can see which tuple versions.

Pitfall: pointers inside pages

Nothing stored in a page may be a memory address — pages get written out, read back at a different address, and shipped between machines. Everything internal is a byte offset relative to the page start; everything external is a (page, slot) pair. If you find yourself serializing a Rust reference in Milestone 1, stop.

Heap tables: writing and reading

A heap table is the simplest file organization: pages hold tuples in no particular order, and neither pages nor the records within them are sorted.11 Insertion is append-where-there's-room; any ordering the query needs is imposed later by indexes (M04) or by sorting at execution time. How do you find a page with room? CS186's notes give two classic wirings: a linked list of pages hanging off a header page (optionally split into full and free lists), or a page directory — header pages holding entries of (data-page pointer, free bytes remaining) — which makes insertion cheaper because you scan compact directory entries instead of touching every data page.11 FerricDB's Milestone-1 HeapFile is the linked design: a chain of heap pages starting at first_page, walked in order — simple, and good enough until M03 gives you cheap page access.

The write path, following PostgreSQL's own description:4 to insert a tuple into a page, the engine appends a new line pointer (moving pd_lower up by 4 bytes), copies the tuple's bytes into the hole ending where the previous newest tuple began (moving pd_upper down by the tuple's size), and points the new line pointer at them. The second tuple on a page sits below the first — stacked from the bottom — and so on.4 Reads come in two flavors: a sequential scan visits every page and follows every line pointer on each,4 while an index scan finds, in the index, an entry pairing a key with a TID — say (block = 7, offset = 2) — reads just that block, and follows just that line pointer.4

Worked example: one million account rows

Concrete numbers, using the FerricDB formats above. Table: accounts(id INTEGER, owner TEXT, balance INTEGER), with owner strings averaging 11 bytes. Per tuple:

  • payload = null bitmap (⌈3/8⌉ = 1 B) + id (8 B) + owner (4 B length + 11 B) + balance (8 B) = 32 B;
  • stored tuple = 16 B TupleMeta + 32 B payload = 48 B;
  • page cost per row = 48 B + one 4 B slot = 52 B.

A page offers 8192 − 24 = 8168 usable bytes, so ⌊8168 / 52⌋ = 157 rows per page (157 × 52 = 8164, leaving a 4-byte hole — too small for anything, and that's fine). One million rows need ⌈1,000,000 / 157⌉ = 6,370 pages ≈ 49.8 MiB. Now price a full scan with CS186's ballpark disk numbers:11 read sequentially, you pay one arm movement (≈ 4.5 ms) plus transfer: 49.8 MiB at 0.25 ms per 64 KB ≈ 0.2 s. Read the same 6,370 pages in random order and every page costs a seek plus rotation plus its transfer, ≈ 4.5 ms each: about 29 s — the identical bytes, roughly 140× slower. That two-orders-of-magnitude gap is why heap files keep a table's pages together, why scans stream pages in order, and why the planner you build in M08 will treat "how many random pages does this plan touch?" as the dominant cost question.

Free space management

When a tuple arrives, which page takes it? Scanning the whole heap for a gap would make inserts O(table size). PostgreSQL answers with the Free Space Map: nearly every heap and index relation (hash indexes excepted) has an FSM stored in its _fsm fork.8 The FSM is a tree of FSM pages: at the bottom level, one byte per heap page records how much free space that page has; each upper level stores, per node, the larger of its two children's values, so the maximum available anywhere in the relation bubbles up to the root.8 To place a tuple, descend from the root toward any leaf whose byte promises enough room — a logarithmic search instead of a heap scan. The one-byte-per-page resolution is deliberately coarse: the FSM is a hint, cheap to maintain, not an exact ledger.8

FerricDB in Milestone 1 does the honest simple thing instead: HeapFile::insert walks the page chain asking each page's free_space() until one fits, appending a fresh page at the end of the chain if none does. That is O(pages) per insert and clearly worse — which is the point: when your inserts crawl on a big table, you will know exactly why Postgres bothers with an FSM fork, and building a small page-directory or FSM-style summary is a natural stretch goal.

Large values: overflow and TOAST

Fixed-size pages have an obvious blind spot: a 100 KB TEXT value does not fit in an 8 KB page, and PostgreSQL does not allow a tuple to span multiple pages.9 Every page-based engine needs an escape hatch, and the two systems we track solve it differently:

TOAST — "The Oversized-Attribute Storage Technique" — kicks in when a row exceeds TOAST_TUPLE_THRESHOLD (normally 2 kB). The engine then compresses and/or moves the widest values out of line until the row drops below TOAST_TUPLE_TARGET (also 2 kB by default).9 Only variable-length (varlena) types participate: their first 4-byte word holds the value's total length, and TOAST borrows two bits of it, capping any TOASTable value at 1 GB (230 − 1 bytes).9

An out-of-line value is chopped into chunks of at most TOAST_MAX_CHUNK_SIZE (about 2,000 B, sized so four chunk rows fill a page) and the chunks become rows — (chunk_id, chunk_seq, chunk_data) — in a companion TOAST table with a unique index on (chunk_id, chunk_seq).9 The main tuple keeps only an 18-byte TOAST pointer recording where the value went and its sizes.9 Per-column strategies tune the behavior: PLAIN (no compression, no out-of-line), EXTENDED (both — the default for most TOASTable types), EXTERNAL (out-of-line only, which speeds substring operations on wide text/bytea), and MAIN (compression only, out-of-line as a last resort).9 The elegance: the 100 KB value is stored as ordinary rows in an ordinary table, reusing the very heap machinery this module describes.

SQLite spills instead of relocating. When a b-tree cell's payload exceeds a threshold computed from the page's usable size, a prefix stays on the b-tree page and the surplus moves to a chain of overflow pages: the first 4 bytes of each overflow page hold the page number of the next page in the chain (zero marks the last), and the rest is content.10 The thresholds are tuned so that a b-tree page keeps a minimum fanout of 4 and enough of the payload stays local that the record header can usually be parsed without visiting the chain at all.10

Reading the tail of a large value means walking the linked list page by page — sequential pointer-chasing, exactly the random-I/O pattern the first section priced out. Compare TOAST's chunk table: with an index on (chunk_id, chunk_seq), Postgres can jump straight to the middle chunk of a value.9

FerricDB's Milestone-1 course choice is stricter than either: a tuple must fit in one page, and HeapPage::insert simply refuses oversized rows (Error::PageFull). You will feel the ceiling the first time you store a long string — a TOAST-style companion table is a lovely stretch project once the heap works.

Contrast: SQLite's single-file world

SQLite is the sharpest available contrast to the Postgres storage story, because it makes different choices at almost every layer while still being a page-based relational engine. The whole database — schema, every table, every index — normally lives in one file, divided into equal-size pages numbered from 1; the page size is a power of two between 512 and 65,536, read from a 2-byte field at offset 16 of the file's 100-byte header, which begins with the magic string "SQLite format 3\0".10

A table is an unordered heap; rows go wherever there is room, and the row's address — the TID (block, offset number) — is stable enough for indexes to point at.3 Indexes are physically separate structures (separate files in Postgres,6 separate page chains in FerricDB) whose entries map keys to TIDs.4 Finding a row by primary key therefore always means: search the index for a TID, then fetch the heap page it names.

There is no heap. Each table is a b-tree keyed by the 64-bit signed integer rowid; the row's column values, encoded in SQLite's record format, are the payload of a leaf cell, and interior pages hold only keys and child pointers.10 A rowid lookup walks one tree and arrives at the data itself. Within each b-tree page you will recognize our slotted layout in mirror finish: after the 8-byte (leaf) or 12-byte (interior) page header comes an array of 2-byte cell pointers kept in key order, while the cells themselves are packed toward the end of the page, unallocated space between them; freed cells go on a freeblock chain, and 1–3-byte scraps too small for a freeblock are counted as fragmented bytes in the page header.10

Values are self-describing: each record starts with a varint header of "serial type" codes — NULL costs zero bytes of payload, integers come in 1/2/3/4/6/8-byte flavors, and odd codes ≥ 13 mean a string of (N−13)/2 bytes.10 FerricDB instead trusts the catalog's schema to drive decoding — which is why tuple::deserialize takes a &Schema.

Neither design dominates. Clustering rows in a rowid b-tree makes primary-key range scans naturally sequential, but every insert must find its sorted position, and secondary indexes must reference rowids through a second tree descent. The heap makes inserts trivially cheap and gives every row a direct physical address, at the price of a heap fetch after every index lookup. You are building the heap design; by M04, when B+Trees arrive, you will be equipped to argue both sides.
