The view from here

You have built a disk-oriented, row-store, single-node, MVCC relational database — the architecture that has anchored the industry since System R. This closing module surveys the major departures from that design and what each one buys. Every section pairs with either a stretch milestone (S1–S4) or a reading trail; none of it is required to consider the course complete, and all of it is easier to learn now than it would have been thirteen modules ago.

LSM storage engines

Your heap files and B+Tree update pages in place. The log-structured merge tree takes the opposite bet: all modifications — inserts, updates, deletes — are applied lazily, batched in memory (the memtable) and written to disk as immutable sorted string table (SST) files; a background compaction process merges SSTs to physically apply updates and deletions.1 Immutability is the design's engine: on-disk data never changes, so concurrency control simplifies dramatically and even offloading compaction to other machines becomes possible.1 The cost is paid on the read path — a lookup may consult the memtable and several SSTs — and in write/space amplification from rewriting data during compaction. RocksDB (built on LevelDB) is the canonical implementation, and distributed systems like TiDB and CockroachDB sit on LSM storage.1

Go build it: Stretch S3 follows Mini-LSM — a course structured as weeks of seven ~2-hour chapters, building memtables, SSTs, and compaction in Rust — and then swaps FerricDB's heap for the result.1

Column stores and OLAP

FerricDB stores rows contiguously — perfect for OLTP, where queries touch few rows and many columns. Analytics inverts the pattern: scan millions of rows, read three columns, aggregate. Columnar systems store each column contiguously instead, which reads only the bytes the query needs, compresses spectacularly (a column is self-similar), and enables vectorized execution — the design direction the 2024 Stonebraker/Pavlo survey singles out as the architecture story for modern OLAP workloads.2 A caution from the same survey while you're near the terminology: column-family stores (Bigtable, Cassandra) are not columnar storage despite the name.2

Go read it: RisingLight is an educational OLAP database in Rust — columnar storage and vectorized execution at a codebase size one person can absorb.3 Your Module 6 executor knowledge maps directly; the difference is that next() returns column batches instead of single rows.

Raft and distributed SQL

One machine bounds durability, capacity, and availability. The distributed answer layers a consensus protocol under the database: writes go through a replicated log that a majority of nodes must acknowledge, and each node applies the log to its local state machine — producing linearizable replication of exactly the kind toyDB demonstrates with Raft underneath an MVCC SQL engine.4 toyDB is the recommended tour: an educational distributed SQL database in Rust whose author went on to build CockroachDB and Neon, deliberately trading performance and availability for understandability.4 Notice how much transfers: its storage engines, MVCC layer, and iterator-based SQL engine are the architecture you just built — consensus slides in underneath a design you already own.4

Go build it: Stretch S4 maps toyDB's Raft architecture onto FerricDB for a three-node local cluster.

What production Postgres adds

FerricDB is Postgres-shaped; production Postgres is that shape plus decades of hardening. The honest inventory of what you skipped:

  • Full TOAST — values too large for a page are compressed and sliced into an out-of-line toast table transparently; you documented the concept in M02 and stored only page-sized tuples.5
  • True SERIALIZABLE via SSI — non-blocking predicate locks that detect dangerous dependency structures; your write-skew test documents the gap, stretch S2 narrows it.6
  • Parallel query — one query fanned across worker backends; your Volcano operators are single-threaded by design.
  • Replication and PITR — streaming WAL to standbys and archiving it for point-in-time recovery: the log you built in Milestone 9, weaponized. interdb's Chapters 10–11 cover both mechanisms in the same depth this course's chapters relied on.5
  • An extensible type system — Postgres's founding idea. Hellerstein's recollection of the Berkeley project traces how user-defined types, functions, and access methods — radical in the 1980s — became the feature that kept Postgres relevant for every new workload since.7

What goes around comes around

In 2005, Stonebraker and Hellerstein surveyed 35 years of data models and concluded that the relational model with an extendable type system had dominated all comers. The 2024 sequel by Stonebraker and Pavlo re-runs the exercise over the NoSQL era — MapReduce, key-value, document, column-family, text, array, vector, and graph systems — and lands in the same place: systems that deviated from SQL and the relational model have not dominated the landscape, often serving niche markets, while many that rejected the RM with fanfare later converged back toward it.2 The moral for a systems builder is not that innovation is futile — it is that data outlives code, and models with sound foundations absorb their challengers' best features. You now know, from the inside, why the architecture you built is the one that keeps winning: every layer of it is replaceable, and this module just showed you the replacements.
