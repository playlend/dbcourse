The view from here

Across ten milestones you built a complete, working relational database from raw 8 KB pages up to a PostgreSQL-compatible network server. Stand back and notice the exact point in design space FerricDB occupies: it is a disk-oriented, row-store, single-node, MVCC engine with in-place slotted pages, B+Tree indexes, tuple-at-a-time Volcano execution, and ARIES write-ahead logging — the architecture that has anchored general-purpose databases since System R and Berkeley Postgres.78

Every major branch of modern database engineering departs from FerricDB along one of four architectural axes: how writes reach storage (in-place pages vs. log-structured merge trees), how tuples are laid out and processed (row-at-a-time OLTP vs. columnar vectorized OLAP), where the primary copy of data lives (disk-backed buffer pool vs. in-memory DRAM), and where the failure and scaling boundary sits (single-node ACID vs. consensus-replicated distributed SQL). This closing survey maps all four departures, catalogs what production PostgreSQL layers onto FerricDB's exact spine, and pairs each direction with a stretch milestone (S1–S4) or reading trail.

LSM storage engines

FerricDB's heap files and B+Trees are update-in-place structures: inserting or modifying a row locates the target 8 KB page, dirties that frame in the buffer pool, and eventually writes the entire 8 KB page back to disk. Under random write-heavy workloads, a single 100-byte update triggers an 8,192-byte page rewrite (plus WAL bytes) — an 80× physical page write overhead and random I/O across the file.

A log-structured merge tree (LSM-tree) — the engine behind LevelDB, RocksDB, TiKV, CockroachDB's Pebble, and the educational Rust course Mini-LSM — inverts that tradeoff by converting random mutations into sequential appends:1

  1. WAL + Memtable (fast sequential writes). Every put(key, value) or delete(key) first appends sequentially to an on-disk write-ahead log (WAL) so committed writes survive a crash before reaching SSTables, and then inserts the entry into a sorted in-memory memtable (typically a skip list or B-tree in RAM).1 No existing data page on disk is read or modified.
  2. Flush to immutable SSTables. Once the active memtable reaches a size threshold (commonly 4–64 MB), it freezes as an immutable memtable while a fresh active memtable accepts new writes. A background worker sequentially writes the frozen memtable to disk as a Level-0 Sorted String Table (SSTable) — an immutable file of sorted key-value data blocks paired with an in-file block index of fence pointers (recording each block's min/max key) and a compact Bloom filter.1
  3. Deletes via tombstones. Because SSTables are strictly immutable, deleting a key that lives in an older SSTable cannot erase bytes in place. Instead, delete(k) writes a special deletion marker — a tombstone — for key k into the active memtable.1 Readers resolve keys by checking newest structures first and stopping on the first hit; encountering a tombstone means "key does not exist", masking any older value in deeper levels. The tombstone and the superseded value are only physically discarded later when compaction merges them into the bottommost level where no older versions can remain.
  4. Read path, fence pointers, and Bloom filters. Because newer versions of a key may sit in the active memtable, frozen memtables, any overlapping L0 SSTable, or one SSTable per lower level (L1, L2, …), a point lookup may have to probe multiple files — the price known as read amplification.1 Two metadata structures bound that cost: fence pointers binary-search directly to the single candidate data block inside an SSTable, and a per-SSTable Bloom filter (a compact bit array with zero false negatives and ~1% false positives at ~10 bits per key) lets readers skip almost every SSTable that does not contain the requested key without issuing a disk read.1

Compaction strategies and the write / read / space tradeoff

Left unchecked, flushing memtables creates an unbounded pile of overlapping L0 files, slowing reads and wasting disk space on dead versions and tombstones. Background compaction performs a multi-way merge sort (the same k-way merge idea from M07) over overlapping SSTables, retaining only the newest live version of each key and writing clean new SSTables to a deeper level.1 Immutability makes compaction dramatically cleaner to synchronize than in-place B+Tree page splits: readers hold references to existing SSTables while compaction builds new files out of band and atomically swaps the manifest.

Two classic compaction designs trade write amplification, read amplification, and space amplification against each other (often called the RUM conjecture — Read, Update, Memory overhead):1

  • Size-tiered compaction (STCS): waits until several SSTables of similar size accumulate (e.g., four 64 MB files) and merges them into one larger SSTable (256 MB). Each byte is rewritten fewer times (lower write amplification), but multiple overlapping runs coexist at every tier (higher read amplification) and merging the largest tier temporarily needs up to ~2× free disk space (high space amplification).
  • Leveled compaction (LCS, LevelDB/RocksDB default): organizes disk into levels whose capacity grows by a fanout factor T (commonly T = 10: L1 = 10 MB, L2 = 100 MB, L3 = 1 GB, L4 = 10 GB).1 Except for L0, every level partitions its key space into strictly non-overlapping SSTables, so a point lookup checks at most one SSTable per level and space amplification stays near T / (T − 1) ≈ 1.11× (90% of data lives in the bottommost level). The cost is write amplification: pushing a key from level i into level i + 1 rewrites up to ~T overlapping SSTables in level i + 1, so across 4 levels a key can be written 30–40× over its lifetime — though always in large sequential transfers.

Column stores and OLAP

FerricDB stores all attributes of a row contiguously inside one slotted-page tuple (an N-ary Storage Model, or row store). That layout is ideal for OLTP, where a transaction fetches or inserts one complete customer record at a time with a single page read or write. Analytical workloads (OLAP) invert the access pattern: scan tens of millions of rows, touch two or three columns out of fifty, and compute grouped aggregations.2

A column store (Decomposition Storage Model — used by DuckDB, ClickHouse, Snowflake, Apache Parquet, and the educational Rust engine RisingLight) stores each column's values contiguously on separate pages or stripes.23 Four compounding mechanisms make columnar systems one to two orders of magnitude faster on analytical scans:

  1. I/O projection pushdown. Answering SELECT AVG(age) FROM users on a 40-column table touches only the age column pages — skipping 95%+ of the table's bytes before they ever enter the CPU cache.2
  2. Lightweight columnar compression. Values within one column share the same data type and narrow value distribution, so simple CPU-cheap codecs achieve dramatic shrinkage: run-length encoding (RLE) collapses sorted or low-cardinality columns (such as country codes or booleans) into (value, count) runs; dictionary encoding maps repeated strings ("london", "paris") to compact integer codes; delta / frame-of-reference encoding stores differences between adjacent timestamps or monotonic IDs; and bit-packing trims leading zero bits. Crucially, analytical operators can filter and aggregate directly on compressed dictionary codes or RLE runs without decompressing row by row.2
  3. Vectorized execution and SIMD. FerricDB's Volcano iterator from M06 calls next() -> Result<Option<ExecRow>> once per tuple, paying virtual dispatch, enum-tag matching, and branch mispredictions on every row. Vectorized engines like RisingLight pass contiguous column batches (e.g., 1,024–4,096 values of one primitive type) between operators.3 The inner loop iterates over a flat &[i64] slice with zero per-row virtual calls, fitting inside L1 cache and auto-vectorizing onto CPU SIMD lanes (AVX2 / NEON).
  4. Late materialization. During a query such as SELECT name, city FROM users WHERE age > 35, a column store evaluates the predicate on the age vector first, producing a compact bitmask or list of matching row offsets, and fetches name and city only for the surviving rows — never reconstructing full tuples for rows the filter rejects.
HTAP tradeoffs and a terminology trap

Hybrid Transactional/Analytical Processing (HTAP) engines try to serve both workloads from one system — typically absorbing OLTP writes in a mutable row-oriented delta store while converting cold slices into compressed columnar segments (or replicating WAL to a columnar replica). Maintaining dual formats adds synchronization and memory overhead, which is why dedicated row and column engines still dominate their respective niches. Also beware a famous naming collision flagged in Stonebraker & Pavlo's 2024 survey: column-family stores (Bigtable, HBase, Cassandra) organize semi-structured attributes under a row key — they are a data model, not true columnar storage.2

Go read it: RisingLight is an educational OLAP database in Rust demonstrating columnar storage, vectorized execution, and a Cascades-style optimizer at a codebase size one engineer can read end to end.3 Your M06 executor intuition maps directly — the core change is that operators exchange column vectors instead of single rows.

In-memory database systems

Wait: what happens if your entire OLTP database — say 128 GB — fits comfortably inside a server's RAM, so FerricDB's or PostgreSQL's buffer pool achieves a 100% cache hit rate? You might expect disk-oriented architecture overhead to vanish. In practice, it does not.28

Classic architecture analyses of disk-oriented DBMSs running entirely out of RAM found that a huge share of CPU instructions still goes to machinery built for slow spinning disks: hashing a PageId through the buffer-pool page table, pinning and unpinning frames, taking buffer-pool and page latches, walking slotted-page indirections, acquiring row/table locks in a central lock manager, and formatting heavy physical before/after WAL images.28 Even with zero disk reads, useful tuple-processing work can account for only a small fraction of total CPU time.

In-memory database systems — notably research and commercial engines such as H-Store / VoltDB, Microsoft's Hekaton, and Silo — strip away the disk-oriented assumption from the ground up:2

  • No buffer pool, direct memory pointers. Tuples live natively in DRAM arenas rather than inside fixed 8 KB slotted pages, and index nodes hold raw 64-bit memory pointers directly to tuples instead of (page_id, slot) addresses that must be translated on every lookup. Eliminating frame pinning and page-table hashing removes an entire layer of synchronization overhead.
  • Latch-free and partitioned concurrency control. With disk stalls gone, transactions finish in microseconds, making central lock-table contention the primary bottleneck. Systems took two distinct paths: H-Store / VoltDB partitions data across CPU cores and executes single-partition stored procedures serially on each core with zero locks and zero latches; Hekaton and Silo target multi-core shared-memory workloads using latch-free indexes (Bw-Tree, Masstree), epoch-based memory reclamation, and optimistic concurrency control (OCC) or lock-free MVCC so concurrent readers never bounce cache lines on shared lock headers.2
  • Command / redo logging plus checkpoints for durability. DRAM is still volatile — a power loss wipes every pointer. In-memory engines preserve ACID durability by writing a streamlined sequential redo or command log (in H-Store, logging only the stored procedure name and parameters rather than page diffs) to SSD, paired with periodic asynchronous checkpoints / snapshots so restart loads the latest checkpoint into RAM and replays the log tail.2
Why disk-oriented engines still dominate general workloads

As Stonebraker & Pavlo observe in their 2024 retrospective, pure in-memory OLTP engines hit two economic realities.2 First, DRAM remains roughly an order of magnitude or more costlier per gigabyte than NVMe flash, and byte-addressable persistent memory (such as Intel Optane) was discontinued — forcing pure in-memory engines to hit a hard capacity wall or bolt on cold-data eviction ("anti-caching"), which reintroduces a buffer pool in disguise. Second, modern NVMe SSDs deliver millions of IOPS and multi-GB/s bandwidth; pairing NVMe with lean buffer pools (using pointer swizzling to turn hot PageIds into direct pointers in RAM and OS-bypass async I/O) captures much of the speed without sacrificing the ability to store datasets larger than memory.2

Consensus (Raft) and distributed SQL

A single FerricDB process hits three walls: if the host's disk or motherboard fails, the database goes offline; if a region loses power, local WAL cannot save availability; and one machine bounds total storage and write throughput. Distributed databases break the single-node availability wall by placing a replicated state machine backed by a consensus protocol underneath the SQL engine.4

The principle is clean: if three (or five) nodes start from the same initial database state and apply the exact same sequence of deterministic write commands in the exact same order, every node converges to the exact same state. Raft — the understandable consensus protocol used by toyDB, etcd, TiKV, and CockroachDB — guarantees that identical log order across a cluster despite crashes, restarts, and network partitions using three mechanisms:4

  1. Terms and leader election. Raft divides logical time into monotonically increasing integer terms, with at most one elected Leader per term. Every node begins as a Follower expecting periodic heartbeats (empty AppendEntries RPCs) from the leader. If a follower's randomized election timeout (e.g., 150–300 ms, randomized to avoid split votes) expires without hearing from a leader, it increments its term, transitions to Candidate, votes for itself, and broadcasts RequestVote RPCs. A candidate wins the election only upon collecting votes from a majority quorum (⌊N/2⌋ + 1 — 2 of 3 nodes, or 3 of 5). Crucially, a voter rejects any candidate whose log is less up-to-date than the voter's own log.4
  2. Log replication (AppendEntries) and quorum commit. Clients send write transactions to the leader (followers either forward requests to the leader, as toyDB does, or return a redirect).4 The leader appends the serialized command to its durable Raft log at (term, index) and sends AppendEntries carrying (prevLogIndex, prevLogTerm) to all followers. Each follower checks that its own log matches at prevLogIndex (if not, the leader backs up and repairs the diverging suffix) and persists the new entry. Once a majority of nodes — including the leader — have persisted the entry, the leader advances commitIndex, applies the entry to its local storage engine (FerricDB's execute()), and returns success to the client. Followers learn the updated commitIndex on the next AppendEntries or heartbeat and apply it locally.4
  3. Quorum intersection (the safety guarantee). Why can a 3-node Raft cluster tolerate 1 failed or partitioned node without ever losing a committed write, yet stall if 2 nodes fail? Because any two majorities of N nodes must overlap in at least one node. Every newly elected leader's voting quorum intersects the quorum that committed entry k, and the up-to-date-log rule ensures the new leader already holds entry k before winning the election. Conversely, a minority partition (1 of 3) can never form a quorum, preventing split-brain divergent commits.

From single-Raft replication to multi-shard distributed SQL

Running one Raft group over the whole database (the architecture of toyDB and Stretch S4) provides linearizable replication and automatic failover, but every write still serializes through one leader.4 Production distributed SQL systems such as CockroachDB, TiDB, and Google Spanner scale writes horizontally using Multi-Raft: they partition each table's key space into ranges (shards, e.g., 64–512 MB each), where every range is its own independent Raft group with its own leader spread across the cluster.2 Transactions touching only one range commit in a single Raft round trip; transactions spanning multiple ranges layer an atomic commit protocol — Two-Phase Commit (2PC) or Google Percolator's asynchronous write-intent / timestamp-oracle design — across the participating Raft groups, trading higher cross-shard commit latency for horizontal scale and geo-distributed resilience.2

Go build it: toyDB — written in Rust by an engineer who went on to work on CockroachDB and Neon — layers Raft directly beneath an MVCC storage and iterator SQL engine structurally identical to FerricDB.4 Stretch S4 guides you through wiring a three-node Raft cluster around your finished FerricDB server.

What production PostgreSQL adds

FerricDB shares PostgreSQL's fundamental architecture — 8 KB slotted pages, B+Tree indexes, cost-based planning, Volcano execution, MVCC snapshots, ARIES-style WAL, and the v3 wire protocol. Production PostgreSQL hardens that exact skeleton with decades of engineering. Here is the honest inventory of what FerricDB deliberately leaves out:

  • Full TOAST for oversized values. As introduced in M02, PostgreSQL forbids a single heap tuple from spanning multiple 8 KB pages.9 When a tuple exceeds TOAST_TUPLE_THRESHOLD (normally 2 kB), PostgreSQL compresses wide variable-length columns (text, bytea, jsonb) using pglz or lz4 and/or slices them into ~2,000-byte chunks stored as ordinary rows in a companion pg_toast table indexed by (chunk_id, chunk_seq), replacing the inline bytes in the main heap tuple with an 18-byte TOAST pointer.9 FerricDB keeps every tuple inside one 8 KB page and returns Error::PageFull if a single row exceeds page capacity.
  • True SERIALIZABLE via Serializable Snapshot Isolation (SSI). FerricDB implements Snapshot Isolation with first-committer-wins write-conflict detection, which prevents lost updates but allows write skew (tested explicitly in ms8_write_skew_is_documented). PostgreSQL delivers true serializability without blocking readers by tracking non-blocking SIREAD predicate locks on tuples, pages, and index gaps to detect rw-antidependency "dangerous structures" (two consecutive read-write conflict edges T1 →rw T2 →rw T3 where T3 commits first) and aborting a participant with SQLSTATE 40001 before an unserializable cycle can commit.6 See Stretch S2 to add SSI detection to FerricDB.
  • Parallel query execution. Your Volcano operators run single-threaded per query. When PostgreSQL's cost model predicts a large scan, join, or aggregation will benefit from multiple cores, the planner inserts a Gather (or Gather Merge) node above parallel-aware operators — Parallel Seq Scan, Parallel Index Scan, Parallel Hash Join, and Parallel Aggregate.10 The leader backend launches dynamic background worker processes that divide heap blocks or hash partitions through shared memory queues and stream partial results back to the Gather node.10
  • Streaming replication, logical replication, and PITR. Milestone 9 used WAL purely for local crash recovery. Production PostgreSQL turns the exact same WAL stream into its replication fabric: archiving completed WAL segments alongside a physical base backup enables Point-in-Time Recovery (PITR) to any past timestamp or transaction; streaming WAL records continuously from a primary's walsender to a standby's walreceiver provides physical hot standbys (either asynchronous or synchronous before COMMIT returns); and logical replication decodes WAL into row-level changes for selective table publishing and zero-downtime major-version upgrades.5
  • Background maintenance processes (autovacuum, checkpointer, bgwriter). In FerricDB you invoke VACUUM and checkpoints explicitly. Production PostgreSQL delegates continuous housekeeping to dedicated daemon processes: autovacuum automatically prunes dead MVCC versions, updates planner statistics, and freezes old 32-bit transaction IDs before wraparound;11 the background writer (bgwriter) steadily flushes dirty buffer frames so client backends rarely stall waiting for a clean frame; and the checkpointer spreads checkpoint disk writes over time (checkpoint_completion_target) to prevent sudden I/O latency spikes.811
  • An extensible type system and pluggable access methods. Joseph Hellerstein's retrospective on the original UC Berkeley POSTGRES project highlights its most enduring architectural idea: instead of hardcoding primitive types and B-trees in C, Postgres stored types (pg_type), operators, functions (pg_proc), and index access methods in data-driven system catalogs.7 That single decision — radical in 1986 — enabled generalized index frameworks (GiST, GIN, SP-GiST, BRIN) and allowed a forty-year-old relational engine to absorb geospatial queries (PostGIS), semi-structured JSONB, full-text search, and modern vector similarity search (pgvector) as first-class extensions without rewriting its core.7

What goes around comes around

In 2005, Michael Stonebraker and Joseph Hellerstein surveyed thirty-five years of database history — hierarchical, network, relational, entity-relationship, object-oriented, and XML models — and concluded that the relational model paired with an extensible type system had outlasted every challenger. Nearly twenty years later, Stonebraker and Andrew Pavlo re-ran the analysis across the entire post-2005 wave: MapReduce, key-value stores, document databases, column-family stores, full-text engines, array stores, graph databases, and vector databases.2

Their 2024 verdict is remarkably consistent with 2005. Systems that discarded schemas, declarative query optimization, and ACID transactions either remained specialized niche tools or steadily converged back toward SQL and the relational model — adding SQL-like query languages, multi-record transactions, and cost-based optimizers over time.2 Meanwhile, relational systems absorbed the challengers' genuinely valuable ideas: columnar storage and vectorized execution for analytics, JSON document types inside extensible catalogs, and distributed consensus beneath SQL.27

The lesson for a systems builder is not that innovation does not matter — it is that data outlives application code, and clean layered boundaries win over decades. Look back at the ten crates you assembled in course/ferricdb/crates/: storage, buffer pool, B+Tree index, SQL frontend, catalog, planner and executor, MVCC transaction manager, ARIES WAL, the PostgreSQL wire server, and the ferricdb CLI/REPL binary. Every single one of those layers can be replaced independently — heap with LSM, Volcano with vectorized columns, local disk with Raft consensus — because the relational abstraction above them holds firm. You no longer treat databases as black boxes; you know, down to the byte, how the machine works.
