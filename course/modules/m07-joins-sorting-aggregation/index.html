The executor's toolbox

In M06 you built the skeleton of a query executor: a tree of operators, each implementing the same iterator interface, pulling tuples from its children one next() call at a time. That design — init, get_next, close — is the iterator (Volcano) model that nearly all relational executors use, and the standard set of operator subclasses in such a system includes file scan, index scan, sort, nested-loop join, merge join, hash join, duplicate elimination, and grouped aggregation; because every operator speaks the same interface, any of them can feed any other.1 So far your operators have been the easy ones: scans, filters, projections. This module is about the hard ones — the operators that combine two inputs or need to see all of one input before emitting anything.

Two habits from earlier modules carry over. First, we measure cost in page I/Os, because reading and writing disk pages dominates everything else when data outgrows memory.6 Second, we use the CS186 notation: for a relation R, [R] is its size in pages and |R| its size in tuples, and B is the number of buffer pages the operator is allowed to use.2 The buffer pool from M03 is where those B pages live; in FerricDB the per-query budget is a field on ExecContext in course/ferricdb/crates/exec — a course choice that mirrors PostgreSQL's work_mem setting, the memory allowance PostgreSQL gives its sort and hash operators before they spill to temporary files.3,5

Our running example for cost arithmetic, used throughout this page:

Nested loop joins

The naive algorithm

The simplest join is two nested loops: for each tuple r of the outer relation R, scan the entire inner relation S and emit (r, s) for every s that satisfies the join predicate.2 Because it evaluates the predicate against every pair, it works for any join condition — equality, inequality, arbitrary expressions — which none of the other algorithms on this page can claim.2,4 It also needs no setup: PostgreSQL models the nested loop join with a start-up cost of zero, meaning it can emit its first row almost immediately, and a run cost that grows as O(Nouter × Ninner).3

Counting I/Os exposes how brutal the naive version is. Reading the outer once costs [R]; re-scanning the inner for every outer tuple costs |R|·[S], for a total of [R] + |R|·[S].2 With our example tables that is 1,000 + 100,000 × 400 = 40,001,000 I/Os. At even 10,000 page reads per second, that is more than an hour for a join of two modest tables. Unsurprisingly, the tuple-at-a-time nested loop is rarely what a real planner selects.3

Page and block nested loop

The first fix is to respect the unit of I/O. Since we read whole pages anyway, loop over pages of R, and for each page of R scan S once, joining all tuple pairs between the two in-memory pages. This page nested loop join costs [R] + [R]·[S], and it pays to make the smaller relation the outer one.2 For our example (with S outer): 400 + 400 × 1,000 = 400,400 I/Os — a 100× improvement for free.

The second fix is to use all the memory we were given, not just two pages. The block nested loop join (BNLJ) reserves one buffer page as the output buffer, one as the input page for the inner relation, and fills the remaining B − 2 pages with a chunk of the outer relation. The inner relation is then scanned once per chunk rather than once per page, so the cost drops to [R] + ⌈[R]/(B−2)⌉ · [S].2

With B = 52 and the smaller S as the outer: 400 + ⌈400 / 50⌉ × 1,000 = 400 + 8 × 1,000 = 8,400 I/Os. Same answer as the naive loop, roughly 4,700× cheaper. This is the single most important lesson of the module: join cost is mostly about how many times you re-read the inner input, and memory buys down that count.

Index nested loop

If the inner relation has an index on the join column (built in M04), we do not need to scan S at all: for each outer tuple, probe the index. Cost: [R] + |R| × (cost of one index lookup).2 PostgreSQL implements this as a parameterized index path — the inner index scan takes the current outer tuple's join value as a parameter — and the total cost then grows only as O(Nouter).3 Beware the arithmetic, though: with 100,000 outer tuples and ~2 I/Os per probe, our example costs about 201,000 I/Os — worse than BNLJ. Index nested loop shines when the outer input is small or heavily filtered, not when you join everything against everything.2

PostgreSQL adds one more twist worth copying: the materialized nested loop. Rather than re-reading the inner table from the heap on every rescan, the executor scans it once and writes the tuples into a temporary tuple store (tuplestore.c) that lives in work_mem and overflows to a temporary file if the tuples outgrow it; every subsequent rescan then reads this compact store instead of the base table, which the cost model treats as much cheaper.3 In FerricDB, Milestone 6's NestedLoopJoin executor follows that materialized pattern — buffering the inner child once in memory during open() and scanning it for each outer row — while the block nested loop join above gives you the general disk-oriented algorithm and cost model when neither side fits.2,3

Pitfall: rescanning an iterator

A nested loop join must restart its inner child once per outer tuple/chunk. In a Volcano executor that means the inner subtree needs a cheap "rewind". If the inner child is itself an expensive subquery, re-running it is a disaster — which is exactly why executors interpose a materialize step that caches the inner tuples after the first pass.3 When you implement open()/next(), decide explicitly what a second open() means.

Merge join

If both inputs happen to be sorted on the join key, joining them is nearly free: walk the two sorted streams in tandem, the way you merge two sorted lists, and emit matches as the cursors pass each other. This is the sort-merge join (PostgreSQL calls the operator merge join), and it only works for equality predicates — PostgreSQL restricts it to natural and equi-joins.2,4

The subtle part: duplicates

With unique keys, one pointer per side and "advance the smaller" is the whole algorithm. Duplicate keys break that: if R has two tuples with key 2 and S has two, the join must emit all 2×2 = 4 combinations, so the S cursor has to re-visit its group of key-2 tuples once per matching R tuple. The standard solution is a mark: when a match is first found, remember (mark) the position in S where the matching run starts; advance S through the run emitting pairs; when S leaves the run, advance R and reset S back to the mark.2

Cost, assuming neither input is sorted yet: sort R, sort S, then a single interleaved pass over both — sort(R) + sort(S) + [R] + [S] in the typical case.2 The merge phase is only linear when duplicate runs are short; in the degenerate worst case where every tuple of both relations carries the same key, the rescanning collapses toward nested-loop behavior, sort(R) + sort(S) + [R] + |R|·[S].2 For our example tables and B = 52 (using sort costs derived below): 4,000 + 1,600 + 1,400 = 7,000 I/Os. A further refinement fuses the last merge pass of each sort into the join itself — legal whenever the leftover sorted runs of both inputs together fit in B − 1 buffers — saving one full read+write of both relations, 2·([R]+[S]) I/Os; here that brings the total down to 4,200.2

Where do sorted inputs come from in practice? Three places, which map exactly onto PostgreSQL's merge join plan shapes: an explicit sort node on either input; a B+Tree index scan that yields rows already in key order, letting the planner skip the sort entirely; and optionally a materialize node on the inner input to make its rescans cheap.4 PostgreSQL performs those input sorts in memory if they fit and falls back to temporary files on disk if they do not.4 Internally a single MergePath chosen by the planner can therefore expand into as many as four plan nodes: the merge join itself, up to two sorts, and a materialize.9

Hash join

Build and probe

For a pure equi-join, sorting is more work than necessary — we do not need order, only matching. The in-memory hash join exploits that in two phases. Build: scan the smaller input once and insert every tuple into an in-memory hash table keyed by the join attribute. Probe: scan the larger input once; hash each tuple's key, look into the corresponding bucket, and emit a joined row for every entry whose key truly matches.2,5 Total cost: [R] + [S] — one read of each relation, the theoretical floor for any join — but it is only legal if the build relation fits in the B − 2 available buffer pages.2

In PostgreSQL's implementation the inner relation is the build side: its hash table (a structure PostgreSQL calls a batch) holds 2n buckets, and the executor picks the bucket count in ExecChooseHashTableSize(). Build inserts all inner tuples into the batch; probe then compares each outer tuple against the bucket its hash selects.5 Note the bucket comparison in the probe phase still checks the real key: different keys can share a bucket, so hashing narrows the candidates but equality decides.5 In FerricDB, LogicalPlan::HashJoin follows the opposite side convention: it builds the hash table on its left input and probes with its right input (a course choice; Milestone 7's optimizer places the smaller relation on the left).

Tip: build on the smaller side

The hash table's size is set by the build relation, so build on the smaller input and probe with the larger. The same instinct as "smaller relation outer" in page nested loop — every join algorithm has an asymmetry you can exploit.2

When the build side doesn't fit: partitioned hash

If the build relation exceeds memory we fall back on divide and conquer, at survey level the Grace hash join. Partition phase: using a hash function h1, scatter both relations into B − 1 partitions on disk; because the same h1 is applied to both sides, any two tuples that could ever join land in the same partition number. Build-and-probe phase: for each partition pair (Ri, Si), load the smaller into an in-memory hash table (using a different hash function h2) and probe with the other. If some partition is still too big, partition it again, recursively.2 The cost is one read+write of both inputs per partitioning pass plus one final read of both: with a single partitioning pass, roughly 3·([R]+[S]) — for our example 2 × 1,400 + 1,400 = 4,200 I/Os, tying the optimized merge join.

Partitioned hashing has one enemy: skew. All copies of one key hash to the same partition, so a key that appears in millions of tuples produces a partition that no amount of re-partitioning can shrink — CS186 bluntly calls Grace hash "really sensitive to key skew".2 Production systems respond with hybrid designs; the tabs below contrast the textbook algorithm with what PostgreSQL actually ships.

Partition both relations into B − 1 pieces, recursing on any piece whose build half still exceeds B − 2 pages; then run the in-memory build/probe per pair. Every tuple of both inputs is written to disk once per partitioning pass and read back once — nothing stays resident between phases. Simple to implement, easy to cost, and the design FerricDB's stretch-goal join follows if you outgrow the in-memory HashJoin of Milestone 6.2

PostgreSQL uses the in-memory variant while the inner table stays small relative to work_mem (about a quarter of it); beyond that it switches to a hybrid hash join with 2m batches, where batch 0 is kept in work_mem and only the remaining batches spill to temporary files — tuples of batch 0 are joined immediately with no I/O detour, while later batches must be written out and reloaded, which the documentation notes is costly.5 Skew is attacked directly: a special skew batch holds the inner tuples whose join keys match the outer relation's most common values (from its MCV statistics), so the highest-frequency outer tuples are joined in memory during the first pass instead of flooding one spilled batch.5

External merge sort

Merge join wanted sorted inputs; ORDER BY wants sorted output; sort-based aggregation (next section) wants groups adjacent; B+Tree bulk loading wants keys in order. Sorting is the executor's workhorse — and the in-memory sorts from the standard library assume the data fits in RAM, which is exactly what a database cannot assume: tables are routinely an order of magnitude larger than available memory, so the sort must be organized around disk I/O.6

Run generation, then merging

External merge sort with B buffer pages has two stages.6

  1. Pass 0 — run generation. Read B pages at a time into memory, sort them with any in-memory sort, and write each sorted batch back out as a run. Result: ⌈N/B⌉ sorted runs of (up to) B pages each.6
  2. Merge passes. Dedicate one buffer page to output and use the other B − 1 as input cursors, merging B − 1 runs into one longer run per group. Each pass over the data divides the number of runs by B − 1; repeat until one run remains.6

Every pass reads and writes all N pages (2N I/Os), which gives the two formulas you should be able to reproduce from memory:6

passes = 1 + ⌈ log_(B−1) ⌈N/B⌉ ⌉
I/O    = 2·N · passes

The special case B = 3 is the classic two-way sort: runs shrink by a factor of 2 per pass, giving 1 + ⌈log₂ ⌈N/B⌉⌉ passes — and the general formula shows why memory is so valuable: B appears inside a logarithm's base. Concretely, sorting N = 10,000 pages with B = 100 buffers produces 100 runs and needs 1 + ⌈log₉₉ 100⌉ = 3 passes → 60,000 I/Os; give it just one more buffer page (B = 101, fan-in 100) and the same sort collapses to 2 passes → 40,000 I/Os. One page of memory, twenty thousand I/Os. This is also where the merge-join numbers earlier came from: sorting our 1,000-page R with B = 52 yields ⌈1000/52⌉ = 20 runs, one 51-way merge pass finishes the job, so 2 passes × 2,000 = 4,000 I/Os.6

Course choice: the sort budget is explicit

FerricDB's sort::ExternalSorter (crate course/ferricdb/crates/exec) takes a memory_pages parameter and must never hold more than that many pages of tuples in memory — spilling sorted runs to temp pages and running a k-way merge (k = max(2, memory_pages − 1)), ordering NULL values last under both ASC and DESC (course convention). The Milestone 6 tests in crates/exec/tests/exec.rs pin memory_pages = 4 (a textbook 3-way merge) on purpose — both directly in ms6_external_sorter_spills_runs (checking spilled_runs() > 0 and NULLS LAST) and end-to-end in ms6_external_sort_under_tiny_budget over 2,000 rows — because correctness bugs in run boundaries and merge cursors only show up when spilling actually happens. The budget-then-spill discipline mirrors PostgreSQL, whose sorts run in memory when they fit and otherwise fall back to temporary files on disk.4

Aggregation: sort it or hash it

GROUP BY dept asks the executor to fold every input tuple into one accumulator per distinct dept value. Architecturally this is a post-processing step: optimizers plan the SELECT‑FROM‑WHERE block first and pin operators for GROUP BY, ORDER BY, HAVING, and DISTINCT on top, with grouped aggregation and duplicate elimination appearing as ordinary iterators in the plan tree.1 There are exactly two classic strategies, and they reuse the two machines you just built.

Sort-based aggregation sorts the input on the grouping key. Equal keys are now adjacent, so a single streaming pass keeps one accumulator, emits a result row each time the key changes, and never holds more than one group in memory. The survey's example plan is precisely this shape — a sort on the grouping column feeding a group-by/average operator.1 The output conveniently arrives sorted by group key.

Hash-based aggregation hashes each input tuple's grouping key into a table whose entries hold the running aggregate state; sorting is skipped entirely. This is the standard use of hashing in a database: often "all we want is to group the same value together" without caring about order, and GROUP BY and duplicate removal are the canonical examples.7 If the table of groups outgrows memory, the same divide-and-conquer as Grace hash applies: partition the input into B − 1 partitions on the grouping key (recursively if needed — every occurrence of a value lands in the same partition), then build an in-memory hash table per partition.7 And the same caveat applies: external hashing is very susceptible to data skew, since a heavily repeated grouping value cannot be split across partitions.7

Which one wins? If the number of groups is small, hashing is hard to beat: the running states fit in memory even when the input is enormous, so aggregation costs a single read of the input — no sort passes at all. Sorting earns its keep when its byproduct is useful: if the query also has ORDER BY dept, or a downstream merge join wants the same order, the sorted aggregation output is an interesting order the planner can reuse, while hash operators never produce ordered output.8 FerricDB's Milestone 6 Aggregate executor is hash-based (a course choice — it is the simpler first implementation, and DISTINCT falls out for free by treating the whole row as the group key7); you can add the sort-based variant once your ExternalSorter lands.

When the planner picks each algorithm

Nothing on this page is "the best join". A cost-based planner enumerates candidate plans, estimates the I/O each would perform using statistics — selectivity of predicates, distinct-value counts, the estimated join output size |R|·|S| / max(distinct(R.k), distinct(S.k)) — and keeps the cheapest, plus any plan that is more expensive but produces an interesting order.8 PostgreSQL represents the candidates explicitly: a JoinPath for nested loop, and MergePath and HashPath variants built on it, each carrying its estimated cost through the search.9 You will build exactly this in M08/Milestone 7; for now, internalize the decision inputs:

  • Predicate type. Merge and hash join handle equality predicates only; an arbitrary condition such as R.a < S.b leaves nested loop as the general fallback.4,5
  • Input sizes and memory. A build side that fits in B − 2 pages makes in-memory hash join the cost floor [R]+[S]; a tiny outer relation makes block nested loop nearly as cheap; big-on-big favors partitioned hash or sort-merge.2
  • Indexes. An index on the inner join column enables index nested loop, which wins when the outer input is small or highly selective; a B+Tree on the join column can also feed a merge join with pre-sorted input, deleting a sort node from the plan.2,4
  • Sortedness, present and future. Already-sorted inputs make merge join cheap; an ORDER BY/GROUP BY/later merge join downstream makes sort-merge's ordered output worth paying extra for. Hash-based operators never contribute order.8
  • Time to first row. Nested loop has zero start-up cost and streams immediately, which matters for LIMIT-style queries and interactive clients that optimize for time-to-first-row; hash join must finish its build, and sorts must finish sorting, before anything is emitted.1,3
  • Data distribution. Heavy key skew punishes partitioned hashing; PostgreSQL's skew batch exists precisely to keep the most common values in memory.2,5
