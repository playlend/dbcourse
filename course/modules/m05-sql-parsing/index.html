Everything below the front-end — buffer pool, heap files, and soon B+Trees — deals in bytes and pages. Everything above it — planner, executor, transactions — deals in tables, columns, and predicates. The front-end is the translation layer: it takes SELECT name FROM users WHERE age >= 18; as a string and delivers a data structure that says, precisely and checkably, what the user meant. In FerricDB you will build it by hand, the way production Rust parsers actually are: a hand-written lexer, a recursive descent statement parser, and a Pratt parser for expressions — the exact architecture of sqlparser-rs, the parser underneath much of the Rust database ecosystem.1

The front-end pipeline

PostgreSQL processes every query through five subsystems: the parser builds a parse tree from the SQL text; the analyzer performs semantic analysis and produces a query tree; the rewriter applies rules; the planner turns the query tree into a plan tree; and the executor runs it.3 FerricDB keeps the same shape with smaller words: lexer → parser → binder, then planner and executor in Modules 6–8. The parser knows grammar but no schema; the binder knows the schema but no grammar. Keeping those concerns apart is what makes both testable.

Lexing: characters to tokens

The lexer's job is deliberately dumb: chop the character stream into tokens — keywords, identifiers, literals, operators, punctuation — and attach positions for error messages. All the intelligence lives in three small policies:

  • Keywords are case-insensitive; a keyword is just a promoted identifier. Scan an identifier first ([A-Za-z_][A-Za-z0-9_]*), then check its uppercased form against the keyword table. select, Select, and SELECT are the same token; selection is an identifier.
  • Maximal munch. At >=, emit one GtEq token, not Gt then Eq. Always take the longest operator that matches — which just means checking two-character operators before one-character ones.
  • Literals carry their value. 42 becomes Token::Integer(42), 'O''Brien' becomes a string token with the doubled quote already collapsed — SQL's string escape is '', not \'. Numbers with a decimal point become floats.

One design choice worth pausing on: SQLite drives its pipeline by having the tokenizer call the parser with one token at a time — the docs argue it is faster and easier to make thread-safe than the parser pulling tokens.2 FerricDB (like sqlparser-rs) does the simplest correct thing instead: tokenize the whole input into a Vec<Token> up front, then let the parser walk it with peek()/next(). For statement-sized inputs the difference is irrelevant, and the two-phase version is far easier to test — your ms3_ lexer tests assert on token vectors directly.

Recursive descent: tokens to statements

A recursive descent parser is a grammar transcribed into functions: one function per rule, each consuming the tokens it expects and delegating to other rule-functions for the parts it contains.1 FerricDB's statement grammar fits on a napkin, and the parser reads like the napkin:

fn parse_statement(&mut self) -> Result<Statement> {
    match self.peek() {
        Token::Keyword(Kw::Select) => self.parse_select(),
        Token::Keyword(Kw::Insert) => self.parse_insert(),
        Token::Keyword(Kw::Create) => self.parse_create(),   // TABLE | INDEX
        // … DROP, UPDATE, DELETE, BEGIN, COMMIT, ROLLBACK
        other => Err(self.unexpected(other, "a statement keyword")),
    }
}

// SELECT projection FROM table [WHERE expr] [ORDER BY expr [DESC], …] [LIMIT n]
fn parse_select(&mut self) -> Result<Statement> { /* one clause at a time */ }

Two disciplines keep a recursive descent parser pleasant for its whole life. First, the peek/expect split: peek() looks without consuming and drives decisions; expect(tok) consumes exactly one required token or returns an error naming what it wanted and what it found. If every consumption goes through those two, you can never "eat" a token on a failed path and derail the error message. Second, errors are values: parse functions return Result<_, Error::Parse(String)> and bubble up with ? — the REPL prints one clean line, and the invalid-SQL test corpus asserts errors, never panics.

Pratt parsing: expressions done right

Statements parse cleanly with recursive descent because each one starts with a distinctive keyword. Expressions don't: price * 1.08 >= 100 AND NOT discontinued is a flat stream of operands and infix operators, and the grammar question is who binds tighter. You can encode precedence into recursive descent as a ladder of functions (parse_or → parse_and → parse_cmp → …), but every new precedence level means a new function, and the call depth grows with the number of levels, not the expression. The elegant alternative — used by sqlparser-rs for exactly this job — is the Pratt parser, also known as top-down operator-precedence (TDOP).1

The whole algorithm is one loop and one number. Every operator gets a binding power; the parse function takes the minimum power it is willing to bind:

fn parse_expr(&mut self, min_bp: u8) -> Result<Expr> {
    // 1. prefix position: literal, column, '(' expr ')', or a prefix op
    let mut lhs = match self.next() {
        Token::Minus => Expr::Unary(Neg, parse_expr(PREFIX_BP)?),  // recurse
        Token::Keyword(Kw::Not) => Expr::Unary(Not, parse_expr(NOT_BP)?),
        tok => self.parse_primary(tok)?,
    };
    // 2. infix loop: extend lhs while the next operator binds tightly enough
    while let Some(op) = self.peek_infix_op() {
        let bp = binding_power(op);
        if bp < min_bp { break; }
        self.next();                       // consume the operator
        let rhs = self.parse_expr(bp + 1)?; // +1 ⇒ left-associative
        lhs = Expr::Binary(lhs, op, rhs);
    }
    Ok(lhs)
}

FerricDB's binding-power table, low to high — the same relative order every SQL engine uses:

PowerOperatorsNote
1ORbinds loosest
2AND
3NOTprefix
4= != <> < <= > >= IS [NOT] NULLcomparisons
5+ -additive
6* / %multiplicative
7unary -prefix

Trace 1 + 2 * 3 through the loop and the magic demystifies. The outer call (min_bp = 0) parses 1, sees + (power 5, ≥ 0), and recurses for the right side with min_bp = 6. That inner call parses 2, sees * (power 6, ≥ 6 — allowed), recurses again, gets 3, and returns 2 * 3. The outer call finishes with 1 + (2 * 3). Now trace a OR b AND c: OR is power 1, so the recursion for its right side uses min_bp = 2, which lets AND (power 2) proceed — yielding a OR (b AND c), exactly SQL's rule. Precedence emerges from a comparison between two integers. That is the entire trick.

Designing the AST

The abstract syntax tree is the contract between the front-end and everything downstream, and Rust's enums are nearly a domain-specific language for writing one. FerricDB's (abridged from crates/sql — the workspace stubs have the full set):

pub enum Statement {
    CreateTable { name: String, columns: Vec<ColumnDef> },
    Insert { table: String, columns: Option<Vec<String>>, rows: Vec<Vec<Expr>> },
    Select(Box<Select>),
    Update { table: String, set: Vec<(String, Expr)>, filter: Option<Expr> },
    Begin, Commit, Rollback,           // parsed now, executed in Milestone 8
    // … DropTable, Delete, CreateIndex, Analyze, Explain, Vacuum
}

pub enum Expr {
    Literal(Value),
    Column(Option<String>, String),    // (qualifier, name): users.age or age
    Unary(UnaryOp, Box<Expr>),
    Binary(Box<Expr>, BinaryOp, Box<Expr>),
    IsNull(Box<Expr>, bool),           // IS NULL / IS NOT NULL
    Cast(Box<Expr>, DataType),
    Function(String, Vec<Expr>),       // aggregates arrive in Milestone 6
}

Notice what is not here: no page ids, no column indexes, no types on expressions. The AST is faithful to the text. SELECT nonexistent FROM ghosts parses perfectly — and should, because "is this grammatical?" and "does this name anything?" are different questions with different owners. Postgres draws the same line: its parser explicitly does not touch the catalog; semantic checking belongs to the analyzer.3

Binding: names meet the catalog

The binder walks the AST with the catalog in hand and settles every question the parser deferred. It resolves users to a table (or fails with a good error), resolves age to column 1 of that table with type Integer (or fails — ambiguous if two FROM tables have an age, unknown if none do), types every expression bottom-up (age >= 18: Integer vs Integer ⇒ Boolean ✓; age + name ⇒ type error), and checks statement-shape rules like INSERT arity — three columns declared, three values per row supplied. Out comes a BoundStatement in which every column reference is a (table_index, column_index) pair and every expression knows its type. This mirrors Postgres's analyzer, which turns the parse tree into a query tree with names resolved against the system catalogs.3

The catalog itself is the best kind of dogfooding: FerricDB stores it in the database — two bootstrap heap tables, __tables and __columns, at fixed page ids, describing every table including themselves. Postgres does the same with pg_class and pg_attribute. Milestone 3's guidance walks the chicken-and-egg: the bootstrap schemas must be compile-time constants, because you cannot look up the schema of __columns inside __columns until you already know it.

Two philosophies: plan trees vs bytecode

Every SQL front-end ends at "a checked representation of the query" — but what happens next splits the database world into two schools.

Postgres transforms tree to tree to tree: parse tree → query tree → plan tree, and the executor walks the final tree directly, each node an operator pulling rows from its children.3 The representation stays structural all the way down, which makes it natural to inspect (EXPLAIN prints the tree), transform (the optimizer rewrites trees), and extend (a new operator is a new node type). FerricDB follows this school: your Milestone 4 planner emits a LogicalPlan tree and your executor is a tree of iterators.

SQLite compiles SQL all the way to bytecode and runs it on a virtual machine (the VDBE): sqlite3_prepare_v2() is literally a compiler, and a prepared statement is a container for one bytecode program.2 Its parser is generated by Lemon — SQLite's own YACC-style generator, chosen for a less error-prone input syntax and a reentrant, thread-safe output — rather than written by hand.2 Bytecode buys SQLite compact prepared statements and a tiny, fast interpreter loop — the right trade for an embedded engine that compiles every statement it runs. The cost is opacity: transforming a bytecode program is much harder than transforming a tree, which is one reason optimizer-heavy systems stay structural. cstack's tutorial builds the miniature version of this design: a "compiler" producing a statement struct and a "virtual machine" executing it.4
