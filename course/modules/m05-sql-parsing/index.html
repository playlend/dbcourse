M05 · SQL Front-End: Tokenizing, Parsing, Binding

From a flat string of SQL characters to a checked, typed tree the planner can transform — hand-written lexing, recursive descent, Pratt expression parsing, and semantic binding against a self-hosted system catalog.

Everything you have built so far — fixed-size 8 KB pages, slotted heap files, and the buffer pool — speaks exclusively in byte offsets, page ids, and frame latches. Everything you will build next — relational planners, cost-based optimizers, and Volcano executors — speaks in tables, column ordinals, typed expressions, and predicates. The SQL front-end is the bridge between those two worlds: it turns a raw string like SELECT name, age FROM users WHERE age >= 18; into a checked, typed data structure that downstream layers can execute without ever touching raw SQL text again.

In FerricDB you build the front-end by hand in Rust, following the exact architecture of sqlparser-rs (Apache DataFusion's SQL parser, widely used across the Rust database ecosystem): a hand-written lexer, a recursive-descent statement parser, and a Pratt (top-down operator-precedence) parser for expressions.1 You also pair it with a catalog-backed binder modeled on PostgreSQL's analyzer.3 Writing a parser by hand demystifies every syntax error you have ever seen from a database, and it keeps your grammar small, explicit, and easy to extend across Milestones 3 through 8.

The front-end pipeline

PostgreSQL routes every incoming SQL command through five distinct query-processing subsystems:3

  1. Parser: checks lexical and grammatical syntax and builds a raw parse tree — without consulting any table metadata.
  2. Analyzer (semantic analysis): resolves table and column names against the system catalogs, checks expression types, and produces a query tree.
  3. Rewriter: applies rule-system transformations (such as expanding views).
  4. Planner / Optimizer: turns the query tree into the cheapest physical plan tree using statistics and a cost model.
  5. Executor: walks the plan tree to read and modify pages through the buffer pool.

FerricDB adopts the same modular architecture with leaner names and crate boundaries: Lexer → Parser live in crates/sql (depending only on crates/common), Catalog lives in crates/catalog (backed by your Milestone 1–2 PageStore), and the Binder (PostgreSQL's analyzer) lives in crates/exec/src/binder.rs. Notice the clean separation of responsibilities: the lexer sees only characters, the parser knows grammar but zero schema, and the binder knows the schema (via the catalog) but zero syntax. Because crates/sql never imports crates/catalog, you can fuzz and unit-test every edge of the grammar in milliseconds without opening a single database file.

Lexing: characters to tokens

A lexer (scanner / tokenizer) walks raw UTF-8 text once from left to right and emits a flat sequence of typed tokens — keywords, identifiers, literals, operators, and punctuation — discarding insignificant whitespace and comments. Putting character-level rules in a dedicated pass keeps the parser free of whitespace checks and lets every downstream rule work on discrete symbols.

Six concrete policies govern FerricDB's lexer (documented in course/ferricdb/crates/sql/src/lib.rs and modeled on standard SQL and PostgreSQL5):

  • Keywords are case-insensitive; unquoted identifiers fold to lowercase. When the scanner sees a leading ASCII letter or underscore ([A-Za-z_]), it consumes the full word [A-Za-z0-9_]* and checks its case-folded form against the keyword table. Thus SELECT, select, and SeLeCt all produce Token::Keyword(Keyword::Select), while Selection or Users is not a reserved word and becomes Token::Ident("selection") or Token::Ident("users"). Folding unquoted identifiers to lowercase matches PostgreSQL's lexical rule so CREATE TABLE Users and SELECT * FROM users refer to the exact same table.5 (Double-quoted case-preserving identifiers are deliberately out of scope in this course.)
  • TRUE / FALSE vs. NULL. In FerricDB, TRUE and FALSE (any case) lex directly to Token::BoolLit(true) and Token::BoolLit(false) rather than keyword tokens. NULL, however, remains Token::Keyword(Keyword::Null) because it plays multiple grammatical roles: a literal expression (VALUES (NULL)), a column constraint (NOT NULL), and a postfix predicate (IS NOT NULL).
  • Maximal munch on operators and comments. At >=, emit one Token::GtEq rather than Gt followed by Eq; at <> or !=, emit Token::NotEq; at --, discard everything through the next newline (or end of input) as a SQL line comment rather than emitting two Token::Minus tokens. Always test two-character sequences before single-character operators.
  • Typed literals with SQL escaping. Digit runs become Token::IntegerLit(i64) (parsed immediately; overflow is a Error::Parse, never a panic). A leading - is not folded into the integer token — it lexes as Token::Minus so x-1 parses as subtraction rather than Ident("x") followed by IntegerLit(-1). Digits with an embedded decimal point (digits.digits, e.g., 3.14) become Token::FloatLit(f64). Single-quoted strings preserve case inside the quotes and unescape doubled single quotes ('O''Brien' → Token::StringLit("O'Brien")) per standard SQL5 — never backslash escaping. An unterminated string reaching EOF must return Err(Error::Parse(...)).
  • Errors are values, never panics. A stray ! not followed by =, an integer overflowing i64, an unterminated string literal, or any unrecognized character (#, @) returns Err(Error::Parse) quoting the offending text.
  • No source spans on Token (course choice). Production compilers and parsers attach (line, column) byte spans to every token for caret diagnostics. FerricDB omits spans from Token to keep the enum compact and pattern-matching ergonomic in Milestone 3 (adding spans is a clean optional refinement; the interactive demo below still displays character offsets so you can trace positions visually).

Push vs. pull lexing

There is an instructive architectural fork in how the lexer and parser hand tokens across their boundary. SQLite uses a push design: the hand-written tokenizer runs the outer loop and calls the generated parser with one token at a time, which SQLite's architecture guide notes is both fast and naturally thread-safe without global state.2 FerricDB — like sqlparser-rs1 — uses a two-phase pull design: Lexer::tokenize(input) produces a complete Vec<Token> up front, and Parser walks a slice cursor over that vector via peek() and next(). For statement-sized SQL inputs (typically tens to hundreds of tokens), allocating one Vec takes nanoseconds, and decoupling the two passes lets Milestone 3's ms3_lexer_* tests assert exact token vectors directly.

Recursive descent: tokens to statements

Once the input is a token vector, the parser turns flat tokens into nested tree nodes. Recursive descent is the most direct way to parse structured statements: each grammar production becomes one Rust method that inspects the next token, consumes the expected punctuation and keywords, and recursively calls sub-methods for nested clauses.1 SQL's top-level statements are ideal for recursive descent because every statement announces itself with a distinctive leading keyword (SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, BEGIN, COMMIT, ROLLBACK, and later ANALYZE, EXPLAIN, VACUUM):

fn parse_statement(&mut self) -> Result<ast::Statement> {
    match self.peek() {
        Some(Token::Keyword(Keyword::Select)) => self.parse_select(),
        Some(Token::Keyword(Keyword::Insert)) => self.parse_insert(),
        Some(Token::Keyword(Keyword::Update)) => self.parse_update(),
        Some(Token::Keyword(Keyword::Delete)) => self.parse_delete(),
        Some(Token::Keyword(Keyword::Create)) => self.parse_create(), // TABLE | INDEX
        Some(Token::Keyword(Keyword::Drop))   => self.parse_drop(),
        Some(Token::Keyword(Keyword::Begin))  => { self.next(); Ok(Statement::Begin) }
        Some(Token::Keyword(Keyword::Commit)) => { self.next(); Ok(Statement::Commit) }
        Some(Token::Keyword(Keyword::Rollback)) => { self.next(); Ok(Statement::Rollback) }
        other => Err(Error::Parse(format!("expected statement keyword, found {other:?}"))),
    }
}

Three habits keep a hand-written recursive-descent parser clean as the grammar grows from Milestone 3 through Milestone 8:

  1. The peek / expect discipline. Branch on self.peek() without consuming, and consume required tokens through helper methods like self.expect_keyword(Keyword::From)? or self.expect(Token::LParen)?. When a helper fails, it returns Err(Error::Parse(...)) naming both what was expected and what token was actually sitting at the cursor. Never speculatively pop a token and hope to put it back.
  2. Optional clauses and multi-statement scripts. Notice how cleanly optional clauses fall out of peek(): in parse_select, FROM is optional (so SELECT 1 + 1 parses with from: vec![]), followed by optional WHERE, optional GROUP BY (MS6), optional ORDER BY (defaulting each key to ascending desc = false), and optional LIMIT. At the script level, Parser::parse loops while tokens remain, skipping empty/stray semicolons (; ; → empty Vec) and allowing an optional trailing semicolon.
  3. Left-associative JOIN chains vs. comma-separated FROM. In Milestone 6, FROM a, b keeps two separate entries in Select::from (implicit cross product), whereas FROM a JOIN b ON … JOIN c ON … loops inside parse_table_ref to nest TableRef::Join left-associatively (Join(Join(a, b), c)) as a single entry in Select::from.

Pratt parsing: expressions done right

Statements announce themselves with leading keywords, so recursive descent handles them effortlessly. Expressions do not: in a + 1 > b AND NOT c IS NULL, every infix and postfix operator sits between or after operands, and the tree shape depends entirely on operator precedence and associativity. Encoding eight precedence levels in pure recursive descent requires eight boilerplate wrapper functions (parse_or calling parse_and calling parse_not calling parse_is_null …), making every literal traverse eight stack frames.

The cleaner solution — and the exact technique sqlparser-rs uses for SQL expressions1 — is Pratt parsing (top-down operator precedence, or TDOP). Instead of one function per precedence level, you write one function parameterized by a minimum binding power min_bp: u8:

fn parse_expr(&mut self, min_bp: u8) -> Result<ast::Expr> {
    // 1. Prefix / nud ("null denotation"): literals, columns, parens, prefix ops
    let mut lhs = match self.next() {
        Some(Token::Keyword(Keyword::Not)) => {
            ast::Expr::Unary(UnaryOp::Not, Box::new(self.parse_expr(3)?))
        }
        Some(Token::Minus) => {
            ast::Expr::Unary(UnaryOp::Neg, Box::new(self.parse_expr(8)?))
        }
        Some(Token::LParen) => {
            let inner = self.parse_expr(0)?;
            self.expect(Token::RParen)?;
            inner
        }
        Some(tok) => self.parse_primary(tok)?,
        None => return Err(Error::Parse("unexpected end of input in expression".into())),
    };

    // 2. Postfix & Infix / led ("left denotation") loop
    loop {
        // Postfix IS [NOT] NULL has binding power 4
        if matches!(self.peek(), Some(Token::Keyword(Keyword::Is))) {
            if 4 < min_bp { break; }
            self.next();
            let negated = self.consume_if(Token::Keyword(Keyword::Not));
            self.expect_keyword(Keyword::Null)?;
            lhs = ast::Expr::IsNull(Box::new(lhs), negated);
            continue;
        }
        let Some((op, bp)) = self.peek_infix_op() else { break };
        if bp < min_bp { break; }
        self.next();                              // consume the infix operator
        let rhs = self.parse_expr(bp + 1)?;       // bp + 1 ⇒ left-associative
        lhs = ast::Expr::Binary(Box::new(lhs), op, Box::new(rhs));
    }
    Ok(lhs)
}

Worked traces: precedence and associativity by integer comparison

Three short traces cover every mechanism in the Pratt loop:

  1. Precedence (1 + 2 * 3): The outer call starts with min_bp = 0, reads 1, sees + (BP 6 ≥ 0), consumes +, and recurses for rhs with min_bp = 7. The inner call reads 2, sees * (BP 7 ≥ 7 — allowed!), consumes *, recurses with min_bp = 8, reads 3, and returns Binary(2, Mul, 3). The outer call wraps that into Binary(1, Add, Binary(2, Mul, 3)).
  2. Left-associativity (a - b - c): The outer call (min_bp = 0) reads a, sees the first - (BP 6 ≥ 0), and recurses with min_bp = 7 (bp + 1). The inner call reads b, peeks at the second - (BP 6 < 7), and breaks, returning bare b. The outer call finishes lhs = (a - b), loops again at min_bp = 0, sees the second - (BP 6 ≥ 0), and builds (a - b) - c. Had you passed bp instead of bp + 1, the inner call would have swallowed the second - and built right-associative a - (b - c).
  3. Mixed prefix, postfix, comparison, and logic (a + 1 > b AND NOT c IS NULL): Figure 2 traces how every operator lands at its exact level: + (6) binds tighter than > (5), which binds tighter than AND (2); on the right of AND, prefix NOT recurses with min_bp = 3, so postfix IS NULL (BP 4 ≥ 3) attaches to c inside NOT, giving ((a + 1) > b) AND (NOT (c IS NULL)).

Special primary forms: CAST and COUNT(*)

Two SQL expression forms live inside parse_primary rather than the infix loop. First, CAST(expr AS type) starts with Keyword::Cast, parses a nested expression at min_bp = 0, expects AS plus a SQL type keyword (BOOLEAN, INT/INTEGER, FLOAT/DOUBLE, TEXT/VARCHAR), and builds Expr::Cast. Second, function calls start with an identifier followed by (: fold the function name to lowercase and parse comma-separated argument expressions, with one special SQL rule for COUNT(*) — seeing * immediately inside COUNT( produces Expr::Function("count".into(), vec![]) (matching AggExpr { func: AggFunc::Count, arg: None } in Milestone 6), while rejecting * inside arbitrary expressions like 1 + *.

Designing the AST

The abstract syntax tree in course/ferricdb/crates/sql/src/ast.rs is the frozen syntactic contract between ferricdb-sql and ferricdb-exec. Every statement variant the course will ever need is declared up front in Milestone 3 so you never have to refactor the enum definitions later — you grow the parser into them milestone by milestone:

pub enum Statement {
    CreateTable { name: String, columns: Vec<ColumnDef> },
    DropTable { name: String },
    Insert { table: String, columns: Option<Vec<String>>, rows: Vec<Vec<Expr>> },
    Select(Box<Select>),
    Update { table: String, set: Vec<(String, Expr)>, filter: Option<Expr> },
    Delete { table: String, filter: Option<Expr> },
    Begin, Commit, Rollback,                             // parsed MS3, executed MS8
    CreateIndex { name: String, table: String, column: String }, // MS5
    Analyze { table: Option<String> },                   // MS7
    Explain { analyze: bool, inner: Box<Statement> },    // MS7
    Vacuum,                                              // MS8
}

pub enum Expr {
    Literal(Value),
    Column(Option<String>, String),    // (qualifier, name): users.age or age
    Unary(UnaryOp, Box<Expr>),
    Binary(Box<Expr>, BinaryOp, Box<Expr>),
    IsNull(Box<Expr>, bool),           // false = IS NULL, true = IS NOT NULL
    Cast(Box<Expr>, DataType),
    Function(String, Vec<Expr>),       // lowercase; COUNT(*) = Function("count", vec![])
}

Notice what is deliberately absent from ast::Statement and ast::Expr: no page ids, no table OIDs, no column offsets, and no inferred types on expressions. SELECT ghost FROM nowhere parses cleanly without error — and should, because "is this sentence grammatical?" and "does this table exist right now?" are separate questions with separate owners. PostgreSQL enforces this exact boundary: its parser never touches the system catalogs; semantic validation belongs strictly to the analyzer.3 The one small normalization the parser does apply is purely syntactic: mapping SQL type synonyms (INT → DataType::Integer, DOUBLE → DataType::Float, VARCHAR → DataType::Text) and marking PRIMARY KEY columns as nullable: false inside ColumnDef.

Binding: names meet the self-hosted catalog

The binder (course/ferricdb/crates/exec/src/binder.rs) walks the parsed AST with a &Catalog reference and settles every semantic question the parser deferred, mirroring PostgreSQL's analyzer.3 Its responsibilities break into four clean checks:

  1. Flattening the FROM scope & resolving columns. Each base table in the FROM clause is looked up via catalog.table(name) and assigned a positional table_idx: usize (0, 1, …) in left-to-right order, remembering its optional alias (e.g., users AS u). A qualified reference u.age searches only the table whose alias or name is u; an unqualified reference age searches every table in scope and rejects with Error::Bind if zero tables have it (unknown column) or two or more tables share it (ambiguous column). Every surviving column becomes BoundExpr::Column { table, column, data_type } — from this point onward, neither the planner nor the executor ever does string lookups on column names.
  2. Bottom-up type checking & implicit numeric widening. Every BoundExpr has a deterministic inferred type: comparisons yield DataType::Boolean, arithmetic requires numeric operands, WHERE and JOIN … ON predicates must type-check to Boolean (rejecting WHERE id or SELECT name + 1 with Error::Bind), and INSERT rows must match the target column list in arity, types, and NOT NULL constraints. One practical SQL convenience FerricDB adopts (exercised heavily in Milestone 6): an Integer expression implicitly widens to Float when inserted or updated into a FLOAT column or combined with a FLOAT in arithmetic or comparisons (such as INSERT INTO orders (o_total) VALUES (100) or o_total > 100).
  3. Wildcard expansion & output schemas. SELECT * expands into every column of every FROM table in order; explicit projections carry their alias (or column name / synthesized name) into BoundSelect::schema, which flows into LogicalPlan::Projection::schema and finally into QueryResult::schema.
  4. Separating aggregates & BoundExpr::InputRef (Milestone 6). When Milestone 6 adds GROUP BY and aggregate functions (COUNT, SUM, AVG, MIN, MAX), the binder extracts aggregates into BoundSelect::aggregates: Vec<AggExpr>. Because LogicalPlan::Aggregate replaces the base-table row layout with [group_by_0, …, agg_0, …], post-aggregate projections and ORDER BY expressions reference columns by flat offset using BoundExpr::InputRef { index, data_type }.

The self-hosted catalog bootstrap trick

Where does the catalog itself live? If it were an in-memory HashMap, restarting FerricDB would wipe every table definition even though the heap pages are still sitting safely on disk. Production relational databases store the catalog as tables inside the database itself — PostgreSQL uses pg_class (tables and indexes) and pg_attribute (columns).36 FerricDB follows the exact same dogfooding pattern with internal heap tables (__tables and __columns, plus index and statistics metadata in Milestones 5 and 7) rooted at fixed bootstrap page ids.

Breaking the bootstrap chicken-and-egg

You cannot read __columns to discover the schema of __columns! Every self-hosted database breaks the cycle the same way: the schemas and root page ids of the bootstrap system tables are compile-time constants inside crates/catalog. On an empty file, Catalog::bootstrap allocates and formats those fixed pages; on an existing file, it reads them with the compiled-in bootstrap schemas, reconstructs the in-memory cache of every user table (filtering out internal __* tables from Catalog::tables()), and resumes handing out OIDs above the highest existing OID.

Two philosophies: plan trees vs. bytecode

Every SQL front-end ends with a validated, typed representation of the query. What happens immediately afterward divides relational database engines into two classic architectural schools:

PostgreSQL keeps its intermediate representation as explicit trees from start to finish: parse tree → query tree → plan tree, and its executor walks the final plan tree directly, pulling tuples up through nested operator nodes.3 Keeping the query structural makes algebraic rewrites (predicate pushdown, projection pruning), cost-based join enumeration, human-readable EXPLAIN output, and adding new physical operators straightforward. FerricDB follows this school: Milestone 4 lowers BoundStatement into a LogicalPlan tree and executes it with Volcano iterators, and Milestone 7 optimizes that same tree.

SQLite takes a compiler architecture all the way down: its tokenizer and Lemon-generated parser (SQLite's own LALR(1) generator, written for a cleaner input grammar and reentrant, thread-safe output) feed a code generator that compiles SQL into register-based bytecode executed by the Virtual Database Engine (VDBE).2 Calling sqlite3_prepare_v2() literally compiles a statement into a tiny bytecode program (which you can inspect with SQLite's EXPLAIN). Bytecode produces compact prepared statements and a tight interpreter loop well suited to an embedded engine, at the expense of making complex multi-stage plan rewrites harder than tree-to-tree passes. cstack's tutorial demonstrates the smallest possible version of this compiler-plus-VM split.4
