Module 1 made a promise on SQL's behalf: declare what rows you want and let the engine discover a fast how. Modules 6 and 7 built the hows — sequential scans, B+Tree index scans, nested-loop and hash joins, hash aggregation, and external merge sort. This module builds the chooser. For real-world performance, the query optimizer is the single highest-leverage component in the engine: two semantically identical physical plans for the same SQL query routinely differ in runtime by three to five orders of magnitude. That is why the paper this module builds on — Selinger et al.'s 1979 System R optimizer paper — remains one of the most influential papers in computer science.1

The declarative bargain comes due

A query optimizer translates a bound logical plan into an executable physical plan by answering three distinct questions, ordered from cheapest to hardest:1

  1. Logical equivalence (rewrites): Which algebraically equivalent tree does the least unnecessary work before we even touch statistics? Pushing filters down below joins, pruning unread columns, and folding constant expressions are wins across almost every dataset.
  2. Access-path selection: For each base table, should we scan the entire heap sequentially (SeqScan) or probe an available B+Tree index (IndexScan)? As Module 4 previewed, an index is not automatically faster — random heap fetches can lose badly to a sequential sweep when many rows match.3
  3. Join ordering and physical algorithm selection: For n joined tables, how should the joins be parenthesized and ordered, and should each join use a nested loop, hash join, or sort-merge join? Even restricting to linear join chains leaves n! orderings; allowing arbitrary tree shapes grows super-exponentially.1

Notice the clean architectural split between logical optimization (transforming one relational-algebra expression into an equivalent one without committing to physical operators) and physical optimization (choosing scans, join algorithms, and orderings using a cost model over table statistics). Historical and modern optimizers organize this search in two broad styles, summarized in the Red Book's Chapter 7 commentary:6

  • Bottom-up dynamic programming (System R / PostgreSQL): Apply heuristic logical rewrites first, then assemble physical plans from single-table access paths upward by subset size, pruning suboptimal partial plans at every level.1 PostgreSQL uses this near-exhaustive search up to geqo_threshold (default 12 relations), falling back to a genetic heuristic only when the table count exceeds that limit.4
  • Top-down memoized search (Volcano / Cascades): Represent equivalence classes of sub-expressions in a compact memo structure and expand logical-to-logical and logical-to-physical rules recursively from the root downward, using branch-and-bound cost limits to prune whole branches early — the architecture behind SQL Server, CockroachDB, and Apache Calcite.6

Despite forty-five years of research into top-down frameworks and adaptive execution, the Red Book notes that Selinger's core three-piece blueprint — statistics, a cost model, and dynamic programming over subsets — still anchors production optimizers, and its hardest unsolved problem is unchanged: accurate cardinality estimation.6 FerricDB's Milestone 7 follows the System R / PostgreSQL recipe at teaching scale inside course/ferricdb/crates/exec: rule-based logical rewrites, catalog statistics gathered by ANALYZE, a PostgreSQL-inspired cost model, cost-based access paths, and left-deep join ordering for up to ~6 tables.

Rule-based logical rewrites

Rule-based transformations run before any cost calculation because they dominate unconditionally: shrinking intermediate cardinality or tuple width early cannot make a downstream operator more expensive (ignoring rare corner cases such as volatile user-defined functions). In PostgreSQL's pipeline, the rewriter stage expands views and rules before the planner applies cost-independent simplifications internally.2 In FerricDB, Planner::optimize applies three tree-to-tree rewrites over LogicalPlan to a fixpoint:

  • Constant folding. Evaluate sub-expressions whose inputs are all literals once at plan time instead of repeating the arithmetic per tuple: o.total * (1 + 0.08) becomes o.total * 1.08, and 1 = 0 AND col > 5 folds to false, letting the planner replace an entire subtree with an empty scan.
  • Predicate pushdown. Split conjunctive predicates (P1 AND P2) into separate conjuncts and move each conjunct as close to the base scans as legality permits. A predicate sitting above a join that references columns from only the left input moves onto the left child; one referencing only the right input moves onto the right child; one referencing both sides stays attached to the join (becoming the join's equi-join keys or residual on condition). Correctness invariant: a predicate may cross below an operator if and only if every column it references is produced by that child subtree (and for outer joins — not in FerricDB's core grammar — null-supplying sides require extra care).
  • Projection pruning (and redundant-projection cleanup). In a full optimizer, a top-down walk tracks the exact set of columns needed by the final SELECT list, WHERE, JOIN ON, GROUP BY, and ORDER BY clauses, dropping unused columns as low in the tree as possible so hash tables, sort buffers, and row allocations stay narrow. In FerricDB's LogicalPlan, base scans preserve full table schemas so create_executor can resolve BoundExpr::Column { table, column } across reordered joins without remapping tables; therefore Milestone 7 implements redundant-projection cleanup (collapsing stacked pass-through Projection nodes while leaving the top-level Projection intact) rather than inserting inner column-dropping projections below joins.

Observe the synergy between logical rewrites and physical optimization: once Filter(tier = 'gold') sits directly above SeqScan(customer) (or fused into its filter field), the cost-based access-path phase can immediately spot an index on customer(tier) and price an IndexScan against the SeqScan. Without pushdown, the index would never even be considered.

Statistics and selectivity estimation

Once rule-based rewrites finish, every remaining decision — scan type, join order, join build side — depends on estimating how many rows flow out of each operator. That rests on one number per predicate: its selectivity factor F ∈ [0, 1], the expected fraction of input rows satisfying the predicate. Multiply the table's row count N by F and you get the estimated output cardinality.

To compute F without reading the table at query-planning time, the engine stores compact summaries in its system catalog whenever the DBA (or autovacuum) runs ANALYZE. In System R, the catalog stored four quantities: table row count (NCARD), table page count (TCARD), number of distinct keys per indexed column (ICARD), and high/low key bounds.1 FerricDB mirrors this budget in crates/catalog: TableStats { row_count, page_count, columns } with per-column ColumnStats { min, max, distinct_estimate, null_count }.

Selinger et al. introduced the selectivity formulas that still serve as every database engine's baseline — using catalog statistics when available and falling back to documented defaults when a table has never been analyzed or a literal cannot be interpolated:1

Predicate shape With statistics (Selinger 1979) Fallback (no stats / non-interpolatable) Underlying assumption
col = value 1 / ICARD(col) (1 / distinct_estimate) 1 / 10 (0.10) Uniform distribution across all distinct keys
col1 = col2 (equi-join) 1 / max(ICARD(col1), ICARD(col2)) 1 / 10 (0.10) Containment: every key in the smaller domain matches in the larger
col > value (max − value) / (max − min) 1 / 3 (0.333) Uniform spacing across [min, max]
col < value (value − min) / (max − min) 1 / 3 (0.333) Uniform spacing across [min, max]
col BETWEEN v1 AND v2 (v2 − v1) / (max − min) 1 / 4 (0.25) Linear interpolation over [min, max] (clamped to [0, 1])

P1 OR P2 F(P1) + F(P2) − F(P1) · F(P2) same composition Inclusion–exclusion under independence

Watch the degenerate edge cases when you implement CostModel::selectivity in crates/exec/src/cost.rs: an empty table (row_count == 0), a constant column (min == max, which divides by zero if you interpolate blindly), a literal outside [min, max] (which produces negative fractions or fractions above 1 unless clamped), and NULL comparisons (SQL three-valued logic rejects NULLs in WHERE, so high null_count scales non-null selectivity by (row_count − null_count) / row_count). Always clamp the final result to [0.0, 1.0].

Where Selinger's assumptions break in production

Every optimizer bug war story traces back to one of two violated assumptions:6

  • Data skew breaks uniformity. If 95% of an orders table has status = 'shipped' and 5% splits across nine other statuses, 1 / 10 guesses 10% for both 'shipped' (9.5× too low — tempting the planner into an index scan that destroys performance) and 'disputed' (100× too high). Production PostgreSQL combats single-column skew by storing a Most Common Values (MCV) list with exact frequencies alongside an equi-depth histogram for the remaining values in pg_statistic.3
  • Column correlation breaks independence. Suppose a 100,000-row table has 100 cities and 50 states, and every row with city = 'Austin' also has state = 'TX'. Multiplying F(city = 'Austin') · F(state = 'TX') gives (1/100) · (1/50) = 1/5,000 (20 rows) when the true count is 1,000 rows — a 50× underestimate that compounds exponentially across multi-table joins.6 Modern PostgreSQL mitigates this with CREATE STATISTICS multivariate statistics, while FerricDB explicitly documents both uniformity and independence in crates/exec/src/cost.rs so you recognize their footprint in EXPLAIN ANALYZE.

Cost models and access-path selection

With estimated cardinalities in hand, the optimizer scores candidate physical plans using a cost model. Selinger's original System R formula was intentionally spartan: COST = PAGE FETCHES + W × RSI CALLS — total disk pages fetched plus a weighted proxy for CPU work (tuples passed across the storage interface), with W an adjustable system constant.1

Forty-five years later, PostgreSQL's cost model is the direct descendant of that equation. Every plan node reports two numbers — start-up cost (work before the first output tuple can be returned, such as sorting an input or building a hash table) and total cost (start-up plus run cost to emit all tuples) — measured in dimensionless units normalized so that one sequential page read equals 1.0.35 PostgreSQL builds operator costs from five default constants documented in interdb §3.2:3

PostgreSQL constantDefaultMeaningIn FerricDB crates/exec/src/cost.rs
seq_page_cost1.0One sequential 8 KB disk page read (the unit)SEQ_PAGE_COST = 1.0
random_page_cost4.0One non-sequential 8 KB disk page read (4× penalty)RANDOM_PAGE_COST = 4.0
cpu_tuple_cost0.01CPU work to process one heap tupleCPU_TUPLE_COST = 0.01
cpu_index_tuple_cost0.005CPU work to process one B+Tree index entryomitted (folded into tuple cost)
cpu_operator_cost0.0025CPU work to evaluate one predicate operatoromitted (folded into tuple cost)

FerricDB adopts the first three PostgreSQL defaults verbatim — SEQ_PAGE_COST = 1.0, RANDOM_PAGE_COST = 4.0, and CPU_TUPLE_COST = 0.01 — as a course choice matching PostgreSQL's defaults,3 dropping the two sub-cent CPU terms because page I/O dominates the access-path boundary. (On modern NVMe SSDs, where random reads are nearly as fast as sequential reads, DBAs routinely lower PostgreSQL's random_page_cost from 4.0 toward 1.1–1.5, shifting the crossover in favor of indexes.)

Using PostgreSQL's five default constants, a sequential scan over a table of P pages and N tuples pays a flat cost independent of how many rows survive the WHERE filter:3

seq_cost(P, N) = seq_page_cost × P + (cpu_tuple_cost + cpu_operator_cost) × N
               = 1.0 × P + 0.0125 × N

Now compare a B+Tree index scan of height h with I leaf pages and predicate selectivity s (matching M = s × N rows). Beyond reading the B+Tree path and matching leaf pages, the scan must fetch matching heap tuples from the table. How many heap pages it touches — and whether those reads are random or sequential — depends critically on clustering (what PostgreSQL tracks as index-to-heap physical correlation c ∈ [0.0, 1.0]):3

  • c = 0.0 (completely unclustered): Heap order is unrelated to key order. Every matching row risks a separate random heap page fetch (M reads at random_page_cost = 4.0 each).
  • c = 1.0 (perfectly clustered): Heap rows sit in the exact same physical order as the index keys (for instance, an append-only primary key or a freshly CLUSTERed table). The scan visits only ⌈s × P⌉ distinct heap pages, reading them sequentially at seq_page_cost = 1.0.

Interpolating linearly across c ∈ [0, 1] gives a transparent teaching formula shared by the worked example and the interactive calculator below:

heap_pages(s, c)     = ⌈s·P⌉ + (1 − c) × max(0, s·N − ⌈s·P⌉)
heap_page_cost(c)    = (1 − c) × random_page_cost + c × seq_page_cost
index_cost(s, P, N, c) = random_page_cost × (h + ⌈s·I⌉)
                       + heap_page_cost(c) × heap_pages(s, c)
                       + (cpu_tuple_cost + cpu_index_tuple_cost) × (s·N)

Worked example. Take a table with P = 1,000 pages and rpp = 100 rows/page (N = 100,000 tuples), plus a B+Tree index of height h = 2 with I = 300 leaf pages, answering a range query WHERE id BETWEEN a AND b of selectivity s:

Access path s = 0.001 (100 rows) s = 0.30 (30,000 rows) Crossover selectivity
Seq scan (flat in s) 1.0·1,000 + 0.0125·100,000 = 2,250 2,250 (always reads every page once) —
Index scan, unclustered (c = 0.00) 4·(2+1) + 4·100 + 0.015·100 = 413.5 (5.4× win) 4·(2+90) + 4·30,000 + 0.015·30,000 = 120,818 (54× loss) 0.56%
Index scan, moderate (c = 0.50) 4·(2+1) + 2.5·50.5 + 1.5 = 139.8 (16× win) 4·(2+90) + 2.5·15,150 + 450 = 38,693 (17× loss) 1.74%
Index scan, clustered (c = 1.00) 4·(2+1) + 1.0·1 + 1.5 = 14.5 (155× win) 4·(2+90) + 1.0·300 + 450 = 1,118 (2.0× win) > 25%

That 4× random-to-sequential ratio plus page scatter creates a knife-edge decision boundary: on an unclustered secondary index over a dense 100-rows/page table, matching even 1% of the table can already make a sequential scan cheaper than bouncing around 1,000 random heap pages! When your Milestone 7 planner prices both scans over catalog statistics, it replaces Milestone 5's naive "always use an index if one exists" rule with this exact comparison.

First, drag clustering down to 0.00: at 100 rows/page, the index scan shoots past the sequential scan line at 0.56% selectivity — matching the worked-example table above. Second, drag clustering up to 0.90 and then 1.00: as heap reads coalesce onto fewer pages and blend from random_page_cost = 4.0 down toward seq_page_cost = 1.0, the crossover races past 13% and exits the right edge of the chart entirely. Third, reduce rows/page to 20 (wide tuples): fewer matching rows per selectivity step means fewer random heap hits, pushing the crossover rightward.

Selinger join ordering

Single-table access paths are cheap to choose because there are only a handful of indexes per table. Multi-table joins are the combinatorial cliff. Join is both associative and commutative (for inner joins), so joining n relations can be parenthesized and ordered in two different regimes:

  • Left-deep trees (System R and FerricDB): Every join's right (inner) input is a base table, never the output of another join. For n tables there are n! left-deep permutations (24 for 4 tables, 720 for 6, 3.6 million for 10). System R chose left-deep trees both to shrink the search space and because nested-loop and probe-side streaming can pipeline tuples from one join straight into the next without materializing intermediate right-hand subtrees.1
  • Bushy trees (PostgreSQL): Both inputs of a join may themselves be join trees — for example (C ⋈ O) ⋈ (L ⋈ S). Bushy trees allow two selective sub-joins to shrink independently before their outputs meet, at the cost of a larger search space of (2n − 2)! / (n − 1)! binary trees (120 for 4 tables, 30,240 for 6, 665,280 for 7). PostgreSQL explores bushy plans too while preferring pairs linked by an explicit join predicate, avoiding cross products whenever a connected join graph exists.4

Even within left-deep trees, enumerating all n! permutations blows up rapidly. Selinger's dynamic-programming insight is the principle of optimality over relation subsets: once a given set S of k relations has been joined, its output rows, available columns, and applicable predicates to any remaining table T are completely independent of the order in which S was built.1 Therefore, index the DP memo table by the subset bitmask S, not by the permutation:

  1. Level 1 (singletons): For each base table {T}, find the cheapest access path (SeqScan vs usable IndexScans).
  2. Levels k = 2 … n: For every subset S of size k, try every way of extending a remembered (k − 1)-subset S \ {T} with base table T (best[S \ {T}] ⋈ T), cost the resulting join using the chosen physical algorithm, and discard every candidate except the cheapest.1

For n = 6 tables, naive permutation enumeration inspects 6! = 720 full plans; Selinger's bitmask DP populates only 2⁶ − 1 = 63 subset entries and evaluates at most n · 2ⁿ⁻¹ = 192 join transitions.

One refinement made the 1979 paper immortal: interesting orders. Suppose plan P₁ for subset {C, O} costs 12,000 and delivers rows in arbitrary hash order, while plan P₂ costs 14,000 (using an index scan on O.oid) and delivers rows already sorted by O.oid. A naive DP would prune P₂ immediately — and miss the fact that the next join on O.oid = L.oid could run a cheap sort-merge join or satisfy a final ORDER BY O.oid with zero extra sorting! System R therefore keeps, per subset S, both the outright cheapest plan and the cheapest plan for each "interesting" sort order (columns appearing in later join predicates, GROUP BY, or ORDER BY).1 Milestone 7's starter DP starts with one best plan per subset (since FerricDB builds hash join and nested-loop join in Milestone 6) and leaves interesting orders as a clean extension once you add sort-merge join.

The join-order explorer

Consider a four-table query written with the largest table first in the SQL FROM clause — FROM lineitem L JOIN orders O ON L.oid = O.oid JOIN supplier S ON L.sid = S.sid JOIN customer C ON O.cid = C.cid WHERE C.tier = 'gold' AND S.region = 'EU'. After predicate pushdown shrinks C to 200 rows and S to 400 rows, FerricDB's HashJoin builds its hash table on the left input and streams the right input as probes, making join cost asymmetric: cost(L ⋈ R) = 2 × rows(L) + rows(R) + rows(out) (hashing and storing the left build table costs roughly twice per tuple compared to streaming right probes). Step through the DP levels below and watch 24 left-deep permutations collapse into 15 subset entries, with losers strictly pruned at every level.

Selinger DP over {C, O, L, S} with asymmetric HashJoin cost

Filtered base cardinalities: C (200), O (10,000), L (40,000), S (400). Join selectivities: C–O = 1/5,000, O–L = 1/10,000, L–S = 1/2,000; unconnected pairs are cross products (F = 1). Per-join cost = 2·left + right + out (build left, probe right).

Notice three concrete wins in the trace above. First, at level 2, join direction is no longer a tie: for {C, O}, building the hash table on 200-row C and probing with 10,000-row O gives (C ⋈ O) at cost 10,800, strictly beating (O ⋈ C) at cost 20,600 (which gets pruned immediately). The same happens on every pair: (S ⋈ L) (48,800) beats (L ⋈ S) (88,400), and (O ⋈ L) (100,000) beats (L ⋈ O) (130,000). Second, every cross-product pair (such as {C, L} with 8,000,000 rows) is priced honestly and loses at higher levels without special-case hacks. Third, the optimal four-table plan (((C ⋈ O) ⋈ L) ⋈ S) finishes at cost 57,120 — starting from the sharpest filtered pair (C ⋈ O) (only 400 intermediate rows) even though C appeared last in the SQL FROM clause, and beating the naive SQL order (((L ⋈ O) ⋈ S) ⋈ C) (cost 234,920) by more than 4.1×.

Reading EXPLAIN and EXPLAIN ANALYZE

An optimizer is a black box unless you can inspect what it chose and check whether its guesses matched reality. EXPLAIN prints the chosen plan tree without executing it, annotating every operator with its estimated start-up cost, total cost, output row count, and average row width in bytes — for example, PostgreSQL's Seq Scan on tenk1 (cost=0.00..445.00 rows=10000 width=244).5 EXPLAIN ANALYZE goes one step further: it actually executes the plan, wraps each operator in a row counter and clock, and prints actual execution times, actual row counts, and loop counts alongside the estimates.5

Because EXPLAIN ANALYZE truly executes the statement, running it on an INSERT, UPDATE, or DELETE mutates the database even though the output rows are discarded — always wrap data-modifying EXPLAIN ANALYZE calls inside BEGIN; … ROLLBACK;.5

A worked diagnostic loop. Suppose a 100,000-row customers table has 100 cities and 50 states, with city = 'Austin' perfectly correlated with state = 'TX' (1,000 rows match both), joined to an indexed orders table. Compare EXPLAIN (estimates only) against EXPLAIN ANALYZE (estimates plus ground truth):

-- Query: SELECT c.name, o.total FROM customers c JOIN orders o ON c.cid = o.cid
--        WHERE c.city = 'Austin' AND c.state = 'TX';

-- 1. EXPLAIN (plan-time estimates only; assumes city and state are independent)
NestedLoopJoin  (cost=0.42..168.90 rows=40)
  -> SeqScan on customers c  (cost=0.00..2250.00 rows=20)
       Filter: (city = 'Austin' AND state = 'TX')
  -> IndexScan on orders o using idx_orders_cid  (cost=0.42..8.44 rows=2)
       Index Cond: (o.cid = c.cid)

-- 2. EXPLAIN ANALYZE (actual execution reveals a 50x cardinality error!)
NestedLoopJoin  (cost=0.42..168.90 rows=40) (actual time=0.81..412.60 rows=2000 loops=1)
  -> SeqScan on customers c  (cost=0.00..2250.00 rows=20) (actual time=0.35..14.20 rows=1000 loops=1)
       Filter: (city = 'Austin' AND state = 'TX')
  -> IndexScan on orders o using idx_orders_cid  (cost=0.42..8.44 rows=2) (actual time=0.38..0.39 rows=2 loops=1000)
       Index Cond: (o.cid = c.cid)

Read those numbers from the leaves up — the exact debugging loop every database engineer uses: SeqScan on customers predicted rows=20 (100,000 × (1/100) × (1/50)) because the cost model assumed city and state were independent, whereas actual rows=1000 was 50× higher! Fooled into expecting only 20 outer rows, the planner chose a NestedLoopJoin probing idx_orders_cid — which then executed loops=1000 random B+Tree lookups taking 412 ms, whereas a HashJoin scanning orders sequentially would have finished in a fraction of the time. Whenever estimated rows and actual rows diverge by an order of magnitude, suspect stale ANALYZE statistics, skewed values, or correlated predicates.56
