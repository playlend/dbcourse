Module 1 made a promise on SQL's behalf: say what you want and the system will find a good how. Modules 6 and 7 built the hows — scans, joins, sorts. This module builds the chooser. It is the most consequential component in the system for real-world performance: the difference between a good and bad plan for the same query is routinely several orders of magnitude, which is why the optimizer paper this module leans on — Selinger et al.'s 1979 System R paper — may be the most influential database paper ever written.1

The declarative bargain comes due

An optimizer answers three questions, in increasing order of difficulty: which equivalent form of the query to run (rewrites), which access path to use for each table (seq scan vs index), and which join order and algorithms to use — where the search space is n! permutations for n tables.1 PostgreSQL answers them with a near-exhaustive search when the table count is modest, switching to a genetic (heuristic) optimizer only past a threshold — evidence of how much a thorough search is worth.4 FerricDB's Milestone 7 follows the same recipe at teaching scale: rewrites, then a cost model over statistics, then Selinger-style ordering for up to ~6 tables.

Rule-based rewrites

Some transformations are wins essentially always, no statistics required. These run first, as pure tree-to-tree rewrites on the logical plan:

  • Predicate pushdown. A filter above a join that references only one side moves below the join. Filtering early shrinks every intermediate result that follows — the single most valuable rewrite in existence. (Correctness rule: a predicate may only push below an operator if every column it references survives there.)
  • Projection pruning. Columns nobody upstream uses are dropped at the lowest possible point, narrowing every tuple in flight.
  • Constant folding. price * (1 + 0.08) becomes price * 1.08 once, at plan time, instead of per row. Folding a predicate to constant false can delete a whole subtree.

Postgres's rewriter stage plays a related role (view and rule expansion) before its planner applies these cost-independent transformations internally.2

Statistics and selectivity

Everything cost-based rests on one number per predicate: selectivity, the fraction of rows expected to survive. Selinger's paper introduced the estimation playbook that every engine still follows — using whatever statistics exist, plus honest guesses where they don't:1

PredicateSelectivity F (Selinger 1979)Assumption
col = value1 / ICARD(col) with an index; 1/10 without values evenly distributed over ICARD distinct keys
col1 = col21 / MAX(ICARD(col1), ICARD(col2)) every key of the smaller domain matches in the larger
col > value(high − value) / (high − low); 1/3 if not interpolatablelinear interpolation across the key range

ICARD — the number of distinct keys — plus min and max per column: that is the entire statistics budget of System R, and it is exactly what FerricDB's ANALYZE gathers (row count, per-column min/max, distinct estimate).1 Two honest caveats you must teach your users (i.e., yourself): the uniformity assumption fails on skewed data (Postgres adds histograms and most-common-value lists for this), and multiplying selectivities of ANDed predicates assumes they are independent — correlated predicates make the estimate optimistic, sometimes catastrophically. Milestone 7 documents both assumptions in your cost model's rustdoc.

Cost models

Selinger's cost formula was COST = PAGE FETCHES + W × RSI CALLS — I/O plus a weighted CPU proxy (tuples returned), with W an adjustable knob.1 Forty-five years later, PostgreSQL's model is recognizably the same idea with more terms. Postgres splits every node's cost into start-up (before the first tuple) and run (to completion), and computes a sequential scan's run cost as:3

run_cost = (cpu_tuple_cost + cpu_operator_cost) × N_tuples
         +  seq_page_cost × N_pages
-- defaults: seq_page_cost = 1.0, cpu_tuple_cost = 0.01, cpu_operator_cost = 0.0025

while an index scan pays random_page_cost (default 4.0) per page it touches non-sequentially — index pages and heap pages both.3 The units are deliberately arbitrary: everything is relative to one sequential page read.5 That 4× ratio between random and sequential access is the entire drama of access-path selection: an index scan reads fewer pages, but each one costs more, so there is a selectivity crossover below which the index wins and above which the sequential scan does. FerricDB adopts the three Postgres constants unchanged (a course choice, matching the defaults documented above3) in exec::cost.

A worked example with FerricDB's model — a table of N = 100,000 tuples on P = 1,000 pages, index of height 2 with 300 leaf pages, query WHERE id BETWEEN … (selectivity s):

Formulas = 0.001 (100 rows)s = 0.30 (30,000 rows)
Seq scan1.0·P + 0.0125·N1,000 + 1,250 = 2,250 1,000 + 1,250 = 2,250 (always)
Index scan4.0·(2 + ⌈s·300⌉ + ⌈s·N⌉·clustering) + cpu 4.0·(2 + 1 + 100) + 1.5 ≈ 414 4.0·(2 + 90 + 30,000·f) ≈ tens of thousands

At 0.1% selectivity the index wins by 5×; at 30% it loses by more than 10×, because every matching row risks a separate random heap page fetch. (The clustering factor f — how well heap order matches index order — decides how many; the calculator below exposes it.) A seq scan's cost is flat in s; an index scan's is linear in s with a steep slope. Where the lines cross is the planner's decision boundary.

Try dragging clustering to 1.0 (index order = heap order, like a freshly built primary key): the crossover races rightward — a clustered index stays competitive even at high selectivity, because its heap reads become nearly sequential. This is why real planners track a clustering/correlation statistic per index.

Selinger join ordering

For n tables there are n! join orders, and the cost of different orders differs substantially — that much is obvious. Selinger's insight is what makes searching survivable: once the first k relations are joined, the best way to join the (k+1)-st does not depend on the order the first k were joined in — the applicable predicates, possible join methods, and available orderings are the same for any ordering of the same set.1 So organize the search by subsets, not permutations: find the best plan for every subset of size 1, then use those to build every subset of size 2, then 3 — classic dynamic programming, keeping one best plan per subset and discarding the rest.1

One refinement made the paper immortal: a subset's "best" plan is kept per interesting order — a plan that is more expensive but delivers rows sorted on an ORDER BY, GROUP BY, or equi-join column may enable a cheap merge join (which requires join-column order) or a free sort later, so it survives the pruning alongside the outright cheapest.1 System R also restricted the search to left-deep trees (each join's inner input is a base table), shrinking the space from all tree shapes to orderings — a restriction FerricDB keeps and Postgres does not. Postgres, for its part, prefers joining pairs that actually share a join clause, which prunes most cross products without forbidding them.4

The join-order explorer

Four tables, fixed sizes and join selectivities. Step through the DP levels and watch 24 permutations collapse into 15 subset entries, with losers pruned at every level.

Selinger DP over {C, O, L, S}

customer (1k rows) ⋈ orders (10k) ⋈ lineitem (40k) ⋈ supplier (100). Join selectivities: C–O 1/1000, O–L 1/10000, L–S 1/100; missing pairs are cross products. Cost of a join = outer rows + inner rows + output rows (a teaching model).

Two things to watch. First, the pruning: at level 2 the pair {C, O} keeps C ⋈ O and discards O ⋈ C — same set, one survivor. Second, the payoff: the final best order avoids the cross products entirely and starts from the most selective join, which is not the order the tables appeared in. No greedy rule finds that reliably; the DP proves it optimal for the model.

Reading EXPLAIN

The optimizer's work product is visible: EXPLAIN prints the chosen plan tree with, per node, the estimated start-up cost, total cost, row count, and row width — in those arbitrary cost units — like Seq Scan on tenk1 (cost=0.00..445.00 rows=10000 width=244).5 EXPLAIN ANALYZE goes further: it actually executes the query and reports true row counts and times alongside the estimates — including side effects, so wrap data-modifying statements in a rollback.5 Reading the two side by side is the optimizer debugging loop: a huge gap between estimated and actual rows points at a bad statistic or a correlated predicate. Milestone 7 implements both (ANALYZE with actual counts and timings), and its acceptance test is EXPLAIN-shaped: the plan must flip from seq scan to index scan as the predicate's selectivity drops.
