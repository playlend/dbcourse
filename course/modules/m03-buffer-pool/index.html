Module 2 left you with a DiskManager that reads and writes 8 KB pages and a heap file that calls it for every single tuple access. That design is correct and unusably slow: every get is a disk round trip. The fix is the most classic idea in systems — a cache — but a DBMS cache has obligations an ordinary cache does not. It must never evict a page someone is actively using, it must remember which cached copies are newer than the disk, and — once Milestone 9 arrives — it must refuse to write a page until the write-ahead log has caught up. This module is about that cache: the buffer pool.

Why not just use the OS page cache?

The operating system already caches file blocks in memory. It seems wasteful to build a second cache above it — and yet essentially every serious DBMS does exactly that. The reasons, laid out in Hellerstein, Stonebraker, and Hamilton's Architecture of a Database System, come in two flavors: correctness and performance.3

Correctness: the DBMS must control when writes happen

OS file buffering silently postpones and reorders writes. For most programs that is a pure win; for a database it breaks the ACID promise. Atomic recovery after a crash depends on explicit control over the timing and ordering of disk writes: the write-ahead logging protocol requires that log records reach the log device before the corresponding database pages are written, and that a commit does not return to the user until its commit record is durably on disk.3 An OS that helpfully flushes a dirty data page ahead of the log — or holds back the log flush a commit is waiting on — has quietly destroyed recoverability. So the DBMS buffers pages itself and writes through to disk at moments it chooses. You will feel this directly in Milestone 9, when the buffer pool you build in Milestone 2 grows a hook that refuses to flush a dirty page until the WAL has flushed past that page's LSN.

Performance: the DBMS knows its own future

The OS predicts access patterns from physical file contiguity: it reads ahead when you scan a file front to back. A DBMS can do better, because the query plan tells it the future — a B+Tree range scan will visit leaf pages that are logically adjacent but physically scattered, and the executor knows which pages it will want before it wants them. DBMS-level read-ahead can act on that knowledge; file-system read-ahead cannot see it.3 There is also the blunt cost of double buffering: if the OS caches a block and the DBMS caches it again, the second copy wastes memory and every read pays an extra memory-to-memory copy — a real bottleneck, since a well-tuned DBMS is typically limited by memory bandwidth, not disk.3 Modern OSes provide direct-I/O hooks (O_DIRECT and friends) precisely so databases can opt out of the file cache.3

FerricDB's position

FerricDB uses ordinary buffered file I/O for simplicity — a common choice for educational systems, and in fact PostgreSQL itself relies on the OS cache alongside its own buffer pool.4 What matters for this course is the part every DBMS must own regardless: pinning, dirty tracking, replacement, and (later) write ordering against the log.

Anatomy: frames, page table, metadata

The buffer pool is an array of frames, each a region of memory exactly one page in size. Pages are copied from disk into frames without any format change, manipulated in place, and written back — the fixed frame size sidesteps external fragmentation entirely.3 The distinction between page and frame is subtle but load-bearing: a page is 8 KB of logical data that may live in memory, on disk, or both; a frame is a physical slot that holds some page's bytes right now.1 Frame 3 might hold page 917 this millisecond and page 12 the next.

Because tuples move between frames, nothing above the buffer pool may hold a raw pointer into one. Instead, the pool keeps a page table — a hash map from page id to frame — plus per-frame metadata: a dirty bit recording whether the in-memory copy has changed since it was read, whatever bookkeeping the replacement policy needs, and a pin count.3

Every page request now takes one of two paths. On a hit, the page table points at a frame, the pin count goes up, and the caller gets access at memory speed. On a miss, the pool must find a frame: a free one if any exist, otherwise a victim chosen by the replacement policy. If the victim is dirty it is written back to disk first — losing that write would lose committed data — and then the requested page is read into the frame and the page table is updated on both sides.15

Pin counts and dirty pages

The pin count is the buffer pool's contract with its callers. Before touching a page's bytes, a worker increments the page's pin count; while the count is non-zero the page is pinned: it will not be evicted, written out from under the caller, or have its frame reused.3 When the worker finishes, it unpins. The intent is that only a tiny fraction of the pool is pinned at any moment — a pinned page is a page the replacement policy cannot touch, so leaked pins slowly strangle the cache.3

In Rust, this contract has a beautiful spelling: RAII. FerricDB's fetch_page returns a PageGuard that increments the pin count on creation and decrements it on Drop. A leaked pin becomes a borrow you can grep for, not a heisenbug. The guard also owns dirty tracking: getting mutable access through DerefMut marks the frame dirty, so "I changed this page" can never be forgotten separately from "I touched this page".

The unpin-too-early bug

The classic buffer pool bug is unpinning a page and continuing to use a reference into its frame. In C++ this corrupts data at a distance when the frame is recycled; BusTub's Project 1 dedicates a task to guard classes for exactly this reason.1 In FerricDB the borrow checker makes the bug unrepresentable — the reference's lifetime is tied to the guard — which is a good moment to appreciate what the type system is doing for you.

How PostgreSQL structures its buffer manager

PostgreSQL's buffer manager is the same idea at production scale, split into three layers that are worth knowing by name because you will meet them again in every systems paper.4

  • Buffer table — a hash table mapping a buffer tag (which page of which relation) to a buffer_id. This is the page table.4
  • Buffer descriptors — an array of per-frame metadata. Each descriptor packs three variables into one atomic 32-bit state field: flags (10 bits), a usage_count (4 bits) for the replacement policy, and a refcount (18 bits) — Postgres's pin count.4
  • Buffer pool — a plain array of 8 KB slots, one per descriptor, holding the page bytes themselves.4

Accessing a cached page means: hash the tag, take the mapping lock partition, find the buffer_id, pin the descriptor (refcount and usage_count both increment), release the mapping lock, and use the slot.5

  • HashMap<PageId, FrameId> — the page table, one map instead of a partitioned hash table (single-file databases don't need relation-qualified tags).
  • Frame metadata — pin count, dirty bit, and replacer state kept as ordinary struct fields behind a latch, not packed atomics. Same information, less contention engineering.
  • Box<[Page]> — the frames.

The one-latch-for-the-whole-pool design is deliberately simple; the Milestone 2 stress test only demands correctness under concurrency, not Postgres-grade scalability. The pitfalls section of the milestone discusses where the single latch hurts and what partitioning would buy.

Replacement policies: LRU, CLOCK, LRU-K

When every frame is full and none are free, someone has to go. The replacement policy chooses — and the choice matters enormously, because a policy that evicts a page the workload is about to re-read converts memory-speed hits back into disk-speed misses.

LRU — and why databases don't trust it

Least-Recently-Used evicts the page whose last access is oldest, betting that the recent past predicts the near future. For many workloads it is a fine bet. Databases, however, routinely run its worst case: the sequential flood. A full-table scan touches every page exactly once, in order, and never again — yet under LRU each freshly scanned page is the most recently used, so the scan systematically evicts the genuinely hot pages and fills the pool with pages nobody will re-read.2 Cycle over a table even one page larger than the pool and LRU's hit rate drops to exactly zero — the simulator below will show you.

CLOCK — LRU's cheap, good-enough cousin

Maintaining a strict LRU ordering costs a list update on every access. CLOCK (second-chance) approximates it with one bit per frame: each frame has a reference bit set whenever the frame is used. A conceptual hand sweeps the frames in a circle; to evict, it examines the frame under the hand — if the reference bit is set, it clears the bit and moves on (the second chance); if the bit is clear, that frame is the victim.2 Recently touched frames survive one sweep; untouched frames don't survive two. PostgreSQL ships a refinement called clock sweep: instead of one bit, each descriptor's usage_count is incremented on access (capped at 5); the hand (nextVictimBuffer) decrements the count as it passes and takes the first unpinned descriptor whose count is zero.45 It's CLOCK with five lives instead of two. FerricDB's Milestone 2 asks for classic one-bit CLOCK.

LRU-K — looking at the k-th-last access

LRU's real flaw is that a single recent access says almost nothing about frequency. LRU-K fixes this by remembering each frame's last K access times and ranking frames by backward k-distance: the time since the k-th most recent access. The evicted frame is the one with the largest backward k-distance; a frame with fewer than K recorded accesses has infinite distance and is evicted first, with ties among the infinities broken by evicting the frame whose oldest recorded access is the least recent.2 With K=2, a page touched once by a passing scan has infinite 2-distance and leaves immediately, while a page accessed steadily keeps a short 2-distance and stays — scan resistance falls out of the definition. The cost is bookkeeping: K timestamps per frame and a smarter victim search. Milestone 2 offers LRU-2 as its stretch goal.

Two things to notice. First, on sequential flood, LRU scores zero after the pool warms — every request evicts exactly the page that will be needed four steps from now. CLOCK does no better on a pure cycle, which is honest: CLOCK approximates LRU, worst case included. Second, on scan with hot page, LRU-2 visibly protects the hot page where LRU dumps it: the frequency signal in the second timestamp is doing its job.2

Prefetching and scan protection

Replacement is the defensive half of buffer management; the offensive half is prefetching. Because the executor knows its plan, it can issue reads before it needs the bytes — including logical read-ahead along a B+Tree leaf chain whose pages are physically scattered, something no file system can infer.3 BusTub's Project 1 makes the same point structurally: its buffer pool routes I/O through a disk scheduler that accepts asynchronous requests, so fetches can be batched, reordered, and overlapped.1

And for the sequential flood specifically, PostgreSQL doesn't ask the policy to cope alone: large sequential scans read through a small ring buffer (a few hundred KB) instead of the main pool, so a giant scan recycles its own frames and leaves the hot working set untouched.5 Keep that trick in mind for Milestone 6, when your external sort starts streaming runs through the pool.

Latches vs locks

One piece of vocabulary before the milestone, because the database literature is stubborn about it: a latch is the low-level mutex protecting an in-memory structure (a frame, the page table) for microseconds; a lock is the transactional concept — held for a transaction's lifetime, subject to deadlock detection, about logical database content rather than memory.1 Postgres's buffer manager takes latches (its light-weight locks) on the buffer table partitions and descriptor content while a query holds locks on tables and rows.4 In Rust terms: Mutex and RwLock are latches. Locks arrive in Module 9 and want an entirely different machine. When Milestone 2's pitfalls warn about "latch ordering", they mean your mutexes, not transactions.
