Module 2 left you with a DiskManager that reads and writes 8 KB pages and a HeapFile that calls it for every tuple access. That works and is unusably slow: the CMU storage notes illustrate the latency gap by scaling an L1 cache reference to one second — at that scale, an SSD read takes ~4.4 hours and a spinning-disk read takes ~3.3 weeks.8 The cure is an in-memory cache, but a DBMS cache carries strict contracts an ordinary cache does not: it must never evict a page in active use, it must serialize concurrent readers and writers of the same 8 KB buffer, it must track which cached copies are dirty and when they first became dirty, and — once Milestone 9 arrives — it must refuse to flush a dirty page until the write-ahead log has caught up.39 This module is about that cache: the buffer pool.

Why not just use the OS page cache?

The operating system already caches file blocks in RAM, and mmap can map a database file directly into virtual memory. Building a second cache inside the DBMS looks redundant — yet every serious relational engine builds its own buffer manager anyway. Hellerstein, Stonebraker, and Hamilton organize the reasons into correctness and performance.3

Correctness: the DBMS must control write ordering

OS buffering silently postpones and reorders dirty writes to coalesce I/O. For a transactional database, reordering breaks crash recovery. Write-ahead logging (Module 10) demands two invariants:39

  1. Log before data (the WAL rule): before a dirty page carrying pageLSN = L reaches disk, every log record through L must already be durable. Writing a dirty page ahead of its undo record leaves recovery unable to roll back an uncommitted change after a crash.39
  2. Force log at commit: a transaction cannot report COMMIT until its commit record is durable on disk, even if dirty data pages stay in RAM.39

Memory-mapping files with mmap is worse: the kernel may flush a dirty mapped page at any instant — even mid-update while a worker holds a latch — producing torn or unrecoverable pages.8 Owning the buffer pool lets the DBMS flush dirty pages strictly at moments it chooses, right after enforcing the WAL hook (LogFlusher::flush_until in Milestone 9).

Performance: double buffering, eviction policy, and prefetching

  • Double buffering: caching a block in both the OS page cache and the DBMS buffer pool halves effective RAM and adds an extra kernel-to-user memory copy on every miss — a real bottleneck because tuned OLTP engines are often memory-bandwidth bound.3 Engines such as Oracle, DB2, and InnoDB pass O_DIRECT to bypass the OS cache entirely.3
  • Eviction control: the OS applies a generic LRU approximation across all files and cannot tell a hot B+Tree root from a one-off scan block. A DBMS knows its query plan, so it can deploy scan-resistant policies (LRU-K) or isolate scans in a ring buffer.27
  • Logical prefetching: file-system read-ahead only follows physical contiguity. A DBMS knows logical adjacency — such as B+Tree leaf sibling pointers scattered across the file — and can prefetch ahead of the executor.3
  • Predictable stalls and errors: an mmap page fault blocks the calling thread inside the kernel with no DBMS scheduler visibility, and an I/O error raises SIGBUS instead of returning a clean Result.8
FerricDB's position (and PostgreSQL's nuance)

FerricDB uses ordinary buffered file I/O in DiskManager — a course choice for portability. PostgreSQL likewise leaves the OS page cache active as a second-tier cache beneath shared_buffers, relying on explicit fsync checkpoints and strict WAL-before-data flushing inside its own buffer manager.46 Either way, the DBMS still owns pinning, latching, dirty tracking, eviction, and WAL ordering.

Anatomy: frames, page table, metadata

A buffer pool is a fixed-size array of frames, each sized to hold one page — 8,192 bytes in FerricDB, a course choice matching PostgreSQL's default block size.14 Pages are read into frames in their exact on-disk layout, modified in place, and written back verbatim; fixed frame sizes eliminate external fragmentation.3 Keep the distinction sharp: a page (PageId) is logical 8 KB data living on disk (and maybe in RAM); a frame (FrameId, 0..pool_size) is a physical memory slot holding whichever page resides there right now.1

Because pages move between frames continuously, callers identify pages by PageId never by raw pointer. Alongside the frame array, the pool maintains three structures:13

  • Page table: HashMap<PageId, FrameId> mapping each resident page to its current frame in O(1) expected time.
  • Free list: unused frame slots available before any eviction is needed.
  • Per-frame metadata: resident page_id, pin_count, dirty flag, rec_lsn (first LSN that dirtied the page since it was clean, for ARIES checkpoints9), and replacer state.

Every fetch updates BufferPoolStats (hits / misses) along one of two paths:16 On a hit, the page table locates frame, pin_count increments (marking the frame non-evictable on 0 → 1), the replacer records the access, and the caller reads or mutates RAM directly (write-back caching — edits remain buffered until explicit flush or eviction). On a miss, the pool pops a free frame or asks replacer.evict() for an unpinned victim. If every frame is pinned, the call returns Error::BufferPoolExhausted rather than blocking or evicting a live page.1 A dirty victim must first flush the WAL up to its pageLSN (once wired in Milestone 9) and write its bytes to disk; the pool then swaps the page-table entry, reads the requested page into the frame, clears dirty and rec_lsn, sets pin_count = 1, and returns the guard.

Worked example — pool sizing and the hit-rate payoff

Consider a 400 MB database (50,000 pages) whose hot working set is 4,000 pages (32 MB) serving 90% of requests. An 8,192-frame pool occupies 64 MB of frames plus ~512 KB of metadata (~64 bytes/frame, under 0.8% overhead) and keeps all 4,000 hot pages resident. With ~100 ns DRAM hits and ~100 µs NVMe page reads (a 1,000× ratio, reflecting the storage-hierarchy gap8), average fetch latency drops from 100 µs without a pool to 0.90 × 0.1 µs + 0.10 × 100 µs ≈ 10.1 µs (10× faster). Pushing the hit rate from 90% to 99% drops latency to 1.1 µs (nearly 100× faster): near 99%, every single percentage point of hit rate cuts disk traffic in half.

Pin counts, page latches, and dirty tracking

Pinning and latching solve two distinct concurrency problems, both reflected in FerricDB's crates/buffer API (modeled on BusTub and PostgreSQL's buffer content locks):15

  • Pinning prevents eviction. While pin_count > 0, the frame is marked non-evictable in the replacer so its bytes cannot be recycled for another page.13 Multiple concurrent readers each increment pin_count; the frame becomes evictable again only when the last guard drops and pin_count reaches 0.
  • Page latches serialize byte access. Pinning keeps page 12 in frame 0, but it does not stop Thread A from reading a slotted-page header while Thread B compacts the same 8 KB buffer. Each frame therefore sits inside a reader–writer latch — RwLock<Page> in FerricDB, content_lock in PostgreSQL.5 fetch_page_read(id) returns a ReadPageGuard holding a shared read latch (many concurrent readers, never dirties); fetch_page_write(id) and new_page() return a WritePageGuard holding an exclusive write latch, where DerefMut sets dirty = true so mutation can never go unrecorded.15

RAII guards and deadlock-free latch ordering

Rust's RAII turns pin leaks and C++'s classic "use after unpin" corruption bug into compile-time borrow errors.1 Combining a pool metadata mutex (meta: Mutex<PoolMeta>) with per-frame latches (frames: Vec<RwLock<Page>>), however, creates an ABBA deadlock hazard if threads acquire them in opposite orders: Thread 1 holding meta while waiting on frames[f] deadlocks against Thread 2 holding frames[f] while re-locking meta inside Drop::drop.5

FerricDB prevents this with two strict rules (Figure 2): on fetch, release meta before acquiring the frame latch (the frame is already pinned, so nothing can evict it); on Drop, release the frame latch before re-locking meta. Because Rust drops struct fields only after Drop::drop returns, each guard wraps Option<RwLockReadGuard<'a, Page>> (or WriteGuard) and executes drop(self.guard.take()); as its first statement in Drop::drop.

Dirty-page rec_lsn tracking for WAL checkpoints

Besides the dirty bit, ARIES recovery (Module 10) tracks each dirty frame's rec_lsn — the LSN of the earliest log record that modified the page since it was last clean.9 When a clean frame transitions to dirty, rec_lsn captures the page's LSN; later edits leave rec_lsn intact, and flushing resets both fields. During fuzzy checkpoints, the WAL manager calls BufferPoolManager::dirty_pages() to snapshot all (PageId, rec_lsn) pairs into the Dirty Page Table, bounding how far back crash redo must scan.9

How PostgreSQL structures its buffer manager

PostgreSQL scales this exact design across hundreds of backend processes using three shared layers:4

  • Buffer table: a hash table mapping a buffer tag (tablespace, database, relation, fork, block number) to a buffer_id, partitioned across separate BufMappingLock light-weight locks (shared on lookup, exclusive on insert/evict) so lookups scale across cores.45
  • Buffer descriptors: an array of BufferDesc entries. Since PostgreSQL 9.6, each descriptor packs three hot fields into one atomic 32-bit state word: 10-bit flags (BM_DIRTY, BM_VALID, …), 4-bit usage_count, and 18-bit refcount (pin count), letting backends pin/unpin via atomic compare-and-swap without a spinlock.4 Each descriptor also holds a per-buffer content_lock (shared/exclusive LWLock).5
  • Buffer pool: a contiguous array of 8 KB slots indexed by buffer_id.4

A resident hit hashes the tag, takes its BufMappingLock partition shared, reads buffer_id, atomically bumps refcount and usage_count in state, drops BufMappingLock, and takes content_lock shared or exclusive.56

  • HashMap<PageId, FrameId>: one unpartitioned page table inside PoolMeta; a single-file database needs only a u32 PageId instead of a multi-field tag.
  • frame_meta + Replacer: per-frame page_id, pin_count, dirty, and rec_lsn plus Box<dyn Replacer> behind one Mutex<PoolMeta>, eliminating lock-ordering bugs between page-table updates and victim selection.
  • Vec<RwLock<Page>>: outside meta, giving threads concurrent per-frame shared/exclusive latches via ReadPageGuard and WritePageGuard with zero unsafe.

This design passes ms2_stress_multithreaded cleanly while preserving the exact structural split between metadata latching and page-content latching that PostgreSQL scales out through mapping-lock partitions.

Replacement policies: LRU, CLOCK, LRU-K

Once every frame is occupied, a miss must choose an unpinned victim. Good policies keep the hot working set resident; poor ones convert memory-speed hits back into disk-speed misses.

LRU — vulnerable to sequential floods

Least-Recently-Used (LRU) evicts the unpinned frame with the oldest last access. That works well for skewed OLTP lookups, but databases routinely run LRU's worst case: the sequential flood.2 A full-table scan touches every page once and never again, yet each freshly scanned page is the most recently used, methodically evicting hot B+Tree and catalog pages. Cycling repeatedly over a relation even one page larger than the pool drives LRU's hit rate to 0%.

CLOCK — LRU's cheap one-bit approximation

Strict LRU must mutate a linked list on every hit, causing contention on hot pages. CLOCK (second chance) replaces timestamps with one reference bit per frame and a sweeping hand: any access sets ref = 1; eviction sweeps circularly, skipping pinned frames, clearing ref = 1 → 0 (the second chance), and evicting the first evictable frame already at ref = 0.2 PostgreSQL extends this to clock sweep: each descriptor increments its 4-bit usage_count on access (capped at 5), and nextVictimBuffer decrements counts as it sweeps, evicting the first unpinned buffer at 0 — five lives instead of two.46 FerricDB's Milestone 2 asks for classic one-bit ClockReplacer.

LRU-K — scan resistance via backward k-distance

A single recent access says nothing about frequency. LRU-K records each frame's last K access times and ranks evictable frames by backward k-distance: time since the k-th most recent access.2 Frames with fewer than K accesses have backward k-distance +∞ and are evicted ahead of all frames with ≥ K accesses, breaking ties among infinities FIFO (oldest single access first).2 With K = 2 (LRU-2, Milestone 2's stretch goal), one-off scan pages stay at +∞ and leave immediately while steady hot pages hold a finite 2-distance and remain resident.2

The eviction simulator

Compare CLOCK, LRU, and LRU-2 across three 20-request workloads on a 4-frame pool. Hot pages mixes repeated hits to pages 1–2 with misses to 3–6; sequential flood cycles pages 1–5 through 4 frames; and scan with hot pages warms pages 1 and 2, then interleaves 4-page sequential scan bursts (3..6, 7..10, 11..12) with return visits to hot pages 1 and 2.

Three patterns stand out when you run every combination:

  • Hot pages: LRU and LRU-2 both score 12/20 (60%). CLOCK scores 10/20 (50%): at t = 10 all four reference bits are 1, so the hand clears all four and evicts hot page 1 in frame 0 instead of colder page 3 — the cost of one-bit compression.
  • Sequential flood: all three score 0/20 (0%). Once the 4 frames fill, every request under LRU evicts the page needed one step from now (it was last accessed four steps ago). CLOCK inherits LRU's worst case, and LRU-2 never sees a second access to any page before eviction, falling back to FIFO.
  • Scan with hot pages: here LRU-2 separates cleanly. Both CLOCK and LRU score 4/20 (20%) because every 4-page scan burst (3..6, 7..10) flushes hot pages 1 and 2 out of the pool. Under LRU-2, every scan page has backward 2-distance +∞ while pages 1 and 2 hold finite 2-distances, so the scan recycles frames 2 and 3 among itself and pages 1 and 2 are never evicted — doubling the hit rate to 8/20 (40%).2

Prefetching and scan protection

Because the executor owns the query plan, it can issue logical read-ahead along a B+Tree leaf chain or a batch of heap RecordIds even when those pages are physically scattered on disk — foresight no file system possesses.3 BusTub's Project 1 wires this directly into its disk scheduler, queueing asynchronous I/O requests so fetches overlap with CPU work.1

For sequential floods specifically, PostgreSQL does not leave the replacement policy to cope alone: large bulk operations bypass the main pool through a temporary circular ring buffer:67

  • BAS_BULKREAD (256 KB = 32 buffers): triggered when a sequential scan reads a table larger than one-quarter of shared_buffers. The scan overwrites its own 32 slots cyclically, leaving the hot working set untouched; concurrent scans on the same table can even share the ring.7
  • BAS_BULKWRITE (16 MB) and BAS_VACUUM (256 KB): bulk loads (COPY FROM, CREATE TABLE AS) and VACUUM similarly cycle through dedicated small rings.7

Remember this trick in Milestone 6 when your external merge sort streams large runs through the buffer pool.

Latches vs locks

Database literature draws a sharp line between latches (short-lived mutexes protecting in-memory structures) and locks (transaction-lifetime coordination over logical database objects):15

PropertyLatchLock
ProtectsIn-memory structures (frames, page table, B+Tree nodes)Logical objects (tables, rows, ranges)
DurationOne critical section (ns to µs)One transaction (ms to minutes)
ModesShared (read) / Exclusive (write)Shared, Exclusive, Intent, etc.
DeadlocksAvoided via strict acquisition order in codeDetected & resolved via wait-for graph / abort
Rollback?NoYes — undone on transaction abort
Postgres / FerricDBLWLock, spinlocks / Mutex, RwLockLock manager + MVCC / MS8 TransactionManager

PostgreSQL uses light-weight locks (latches) on BufMappingLock partitions and per-buffer content_locks while transactions hold heavy-weight locks and MVCC snapshots on relations and tuples.5 Milestone 2 is purely about latches; transactional concurrency control arrives in Module 9 / Milestone 8.
