Why start with a data model?

Suppose you skip the theory and build the most obvious database imaginable: one CSV file per entity, plus application code that opens the file, reads it line by line, and parses each record when it wants anything.1 This strawman fails in three distinct ways. Integrity: nothing stops two records from spelling the same artist differently, or someone overwriting a year with a random string.1 Implementation: every application re-implements record lookup, and two threads writing the same file at the same time corrupt it.1 Durability: a crash in the middle of an update leaves the file in a state nobody can reason about.1 Most of this course is about the machinery that fixes those three failures; this module is about the abstraction that makes the machinery buildable at all.

The database systems of the late 1960s — IDS, IMS, CODASYL — were only a partial fix. Queries were procedural code: the developer chose access paths and execution ordering by hand, based on how the data happened to be laid out at the time.1 When the data grew or its physical organization changed, hard-coded query programs became inefficient or outright wrong, and had to be rewritten.1

Ted Codd, at IBM Research, watched people rebuild their database systems every time the physical layer changed and in 1969 proposed the relational model as the way out.1 The model defines three things: structure — relations and their contents, defined independently of physical representation; integrity — constraints the stored data must satisfy; and manipulation — a declarative interface where the programmer specifies the desired result and the system decides how to compute it.1

The payoff is data independence: applications see only relations, so the DBMS is free to lay data out however suits the environment, contents, and workload — and to re-organize later without breaking a single query.1 Fifty years on, that property is still the reason the relational model outlives every challenger, a story we return to at the end of this module.6

Relations, tuples, attributes

A relation is an unordered set of tuples, where each tuple describes one entity as a set of attribute values.1 An attribute has a name and a domain — the set of values it may take.1 A relation with n attributes is an n-ary relation, which is exactly a table with n columns; "relation" and "table" are interchangeable from here on.1

A tuple is one row: a set of attribute values drawn from those domains. Values were classically required to be atomic scalars, though modern systems also permit lists and nested structures; and every attribute can hold the special value NULL, meaning the attribute is undefined for that tuple.1 NULL will earn its own section.

The word unordered is load-bearing. Because a relation imposes no tuple order, the DBMS may store rows in whatever physical arrangement it finds efficient,1 and query results come back in no particular order unless you demand one with ORDER BY.2 When FerricDB's heap files (module M02) scatter tuples across pages in insertion order, they are exploiting exactly this freedom.

One more distinction you need before the algebra: sets versus bags. The mathematical model and the algebra operate on sets, which cannot contain duplicate tuples.5 SQL, by contrast, operates on bags — unordered collections that allow duplicates — because deduplicating every intermediate result would be wasted work; you opt back into set semantics explicitly with DISTINCT.2 Keep this in mind whenever a theory statement and an engine behavior seem to disagree.

Keys and integrity constraints

Within a relation, some attribute sets uniquely identify tuples. Any minimal such set is called a candidate key; you designate one of them as the primary key, the identity by which a single tuple can be named.1 The other candidate keys are typically declared with UNIQUE constraints. In PostgreSQL a table may carry many unique constraints but at most one primary key, and the primary key is exactly a unique constraint plus not-null, enforced through an automatically created B-tree index.9 If you do not define a primary key, some systems quietly make one for you: a DBMS can auto-generate identity values,1 and every ordinary SQLite table is keyed internally by a 64-bit signed integer rowid, with the table's B-tree using that rowid as its key.11

A foreign key declares that an attribute in one relation maps to a tuple of another relation, generally by matching that relation's primary key.1 This is referential integrity: PostgreSQL requires the referenced columns to be a primary key or unique constraint, and lets you choose what happens to referencing rows when the referenced row disappears — NO ACTION (the default, checkable at end of transaction), RESTRICT, CASCADE, SET NULL, or SET DEFAULT.9 In Figure 1, deleting artist 101 (Nirvana) under CASCADE would automatically delete album 9001 (In Utero) with it, while leaving albums 9002 and 9003 untouched.

Keys are the most common instances of a more general idea. An integrity constraint is a user-defined condition that must hold for every instance of the database, with unique-key and referential constraints being the most widely used.1 The rest of the toolbox: NOT NULL forbids missing values (and is more efficient than the equivalent check constraint),9 and a CHECK constraint attaches an arbitrary boolean expression to the table — with the subtlety that it is satisfied when the expression evaluates to true or to NULL.9 That last clause is your first hint that SQL's logic has three truth values, not two.

Pitfall

"Primary key implies NOT NULL" is not portable folklore — it is true in PostgreSQL but not in SQLite, where a historical bug allows NULLs in primary-key columns unless the column is an INTEGER PRIMARY KEY, the table is WITHOUT ROWID or STRICT, or the column is separately declared NOT NULL.11 The NULL section compares the two engines' NULL rules side by side.

For FerricDB we make a deliberately narrow course choice: Milestone 3's catalog supports a single-column primary key and NOT NULL per column, and defers foreign keys and CHECK to the stretch goals — enough to exercise the concepts without drowning the parser. The semantics we implement follow PostgreSQL's, as cited above.

Relational algebra: the executor's vocabulary

Relational algebra is a small set of operators over relations: each operator consumes one or two relations and produces a new relation, so operators compose into arbitrarily deep expressions.1 Where SQL is declarative, the algebra is procedural — an algebra expression states an order of steps, which is precisely why it is the language query plans are written in.5 When you build FerricDB's executor across Milestones 4 and 6, every operator struct you write is one of the symbols below.

Selection (σ) emits the subset of input tuples that satisfy a predicate; predicates combine with conjunction and disjunction.1 The SQL counterpart is the WHERE clause: σyear=1994(albums) is SELECT * FROM albums WHERE year = 1994.1

Projection (π) emits tuples containing only the listed attributes; it can also reorder attributes and compute derived values, as in πalbum_id−9000, title(albums).1 Under the algebra's set semantics, projection also eliminates any duplicates it exposes5 — whereas SQL's bag-based SELECT list keeps them unless you say DISTINCT.2

Cross product (×) pairs every tuple of one relation with every tuple of the other, concatenating their attributes; the schemas need not be compatible.15 On its own it is rarely what you want — |R| · |S| rows — but it is the formal foundation of joins.

Join (⋈) comes in flavors that are all definable from what you already have. The theta join is a cross product followed by a selection: R ⋈θ S = σθ(R × S).5 An equi-join is a theta join whose predicate is pure equality, and the natural join equi-joins on every attribute name the two relations share.1 SQL's INNER JOIN … ON is likewise syntactic sugar for a cross join plus a join condition.4 Outer joins additionally preserve unmatched rows from the left, right, or both inputs, padding the missing side with NULLs4 — survey-level here; you implement join algorithms in M07.

Rename (ρ) renames relations or attributes — the algebra's version of SQL aliasing — and matters mostly for disambiguating self-joins and nested expressions.5

Aggregation (γ) partitions its input by grouping columns and computes aggregate functions such as COUNT, SUM, MIN, MAX per group, optionally filtering groups — it is the algebraic home of both GROUP BY and HAVING.5 An aggregate function takes a bag of tuples in and produces a single scalar out.2

Set operations, at survey level: union (∪) keeps tuples appearing in either input, intersection (∩) keeps tuples appearing in both, and difference (−) keeps tuples of the first input absent from the second; all three require the two inputs to have identical attributes.1 Their SQL surface is UNION/UNION ALL, INTERSECT, and EXCEPT.1

Mapping SQL clauses onto algebra

A SQL query reads top-to-bottom in exactly the wrong order. Its logical processing order — the order that defines what the query means — is: FROM (and joins), then WHERE, then GROUP BY, then HAVING, then the SELECT list, then ORDER BY, then LIMIT.3 A real engine is free to execute in some other order — that freedom is the subject of the optimization section — but the result must match this specification.3

Pitfall

The worst-named clause in computing: SQL's SELECT list is the algebra's projection π. The algebra's selection σ corresponds to WHERE, not to SELECT.5 Interviewers love this one; so do bugs.

Two grouping rules complete the mapping. First, WHERE filters tuples before grouping, while HAVING filters whole groups after aggregation — HAVING behaves like a WHERE for GROUP BY.32 Second, every non-aggregated expression in the SELECT list must appear in GROUP BY, because a group has no single value for any other column.3 Most systems reject violations, but SQLite permits them and picks an arbitrary value from the group, behavior the SQL:2023 standard legitimized with the ANY_VALUE aggregate.2 Note also that the standard-compliant way to filter on an aggregate is to repeat the aggregate expression inside HAVING rather than referencing its output alias.2

ORDER BY and LIMIT sit at the edge of the algebra rather than inside it: relations are unordered, so ORDER BY imposes a presentation order on the final result, and a LIMIT without ORDER BY may legitimately return different rows on every execution.23 FerricDB still implements them as executor operators (Sort, Limit) — a course choice that mirrors how the Volcano-style engines you will study treat them, as plan nodes above the algebraic core.

NULL and three-valued logic

Every attribute may be NULL, meaning that the value is unknown or undefined for that tuple.1 Because NULL is an unknown, comparing anything to it cannot honestly yield true or false: 7 = NULL evaluates to NULL, and so does NULL = NULL — it is not known whether two unknown values are equal.8 That gives SQL's boolean expressions three possible values — true, false, and unknown (NULL) — with the following truth tables:7

The tables encode one intuition: a result is NULL only when the unknown input could change the answer. TRUE OR NULL is TRUE — the expression is true no matter what the unknown turns out to be — and FALSE AND NULL is FALSE for the same reason.7 A WHERE clause then keeps only rows whose predicate evaluates to TRUE; rows that evaluate to NULL are excluded just like FALSE ones.3 So a row with age = NULL and num_dogs = 3 does satisfy WHERE age <= 20 OR num_dogs = 3 — the second disjunct settles the question regardless of the unknown age.3

Tip

To test for NULL, use the predicates built for it: IS NULL and IS NOT NULL.8 When you need equality that treats NULL as an ordinary comparable value, use IS [NOT] DISTINCT FROM: NULL IS DISTINCT FROM NULL is false, not NULL.8 And IS TRUE / IS FALSE / IS UNKNOWN always return true or false, never NULL8 — handy at the top of a predicate tree. FerricDB's expression evaluator in Milestone 4 must implement exactly these rules.

Aggregates add one more wrinkle: every aggregate function ignores NULL inputs, except COUNT(*), which counts rows.3 Concretely: in a 6-row table whose email column contains 2 NULLs, COUNT(*) returns 6 while COUNT(email) returns 4,3 and an AVG over a column with NULLs averages only the non-NULL values.3 (COUNT(*), COUNT(1), and COUNT(login) on a NULL-free column are equivalent ways to count rows.2)

Where things get genuinely inconsistent is duplicate detection. For UNIQUE constraints, NULLs are treated as distinct — two NULLs do not collide — yet for SELECT DISTINCT and UNION, NULLs are treated as indistinct and collapse into one; SQLite's documentation flags this asymmetry as puzzling — yet every engine it surveys behaves this way — and SQLite was deliberately modified to match Oracle, PostgreSQL, and DB2 on it.10

  • Primary key = unique + not-null; at most one per table; NULL never allowed in PK columns.9
  • UNIQUE treats NULLs as distinct by default (many NULL rows allowed), but you can opt into UNIQUE NULLS NOT DISTINCT to allow at most one NULL.9
  • A foreign-key row with a NULL referencing column escapes the constraint check by default; MATCH FULL or NOT NULL tighten this.9
  • CHECK constraints pass on true or NULL — a NULL price satisfies CHECK (price > 0).9
  • NULLs are allowed in PRIMARY KEY columns (historical bug, kept for backward compatibility) unless the column is INTEGER PRIMARY KEY, declared NOT NULL, or the table is WITHOUT ROWID or STRICT.11
  • For UNIQUE constraints, NULL is distinct from every value including other NULLs — many NULLs coexist, matching PostgreSQL's default.1110
  • SELECT DISTINCT and UNION treat NULLs as indistinct — one NULL survives — matching Oracle, PostgreSQL, and DB2.10
  • Ordinary tables are rowid tables: a 64-bit signed integer rowid keys the table's B-tree even if you never declared it.11

FerricDB's course choice: our NULL semantics follow PostgreSQL's defaults — PRIMARY KEY implies NOT NULL, and WHERE keeps a row only when its predicate evaluates to TRUE (dropping both FALSE and NULL), as asserted by the test harness from Milestone 4 onward. FerricDB omits a separate SQL UNIQUE constraint keyword; instead, Milestone 5's B+Tree index orders entries by the composite pair (key, rid) (supporting non-unique secondary indexes and MVCC tuple versions) and rejects NULL keys outright.

Why declarative queries enable optimization

Here is the payoff of everything above. Consider σb_id=102(R ⋈ S) versus R ⋈ (σb_id=102(S)): the first joins everything and then filters; the second filters S first and joins only the survivors. The two expressions always produce the same answer — but if S has a billion tuples and one of them has b_id = 102, the second is dramatically faster.1 If you were writing procedural code against a data-structure API, choosing between these would be your job, forever, for every query, re-done whenever the data changed.1

SQL's contract is that you state what you want and never how to compute it; the DBMS finds the best strategy through query optimization, and this abstraction is what made SQL the de facto standard for querying relational systems.1 The mechanism is algebraic: because many different algebra expressions are equivalent — filter before or after a join, project early or late — one SQL query admits many plans, and the optimizer's job is to search that space for a cheap one.5 Honesty from the field: the first SQL optimizers were slow and ineffective, they improved immensely over five decades, and the optimizer remains the hardest part of a DBMS to build.6 You will build a small one in M08.

Why the relational model keeps winning

You are about to spend months building a relational engine, so it is fair to ask whether the model is worth the investment. In 2005, Stonebraker co-authored a Red Book chapter arguing that the relational model and SQL had prevailed over every alternative data model to date; the 2024 sequel by Stonebraker and Pavlo revisits two more decades and reaches the same verdict — the relational model remains dominant, and SQL keeps absorbing the best ideas from its challengers.6

The case studies rhyme. MapReduce arrived with enormous enthusiasm, but Google itself moved its crawl processing off MR and announced in 2014 that the technology had no future place in its stack; Hadoop's market cratered.6 Key-value stores either matured into relational systems or settled into niches — an RDBMS can easily emulate a KV store, while re-engineering a KV store into a full data model is much harder.6 The NoSQL document databases marketed themselves on two claims — SQL and joins are slow, and ACID transactions are unnecessary (BASE suffices) — yet by the end of the 2010s almost every NoSQL DBMS had added a SQL interface, with MongoDB the last holdout in 2021, and many added strongly consistent transactions as well.6 The slogan itself retreated from "do not use SQL — it is too slow" to "Not only SQL".6

The paper's explanation is the one this module has been building: higher-level declarative languages require less code and provide greater data independence than record-at-a-time interfaces, and the historical burden of writing an optimizer — the price of going declarative — is likely part of why early NoSQL systems skipped SQL in the first place.6 Stonebraker and Pavlo predict the cycle will continue: new waves will declare SQL and the relational model insufficient, propose replacements, and end up donating their good ideas to the SQL standard, without supplanting the model.6 For this course the conclusion is practical: the relational core you are building is the durable center of the field, not a historical curiosity.
