Everything in FerricDB through Milestone 7 assumed one session running one statement at a time. Real database servers juggle dozens or thousands of concurrent clients, and the moment two transactions touch overlapping rows, naive interleaving produces corrupted balances, phantom rows, and broken application invariants. This module introduces the formal vocabulary (schedules, conflict vs view serializability, and the anomaly hierarchy), compares the three major concurrency-control families (two-phase locking, optimistic concurrency control, and multi-version concurrency control), and goes deep on the PostgreSQL-style MVCC architecture you will implement in course/ferricdb/crates/txn for Milestone 8 — where readers never block writers and writers never block readers.1

ACID and the isolation problem

A transaction is a sequence of reads and writes demarcated by BEGIN and COMMIT (or ROLLBACK) that the engine treats as a single logical unit of work. Its correctness contract is ACID:

  • Atomicity: Either every write in the transaction takes effect or none of them do. Milestone 8 enforces logical atomicity via MVCC visibility rules; Module 10 and Milestone 9 add physical crash-safe undo via write-ahead logging (WAL).
  • Consistency: Every committed transaction carries the database from one state that obeys declared integrity constraints (types, keys, application invariants) to another.
  • Isolation: Concurrent transactions must not corrupt each other's view of the database, even when the OS scheduler interleaves their page accesses arbitrarily — the core subject of this module.
  • Durability: Once COMMIT returns success to the client, the transaction's changes survive process crashes and power loss (Module 10 / Milestone 9).

Concurrency control protocols fall into three broad families:1 pessimistic locking (strict two-phase locking, S2PL), optimistic concurrency control (OCC), and multi-version concurrency control (MVCC). FerricDB implements MVCC snapshot isolation — the same foundation as PostgreSQL — and understanding all three families clarifies every tradeoff in that choice.

Schedules and serializability

A schedule is the interleaved timeline of read and write operations executed by a set of concurrent transactions. A serial schedule runs one transaction completely to commit or abort before starting the next; serial schedules are trivially isolated but sacrifice all concurrency. The gold standard for interleaved execution is serializability: a schedule is serializable if its final database state and every value returned to every transaction are identical to some serial ordering of the committed transactions.6

Checking semantic equivalence against every possible serial schedule is intractable because the database does not know what arbitrary arithmetic a client executes between reads and writes. Theory therefore defines two syntactic notions of equivalence:6

  • Conflict-serializability (practical standard): Two operations conflict if they belong to different transactions, access the same data item, and at least one of them is a write — giving three conflict kinds: read–write (RW), write–read (WR), and write–write (WW). Build a directed precedence (conflict) graph whose nodes are committed transactions, drawing an edge Tᵢ → Tⱼ whenever an operation of Tᵢ conflicts with and precedes an operation of Tⱼ. A schedule is conflict-serializable if and only if its precedence graph is acyclic; any topological sort of the acyclic graph is an equivalent serial order.6
  • View-serializability (strictly broader, NP-complete): Notice carefully that a cycle in the precedence graph means the schedule is not conflict-serializable — not necessarily unserializable in the broader semantic sense! Consider a schedule with blind writes (writes without prior reads): T1: R(A), T2: W(A), T1: W(A), T3: W(A). The precedence graph has a cycle T1 → T2 (RW) and T2 → T1 (WW), so it is not conflict-serializable; yet every transaction reads the same initial value of A and T3's blind write determines the final state, making the schedule view-equivalent to the serial order T1, T2, T3.6 Because testing view-serializability is NP-complete, real lock managers enforce conflict-serializability (a strict subset of view-serializability).

The anomaly zoo and isolation levels

Enforcing full serializability carries real runtime overhead (lock blocking or read-set tracking and retries). The SQL standard therefore defines four tiered isolation levels characterized by which concurrency phenomena (anomalies) they forbid. PostgreSQL's documentation defines the four canonical phenomena plus the write-protection anomalies that matter in production:2

  • Dirty write: Transaction T2 overwrites a value written by an uncommitted transaction T1. If T1 later aborts (or commits out of order), rolling back can clobber committed data. Every serious engine forbids dirty writes at every isolation level.
  • Dirty read: Transaction T2 reads data modified by a concurrent uncommitted transaction T1.2 If T1 rolls back, T2 acted on data that never existed.
  • Non-repeatable (fuzzy) read: Transaction T1 reads a row, T2 modifies or deletes that row and commits, and T1 re-reads the same row and observes a different value.2
  • Phantom read: Transaction T1 executes a predicate query (e.g., COUNT(*) WHERE dept = 7), T2 inserts or modifies rows matching that predicate and commits, and T1 re-runs the query and finds a different set of rows.2
  • Lost update: Both T1 and T2 read the same row (say balance = 100), compute a new value locally (+20 and +50), and write back; T2 overwrites T1's committed increment so the final balance is 150 instead of 170.
  • Write skew (serialization anomaly): Two concurrent transactions read an overlapping set of rows, check a multi-row invariant, and update disjoint rows so that each transaction is valid alone yet their combined committed state is impossible under any serial execution.2

Because the 1992 SQL standard defined levels solely in terms of the first three read anomalies (a famous gap analyzed by Berenson et al.), PostgreSQL's actual implementations are strictly stronger than the SQL minimum at two levels:2

Two-phase locking and deadlocks

Before MVCC became universal, databases guaranteed conflict-serializability using a lock manager issuing two lock modes: Shared (S) locks for reads (compatible with other S locks) and Exclusive (X) locks for writes (incompatible with both S and X).7 Acquiring a lock before each access and releasing it right afterward does not guarantee serializability — interleaving can still create cycles in the conflict graph.

The protocol that makes locking sufficient for conflict-serializability is Two-Phase Locking (2PL): every transaction divides its lifetime into two phases:7

  1. Growing phase: The transaction may acquire new locks (or upgrade S → X), but may not release any lock.
  2. Shrinking phase: Once the transaction releases its first lock, it may never acquire another lock.

2PL guarantees that every committed schedule is conflict-serializable (the equivalent serial order follows each transaction's lock point — the instant it held its last newly acquired lock). However, plain 2PL still suffers from cascading aborts: if T1 writes A, finishes acquiring its locks, unlocks A early during its shrinking phase, and T2 reads A before T1 aborts, then T2 read dirty data and must also abort (and if T2 already committed, the schedule is non-recoverable!). Strict 2PL (S2PL) closes both holes by holding all locks — or at minimum all exclusive locks — until the transaction commits or aborts.7

Blocking creates a new hazard: deadlock, a cycle of transactions each waiting for a lock held by the next.7 The classic deadlock requires only a single row: T1 and T2 both take compatible S(A) locks, then both request an upgrade to X(A); each blocks on the other's S(A) forever. Engines handle deadlocks either via detection — maintaining a directed waits-for graph (Tᵢ → Tⱼ when Tᵢ waits on a lock held by Tⱼ), periodically checking for cycles, and aborting a victim — or via timestamp-priority prevention (wait-die: older waits for younger, younger aborts; wound-wait: older preempts/aborts younger, younger waits), which forbids cycles at the cost of extra aborts.7

Optimistic concurrency control (OCC)

Two-phase locking is pessimistic: it assumes conflicts are frequent, so every read and write pays lock-table latching overhead up front and risks blocking or deadlocking even when no other transaction touches the same row. Optimistic Concurrency Control (OCC) — introduced by Kung and Robinson and summarized alongside S2PL and MVCC in interdb Ch. 5 — bets the opposite: assume conflicts are rare, execute without locking, and verify serializability only at commit time.1

Every OCC transaction moves through three distinct phases:

  1. Read phase: Read tuples freely from the shared database without acquiring locks, recording every read item in a private read set. All inserts, updates, and deletes are buffered in a private write workspace (never visible to other transactions during execution).
  2. Validation phase: On COMMIT, enter a brief critical section, assign a commit timestamp, and check whether any concurrently committed transaction wrote an item in this transaction's read set (or, in parallel write phases, overlapped its write set). If an overlap exists, validation fails and the transaction aborts and retries from scratch — discarding its private workspace cleanly without touching shared pages.
  3. Write phase: If validation succeeds, copy the private workspace into the shared database and mark the transaction committed.

OCC shines on read-heavy, low-contention workloads (such as analytical reads over in-memory tables) because readers never contend on shared lock structures and deadlocks are impossible. Under hot-row write contention (think a global counter or a popular inventory SKU), however, OCC degrades harshly: ten concurrent updaters all do full execution work only for nine of them to fail validation at the finish line and retry repeatedly, wasting CPU (livelock risk). MVCC: versions, snapshots, and the ten rules

MVCC resolves the reader-vs-writer conflict by refusing to overwrite rows in place. Every write creates a new physical tuple version while leaving the old version on the heap page for readers whose transactions began earlier.1 Specifically, every tuple carries two transaction-id stamps: xmin (the transaction that created this version) and xmax (the transaction that deleted or superseded it, or 0 while alive). An INSERT writes a tuple with xmin = my_id, xmax = 0; a DELETE stamps xmax = my_id on the existing version without erasing its bytes; an UPDATE is strictly a delete plus insert — stamping xmax = my_id on the old version and inserting a brand-new tuple with xmin = my_id, xmax = 0.3

Tuple header sizing: PostgreSQL (32-bit xid) vs FerricDB (64-bit TxnId)

PostgreSQL packs 32-bit TransactionId fields (4-byte t_xmin and 4-byte t_xmax, alongside command id, t_ctid, and infomask flags) into a compact 23-byte HeapTupleHeaderData.9 Because 32-bit transaction ids wrap around every ~2 billion transactions (2³¹), production PostgreSQL requires aggressive transaction-id freezing during VACUUM to prevent old committed tuples from suddenly looking like the future.4 FerricDB makes an explicit course choice in crates/common: every tuple carries a 16-byte TupleMeta { xmin: u64, xmax: u64 }. Widening TxnId to 64 bits eliminates wraparound machinery completely (even at 1 million transactions per second, a u64 lasts over 584,000 years) while preserving PostgreSQL's exact visibility logic, with xmin == 0 denoting frozen/bootstrap tuples written before Milestone 8 or during catalog initialization.

To decide which tuple versions belong to its consistent point in time, a transaction captures a snapshot atomically with transaction-id assignment under a single lock. In PostgreSQL's xmin:xmax:xip_list notation:3

  • xmin is the oldest transaction id still active at snapshot time — every id strictly below xmin has already settled (committed or aborted).
  • xmax is the first unassigned transaction id at snapshot time — every id ≥ xmax had not even started yet ("the future").
  • active (PostgreSQL's xip_list) lists every other transaction in [xmin, xmax) that was still in flight when the snapshot was taken. In FerricDB's crates/txn, Snapshot { owner, xmin, xmax, active } stores owner explicitly and keeps active: BTreeSet<TxnId> strictly to other in-flight transactions (excluding owner). For any other transaction x, "active in the snapshot" means snap.active.contains(&x) || x >= snap.xmax.3

One timing decision separates Read Committed from Repeatable Read (Snapshot Isolation): under Read Committed, PostgreSQL takes a fresh snapshot before every SQL statement; under Repeatable Read (and FerricDB's Milestone 8), a single snapshot taken at BEGIN serves the entire transaction.3

With xmin, xmax, a Snapshot, and a commit-state oracle (PostgreSQL's pg_xact / clog; FerricDB's TransactionManager::is_committed), tuple visibility becomes a pure, side-effect-free boolean function Snapshot::is_visible(meta, committed). Pause on Rules 5 and 9 — together, they are Snapshot Isolation. Rule 5 blocks post-snapshot inserts from leaking into your scan; Rule 9 freezes pre-snapshot rows in place even after a concurrent transaction deletes them and commits. Notice also how clean the Rust oracle signature in crates/txn/src/lib.rs is: because is_visible receives only committed: &dyn Fn(TxnId) -> bool, it distinguishes "aborted" from "still in progress" without needing a third state in the closure — an uncommitted xmin (other than owner) is invisible either way (R1 and R4 both return false!), and an uncommitted xmax (other than owner) leaves the tuple visible either way (R6b and R8 both return true!). That collapse is why the entire Milestone 8 Snapshot::is_visible function fits in ~35 lines of pure Rust.

Snapshot isolation, write conflicts, and write skew

Snapshots alone protect readers; they do not by themselves prevent two concurrent writers from clobbering the same row (the lost update anomaly). Preventing lost updates under Snapshot Isolation requires a write-conflict rule — and there are two ways engines enforce it:

  • First-updater-wins (PostgreSQL): When transaction T2 attempts to UPDATE or DELETE a tuple version v1 whose xmax is already set by another concurrent transaction T1, PostgreSQL blocks T2 on T1's transaction lock until T1 finishes. Under REPEATABLE READ, if T1 commits, PostgreSQL immediately aborts T2 with ERROR: could not serialize access due to concurrent update (SQLSTATE 40001); if T1 aborts, T2 proceeds.2
  • First-committer-wins (FerricDB Milestone 8): Each transaction records every RecordId it modifies via TransactionManager::record_write. At TransactionManager::commit, inside the same mutex that flips the transaction's state to Committed, the manager checks whether any RecordId in its write set was also written by a transaction that committed after this transaction's snapshot was captured. If so, the second committer is marked Aborted and receives Err(Error::Serialization) — FerricDB's analog of SQLSTATE 40001.
Critical subtlety: never blindly overwrite another writer's xmax

Suppose T1 and T2 both run DELETE FROM acct WHERE id = 1 against the same tuple v1 (xmin=95, xmax=0). T1 stamps v1.xmax = T1. If T2 then blindly overwrites v1.xmax = T2 on the heap page before calling commit(), watch what happens when T1 commits first and T2 aborts under first-committer-wins: v1.xmax now holds T2 (ABORTED)! Rule 6b sees an aborted deleter and treats v1 as still alive — silently resurrecting the row T1 committed deleting! Therefore, before stamping meta.xmax during an UPDATE or DELETE, the executor must check whether meta.xmax is already held by another active or post-snapshot committed transaction and fail with Error::Serialization rather than clobbering it — combining safe eager xmax guarding with commit-time first-committer-wins.

What anomaly coverage does MVCC Snapshot Isolation plus first-committer-wins achieve? Both PostgreSQL's REPEATABLE READ documentation2 and toyDB's MVCC specification5 state the exact boundary with total honesty: dirty writes, dirty reads, lost updates, non-repeatable reads, and phantoms are all eliminated — yet write skew remains possible.

Write skew breaks the tempting assumption that "no lost updates + no phantoms = serializable". Suppose a hospital requires at least one doctor on call, and both Alice and Bob currently have on_call = true. Transaction T1 checks SELECT COUNT(*) FROM doctors WHERE on_call (sees 2) and sets Alice.on_call = false. Concurrently, T2 runs the same count (also sees 2 from its snapshot) and sets Bob.on_call = false. Because T1's write set {Alice} and T2's write set {Bob} are disjoint, neither first-updater-wins nor first-committer-wins detects a conflict: both transactions commit, leaving zero doctors on call — a committed state impossible in any serial ordering!2

Closing write skew requires tracking read sets (or predicate locks) in addition to write sets. PostgreSQL's SERIALIZABLE level implements Serializable Snapshot Isolation (SSI): non-blocking SIREAD predicate locks record read–write anti-dependencies (rw edges) and abort a transaction with SQLSTATE 40001 whenever two consecutive rw edges form a dangerous structure, requiring applications to retry on serialization errors.2 In FerricDB, Milestone 8 honestly documents this exact boundary with the provided test ms8_write_skew_is_documented (which asserts that disjoint-write skew commits under plain SI), and Stretch Milestone S2 adds SSI to flip that test to Err(Error::Serialization).

VACUUM and the bridge to WAL recovery

Because MVCC never mutates tuples in place, every UPDATE leaves a superseded version behind, every DELETE leaves a tombstoned version behind, and every ROLLBACK leaves aborted-insert corpses scattered across heap pages. Without garbage collection, tables and indexes grow forever even when the live row count stays constant.

Reclaiming dead versions safely requires knowing when no running transaction can possibly see them anymore. CMU 15-445 calls this global cutoff the watermark — the lowest read timestamp among all unfinished transactions.8 FerricDB computes the exact same horizon in TransactionManager::oldest_visible_xid() (the minimum xmin across all active snapshots, or the next unassigned TxnId when no transactions are active). When VACUUM runs, it reclaims two classes of dead tuples:

  1. Dead deleted/superseded versions: Any tuple whose xmax != 0 is COMMITTED and strictly below oldest_visible_xid(). Every active and future snapshot sees that deletion under Rule 10, so the old version is permanently unreachable.
  2. Aborted-insert corpses: Any tuple whose xmin is ABORTED. Rule 1 makes it invisible to every transaction immediately, so it is reclaimable regardless of active snapshots.

Physical reclamation happens at two storage layers that you built earlier in the course:

  • Heap pages (HeapPage::compact): For each dead slot, VACUUM marks the slot tombstoned and calls HeapPage::compact() to pack surviving tuple payloads contiguously toward the end of the 8 KB page, growing the middle free-space region back without moving any surviving slot index — so live RecordId { page_id, slot } pointers remain valid!
  • Secondary B+Tree indexes: Remember why Milestone 5 ordered B+Tree entries by composite (key, rid) (matching PostgreSQL's heap-TID tie-breaker)? Because MVCC out-of-place UPDATEs insert a new (key, new_rid) while leaving (key, old_rid) in place for older snapshots. During VACUUM, before freeing a dead tuple's slot, FerricDB removes its exact (key, rid) entry from every index on the table via BPlusTree::delete(key, rid) so stale index pointers never outlive the heap slot they reference.
How Milestone 8's MVCC abort meets Milestone 9's ARIES recovery

In Milestone 8, TransactionManager::abort marks the transaction Aborted and removes it from the active set: Rule 1 instantly hides its inserts and Rule 6b ignores its xmax stamps without touching a single heap page. Why then does Module 10 (Milestone 9) introduce a write-ahead log and ARIES physical undo? Because in-memory transaction-state maps vanish on a crash! In Milestone 9, FerricDB logs every mutation and commit to the WAL, runs ARIES physical undo with compensation log records (CLRs) on aborts and crashes to leave on-disk pages clean independently of MVCC, and calls TransactionManager::restore(report.max_txn_id, report.committed_txns) at startup so every pre-crash committed tuple remains visible after restart.
