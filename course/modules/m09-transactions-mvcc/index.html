Everything so far assumed one user. Real databases juggle many transactions at once, and the moment two of them touch the same row, correctness stops being obvious. This module builds the vocabulary (schedules, serializability, anomalies), tours the classic solution (locking), and then goes deep on the design FerricDB and PostgreSQL actually use: multi-version concurrency control, where readers don't block writers and writers don't block readers.1

ACID and the isolation problem

A transaction is a group of statements that succeeds or fails as one. The classic contract is ACID: Atomicity (all or nothing — Milestone 9's WAL delivers this), Consistency (integrity constraints hold), Isolation (concurrent transactions don't corrupt each other's view — this module), and Durability (committed means committed — WAL again). Concurrency control is the machinery that maintains atomicity and isolation while transactions run concurrently, and there are three broad families: multi-version (MVCC), strict two-phase locking (S2PL), and optimistic (OCC).1 FerricDB implements MVCC; you should understand all three well enough to say why.

Schedules and serializability

A schedule is the interleaved order in which operations of concurrent transactions actually execute. The gold standard is serializability: a schedule is acceptable if its result equals some serial (one-at-a-time) execution of the same transactions. Checking results directly is hopeless, so we use a syntactic sufficient condition: two operations conflict if they belong to different transactions, touch the same object, and at least one writes. A schedule is conflict-serializable if its conflicting pairs can be ordered consistently with some serial order — checked in practice with a precedence graph: a cycle means not serializable.6

The anomaly zoo

Isolation levels are defined by which phenomena they forbid. The PostgreSQL documentation defines the standard four:2

AnomalyDefinition (per the Postgres docs)
Dirty readreading data written by a concurrent uncommitted transaction2
Nonrepeatable (fuzzy) readre-reading data and finding it modified by another transaction that committed since the first read2
Phantom readre-running a query and finding the set of rows matching the condition has changed due to a recently-committed transaction2
Serialization anomalya committed result inconsistent with every one-at-a-time ordering of the transactions (write skew is the canonical example)2

Two more matter in practice: the dirty write (overwriting uncommitted data) which every real system forbids at all levels, and the lost update — two read-modify-write transactions both based on the same original value, one overwriting the other's increment. Keep the zoo straight and isolation levels become simple: each level is just a row in the which-anomalies-can-happen table.

Two-phase locking and deadlocks

The classical route to serializability is locking: shared (S) locks to read, exclusive (X) locks to write, granted by a lock manager that queues conflicting requests.7 The protocol that makes locks sufficient is two-phase locking: every transaction has a growing phase in which it acquires locks and a shrinking phase in which it releases them — once it releases anything, it may never acquire again. 2PL guarantees conflict-serializable schedules, but it still allows cascading aborts: T1 releases a lock early, T2 reads T1's write, T1 aborts, and T2 must abort too. Strict 2PL closes that hole by holding all locks until the transaction completes.7

The price of blocking is the deadlock: two transactions each waiting for a lock the other holds — the textbook case being two holders of S locks on the same row both requesting an upgrade to X.7 The standard cure is detection: maintain a waits-for graph with an edge Ti → Tj whenever Ti waits on a lock Tj holds; a cycle is a deadlock, and the system aborts a victim to break it. The alternative is avoidance by priority (wait-die / wound-wait), which never deadlocks but aborts more.7 FerricDB's core path doesn't need any of this — MVCC reads take no locks — but stretch milestone S1 builds a lock manager for SELECT FOR UPDATE, and the checker below builds the intuition.

MVCC: versions, snapshots, visibility

MVCC's move is to never update in place: each write creates a new version of the row while retaining the old one, and each reader is shown the version appropriate to its transaction — which is how readers and writers stop blocking each other.1 In PostgreSQL — and byte-for-byte in your Milestone 1 tuple header — every tuple version carries two transaction ids: xmin, the transaction that created it, and xmax, the transaction that deleted it (zero/invalid while alive). An UPDATE is a delete plus an insert: the old version gets its xmax stamped, and a new version is written with xmin = the updater.3

A transaction decides what it can see using a snapshot taken at BEGIN. Postgres represents one as xmin:xmax:xip_list — for example 100:104:100,102: transactions below 100 are settled, 104 and above haven't started (or are unfinished), and 100, 102 were in flight when the snapshot was taken.3 "Active in the snapshot" means: in the xip list, or ≥ the snapshot's xmax. One subtlety with big consequences: under Read Committed, Postgres takes a new snapshot for every statement; under Repeatable Read and Serializable, one snapshot at the first statement serves the whole transaction.3 FerricDB implements the latter — one snapshot per transaction.

Visibility is then a pure function is_visible(xmin, xmax, snapshot, clog) → bool, and interdb Ch. 5 pins it down as ten rules organized by the commit status of xmin:4

  • xmin aborted → invisible, always (R1).
  • xmin in progress → invisible (R4) — unless it is my own transaction: then visible if I haven't also deleted it (R2), invisible if I have (R3).
  • xmin committed → visible (R6, R8, R9) with three exceptions: the creator is still active in my snapshot — it committed after I began — (R5, invisible); I deleted it myself (R7, invisible); or the deleter committed and is not active in my snapshot (R10, invisible). A deleter that is another in-progress transaction (R8) or committed-but-active-in-snapshot (R9) leaves it visible.

Read those exceptions twice — they are snapshot isolation. R5 makes commits that happen after your BEGIN invisible; R9 keeps rows alive for you even after their deleter commits, because the delete happened in your future. Your Milestone 8 Snapshot::is_visible implements exactly these rules, and the table-driven test in the workspace walks every one.

Snapshot isolation vs serializable

What does one-snapshot-per-transaction MVCC plus first-committer-wins write-conflict detection buy you? PostgreSQL calls this level Repeatable Read and implements it as what the literature calls Snapshot Isolation;2 toyDB's docs state the coverage with admirable honesty, and FerricDB inherits exactly it: protected from dirty writes, dirty reads, lost updates, fuzzy reads, and phantoms — but write skew remains possible, because serializable snapshot isolation is not implemented.5

Write skew deserves its moment, because it breaks the intuition that "no lost updates + no phantoms = safe". Two doctors are on call; the rule is at least one must remain. Both transactions read the roster (two on call), each removes a different doctor, neither writes what the other wrote — so first-committer-wins sees no conflict, both commit, and the invariant is dead. Each transaction was consistent alone; the pair is inconsistent with any serial order — a serialization anomaly.2 Postgres's Serializable level catches it with SSI: predicate locks that don't block anything but record read/write dependencies, aborting a transaction with SQLSTATE 40001 when a dangerous pattern completes — which is why serializable applications must be written to retry.2 Your Milestone 8 test suite includes ms8_write_skew_is_documented, which asserts the anomaly happens — the most honest test in the course. Stretch milestone S2 flips it.

Vacuum: taking out the dead versions

MVCC's price is garbage: every UPDATE and DELETE leaves a dead version behind, invisible to everyone but still occupying its slot. Cleanup is bounded by the oldest snapshot still running: a version deleted by transaction X can be physically removed only once every active snapshot sees X as committed — otherwise some reader still needs it. CMU's project calls this cutoff the watermark: the lowest read timestamp among transactions that have not yet finished.8 FerricDB's VACUUM computes the same horizon (oldest_visible_xid) and reclaims tombstoned versions older than it; Postgres's vacuum additionally fights transaction-id wraparound, a production concern your u64 txids let you wave at from a distance.4
