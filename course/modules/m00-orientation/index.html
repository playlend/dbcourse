What a DBMS is — and why you should build one

A database management system is the software that keeps structured data correct while many programs read and write it at once, and keeps that data alive across crashes, power failures, and decades of schema changes. Relational DBMSs sit at the core of most of the world's application infrastructure — commerce, billing, medical records, payroll — and serve as the repository of record behind nearly all online transactions.1 They were also among the earliest widely deployed multi-user server systems, which means they pioneered many of the design techniques for scalability and reliability that other server software later copied.1

Here is the odd part: despite that influence, the architecture of these systems is under-documented. Hellerstein, Stonebraker, and Hamilton open their survey by observing that textbook treatments of databases focus on algorithms and theory — the things that are natural to teach and test — while the holistic system design that makes a real DBMS work lives mostly in product manuals and the community's oral tradition.1 The most reliable cure for that gap is the one used by the university courses this curriculum is modeled on: implement the system yourself. CMU's 15-445/645, for example, pairs its lecture sequence with a strictly ordered chain of programming projects — a buffer pool manager, then a database index, then query execution, then concurrency control — each built into the same teaching system (BusTub), so every lecture's ideas land in code within a couple of weeks.7 The lectures themselves lean on case studies of open-source and commercial systems to show how the trade-offs play out in practice.6

This course follows the same recipe with a Rust accent. The concept modules (M00–M12) are the lecture track; the project milestones (MS0–MS10) are the build track. Across them you will implement FerricDB: a disk-oriented, transactional, SQL-speaking database that models PostgreSQL's semantics closely enough that, by Milestone 10, a stock psql client connects to your process and runs queries against your code. Nothing on these pages is hand-waved: every factual claim about how real systems behave carries a superscript citation to a primary source, and every number this course invents is labeled as a course choice.

Anatomy of a relational DBMS

Hellerstein, Stonebraker, and Hamilton describe a typical RDBMS as five main components: a client communications manager that speaks connection protocols; a process manager that assigns each query a thread of computation and applies admission control; a relational query processor that checks authorization, compiles SQL into a query plan, and executes it through a suite of operators; a transactional storage manager bundling access methods, a buffer manager, a lock manager, and a log manager; and a set of shared components and utilities — catalog, memory manager, replication and administration tools — used by everything else.1

FerricDB refines those five components into the twelve boxes of Figure 2, because twelve boxes map one-to-one onto crates you will write. This diagram is the course's master map: milestone pages re-render it with finished components in green so you can watch the system light up as you build. Every box below is clickable — each links to the module that teaches that component, so treat the figure as a second table of contents.

Reading the spine top-down, with the fntdb07 component each box came from:

  • Client & wire protocol server (client communications manager). The client — psql, a driver, an ORM — connects and ships SQL; the DBMS end of the wire remembers connection state, receives commands, and returns data and control messages.1 PostgreSQL listens on TCP port 5432 by default and dedicates a backend process to each connection.4 FerricDB will do the tokio-task equivalent in M11/MS10.
  • SQL front-end (query processor, first half). Lexing and parsing produce a parse tree; in PostgreSQL the parser checks syntax only, and a separate analyzer pass performs semantic analysis against the catalog to produce a typed query tree.5 A rewriter then applies stored rules — this is the machinery views are implemented with.5
  • Catalog (shared components). The system's tables-about-tables: schemas, column types, index definitions, statistics. The query processor consults it during authorization, parsing, and optimization.1
  • Planner / optimizer (query processor, second half). Turns the query tree into the cheapest plan tree it can find; PostgreSQL's planner is purely cost-based rather than rule-driven.5
  • Executor. A suite of operators — selection, projection, join, aggregation, sorting — that implement relational algebra and call down into storage for records.1 PostgreSQL's executor processes tuples one at a time, pulled upward through the plan tree.5
  • Access methods: heap and index (storage manager). The on-disk data structures. A heap file is an unordered collection of pages holding tuples in no particular order;8 a B+Tree index maps key values to record IDs — physical addresses of the form (page, slot).8
  • Buffer pool (storage manager). All persistent data is staged through it: a big array of memory frames, each able to hold one disk page.1 The execution engine never reads a file itself — it asks the buffer pool for a page and receives a pointer to that page in memory, with the pool guaranteeing the page stays put while it is being used.8
  • Disk manager (storage manager). Owns the files and the mapping from page number to file offset; upper layers speak page IDs, and the storage manager translates them to a file and offset.8
  • Transaction manager (storage manager). Enforces the ACID contract; before touching shared data, queries coordinate through concurrency-control machinery — classically a lock manager1, in PostgreSQL and FerricDB primarily MVCC snapshots (M09).
  • WAL / recovery (storage manager). The log manager makes committed work durable and aborted work invisible; a transaction cannot be reported committed until its commit log record has been flushed to the log device.1

Two fntdb07 components have no box of their own. Admission control and dispatch (the process manager) collapse into the wire-protocol server, which is a reasonable simplification for a teaching system with tens of connections rather than tens of thousands.1 And of the shared utilities, FerricDB keeps only the catalog — no replication, no batch loaders. One SELECT, end to end

The architecture diagram becomes much less abstract once you trace a single statement through it. Hellerstein et al. structure their whole survey around exactly this exercise — the "life of a query" at an airport gate, where one button click becomes a single-query transaction1 — and PostgreSQL's internals documentation names the five subsystems every query passes through: parser, analyzer, rewriter, planner, executor.5 Here is the trip for a query you will be able to run against your own code by Milestone 10:

SELECT name, gpa FROM students WHERE gpa > 3.5;
  1. Client. You type the statement into psql. The client encodes it as a protocol message and sends it over the connection it established at startup; the DBMS side of that conversation is responsible for connection state, receiving SQL, and later returning both data and status messages.1
  2. Wire protocol server. The server decodes the message and routes the SQL text to the worker owning this session. In PostgreSQL that worker is a dedicated backend process serving all queries from this one client;4 a high-scale system would first pass through admission control to decide whether to run the query now or defer it.1
  3. Parser. The text becomes a parse tree. Nothing is looked up yet: the PostgreSQL parser validates only the syntax of the input query, so a misspelled table name sails through this stage.5
  4. Binder / analyzer + catalog. Semantic analysis resolves students, name, and gpa against the catalog, checks types, and produces a query tree.5 This is where a missing table finally raises an error. (PostgreSQL would additionally run the rewriter here to expand views and rules.5)
  5. Planner / optimizer. The query tree becomes a plan tree — a dag of concrete operators. The planner weighs alternatives by estimated cost;5 with no index on gpa, the only real option is a sequential scan with the filter applied on top.
  6. Executor. The executor walks the plan tree, pulling tuples upward one at a time5 — the iterator ("Volcano") discipline you will implement in MS4. Its operator suite is exactly the algebra toolbox: scans, selection, projection, joins, aggregation, sorting.1
  7. Heap scan. At the base of the plan, a scan operator requests the table's pages in order. The heap file is unordered, so the scan is a straightforward walk of page 0, page 1, page 2, …8
  8. Buffer pool. Each page request goes to the buffer pool, which either finds the page already cached in a frame or evicts something to make room; either way the scan gets back a pointer to the page in memory, valid until it releases it.8 All persistent data flows through this one choke point.1
  9. Disk manager. On a miss, the page ID is translated to a file and byte offset and one 8 KB read fills the chosen frame.8
  10. The unwind. Now the stack of calls pays off in reverse: the scan decodes tuples from the page and hands matching ones up, operators transform them, and result rows are buffered for the communications manager, which ships them back to the client — for large results the client fetches incrementally, looping through executor and storage again.1 When the statement finishes, transaction state and connection scratch space are cleaned up.1

Pitfall

Learners often assume the parser rejects SELECT * FROM no_such_table. It does not: syntax checking and name resolution are separate passes, and only the analyzer/binder consults the catalog.5 Keeping those passes separate in MS3 will save you from tangling grammar code with catalog lookups.

Worked example — how much does that scan actually read?

Give students 40,000 rows averaging 100 bytes each (tuple header included). FerricDB's pages are 8,192 bytes — our course choice, matching PostgreSQL's usual 8 kB block size.9 Following PostgreSQL's heap page layout, a 24-byte page header sits at the front, and each stored tuple also costs a 4-byte item identifier in the page's line-pointer array.9 So one page holds ⌊(8192 − 24) / (100 + 4)⌋ = 78 rows, and the table needs ⌈40,000 / 78⌉ = 513 pages ≈ 4.2 MB. A cold sequential scan therefore issues 513 page requests, every one a buffer-pool miss; with a 128-frame (1 MiB) pool — another course choice — the scan also forces at least 385 evictions along the way. Why we care so much: the CMU storage notes put the latency gap in human terms — if an L1 cache reference took one second, an SSD read would take about 4.4 hours and a spinning-disk read about 3.3 weeks.8 Those 513 "weeks-long" trips are the cost the buffer pool (M03) and indexes (M04) exist to avoid.

Disk-oriented vs in-memory architectures

Everything above assumed a disk-oriented architecture: the primary home of the database is non-volatile storage, and the DBMS's job is to shuttle pages between disk and memory intelligently.8 That assumption rests on the two ways storage devices differ. Volatile memory (DRAM) loses its contents on power loss but supports fast, byte-addressable random access — a program can jump to any address and read the value there.8 Non-volatile devices survive restarts but are block-addressable: to read one value you must load the whole surrounding page into memory first, and they historically favor sequential access over random access.8

A disk-oriented engine is built around the block interface. Data files are organized into pages; the execution engine asks the buffer pool for a page and operates on it in memory through a pointer the pool hands back.8 The payoff is the design goal stated outright in the CMU notes: the system can manage databases that exceed the amount of memory available, as long as it manages the traffic carefully.8 The price is indirection on every access — page IDs instead of pointers, pins instead of plain references.

An in-memory engine flips the assumption: the primary copy of records and indexes lives in DRAM, so operators follow ordinary pointers with no page translation on the hot path. Because it exploits byte-addressable random access,8 the buffer-pool machinery disappears — but two constraints replace it. Capacity is bounded by RAM, and since DRAM is volatile,8 durability still requires writing a log and periodic checkpoints to non-volatile storage; the disk does not vanish, it just stops being where queries read from.

FerricDB is disk-oriented, for the same reasons the reference courses are: it is the architecture of PostgreSQL and SQLite, and it forces you to build the two most instructive subsystems — the buffer pool and disk-resident B+Trees — rather than letting DRAM make the hard problems disappear. CMU's project sequence makes the same bet, spending its first big project on a buffer pool manager.7

Why not just mmap?

A tempting shortcut is to mmap the database file and let the OS page data in and out — virtual memory as a free buffer pool. The CMU notes advise against it for both correctness and performance: a page fault blocks the faulting thread, the DBMS loses control over when dirty pages reach disk (fatal for recovery ordering, as you will see in M10), and the OS simply knows less about access patterns than the database does.8 FerricDB reads and writes its files explicitly through the disk manager.

Two role models: PostgreSQL and SQLite

This course keeps two real systems on the desk at all times. PostgreSQL is the model we imitate: FerricDB copies its semantics — the parse/analyze/rewrite/plan/execute pipeline,5 heap tables of 8 kB slotted pages,9 MVCC transactions, a write-ahead log, and its wire protocol — because those semantics are exhaustively documented (Suzuki's The Internals of PostgreSQL devotes chapters to each subsystem, from process and memory architecture through buffer manager, concurrency control, vacuum, and WAL3), and because protocol compatibility gives the project a spectacular finish line: real clients talking to your database. SQLite is the contrast that proves these are choices, not laws of nature: the world's most widely deployed SQL engine is not a server at all but a library compiled into the application, storing the whole database in a single file.210

Deployment. A standalone server: the postgres server process (historically the postmaster) allocates a shared memory region, launches background processes, and listens on TCP port 5432 by default.4 Each client connection gets its own backend process, which serves all queries for that one client and can operate on only one database at a time; connections are capped by max_connections, default 100.4 Because there is no built-in connection pooling, busy deployments put middleware such as pgbouncer in front.4 This is the classic process-per-worker model, which the architecture survey notes is also used by DB2 and Oracle.1

Executing a query. Five stages transform the statement: parser (parse tree, syntax only) → analyzer (query tree, names and types resolved) → rewriter (rule and view expansion) → planner (cost-based choice of plan tree) → executor, which visits tables and indexes in the order the plan dictates, pulling tuples one at a time and reading pages through the buffer manager.5 Housekeeping runs in dedicated background processes: checkpointer, background writer, WAL writer, autovacuum launcher.4

What FerricDB copies: the pipeline shape, the storage stack, MVCC + WAL semantics, and the wire protocol — swapping processes for async tasks in one process.

Deployment. A C library inside your application's process — serverless, no sockets, no worker processes.10 The entire database (every table, every index) lives in one file,10 and the API is a pair of calls: sqlite3_prepare_v2() compiles SQL, sqlite3_step() executes it.2

Executing a query. The pipeline compiles rather than interprets: a hand-coded tokenizer feeds a parser generated by SQLite's own Lemon parser generator (unusually, the tokenizer calls the parser), a code generator turns the parse tree into a bytecode program, and the Virtual Database Engine (VDBE) runs that bytecode; a prepared statement object is literally a container for a single bytecode program.2 The query planner inside the code generator still chooses among algorithms, but the executor artifact is instructions, not a tree of iterator nodes.2

Storage. Below the VDBE, each table and each index is a separate B-tree in the same file; a pager module provides caching, atomic commit and rollback, and locking over fixed-size pages — 4,096 bytes by default, configurable from 512 to 65,536 — and an abstract VFS layer isolates all OS-specific file I/O.2

What FerricDB borrows: perspective. Same relational semantics, radically different packaging — proof that "walk a plan tree" (M06) and "compile to bytecode" are both legitimate executor designs, and that a storage engine is a stack of clean layers whichever way you slice the top.

Note what the two systems share: both are disk-oriented row stores with pages, a page cache, B-trees, and write-ahead logging.23 The storage stack you build in MS1–MS5 would be recognizable to an engineer from either project; the fork in the road is everything above and around it.
