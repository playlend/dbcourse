Build a disk-resident B+Tree keyed on a single column, wire it into the catalog, executor, and planner, and prove it correct with an invariant-checking fuzz test.

This is the most intricate data structure in the whole project, and the one CMU warns its students about in bold type3. It is also the most satisfying: when you finish, SELECT * FROM users WHERE id = 42 stops scanning the whole table and lands on the right page in three reads. Budget more time than you did for Milestone 4, keep check_invariants running after every mutation, and the tree will tell you the moment you corrupt it — instead of twenty inserts later.

Learning objectives

  • Design on-disk layouts for B+Tree leaf and internal nodes, one node per 8 KB page, using a sorted cell-pointer array.
  • Implement point search, insert with cascading leaf/internal/root splits, and lazy delete on a paged B+Tree.
  • Explain why a leaf split copies its separator key up while an internal split pushes it up, and what breaks when you mix the two.
  • Implement a range iterator that walks the sibling-linked leaf chain across node boundaries.
  • Integrate an index with the rest of the system: CREATE INDEX in the front-end, index maintenance in the write executors, and a simple access-path rule in the planner.
  • Verify structural invariants (sorted keys, uniform leaf depth, key-range containment) mechanically, under randomized workloads.

Where this fits

The index is a peer of the heap file, not a layer above it: both are access methods that store their pages through the same PageStore trait, which means the buffer pool from Milestone 2 caches index pages and heap pages in the same frames with zero new plumbing. The tree stores no tuples. Its leaves map key values to RecordIds — the (page, slot) addresses from Milestone 1 — and the executor fetches the actual rows from the heap. Above you, the catalog records which indexes exist and where their roots live, and the planner starts making its first real decision: SeqScan or IndexScan.

Specification

The tree (crates/index)

You implement package ferricdb-index in course/ferricdb/crates/index. The public surface, quoted verbatim from course/ferricdb/docs/api-spec.md (note that open and root_page are already implemented in the starter stub):

// crates/index/src/lib.rs — public surface to implement

/// Disk-resident B+Tree mapping a single-column key to RecordIds, ordered by
/// composite `(key, rid)` (PostgreSQL heap-TID tie-breaker design: supports
/// non-unique secondary indexes AND Milestone 8 MVCC out-of-place updates).
/// One node = one page. Rejects Value::Null, Float(NaN), and mismatched types.
pub struct BPlusTree { /* Arc<dyn PageStore>, root PageId, key type */ }
impl BPlusTree {
    pub fn create(store: std::sync::Arc<dyn PageStore>, key_type: DataType) -> Result<Self>;
    pub fn open(store: std::sync::Arc<dyn PageStore>, root: PageId, key_type: DataType) -> Self;
    pub fn root_page(&self) -> PageId;
    pub fn insert(&mut self, key: &Value, rid: RecordId) -> Result<()>;   // errors only on duplicate (key, rid)
    pub fn get(&self, key: &Value) -> Result<Vec<RecordId>>;              // all matching rids, sorted
    pub fn delete(&mut self, key: &Value, rid: RecordId) -> Result<bool>; // removes exact (key, rid)
    pub fn range(
        &self,
        lower: std::ops::Bound<Value>,
        upper: std::ops::Bound<Value>,
    ) -> Result<RangeIter>;   // Iterator<Item = Result<(Value, RecordId)>>, leaf-chain walk
    /// Test hook: verify sortedness, balance, leaf-chain, and key-range invariants.
    pub fn check_invariants(&self) -> Result<()>;
}

Semantic notes:

  • Two node kinds. Internal nodes hold K separator entries and K+1 child page pointers and exist only to route searches; leaf nodes hold (key, RecordId) entries. All entries live at the leaf level — that separation is what makes this a B+Tree rather than a B-Tree.12
  • Balance. Every leaf sits at the same depth, and the tree gets taller only when the root itself splits.1 Your check_invariants must verify both, along with the leaf sibling chain and key-range containment.
  • Composite (key, rid) ordering (PostgreSQL style). Unlike BusTub's unique-key-only B+Tree,3 FerricDB orders every entry by the composite pair (key, rid) — the same heap-TID tie-breaker PostgreSQL uses. insert allows multiple distinct RecordIds under the same key (needed both for non-unique secondary indexes like CREATE INDEX idx_items_grp ON items (grp) and for Milestone 8 MVCC out-of-place UPDATEs, where two live versions of one row temporarily share the same indexed key) and rejects only an exact duplicate (key, rid) pair with Err(Error::Execution). get(&key) returns all matching RecordIds in ascending order (Vec<RecordId>), and delete(&key, rid) removes only the exact (key, rid) entry so Milestone 8's VACUUM can prune a dead tuple version without touching a newer version that shares the same key.
  • Key validation & strict total order. Keys are Values of one DataType, fixed at create/open. Reject Value::Null, Value::Float(NaN), and mismatched DataTypes with Err(Error::Execution) rather than panicking. Once Null and NaN are excluded, Value::sql_cmp is a strict total order on keys, and (key, rid) is a strict total order on entries (RecordId implements Ord).
  • Lazy delete is acceptable as a first version: remove the leaf entry and leave underfull nodes alone. CMU requires merge/redistribution3; we defer that to the stretch step, honestly trading disk space for a much smaller state space while you stabilize splits.
  • range takes standard std::ops::Bound pairs, so it must handle Included, Excluded, and Unbounded on each side, walking the leaf sibling chain in ascending (key, rid) order rather than re-descending from the root per key.3

Node layout on the page

How you arrange bytes inside a node is your design decision, but you should steal the shape SQLite uses: after the page header comes a cell pointer array of 2-byte offsets kept in (key, rid) order, while the cells themselves are packed from the end of the page toward the middle; the space between the two is free.2 Inserting into a sorted position then shifts only 2-byte pointers, never whole cells. SQLite's interior pages additionally keep the right-most child pointer in the page header rather than in a cell, so K cells plus one header field give the K+1 children.2 Because duplicate keys can span multiple leaves, store the full composite (key, rid) separator in internal cells too — that keeps every routing comparison strictly unambiguous. The first 16 bytes of every FerricDB page are already reserved by Milestone 1 (pageLSN, page_type, reserved) — stamp them with PAGE_TYPE_BTREE_LEAF (2) and PAGE_TYPE_BTREE_INTERNAL (3) via Page::set_page_type.

A worked fanout example with course numbers, so you can sanity-check your own layout. Take an INTEGER key: an internal cell is an 8-byte key plus a 6-byte RecordId tie-breaker plus a 4-byte child PageId, plus its 2-byte cell pointer — 20 bytes per entry. With 8,192-byte pages and 32 bytes of headers, that is ⌊8,160 / 20⌋ = 408 separators (409 children) per internal node. A leaf cell is an 8-byte key plus a 6-byte RecordId (u32 page, u16 slot) plus the 2-byte pointer — 16 bytes, so ≈ 510 entries per leaf. A height-3 tree — root, one internal level, leaves — then addresses about 409 × 409 × 510 ≈ 85 million entries, reachable in three page reads. That is the whole argument for B+Trees: logarithmic point lookups with a base in the hundreds, plus ordered traversal that a hash table cannot give you.1 TEXT keys are variable-length, so do not hard-code a max cell count: a node is “full” when the incoming cell no longer fits in free space, exactly like PageFull in Milestone 1 (and note that ms5_text_keys_height_three_internal_splits uses 159-byte text keys specifically to force ~120 leaves and height-3 internal splits within 4,000 inserts).

Integration surface (crates/sql, crates/catalog, crates/exec)

The tree alone is invisible to SQL. Three existing crates gain small, already-stubbed pieces this milestone (quoted verbatim from api-spec.md):

// crates/sql — ast::Statement gains one variant (already declared in ast.rs):
CreateIndex { name: String, table: String, column: String },       // MS5

// crates/catalog — every index is a catalog object:
pub struct IndexInfo { pub oid: Oid, pub name: String, pub table: String,
                       pub column: String, pub root_page: PageId }

impl Catalog {
    pub fn create_index(&self, name: &str, table: &str, column: &str,
                        root_page: PageId) -> Result<Oid>;                  // MS5
    pub fn set_index_root(&self, index_oid: Oid, root: PageId) -> Result<()>;
}

// crates/exec — plan::LogicalPlan gains one variant:
IndexScan { table_idx: usize, table: TableInfo, index: IndexInfo,
            lower: Bound<Value>, upper: Bound<Value> },             // MS5

A complete b-tree is reachable from its root page alone, so the root page number is the identity of the index — SQLite stores exactly that in its schema table.2 FerricDB does the same: IndexInfo.root_page in the catalog. In crates/catalog, persist index definitions across reopens alongside __tables and __columns — e.g., in a fixed-page-id __indexes system heap file allocated at bootstrap (or an extra catalog page linked from your catalog bootstrap header) storing (oid, name, table, column, root_page) tuples. When a root split moves the root (see pitfalls), set_index_root updates both the in-memory cache and the on-disk record (for example by tombstoning the old __indexes tuple and inserting the updated row). Notice that LogicalPlan::IndexScan has no filter field: the planner extracts bounds for an indexed column from =, <, <=, >, or >= conjuncts and emits IndexScan, keeping any residual predicates as a LogicalPlan::Filter node above the IndexScan. Whether the index is actually cheaper than SeqScan is Milestone 7's cost-model problem, not yours today.

Step-by-step guidance

Ordered so that each step is testable before the next begins. Steps 1–4 are a solid first session; splits (steps 5–6) are the hard middle; integration (step 9) is mostly plumbing you have done before.

  1. Design both node layouts on paper first. Decide every header field and its offset before writing code: for leaves — cell count, free-space offset, previous-leaf and next-leaf PageIds; for internal nodes — cell count, free-space offset, right-most child. Write the layout as a comment block at the top of the module and treat it as a contract. Decide your separator convention now too: FerricDB pages use “child i holds entries < separator i (comparing composite (key, rid)); entries ≥ the last separator go to the right-most child”, but any convention works if search and split agree on it (SQLite routes with ≤/> instead2).

  2. Build typed page views, then unit-test them in isolation. Mirror the HeapPage/HeapPageRef pattern from Milestone 1: private LeafNode/InternalNode structs that init or attach over a &mut Page (plus read-only views for with_page) and expose cell-level operations — entry_at(i) returning (Value, RecordId), insert_at(i, cell), and a binary search returning Result<usize, usize> like the standard library's. Use binary search from the start; CMU warns that linear scans of 500-entry nodes will blow your time budget.3 You can test “insert sorted, search, split at midpoint” on a single page long before a tree exists.

  3. Write check_invariants and a debug dump before insert. This inverts the obvious order on purpose. The checker is a recursive walk that verifies: (key, rid) pairs strictly ascending within every node (no exact duplicates), every child's entries inside the parent's separator bounds, every leaf at the same depth, and the leaf chain visiting exactly the leaves reachable from the root in globally sorted (key, rid) order. BusTub ships a tree-printer tool for exactly this reason3; your Display-style dump of “page id → entries per level” is 30 lines and will save you hours. Call the checker after every mutation in your own tests.

  4. Point lookup (get). Because multiple distinct RecordIds can share the same key — and may even span across adjacent leaf pages — get(&key) descends to the first leaf that could hold (key, RecordId { page_id: 0, slot: 0 }), binary-searches to the first matching entry, and collects every entry with that key (hopping to the next sibling leaf if the run reaches the end of the page) until a strictly larger key or end-of-chain is reached — or equivalently delegates to range(Bound::Included(key.clone()), Bound::Included(key.clone())). Validate key up front (reject Null, NaN, and wrong DataType) and compare with Value::sql_cmp.

  5. Insert, then the leaf split. Validate key first, then descend by composite (key, rid) while recording the path as a Vec<(PageId, usize)> of (node, chosen-child slot) — this replaces parent pointers and is the same role BusTub's write-set context plays.3 In the target leaf, binary-search for (key, rid): if that exact pair is already present, return Err(Error::Execution) without modifying the tree (same key with a different rid is allowed!). If the leaf has room, insert and stop. Otherwise: allocate a new page from the PageStore, move the upper half of the cells into it, stitch the leaf chain (new node inherits the old next; old node points at the new one), and insert the new leaf's first (key, rid) entry into the parent at the recorded slot — copied up, so it still exists in the leaf (Figure 3). Because FerricDB supports variable-length TEXT keys, test fullness by checking whether the incoming cell plus its 2-byte pointer fits in free_space — if not, materialize the sorted cell list with the new entry included and split it cleanly in memory.3

  6. Internal splits and the root split. Inserting the separator can overflow the parent; split it by moving the upper half of its cells to a new internal node and pushing the middle separator up — it moves to the grandparent and appears in neither half (Figure 3). Recurse up your recorded path. When the node that overflows is the root, allocate a fresh root holding one separator and two children: this is the only way the tree ever gets taller, and it is what keeps every leaf at the same depth.1 BPlusTree updates self.root (already exposed by root_page()), and whoever owns the catalog entry must persist it with set_index_root — BusTub has the identical requirement with its header page.3 After this step, run the fuzz test for the first time.

  7. Delete — lazily, by exact (key, rid). Validate key, descend by composite (key, rid) to the leaf, and remove only that exact cell (shifting the 2-byte pointers), returning Ok(true) if it was present and Ok(false) otherwise — leaving any sibling entries with the same key and different RecordIds untouched. Do not merge underfull nodes yet. Consequences you must handle: your invariant checker cannot enforce minimum occupancy, and a leaf may become completely empty while staying in the chain — the range iterator has to skip it without yielding anything. Textbook B+Trees keep every node at least half full13; note in a comment that you are relaxing this, and by how much your fuzz runs actually degrade.

  8. The range iterator. range(lower, upper) validates any bounded endpoints and seeks once: for Unbounded, descend to the left-most leaf; for Included(v), seek to (v, min RecordId) so all duplicate keys equal to v are included; for Excluded(v), seek past (v, max RecordId) (or advance past all entries with key == v). next() yields (key, rid) in ascending composite order, advances the slot, and when it runs off the end of a leaf, hops to the sibling through the next-leaf pointer (skipping empty leaves) — sibling pointers exist precisely to make in-order scans cheap.3 Check the upper bound on every yielded key and stop past it (an empty or inverted range yields zero items, not an error). Keep the iterator's state minimal — current PageId plus slot index, re-fetching the page per step through with_page — so you never hold a page pinned across the whole scan.

  9. Integrate with SQL, catalog, and executor. Six small sub-tasks across three crates: (a) in crates/sql, parse CREATE INDEX name ON table (column) into ast::Statement::CreateIndex (Keyword::Index and Keyword::On are already in the lexer enum); (b) in crates/catalog, implement create_index (validating table, column, and unique index name) and set_index_root, persisting index metadata in a system heap page (e.g. __indexes) so indexes and updated roots survive reopen; (c) in crates/exec, bind CreateIndex and execute it: BPlusTree::create, backfill by scanning the heap and inserting every non-NULL (key, rid), then register the tree with catalog.create_index(..., tree.root_page()); (d) maintain every index in TableInfo.indexes inside the write executors — Insert adds (key, rid), Delete removes (key, rid), Update removes (old_key, old_rid) and inserts (new_key, new_rid) (calling catalog.set_index_root whenever tree.root_page() changes!); (e) keep the Halloween guard from Milestone 4 intact so Update/Delete never observe their own writes; (f) in the planner, detect equality/range predicates on an indexed column and emit LogicalPlan::IndexScan { table_idx, table, index, lower, upper } — because IndexScan has no filter field, wrap it in a LogicalPlan::Filter node above it whenever residual predicates remain. The IndexScan executor builds a RangeIter in open() and resolves each RecordId through the table's HeapFile in next().

  10. Stretch: rebalance and latch crabbing. Real deletion: on underflow, borrow a cell from a sibling (updating the parent separator) or merge with it (removing the separator), recursing upward; a root left with a single child is replaced by that child, shrinking the tree. For concurrency, study latch crabbing: acquire latches top-down, releasing a parent as soon as the child is “safe” (cannot split or merge). CMU's spec adds two hard rules: release latches in the same top-down order you acquired them, and never take the same read latch twice in one thread.3 FerricDB's &mut self writers make the tree single-writer today, so crabbing only pays off once you share the tree behind interior mutability — treat it as a design exercise first.

Common pitfalls

Pitfall — mixing up copy-up and push-up

Why it happens: the two split routines look nearly identical, and both “move the middle key to the parent”. But a leaf split must copy the separator (the key still lives in the right leaf, because in a B+Tree every entry must exist at the leaf level12), while an internal split must push it (routing keys are not entries; keeping a copy in a child shifts every child pointer by one). The symptom is silence: the tree keeps answering queries, but get misses keys that range still finds, or children end up under the wrong separator. You will not notice at insert time — only check_invariants notices, which is why you run it after every mutation while developing.

Pitfall — root split without telling the catalog

Why it happens: the root split allocates a new root page, and a b-tree is identified by its root page number2 — but the old root page still exists and still parses as a valid node. Symptom: everything works until the process restarts or another BPlusTree::open reads IndexInfo.root_page from the catalog; the stale root is now a mid-level node, so scans silently miss every key outside its subtree. After any operation that changes root_page(), the executor layer must call Catalog::set_index_root. BusTub bakes the same requirement into its header page.3 Add a test that reopens the tree from the catalog after a forced root split.

Pitfall — the range iterator stops at a leaf boundary

Why it happens: the happy-path iterator walks one leaf's cell array and forgets the hop through the next-leaf pointer, or hops but forgets to reset the slot index to 0, or (with lazy delete) lands on an empty leaf and yields nothing instead of hopping again. Symptom: range queries return exactly a leaf-capacity number of rows (a suspiciously round number like 510), or duplicate the first key after each boundary. Test a scan whose bounds span at least three leaves, and re-run it after deleting an entire middle leaf's worth of keys.

Pitfall — UPDATE and DELETE forget the indexes

Why it happens: the heap and the index are separate structures with no magic link between them; only your executors keep them in agreement. It is easy to wire index inserts into INSERT and stop there. Symptom: an IndexScan returns a RecordId whose tuple is dead (deleted row still indexed) or misses rows whose indexed column was updated — which is caught immediately when you cross-check IndexScan against SeqScan (and in ms5_create_index_and_index_scan_execution for post-create inserts). Route every write through a single helper that touches the heap and all of TableInfo.indexes, and remember that any UPDATE (even on an unindexed column, because HeapFile updates out of place to a new RecordId) deletes (old_key, old_rid) and inserts (new_key, new_rid) in every index on the table.

Pitfall — comparing Values of the wrong type, NULL, or NaN

Why it happens: node search compares a probe key against stored keys with Value::sql_cmp, which returns Option<Ordering> — it is None when either side is Null, and Float(NaN) or mixed types (probing a Text tree with an Integer) have no meaningful SQL ordering. Symptom: a panic on unwrap() deep inside binary search if you are lucky; interleaved, unsorted entries and a corrupted tree if you are not. Enforce the boundary once at every public entry point: reject Value::Null, Value::Float(f) where f.is_nan(), and keys whose data_type() differs from the tree's key_type with Err(Error::Execution); at the SQL executor layer, skip inserting index entries for rows whose indexed column is Null (tested by ms5_float_boolean_and_invalid_keys).

Definition of done

  • All four Milestone 5 test suites pass with --include-ignored ms5_ (keeping the #[ignore] attributes intact): ferricdb-index (all 9 tests, including ms5_non_unique_keys_and_exact_duplicate_error, ms5_text_keys_height_three_internal_splits, and ms5_btree_invariants_fuzz), ferricdb-catalog (ms5_create_index_and_set_root_persist), ferricdb-sql (ms5_create_index_parse), and ferricdb-exec (ms5_create_index_and_index_scan_execution).
  • CREATE INDEX works end to end: it parses, backfills from existing heap rows, persists in the catalog across reopen, and supports both unique and non-unique secondary indexes.
  • Index scans return exactly the same rows as sequential scans for the same predicate, with any residual predicates enforced by a Filter node above IndexScan.
  • The planner emits IndexScan for equality and range predicates on an indexed column, and still emits SeqScan for everything else.
  • INSERT, UPDATE, and DELETE maintain every index on the table; a reopened database (fresh BPlusTree::open from IndexInfo.root_page) still answers correctly after root splits.
  • You can explain, without notes, why the leaf split copies its separator up, why the internal split pushes it up, and why composite (key, rid) ordering is needed for both non-unique indexes and MVCC updates.
