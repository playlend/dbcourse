Milestone 5 · B+Tree Index

Build a disk-resident B+Tree keyed on a single column, wire it into the catalog, executor, and planner, and prove it correct with an invariant-checking fuzz test.

This is the most intricate data structure in the whole project, and the one CMU warns its students about in bold type3. It is also the most satisfying: when you finish, SELECT * FROM users WHERE id = 42 stops scanning the whole table and lands on the right page in three reads. Budget more time than you did for Milestone 4, keep check_invariants running after every mutation, and the tree will tell you the moment you corrupt it — instead of twenty inserts later.

Learning objectives

  • Design on-disk layouts for B+Tree leaf and internal nodes, one node per 8 KB page, using a sorted cell-pointer array.
  • Implement point search, insert with cascading leaf/internal/root splits, and lazy delete on a paged B+Tree.
  • Explain why a leaf split copies its separator key up while an internal split pushes it up, and what breaks when you mix the two.
  • Implement a range iterator that walks the sibling-linked leaf chain across node boundaries.
  • Integrate an index with the rest of the system: CREATE INDEX in the front-end, index maintenance in the write executors, and a simple access-path rule in the planner.
  • Verify structural invariants (sorted keys, uniform leaf depth, key-range containment) mechanically, under randomized workloads.

Required reading

  • M04 · B+Trees and Friends — the concept module: why B+Trees won, occupancy math, hash indexes, and the design space this milestone draws from.
  • cstack, Let's Build a Simple Database, Part 7 — the gentlest possible introduction to leaf vs. internal nodes and how a tree grows by splitting.1
  • The SQLite Database File Format, §1.6 “B-tree Pages” — a production page layout worth imitating: page header, cell pointer array, cells packed at the page end.2
  • CMU 15-445 Fall 2025, Project #2 — read “Task #2” and “Requirements and Hints” for operation semantics and edge cases: duplicate keys, root changes, iterator design, latch crabbing.3

Where this fits

The index is a peer of the heap file, not a layer above it: both are access methods that store their pages through the same PageStore trait, which means the buffer pool from Milestone 2 caches index pages and heap pages in the same frames with zero new plumbing. The tree stores no tuples. Its leaves map key values to RecordIds — the (page, slot) addresses from Milestone 1 — and the executor fetches the actual rows from the heap. Above you, the catalog records which indexes exist and where their roots live, and the planner starts making its first real decision: SeqScan or IndexScan.

Specification

The tree (crates/index)

You implement package ferricdb-index in course/ferricdb/crates/index. The public surface, from the API spec:

// crates/index/src/lib.rs — public surface to implement

/// Disk-resident B+Tree mapping a single-column key to RecordIds.
/// One node = one page. Keys are Values of one DataType.
pub struct BPlusTree { /* Arc<dyn PageStore>, root PageId, key type */ }
impl BPlusTree {
    pub fn create(store: std::sync::Arc<dyn PageStore>, key_type: DataType) -> Result<Self>;
    pub fn open(store: std::sync::Arc<dyn PageStore>, root: PageId, key_type: DataType) -> Self;
    pub fn root_page(&self) -> PageId;
    pub fn insert(&mut self, key: &Value, rid: RecordId) -> Result<()>;   // splits as needed
    pub fn get(&self, key: &Value) -> Result<Option<RecordId>>;
    pub fn delete(&mut self, key: &Value) -> Result<bool>;                // lazy delete OK
    pub fn range(
        &self,
        lower: std::ops::Bound<Value>,
        upper: std::ops::Bound<Value>,
    ) -> Result<RangeIter>;   // Iterator<Item = Result<(Value, RecordId)>>, leaf-chain walk
    /// Test hook: verify sortedness, balance, and key-range invariants.
    pub fn check_invariants(&self) -> Result<()>;
}

Semantic notes:

  • Two node kinds. Internal nodes hold K keys and K+1 child page pointers and exist only to route searches; leaf nodes hold keys paired with RecordIds. All entries live at the leaf level — that separation is what makes this a B+Tree rather than a B-Tree.12
  • Balance. Every leaf sits at the same depth, and the tree gets taller only when the root itself splits.1 Your check_invariants must verify both.
  • Unique keys. Keys are unique, following BusTub, where re-inserting an existing key leaves the tree unchanged and reports failure.3 In this milestone you index the primary key and unique-valued secondary columns; decide and document what your insert does on a duplicate (error out or overwrite) — just make it deliberate.
  • Keys are Values of one DataType, fixed at create/open. Compare them with Value::sql_cmp, and never let a Null key reach the tree (see the pitfalls).
  • Lazy delete is acceptable as a first version: remove the leaf entry and leave underfull nodes alone. CMU requires merge/redistribution3; we defer that to the stretch step, honestly trading disk space for a much smaller state space while you stabilize splits.
  • range takes standard std::ops::Bound pairs, so it must handle Included, Excluded, and Unbounded on each side, and it must walk the leaf sibling chain rather than re-descending from the root per key.3

Node layout on the page

How you arrange bytes inside a node is your design decision, but you should steal the shape SQLite uses: after the page header comes a cell pointer array of 2-byte offsets kept in key order, while the cells themselves are packed from the end of the page toward the middle; the space between the two is free.2 Inserting into a sorted position then shifts only 2-byte pointers, never whole cells. SQLite's interior pages additionally keep the right-most child pointer in the page header rather than in a cell, so K cells plus one header field give the K+1 children.2 The first 16 bytes of every FerricDB page are already reserved by Milestone 1 (pageLSN, page-type tag, padding) — use that type tag to mark pages as index leaf or index internal.

A worked fanout example with course numbers, so you can sanity-check your own layout. Take an INTEGER key: an internal cell is an 8-byte key plus a 4-byte child PageId, plus its 2-byte cell pointer — 14 bytes per entry. With 8,192-byte pages and 32 bytes of headers, that is ⌊8,160 / 14⌋ ≈ 582 children per internal node. A leaf cell is an 8-byte key plus a 6-byte RecordId (u32 page, u16 slot) plus the 2-byte pointer — 16 bytes, so ≈ 510 entries per leaf. A height-3 tree — root, one internal level, leaves — then addresses about 582 × 582 × 510 ≈ 173 million keys, reachable in three page reads. That is the whole argument for B+Trees: logarithmic point lookups with a base in the hundreds, plus ordered traversal that a hash table cannot give you.1 TEXT keys are variable-length, so do not hard-code a max cell count: a node is “full” when the incoming cell no longer fits in free space, exactly like PageFull in Milestone 1.

Integration surface (crates/sql, crates/catalog, crates/exec)

The tree alone is invisible to SQL. Three existing crates gain small, already-stubbed pieces this milestone:

// crates/sql — ast::Statement gains one variant:
CreateIndex { name: String, table: String, column: String },       // MS5

// crates/catalog — every index is a catalog object:
pub struct IndexInfo { pub oid: Oid, pub name: String, pub table: String,
                       pub column: String, pub root_page: PageId }

impl Catalog {
    pub fn create_index(&self, name: &str, table: &str, column: &str,
                        root_page: PageId) -> Result<Oid>;                  // MS5
    pub fn set_index_root(&self, index_oid: Oid, root: PageId) -> Result<()>;
}

// crates/exec — plan::LogicalPlan gains one variant:
IndexScan { table: TableInfo, index: IndexInfo,
            lower: Bound<Value>, upper: Bound<Value> },             // MS5

A complete b-tree is reachable from its root page alone, so the root page number is the identity of the index — SQLite stores exactly that in its schema table.2 FerricDB does the same: IndexInfo.root_page in the catalog. When a root split changes the root (see pitfalls), set_index_root is how the new identity gets persisted. The planner rule this milestone is deliberately naive: if the filter constrains an indexed column with =, <, <=, >, or >=, emit IndexScan with the matching bounds; otherwise SeqScan. Whether the index is actually the cheaper choice is Milestone 7's cost-model problem, not yours today.

Step-by-step guidance

Ordered so that each step is testable before the next begins. Steps 1–4 are a solid first session; splits (steps 5–6) are the hard middle; integration (step 9) is mostly plumbing you have done before.

  1. Design both node layouts on paper first. Decide every header field and its offset before writing code: for leaves — cell count, free-space offset, previous-leaf and next-leaf PageIds; for internal nodes — cell count, free-space offset, right-most child. Write the layout as a comment block at the top of the module and treat it as a contract. Decide your separator convention now too: FerricDB pages use “child i holds keys < separator i; keys ≥ the last separator go to the right-most child”, but any convention works if search and split agree on it (SQLite routes with ≤/> instead2).

  2. Build typed page views, then unit-test them in isolation. Mirror the HeapPage pattern from Milestone 1: private LeafNode/ InternalNode structs that init or attach over a &mut Page and expose cell-level operations — key_at(i), insert_at(i, cell), and a binary search returning Result<usize, usize> like the standard library's. Use binary search from the start; CMU warns that linear scans of 500-entry nodes will blow your time budget.3 You can test “insert sorted, search, split at midpoint” on a single page long before a tree exists.

  3. Write check_invariants and a debug dump before insert. This inverts the obvious order on purpose. The checker is a recursive walk that verifies: keys strictly ascending within every node, every child's keys inside the parent's separator range, every leaf at the same depth, and the leaf chain visiting keys in globally sorted order. BusTub ships a tree-printer tool for exactly this reason3; your Display-style dump of “page id → keys per level” is 30 lines and will save you hours. Call the checker after every mutation in your own tests.

  4. Point search. get descends from the root: binary-search the internal node's separators to choose a child, repeat until a leaf, binary-search the leaf for an exact match. Deserialize only the key you are probing (you stored its cell offset; you know the key DataType), and compare with Value::sql_cmp. If your search visits more nodes than the tree's height, something is wrong.

  5. Insert, then the leaf split. While descending, record the path as a Vec<(PageId, usize)> of (node, chosen-child slot) — this replaces parent pointers and is the same role BusTub's write-set context plays.3 If the leaf has room, insert and stop. Otherwise: allocate a new page from the PageStore, move the upper half of the cells into it, stitch the leaf chain (new node inherits the old next; old node points at the new one), and insert the new leaf's first key into the parent at the recorded slot — copied up, so it still exists in the leaf (Figure 3). A useful timing rule from CMU: split a leaf when it is full after insertion, split an internal node when full before insertion — it avoids nasty overflow corner cases.3

  6. Internal splits and the root split. Inserting the separator can overflow the parent; split it by moving the upper half of its cells to a new internal node and pushing the middle key up — it moves to the grandparent and appears in neither half (Figure 3). Recurse up your recorded path. When the node that overflows is the root, allocate a fresh root holding one separator and two children: this is the only way the tree ever gets taller, and it is what keeps every leaf at the same depth.1 BPlusTree must report the new root via root_page(), and whoever owns the catalog entry must persist it with set_index_root — BusTub has the identical requirement with its header page.3 After this step, run the fuzz test for the first time.

  7. Delete — lazily. Find the leaf, remove the cell (shift the 2-byte pointers, reclaim the space or leave a gap and compact later), return whether the key was present. Do not merge underfull nodes yet. Consequences you must handle: your invariant checker cannot enforce minimum occupancy, and a leaf may become completely empty while staying in the chain — the range iterator has to skip it without yielding anything. Textbook B+Trees keep every node at least half full13; note in a comment that you are relaxing this, and by how much your fuzz runs actually degrade.

  8. The range iterator. range(lower, upper) seeks once: for Unbounded, descend to the left-most leaf; for Included(v)/Excluded(v), descend to v's leaf and binary-search the starting slot (mind the exclusive case). next() yields (key, rid), advances the slot, and when it runs off the end of a leaf, hops to the sibling through the next-leaf pointer — sibling pointers exist precisely to make in-order scans cheap.3 Check the upper bound on every yielded key and stop past it. Keep the iterator's state minimal — current PageId plus slot index, re-fetching the page per step through with_page — so you never hold a page pinned across the whole scan.

  9. Integrate with SQL. Five sub-tasks, each small: (a) parse CREATE INDEX name ON table (column) into ast::Statement::CreateIndex, and let the binder verify the table and column exist; (b) execute it: BPlusTree::create, backfill by scanning the heap and inserting (key, rid) for every live row, then catalog.create_index(...) with the final root; (c) maintain indexes in the write executors — Insert adds to every index in TableInfo.indexes, Delete removes, Update removes the old key and inserts the new one when the indexed column changed; (d) have Update/Delete drain their input RecordIds into a buffer before writing, so a scan never observes its own writes (the classic self-updating-scan trap); (e) implement the IndexScan executor: open() builds the range iterator from the plan's bounds, next() resolves each RecordId through the heap and re-applies the full predicate as a residual filter, which keeps the planner rule simple and always correct.

  10. Stretch: rebalance and latch crabbing. Real deletion: on underflow, borrow a cell from a sibling (updating the parent separator) or merge with it (removing the separator), recursing upward; a root left with a single child is replaced by that child, shrinking the tree. For concurrency, study latch crabbing: acquire latches top-down, releasing a parent as soon as the child is “safe” (cannot split or merge). CMU's spec adds two hard rules: release latches in the same top-down order you acquired them, and never take the same read latch twice in one thread.3 FerricDB's &mut self writers make the tree single-writer today, so crabbing only pays off once you share the tree behind interior mutability — treat it as a design exercise first.

Test plan

The starter workspace ships every Milestone 5 test marked #[ignore = "milestone 5"] with an ms5_ name prefix. You do not edit the tests to activate them: --include-ignored runs ignored tests too, and the ms5_ filter selects just this milestone's group. (Once you are done, you may also delete the #[ignore] attributes so plain cargo test keeps guarding the crate.)

# from course/ferricdb/ — the tree itself: unit, property, and fuzz tests
cargo test -p ferricdb-index -- --include-ignored ms5_

# end-to-end SQL behaviour (CREATE INDEX, index maintenance, IndexScan),
# via the sqllogictest files crates/ferricdb/tests/slt/ms5_*.slt
cargo test -p ferricdb slt_all
Coverage areaHow it is checked
Point operationsms5_ unit tests: insert/get/delete round trips at single-node scale, duplicate handling, empty-tree edge cases.
Splits and root growthms5_ tests insert far past one page's capacity in ascending, descending, and shuffled orders, then verify every key is findable and root_page() changed.
Structural invariantsms5_btree_invariants_fuzz: a seeded-random interleaving of inserts and deletes that calls your own check_invariants after every batch — sorted keys, uniform leaf depth, key-range containment. A seed is printed so failures replay deterministically.
Range iterationms5_ tests compare range() output against a BTreeMap oracle for all nine bound combinations, including scans that cross many leaves.
SQL integrationms5_*.slt files: the same predicate is run with and without an index and must return identical rows — the “index scan ≡ seq scan” cross-check.

Write your own tests before trusting the provided ones: after step 5 you should already have a hand-rolled “insert 10,000 sequential integers, get each one back” test. And keep the fuzz test running in a loop while you develop deletion — it is the test that finds split-boundary bugs the deterministic tests miss.

Common pitfalls

Pitfall — mixing up copy-up and push-up

Why it happens: the two split routines look nearly identical, and both “move the middle key to the parent”. But a leaf split must copy the separator (the key still lives in the right leaf, because in a B+Tree every entry must exist at the leaf level12), while an internal split must push it (routing keys are not entries; keeping a copy in a child shifts every child pointer by one). The symptom is silence: the tree keeps answering queries, but get misses keys that range still finds, or children end up under the wrong separator. You will not notice at insert time — only check_invariants notices, which is why you run it after every mutation while developing.

Pitfall — root split without telling the catalog

Why it happens: the root split allocates a new root page, and a b-tree is identified by its root page number2 — but the old root page still exists and still parses as a valid node. Symptom: everything works until the process restarts or another BPlusTree::open reads IndexInfo.root_page from the catalog; the stale root is now a mid-level node, so scans silently miss every key outside its subtree. After any operation that changes root_page(), the executor layer must call Catalog::set_index_root. BusTub bakes the same requirement into its header page.3 Add a test that reopens the tree from the catalog after a forced root split.

Pitfall — the range iterator stops at a leaf boundary

Why it happens: the happy-path iterator walks one leaf's cell array and forgets the hop through the next-leaf pointer, or hops but forgets to reset the slot index to 0, or (with lazy delete) lands on an empty leaf and yields nothing instead of hopping again. Symptom: range queries return exactly a leaf-capacity number of rows (a suspiciously round number like 510), or duplicate the first key after each boundary. Test a scan whose bounds span at least three leaves, and re-run it after deleting an entire middle leaf's worth of keys.

Pitfall — UPDATE and DELETE forget the indexes

Why it happens: the heap and the index are separate structures with no magic link between them; only your executors keep them in agreement. It is easy to wire index inserts into INSERT and stop there. Symptom: an IndexScan returns a RecordId whose tuple is dead (deleted row still indexed) or misses rows whose indexed column was updated — which is exactly what the “index scan ≡ seq scan” slt cross-checks are designed to catch. Route every write through a single helper that touches the heap and all of TableInfo.indexes, and remember that an UPDATE of an indexed column is a delete-then-insert in the tree.

Pitfall — comparing Values of the wrong type

Why it happens: node search compares a probe key against stored keys with Value::sql_cmp, which returns Option<Ordering> — it is None when either side is Null, and mixed types (probing a Text tree with an Integer) have no meaningful ordering. Symptom: a panic on unwrap() deep inside binary search if you are lucky; interleaved, unsorted keys and a corrupted tree if you are not. Enforce the boundary once: the tree rejects keys whose data_type() differs from the tree's key_type, the binder has already coerced literals, and rows with a Null in the indexed column are skipped at insert (document this choice next to the code).

Definition of done

  • cargo test -p ferricdb-index -- --include-ignored ms5_ passes in full, including ms5_btree_invariants_fuzz — the seeded insert/delete fuzz run that validates sorted keys, uniform leaf depth, and key-range containment through your own check_invariants.
  • CREATE INDEX works end to end: it backfills from existing heap rows and the index appears in the catalog with a live root page.
  • Index scans return exactly the same rows as sequential scans for the same predicate — the ms5_*.slt cross-check files pass under slt_all.
  • The planner emits IndexScan for equality and range predicates on an indexed column, and still emits SeqScan for everything else.
  • INSERT, UPDATE, and DELETE maintain every index on the table; a reopened database (fresh BPlusTree::open from IndexInfo.root_page) still answers correctly after root splits.
  • You can explain, without notes, why the leaf split copies its separator up and the internal split pushes it up.
