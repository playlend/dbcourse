Milestone 4 · Planner and Volcano Executor

The milestone where FerricDB becomes a database: bound statements become plans, plans become iterator trees, and real SQL runs end to end in your REPL.

Every piece you have built so far was in service of this moment. Storage holds tuples, the buffer pool serves pages, the front-end produces checked statements — and today you write the machine that connects them: a planner that turns BoundStatements into operator trees and an executor that pulls tuples through those trees one next() at a time. When the last test goes green, type INSERT and SELECT into your REPL and take the moment. You wrote a database.

Learning objectives

  • Implement the Volcano iterator contract — open/next/close — and explain why pull-based composition makes operators independent.1
  • Implement the nine core operators: SeqScan, Filter, Projection, Values, Limit, in-memory Sort, Insert, Update, Delete.2
  • Implement an expression evaluator with SQL three-valued logic.
  • Build the planner that maps bound statements to logical plans and logical plans to executor trees.
  • Recognize blocking vs streaming operators and the Halloween problem — and defuse the latter.2

Where this fits

Specification

You implement the heart of crates/exec:

pub mod plan {
    pub enum LogicalPlan {
        SeqScan { table: TableInfo, filter: Option<BoundExpr> },
        Filter { input: Box<LogicalPlan>, predicate: BoundExpr },
        Projection { input: Box<LogicalPlan>, exprs: Vec<BoundExpr> },
        Sort { input: Box<LogicalPlan>, keys: Vec<(BoundExpr, bool)> },
        Limit { input: Box<LogicalPlan>, limit: u64 },
        Insert { table: TableInfo, input: Box<LogicalPlan> },
        Update { table: TableInfo, set: Vec<(usize, BoundExpr)>, input: Box<LogicalPlan> },
        Delete { table: TableInfo, input: Box<LogicalPlan> },
        Values { rows: Vec<Vec<BoundExpr>>, schema: Schema },
        // IndexScan, joins, aggregates: Milestones 5–6
    }
}

/// Volcano iterator contract. next() returns Ok(None) at end of stream.
pub trait Executor {
    fn schema(&self) -> &Schema;
    fn open(&mut self) -> Result<()>;
    fn next(&mut self) -> Result<Option<Vec<Value>>>;
    fn close(&mut self) -> Result<()>;
}

pub struct Planner<'a> { /* &'a ExecContext */ }
impl<'a> Planner<'a> {
    pub fn plan(&self, stmt: binder::BoundStatement) -> Result<plan::LogicalPlan>;
    pub fn create_executor(&self, plan: &plan::LogicalPlan) -> Result<Box<dyn Executor>>;
}

pub struct QueryResult { pub schema: Schema, pub rows: Vec<Vec<Value>>,
                         pub affected: u64, pub explain: Option<String> }
/// One-stop entry used by REPL, tests, and server.
pub fn execute(sql: &str, ctx: &ExecContext) -> Result<Vec<QueryResult>>;

Operator semantics you must honor (each is checked by a test):

  • SeqScan wraps HeapFile::scan, deserializes tuples, and (optionally) applies an inlined filter. Skips tombstones.
  • Filter passes a row iff its predicate evaluates to true — NULL is not true, so a NULL predicate drops the row. Three-valued logic is not optional; it is the tests' favorite subject.
  • Projection evaluates its expressions per row and emits the new shape; its schema() reports the projected columns and types.
  • Sort is blocking: open() drains its child, sorts in memory with Value::sql_cmp (NULLs order last in this course — document any choice you make), and next() replays. External sort arrives in Milestone 6.
  • Limit is streaming: stop calling the child after N rows — the M06 stepper's short-circuit, now in code.
  • Insert / Update / Delete consume their input, write through HeapFile, and report affected counts (rows produced: none). Update and Delete take their victims from a child SeqScan.
  • Values emits its literal rows; it is INSERT's usual child.

Step-by-step guidance

  1. Expression evaluator first. eval(expr: &BoundExpr, row: &[Value]) -> Result<Value> — a match over the expression tree. The delicate part is NULL: any arithmetic or comparison with a NULL operand yields NULL; AND/OR follow the three-valued truth tables from M01 (false AND NULL = false, true OR NULL = true — the short-circuit rows matter); IS NULL is the one expression that looks at NULL and returns a real boolean. common::Value::sql_cmp already encodes comparison semantics — use it, don't re-derive it.
  2. Values + Projection next. With those two and the evaluator, SELECT 1 + 2 * 3; runs end to end through execute(). Get that green before touching storage.
  3. SeqScan, then Filter, then Insert. Scan is a thin adapter over HeapFile::scan; Insert is Values feeding serialized tuples into HeapFile::insert. At this point the first sqllogictest statements pass.
  4. Update/Delete: materialize victims first. Collect the target RecordIds from the child scan completely, close the scan, then mutate. Interleaving scan and mutation is the Halloween problem: an update that moves a tuple forward can meet its own output and update it again. The provided test constructs exactly that trap (an UPDATE bumping values into the scan's path); materialization defuses it.2
  5. Sort and Limit. Sort teaches the blocking pattern (all work in open); Limit teaches early termination. Together they finish the SELECT clause set.
  6. Planner: two honest functions. plan() is a structural mapping — SELECT becomes Scan→Filter→Sort→Limit→Projection (build the tree bottom-up; Projection outermost so ORDER BY can reference unprojected columns for now). create_executor() recursively converts nodes to boxed executors. Resist cleverness here — optimization is Milestone 7's whole job.
  7. The result table. Wire execute() into the REPL's print_result: column headers from QueryResult::schema, width-aligned rows, N rows / N affected trailers. This is the REPL payoff moment from Milestone 0.
  8. Run the sqllogictest suite last. The harness (provided in crates/ferricdb/tests/slt_harness.rs) drives execute() with tests/slt/ms4_crud.slt — CREATE/INSERT/SELECT/UPDATE/DELETE with WHERE, ORDER BY, LIMIT, and NULL cases, in the standard sqllogictest format.3

Test plan

cargo test -p ferricdb-exec -- --include-ignored ms4_

# end-to-end: the sqllogictest suite
cargo test -p ferricdb -- --include-ignored slt_all

# regressions
cargo test -p ferricdb-sql -p ferricdb-catalog -- --include-ignored ms3_

The ms4_ group builds a fresh ExecContext over a tempfile-backed store and drives everything through execute(): CRUD round-trips, three-valued WHERE semantics, ORDER BY + LIMIT interplay, affected counts, expression evaluation (including CAST and IS NULL), and the Halloween guard. slt_all then replays ms4_crud.slt; when a case fails, the harness prints the statement and both result sets — read them, they are precise.

Common pitfalls

Treating NULL as false everywhere

Symptom: SELECT * FROM t WHERE NOT (x > 5) returns rows where x is NULL. Cause: collapsing NULL to false before NOT instead of after: NOT NULL is NULL, which the filter then drops. Keep NULL a first-class value through the whole expression tree and convert to "row passes?" only at the filter boundary.

The Halloween problem

Symptom: UPDATE t SET x = x + 10 WHERE x < 100 bumps some rows twice (or loops). Cause: the update's writes land ahead of the scan cursor and are re-visited. Named for the day IBM's System R team discovered it; the fix is the one in the guidance — fully materialize the victim list before writing.2

Sort as a streaming operator

Symptom: ORDER BY output is correct for one-page tables and interleaved for larger ones. Cause: sorting each next() batch instead of draining the child in open(). A sort cannot emit its first row before seeing its last input row — blocking is the definition, not an implementation detail.1

Schema lies

Symptom: downstream operators panic on column indexes. Cause: an operator whose schema() doesn't match what next() actually emits (classically: Projection reporting its input schema). Every test failure of the form "index out of bounds" starts here.

Definition of done

  • ms4_ and slt_all pass; ms1_–ms3_ still pass.
  • A full REPL session works: create a table, insert three rows (one with NULLs), select with WHERE/ORDER BY/LIMIT, update, delete, select again — with aligned result tables and correct counts.
  • The Halloween UPDATE from the pitfall bumps every row exactly once.
  • You can explain why Limit over Sort still reads the whole table, but Limit over SeqScan does not.

Check your understanding

SELECT … ORDER BY x LIMIT 5 on a million-row table: how many rows does Sort consume?
What does false AND NULL evaluate to?
