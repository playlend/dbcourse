Storage holds tuples (MS1), the buffer pool caches pages (MS2), and the front-end produces catalog-checked statements (MS3). Today you build the execution engine in course/ferricdb/crates/exec: a planner mapping BoundStatements to LogicalPlan trees, a Volcano executor pulling ExecRows one next() at a time, a three-valued expression evaluator, and the top-level execute() driver powering your REPL, tests, and future wire server. When ms4_slt_crud turns green, run INSERT, SELECT, UPDATE, and DELETE in your REPL and restart the binary to see your rows persist. You built a database.

Learning objectives

  • Implement the Volcano iterator contract — open / next / close yielding Option<ExecRow> — and compose operators via Box<dyn Executor>.12
  • Implement all nine Milestone 4 physical operators: SeqScan, Filter, Projection, Values, Limit, blocking in-memory Sort, Insert, Update, and Delete.24
  • Implement SQL expression evaluation with three-valued logic, Value::sql_cmp, implicit Integer → Float widening, CAST conversions, and safe division-by-zero handling.5
  • Build Planner::plan, identity Planner::optimize, Planner::create_executor, and execute() with direct DDL dispatch and PostgreSQL CommandComplete tags.47
  • Propagate physical RecordIds via ExecRow and defuse the Halloween problem on out-of-place HeapFile updates.2
  • Upgrade the REPL to ferricdb_exec::execute with aligned ASCII tables and verify end-to-end SQL with sqllogictest.3

Where this fits

Two seams on ExecContext remain dormant until later milestones: txn_manager / current_txn / failed_txn (Milestone 8 MVCC) and wal (Milestone 9 write-ahead logging). In Milestone 4, every inserted tuple writes TupleMeta::default() (xmin = 0, xmax = 0: frozen and live) and wal stays None. Keeping these fields in place lets Milestones 5–10 slot in without breaking ferricdb-exec's public signatures.

Specification

You implement Milestone 4 inside course/ferricdb/crates/exec (package ferricdb-exec). All public signatures below are quoted verbatim from course/ferricdb/docs/api-spec.md and crates/exec/src/{lib,plan}.rs — do not alter them.

1. Row container, Volcano trait, and execution context

// crates/exec/src/lib.rs — verbatim public API from api-spec.md

#[derive(Clone, Debug, PartialEq)]
pub struct ExecRow { pub values: Vec<Value>, pub rid: Option<RecordId> }
impl ExecRow {
    pub fn new(values: Vec<Value>) -> Self;
    pub fn with_rid(values: Vec<Value>, rid: RecordId) -> Self;
}

/// Volcano iterator contract. next() returns Ok(None) at end of stream.
pub trait Executor {
    fn schema(&self) -> &Schema;
    fn open(&mut self) -> Result<()>;
    fn next(&mut self) -> Result<Option<ExecRow>>;
    fn close(&mut self) -> Result<()>;
}

pub const DEFAULT_MEMORY_PAGES: usize = 64;
pub struct ExecContext {
    pub catalog: Arc<Catalog>,
    pub store: Arc<dyn PageStore>,
    pub txn_manager: Arc<TransactionManager>,
    pub current_txn: Mutex<Option<Arc<Transaction>>>,
    pub failed_txn: Mutex<bool>,
    pub wal: Option<Arc<dyn WalHook>>,
    pub memory_pages: usize,
}
impl ExecContext {
    pub fn new(catalog: Arc<Catalog>, store: Arc<dyn PageStore>,
               txn_manager: Arc<TransactionManager>) -> Self;
    pub fn new_session(&self) -> Self; // isolated per-connection session for Server
}

2. Logical plan tree

// crates/exec/src/plan.rs — verbatim public API from api-spec.md

pub mod plan {
    #[derive(Clone, Debug)]
    pub enum LogicalPlan {
        SeqScan { table_idx: usize, table: TableInfo, filter: Option<BoundExpr> },
        IndexScan { table_idx: usize, table: TableInfo, index: IndexInfo,
                    lower: Bound<Value>, upper: Bound<Value> },             // MS5
        Filter { input: Box<LogicalPlan>, predicate: BoundExpr },
        Projection { input: Box<LogicalPlan>, exprs: Vec<BoundExpr>, schema: Schema },
        NestedLoopJoin { left: Box<LogicalPlan>, right: Box<LogicalPlan>,
                         on: Option<BoundExpr> },                            // MS6
        HashJoin { left: Box<LogicalPlan>, right: Box<LogicalPlan>,
                   left_keys: Vec<BoundExpr>, right_keys: Vec<BoundExpr> },  // MS6
        Aggregate { input: Box<LogicalPlan>, group_by: Vec<BoundExpr>,
                    aggregates: Vec<AggExpr> },                              // MS6
        Sort { input: Box<LogicalPlan>, keys: Vec<(BoundExpr, bool)> },      // NULLs LAST in ASC & DESC
        Limit { input: Box<LogicalPlan>, limit: u64 },
        Insert { table: TableInfo, input: Box<LogicalPlan> },
        Update { table: TableInfo, set: Vec<(usize, BoundExpr)>, input: Box<LogicalPlan> },
        Delete { table: TableInfo, input: Box<LogicalPlan> },
        Values { rows: Vec<Vec<BoundExpr>>, schema: Schema },
    }
}

Milestone 4 builds and executes nine variants: SeqScan, Filter, Projection, Sort, Limit, Insert, Update, Delete, and Values. IndexScan arrives in Milestone 5; joins and Aggregate arrive in Milestone 6 — return Err(Error::Execution(...)) if create_executor encounters them today.

3. Planner, QueryResult, and execute()

// crates/exec/src/lib.rs — verbatim public API from api-spec.md

pub struct Planner<'a> { /* &'a ExecContext */ }
impl<'a> Planner<'a> {
    pub fn new(ctx: &'a ExecContext) -> Self;
    pub fn plan(&self, stmt: binder::BoundStatement) -> Result<plan::LogicalPlan>;
    /// MS4: identity (return Ok(plan)); MS7: rewrite rules + cost-based optimizer.
    pub fn optimize(&self, plan: plan::LogicalPlan) -> Result<plan::LogicalPlan>;
    pub fn create_executor(&self, plan: &plan::LogicalPlan) -> Result<Box<dyn Executor>>;
}

#[derive(Clone, Debug, Default)]
pub struct QueryResult {
    pub schema: Schema,
    pub rows: Vec<Vec<Value>>,
    pub affected: u64,
    pub tag: String,
    pub explain: Option<String>,
}
/// One-stop entry used by REPL, tests, and server.
pub fn execute(sql: &str, ctx: &ExecContext) -> Result<Vec<QueryResult>>;

The starter file already implements ExecRow::new / with_rid, ExecContext::new / new_session, and Planner::new. Keep those intact and replace the four todo!("Milestone 4") stubs: Planner::plan, Planner::optimize (implemented as the identity function Ok(plan) in Milestone 4!), Planner::create_executor, and execute.

Operator contract summary

  • SeqScan (streaming): opens HeapFile::scan(), deserializes live tuples, applies any fused filter, and emits ExecRow::with_rid(values, rid).
  • Filter (streaming): pulls child rows and forwards the original ExecRow (preserving row.rid) iff its predicate evaluates to Value::Boolean(true).
  • Projection (streaming): evaluates exprs per row, emits ExecRow::new(vals) (rid: None), and reports plan.schema from schema().
  • Values (streaming): evaluates literal row expressions against &[] and emits ExecRow::new(vals).
  • Sort (blocking): drains its child in open(), sorts in memory with NULLs LAST in both ASC and DESC, then replays on next().
  • Limit (streaming): stops pulling from its child after limit rows (LIMIT 0 pulls zero rows).
  • Insert / Update / Delete (DML): perform their HeapFile writes (with a materialization guard for Update and Delete) and emit one 1-column row [Value::Integer(affected)], then Ok(None).

Two consumers rely on exact QueryResult fields: slt_harness.rs checks result.schema.columns.is_empty() to distinguish statement ok from query results,3 and Milestone 10's PostgreSQL wire server forwards QueryResult::tag verbatim in its CommandComplete ('C') message.7 Populate every statement according to this table:

Statement dispatch, RecordId flow, and the Halloween guard

Four structural invariants tie execute(), Planner, and HeapFile together cleanly.

1. Direct DDL / TCL dispatch in execute()

LogicalPlan has no CreateTable or DropTable variant. Following PostgreSQL's split between utility commands and plannable queries (and toyDB's dispatcher),14 execute(sql, ctx) intercepts DDL directly against ctx.catalog before Planner::plan, while plannable statements flow through the full Volcano pipeline:

execute(sql, ctx):
    for stmt in Parser::parse(sql)?:               // empty / ";" → Ok(vec![])
        bound ← Binder::new(&ctx.catalog).bind(stmt)?
        match bound:
            CreateTable { name, schema, .. } →
                ctx.catalog.create_table(&name, schema)?
                push QueryResult { tag: "CREATE TABLE", ..default }
            DropTable { name } →
                ctx.catalog.drop_table(&name)?
                push QueryResult { tag: "DROP TABLE", ..default }
            Select | Insert | Update | Delete →
                plan ← planner.optimize(planner.plan(bound)?)?   // identity in MS4
                exec ← planner.create_executor(&plan)?
                push drive_executor(exec, stmt_kind)?            // open → next* → close
            CreateIndex | Analyze | Explain | Begin | Commit | Rollback | Vacuum →
                return Err(Error::Execution("not implemented until a later milestone"))

Inside drive_executor, always run open(), drain next() to None, and call close().1 For SELECT, collect row.values with exec.schema().clone(). For DML (Insert, Update, Delete), extract the single [Value::Integer(n)] row emitted by the operator into QueryResult::affected and return an empty schema and empty rows.

2. Why Projection sits above Sort and Limit

Look at SELECT id FROM users ORDER BY age DESC in the provided suite: age is not in the projection list, yet ORDER BY sorts on BoundExpr::Column { table: 0, column: 2 }. If Projection ran below Sort, each row would shrink to [id] and Sort would panic indexing column 2. Build every SELECT bottom-up in the order documented in crates/exec/src/lib.rs: Scan (or 1-row empty Values if FROM is empty) → Filter? → Sort? → Limit? → Projection. Sort then sees all base-table columns, and Projection evaluates expressions only on the rows that survive Limit. For table-less queries like SELECT 1 + 2 * 3, plant LogicalPlan::Values { rows: vec![vec![]], schema: Schema::default() } under Projection so Projection pulls one dummy row, evaluates its constants, and stops.

3. Composable RecordId flow & the Halloween guard on HeapFile

Modeled on BusTub's (Tuple, RID) iterator output,2 ExecRow attaches rid: Option<RecordId> alongside SQL values. SeqScan emits ExecRow::with_rid(values, rid), Filter forwards row.rid untouched, and Update / Delete pull victims from any child Box<dyn Executor> (SeqScan or Filter(SeqScan) today; IndexScan transparently in Milestone 5) without smuggling physical addresses into SQL columns.

That clean composition exposes a classic hazard immediately — even before B+Tree indexes exist. Because HeapFile has no in-place update (variable-length TEXT can grow, and Milestone 8 MVCC needs old tuple versions preserved), Update executes out of place: heap.delete(old_rid) followed by heap.insert(TupleMeta::default(), &new_bytes). Because insert appends into a higher slot (or new tail page) ahead of a live HeapScan cursor, a streaming Update re-encounters its own writes — the Halloween problem.2 On UPDATE n SET x = x + 1 WHERE x < 100 over 95..105 (ms4_halloween_guard), streaming bumps 95 five times up to 100 (15 total updates instead of 5). The fix: inside Update::open() (and Delete::open()), drain all matching (RecordId, new_values) victims from the child first, call child.close()?, and only then mutate HeapFile.2

Expression evaluation, three-valued logic, and NULL ordering

Your evaluator — eval_expr(expr: &BoundExpr, row: &[Value]) -> Result<Value> — resolves BoundExpr::Column { table, column, .. } (in single-table MS4, table == 0 and row[column] is direct; resolving via a small table_idx → offset helper in create_executor pays off in MS6 joins) and BoundExpr::InputRef { index, .. } (row[index]).

1. Three-Valued Logic (3VL) truth table

In SQL, NULL means “unknown”, not false.5 Keep Value::Null intact through every expression and convert to pass/drop only inside Filter (matches!(val, Value::Boolean(true))):

2. Comparisons, arithmetic, widening, and CAST

  • Comparisons: always use lhs.sql_cmp(&rhs) from ferricdb-common — never Rust's derived == (where Value::Null == Value::Null is true!). Map None to Value::Null and Some(ord) to Value::Boolean.
  • Arithmetic & division by zero: any Value::Null operand yields Value::Null (including 1 / NULL). Dividing or taking remainder by zero (0 or 0.0) — or overflowing i64::MIN / -1 — returns Err(Error::Execution(...)), never a panic.
  • Implicit Integer → Float widening: widen mixed (Integer, Float) arithmetic operands to f64, and in Insert / Update coerce Value::Integer(i) to Value::Float(i as f64) whenever the target column's type is DataType::Float.
  • CAST(expr AS type) rules:

3. ORDER BY and NULL ordering

Whereas PostgreSQL defaults to NULLS LAST for ASC and NULLS FIRST for DESC,6 FerricDB orders NULLs LAST in both ASC and DESC (matching ms4_order_by_limit_and_null_ordering, ms4_crud.slt, and Milestone 6's ExternalSorter). Handle NULL before reversing for desc:

cmp_sort_key(a, b, desc):
    match (a, b):
        (Null, Null) → Equal
        (Null, _)    → Greater      // NULL always sorts LAST, even under DESC
        (_, Null)    → Less
        (x, y)       →
            ord ← x.sql_cmp(y).unwrap_or(Equal)
            if desc { ord.reverse() } else { ord }

For multi-key ORDER BY, walk keys in order and return the first non-Equal comparison. Pre-evaluate sort keys once per row inside Sort::open() so expression errors propagate cleanly before sorting.

    while let Some(row) = child.next()?:

Common pitfalls

Pitfall — collapsing NULL to false early (or using Rust ==)

Symptom: WHERE NOT (age > 30) returns rows with NULL age, or WHERE age = NULL matches them. Fix: use Value::sql_cmp for every comparison, preserve Value::Null through the 3VL truth table, and coerce to bool only at Filter.5

Pitfall — putting Projection below Sort

Symptom: SELECT id FROM users ORDER BY age DESC panics with index out of bounds. Fix: build SELECT bottom-up as Scan → Filter? → Sort? → Limit? → Projection so Sort still sees unprojected base-table columns.

Pitfall — streaming Update on HeapFile (Halloween bug)

Symptom: ms4_halloween_guard reports affected == 15 and bumps 95..99 all the way to 100. Fix: materialize all (RecordId, new_values) victims in Update::open() and call child.close()? before any HeapFile write.2

Pitfall — non-empty QueryResult::schema on DML

Symptom: ms4_slt_crud fails on INSERT / UPDATE expecting statement ok. Fix: unpack the DML executor's single [Value::Integer(n)] row into QueryResult::affected and return empty Schema::default() and empty rows.3

Pitfall — reversing NULL ordering under DESC

Symptom: ORDER BY age DESC puts NULL first ([3,4,1,2]). Fix: return Greater / Less for NULL before applying if desc { ord.reverse() }.

Pitfall — schema lies, streaming sorts, or divide-by-zero panics

Symptom: downstream index panics, interleaved multi-page ORDER BY output, or a panic on SELECT 1 / 0. Fix: return plan.schema from Projection::schema(), drain the entire child in Sort::open(),1 and return Err(Error::Execution) on zero divisors.
