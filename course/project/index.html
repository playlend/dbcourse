What you are building

FerricDB is a Postgres-flavored relational database: heap tables made of 8 KB slotted pages, a buffer pool that owns all I/O, a hand-written SQL front-end, a cost-aware planner, a Volcano-style executor, MVCC snapshot isolation with tuple-level xmin/xmax versioning modeled on PostgreSQL's,3 ARIES-style write-ahead logging and recovery, and finally the PostgreSQL frontend/backend wire protocol, so real clients — psql, drivers, GUI tools — connect to your server without knowing it isn't Postgres.4

The project follows the model of CMU 15-445, where each lecture block maps onto a project that extends one educational system (BusTub) — buffer pool, then B+Tree, then executors, then concurrency control — so every concept is applied to code you already own.1 FerricDB milestones are cumulative in the same way: nothing is thrown away, and each layer is exercised by everything built above it. The concept modules and milestones interleave along the recommended path; each milestone page opens with the module you should have read first.

Why build instead of just read?

Database internals are full of designs that sound obvious until you hold the invariants yourself: why eviction must respect pin counts, why a leaf split copies its separator key up while an internal split moves it, why recovery must re-apply history it is about to undo. The milestones are sized so the tests catch you exactly where those designs bite.

The architecture

This is the whole system. Every box is clickable and links to the concept module that teaches it; the milestone pages show this same diagram with the parts you have built lit up.

Reading the diagram bottom-up gives the build order: storage and the disk manager first (MS1), the buffer pool in front of them (MS2), then the SQL front-end and catalog (MS3), the planner and executor (MS4), the B+Tree beside the heap (MS5), richer operators (MS6), the optimizer (MS7), then the cross-cutting services: MVCC (MS8), WAL and recovery (MS9), and the wire protocol on top (MS10).

Ground rules

  • Core algorithms by hand. Slotted pages, the buffer pool and its replacement policy, the B+Tree, the parser, the executor operators, MVCC visibility, and the WAL/recovery machinery are the learning content — you implement them yourself.
  • Allowed helper crates (already wired in the workspace): bytes, thiserror, tempfile (ferricdb binary temp DBs and dev tests), criterion (dev, benchmarks), rustyline (REPL), tokio (server crate and ferricdb --serve entrypoint), plus rand (dev, fixed-seed property/fuzz tests) and sqllogictest (dev, harness only). Do not add other dependencies.
  • One escape hatch: sqlparser (sqlparser-rs) is permitted solely as the Milestone 3 escape hatch if parsing is not where you want to spend your time — it is not a default workspace dependency. Module 5 teaches you to write the parser by hand, and the hand-written path is the recommended one. The AST stays the same either way.
  • Each milestone page gives you: learning objectives, required reading, the public Rust API to implement (quoted from the workspace's API contract), step-by-step guidance with hints — never solutions — a test plan, common pitfalls, and a definition of done.
  • Don't copy reference code. The cited projects (BusTub, toyDB, Mini-LSM) are for reading. BusTub's course policy forbids copying solution code; toyDB and Mini-LSM are Apache-2.0 and require attribution if you adapt anything.1

How testing works

The workspace ships with the full test suites already written. Tests for future milestones are marked #[ignore = "milestone N"] and named with an msN_ prefix, so cargo test is green from day one and each milestone has a concrete finish line:

# see everything that is waiting for you
cargo test --workspace -- --list --ignored

# work on milestone 2
cargo test -p ferricdb-buffer -- --include-ignored ms2_

# sqllogictest suites (from Milestone 4 onward)
cargo test -p ferricdb -- --include-ignored ms4_slt_crud
cargo test -p ferricdb -- --include-ignored ms6_slt_joins_agg_sort
cargo test -p ferricdb -- --include-ignored slt_all

From Milestone 4 onward — once SQL executes end to end — correctness is also checked by sqllogictest files: scripted SQL sessions with expected results, run by the sqllogictest crate (the Rust runner maintained by the RisingLight project and used by several Rust database projects).2 The files live in crates/ferricdb/tests/slt/ and are driven by the ms4_slt_crud, ms6_slt_joins_agg_sort, and slt_all harness tests. The same SQL workload that runs in-process in MS4–MS6 runs over a real psql session in MS10 — the strongest possible statement that your database behaves like a database.

The workspace

The Cargo workspace lives at course/ferricdb/. Public APIs are declared as stubs with documentation — the shape is given, the bodies are yours. One crate is provided fully implemented: common, the shared plumbing (values, schemas, error types), because copying type definitions teaches nothing.

CrateWhat you build thereMilestoneModule
crates/commonprovided — values, schema, errors——
crates/storagepages, slotted heap pages, tuple format, disk manager, heap filesMS1M02
crates/bufferbuffer pool manager, CLOCK / LRU-K replacers, page guardsMS2M03
crates/sqllexer, recursive-descent + Pratt parser, ASTMS3M05
crates/catalogself-hosting system catalog, table/index metadata, statisticsMS3, MS5, MS7M05
crates/execbinder, planner, Volcano operators, joins, external sort, optimizerMS3–MS8M06–M08
crates/indexdisk-resident B+Tree with splits and range iteratorsMS5M04
crates/txntransaction manager, snapshots, MVCC visibility, conflict detectionMS8M09
crates/walwrite-ahead log, checkpoints, ARIES recoveryMS9M10
crates/serverPostgreSQL wire protocol codec + tokio serverMS10M11
crates/ferricdbthe binary: REPL, flags, sqllogictest harnessMS0M00

The crate dependency graph is acyclic and mirrors the architecture diagram: common sits at the bottom; storage → buffer → wal form the page and logging spine (wal implements buffer's LogFlusher trait so the WAL rule is enforced without a cycle); catalog and index depend only on common and storage (through the PageStore trait, so either DiskManager or BufferPoolManager plugs in); sql, txn, catalog, index, and storage feed exec; server depends on common, exec, catalog, and txn; and the ferricdb binary wires everything together.

Milestones at a glance

Milestone 0

Skeleton, REPL, Test Harness

Tour the workspace, implement the rustyline REPL and meta-commands, wire CI.

 Milestone 1

Pages, Tuples, Heap Storage

8 KB slotted pages, tuple serialization, DiskManager, HeapFile.

 Milestone 2

Buffer Pool Manager

Frames, page table, pins, CLOCK eviction; all I/O goes through the pool from here.

 Milestone 3

SQL Front-End

Lexer, recursive-descent + Pratt parser, AST, self-hosting catalog, binder.

 Milestone 4

Planner & Volcano Executor

Iterator operators and expression evaluation — SQL runs end to end.

 Milestone 5

B+Tree Index

Disk-resident B+Tree with splits and range scans; IndexScan in the planner.

 Milestone 6

Joins, Aggregation, External Sort

NestedLoopJoin, HashJoin, GROUP BY aggregates, spill-to-disk sorting.

 Milestone 7

Query Optimization

Rewrites, ANALYZE statistics, a cost model, join ordering, EXPLAIN.

 Milestone 8

Transactions & MVCC

Snapshots, visibility rules, first-committer-wins, VACUUM.

 Milestone 9

WAL & ARIES Recovery

LSNs, CLRs, checkpoints, crash-injection testing — no committed row ever lost.

 Milestone 10

Wire Protocol Server

A tokio server speaking the PG protocol; psql connects on port 5433.

Stretch milestones

Optional, lower-detail specs for after the core is done — each takes one production idea from Module 12 and grafts it onto your finished system.

Stretch S1

Lock Manager & Row Locks

SELECT FOR UPDATE, wait queues, deadlock handling.

 Stretch S2

Serializable Isolation (SSI)

Close the write-skew hole your MS8 tests document.

 Stretch S3

LSM Storage Engine

Swap the heap for an LSM tree, following Mini-LSM.

 Stretch S4

Raft Replication

Replicate FerricDB across a local cluster, following toyDB.
