Stretch pages are deliberately lower-detail: this one maps an existing excellent course onto FerricDB rather than re-teaching it.

The goal

Module 12 surveyed the LSM design: writes buffered in a memtable, flushed as immutable SST files, merged by background compaction.1 This stretch builds one — by following Mini-LSM, a structured Rust course of week-long parts (seven ~2–3 hour chapters each, with starter code, tests, and solution checkpoints)1 — and then integrates it: FerricDB tables gain a storage option, CREATE TABLE t (…) WITH (storage = lsm), running CRUD through the LSM engine while heap tables continue unchanged. Mini-LSM is Apache-2.0: attribute anything you adapt.1

Integration plan

  1. Extract the storage-engine boundary. Write down what the executor actually needs from HeapFile: insert → address, get by address, set_meta, delete, full scan. Define a TableStorage trait with exactly that surface — no more — and implement it for the existing heap first (a pure refactor; every test stays green).
  2. Key design. An LSM table is a sorted map, so it needs a key: use the primary key (encoded in an order-preserving format) rather than RecordId. To preserve Milestone 8 MVCC snapshot isolation across concurrent UPDATEs, do not overwrite old versions under the bare primary key — encode (encoded PK, xmin) as the LSM key (or keep a version chain in the value) so every committed version stays readable to older snapshots until VACUUM.
  3. Implement LsmTable: TableStorage over your Mini-LSM engine: insert / update = put a new version under (encoded PK, xmin) (and stamp xmax on the prior version), delete = stamp TupleMeta.xmax on the live version (never emit a raw LSM tombstone on DELETE — let VACUUM emit real tombstones once the deleter is below oldest_visible_xid(); see the pitfall below), scan = range iterator filtering each version through Snapshot::is_visible.
  4. Catalog + DDL. A storage flag on TableInfo, parsed from the WITH clause; the planner picks the scan implementation by table storage.
  5. Reuse the behavioral suites. Run the ms1_ heap-semantics tests (where they apply) and the full slt_all suite against LSM-backed tables — same queries, different engine, same answers.

Pitfalls

RecordId stability

Compaction moves data; there is no stable (page, slot) address. Both secondary indexes and Milestone 8's TransactionManager::record_write(txn, rid) assume stable tuple addresses: for LSM-backed tables, generalize write-set keys to an enum (RowKey::Heap(RecordId) | RowKey::Lsm(Oid, Vec<u8>)) and store primary keys instead of RecordIds in secondary indexes — a real design fork from your heap + B+Tree stack, worth a paragraph in your notes even if you skip secondary indexes here.

Two WALs, one truth

Mini-LSM has its own WAL; FerricDB has Milestone 9's. Running both means double writes and ambiguous recovery ownership. Pick one owner per table type and document the recovery story for LSM tables explicitly (simplest: LSM tables trust the LSM WAL; FerricDB's ARIES machinery covers heap tables and the catalog).

MVCC versions vs LSM tombstones

An LSM tombstone means "key deleted"; your MVCC xmax means "deleted for snapshots after T". Naively writing LSM tombstones on DELETE breaks snapshot reads. Keep MVCC metadata in the value and let VACUUM (not DELETE) emit the real tombstones.

Definition of done

  • Mini-LSM's own tests pass through its compaction weeks.
  • An LSM-backed FerricDB table round-trips the full CRUD sqllogictest suite and survives restart.
  • Under sustained writes, compaction demonstrably reduces SST count while queries keep answering correctly.
  • A short design note records the key encoding, the WAL ownership decision, and the MVCC/tombstone interaction.
