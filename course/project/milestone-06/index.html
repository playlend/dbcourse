Learning objectives

  • Implement NestedLoopJoin, a join that evaluates an arbitrary ON predicate with correct SQL three-valued logic — including non-equality predicates and predicate-free cross joins.
  • Implement HashJoin with a build phase and a probe phase over equi-join keys, and explain why rows with NULL keys can never join.49
  • Implement hash aggregation for GROUP BY with COUNT/SUM/AVG/MIN/MAX, matching SQL NULL semantics for inputs and for empty inputs.8
  • Implement the ExternalSorter: sorted-run generation inside a fixed budget of buffer pages, runs spilled to temporary pages through the buffer pool, and a k-way merge — and predict its I/O with the pass-count formula.5
  • Extend the parser, binder, and planner to accept JOIN … ON, GROUP BY, and aggregate function calls (the AST types already exist).
  • State what a global aggregate returns over zero rows, and why grouping treats two NULL keys as one group while joining treats them as never equal.89

Semantic notes (binding decisions — read carefully)

  • Join output schema. Left child’s columns first, then the right child’s, in child order. This is a course choice; the important part is that you pick it once and the binder, planner, and executors all agree, because bound column references are positional (table index, column index) pairs. Duplicate bare names (customer.id and orders.id) are legal in the combined schema — they are disambiguated by qualifier at bind time, and an unqualified ambiguous name is a bind error.
  • HashJoin build/probe convention and keys. Per crates/exec/src/plan.rs, HashJoin builds its hash table on the left input using left_keys and probes with the right input using right_keys (output rows remain left ++ right). left_keys[i] pairs with right_keys[i]; the planner extracts these pairs from equality conjuncts of the ON clause. Rows whose key evaluates to NULL on either side never appear in the output, because = with a NULL operand yields unknown, not true.9
  • AggExpr and COUNT(*). COUNT(*) parses as Expr::Function("count", vec![]) (lowercase function name) and binds to AggExpr { func: AggFunc::Count, arg: None }; all other aggregates carry arg: Some(BoundExpr).
  • Aggregate output schema and BoundExpr::InputRef. LogicalPlan::Aggregate emits [group_by_0, …, group_by_{g-1}, agg_0, …, agg_{a-1}] — group-by columns first (in GROUP BY order), then one column per aggregate. Ancestor Projection and Sort nodes reference those output slots via BoundExpr::InputRef { index, data_type } (for example, aggregate k sits at index = g + k). With an empty group_by, the operator computes one global group.
  • Implicit Integer → Float widening. As documented on Binder::bind, an Integer expression widens implicitly to Float (e.g. by inserting BoundExpr::Cast(..., DataType::Float) during binding, or numeric promotion during evaluation) when inserted into or assigned to a Float column (such as INSERT INTO orders ... VALUES (..., 80, ...) for o_total FLOAT) or combined with a Float in arithmetic or comparisons (such as WHERE o_total > 100). Both ms6_joins_agg_sort.slt and crates/exec/tests/exec.rs rely on this widening.
  • Grouping vs. joining on NULL. Grouping compares keys by distinctness, not by =: two NULLs are “not distinct” from each other,9 so all rows with a NULL group key collapse into a single group — the opposite of join keys, which use = and never match.
  • ORDER BY and NULL (course convention). NULLs order LAST in both ASC and DESC (consistent across Milestone 4's ms4_order_by_limit_and_null_ordering, ms4_crud.slt, crates/exec/src/plan.rs, and crates/exec/src/sort.rs). Contrast this with PostgreSQL's default, which treats NULL as larger than every non-null value (NULLS LAST for ASC, NULLS FIRST for DESC).10 We do not implement explicit NULLS FIRST/LAST syntax; placing NULL strictly after every non-null value regardless of direction turns sql_cmp's Option<Ordering> into the total order a sort needs.
  • Memory budget. ExecContext carries a memory budget for sort/hash, denominated in buffer pages (memory_pages × PAGE_SIZE bytes, with PAGE_SIZE = 8192 from ferricdb-common). It is the course analog of PostgreSQL’s work_mem, which caps hash tables and in-memory sorts.4 In this milestone only the sort path is required to respect it by spilling; hash join and hash aggregation may assume their build side fits (spilling hash operators is a documented stretch — see the merge-join note in the guidance).
  • MergeJoin is optional. The public LogicalPlan enum has no merge-join variant, so if you build one, keep it crate-private. It is a natural extension once ExternalSorter exists.

Step-by-step guidance

This is the largest executor milestone, but it decomposes cleanly: front-end first, then joins, then aggregation, then sort. Each stage is independently testable, and nothing here touches storage formats — the layers below you are stable. Expect the external sorter to take as long as the other three stages combined; that is normal.

  1. Grow the grammar: JOIN … ON. Extend the FROM-clause parser so a table reference is a base table (with optional alias) followed by zero or more join clauses, folded left-associatively into nested TableRef::Join values. CROSS JOIN takes no ON; plain JOIN requires one. A comma-separated FROM list stays as multiple entries in Select::from — the binder treats those as an implicit cross-join chain (course choice). Check yourself in the REPL with .ast SELECT * FROM a JOIN b ON a.x = b.y JOIN c ON b.z = c.z: the tree should nest to the left.
  2. Grow the grammar: GROUP BY and aggregate calls. GROUP BY parses a comma-separated expression list between WHERE and ORDER BY. In the Pratt expression parser, an identifier followed by ( becomes Expr::Function(name, args) (lowercased). Parse COUNT(*) as Expr::Function("count".into(), vec![]) — the course convention documented in api-spec.md.
  3. Bind joins and implicit widening. Walk the TableRef tree and build the combined scope (each base table in FROM gets an incrementing table_idx: 0, 1, …). Resolve qualified names through the alias or table name; reject unqualified names that match more than one column with Error::Bind. Bind the ON expression into BoundExpr::Column { table: table_idx, column: col_idx, data_type } where col_idx stays the column's ordinal within its own table's schema — do not add the left child's column count inside the binder! Instead, Planner::create_executor resolves each (table_idx, col_idx) to a flat slot against each operator's child layout (left ++ right for NestedLoopJoin and operators above a join, and left / right individually for HashJoin's build/probe key expressions; this also keeps Milestone 7 join reordering and predicate pushdown working cleanly). Also make sure your binder/evaluator performs implicit Integer → Float widening in INSERT, UPDATE, arithmetic, and comparisons (exercised by ms6_joins_agg_sort.slt and exec.rs).
  4. Bind aggregates. Recognize count/sum/avg/min/max case-insensitively in Expr::Function (binding Function("count", []) to AggExpr { func: AggFunc::Count, arg: None }). Enforce three rules: aggregates cannot nest; aggregates may not appear in WHERE (that is what HAVING would be for — FerricDB doesn’t have it); and every projection expression must either be an aggregate or appear in GROUP BY. Rewrite projection and ORDER BY references to grouped keys and aggregates into BoundExpr::InputRef { index, data_type } pointing into the [group_by…, aggregates…] row emitted by LogicalPlan::Aggregate. Emitting clear Error::Bind messages now saves you slt-debugging later.
  5. NestedLoopJoin executor. On open(), open both children and materialize the inner (right) side into a Vec of rows — the same trick PostgreSQL uses in its materialized nested loop, where the inner table is scanned once and written to work_mem or a temporary file2 (materializing to memory is fine here; the provided tests keep nested-loop inputs small). next() holds the current outer row and an index into the inner vector; concatenate the two rows, evaluate the predicate, and emit only when it is true — a NULL predicate result drops the pair, exactly like WHERE.9 With on: None you have a cross join for free. This operator is your correctness baseline: it must work for any predicate, e.g. ON a.lo <= b.x AND b.x < a.hi.
  6. HashJoin executor. Two phases, matching PostgreSQL’s in-memory hash join: the build phase inserts every build-side tuple into the hash table, then the probe phase streams the other side and compares each tuple against the matching bucket.4 Following crates/exec/src/plan.rs, build on the left child (left_keys) and probe with the right child (right_keys) — Milestone 7’s optimizer puts the smaller input on the left, which is what you want when loading a build side into memory:6 
    -- build phase                                (interdb §3.5.3, CS186 note 9)
for each build-side (left) row:
    k := evaluate left_keys
    if any value in k is NULL: skip row        -- NULL never joins
    table[hash(k)].push(row)

-- probe phase
for each probe-side (right) row:
    k := evaluate right_keys
    if any value in k is NULL: skip row
    for each build row in table[hash(k)] whose keys equal k:
        emit left row ++ right row
    Two Rust snags to anticipate. First, Value is not Eq + Hash (it contains f64), so a HashMap<Vec<Value>, …> won’t compile; one workable approach is to serialize the evaluated key tuple to bytes and key the map on those — you have already skipped NULLs, and the encodings of Integer/Boolean/Text are canonical (if you allow Float keys, decide what to do about 0.0 vs -0.0 and write it down). Second, buckets must hold lists of rows: duplicate keys are normal, and each probe row joins with every match.
  7. Hash aggregation. One executor handles both grouped and global aggregation. Drain the child in open() into a map from group key (empty key when group_by is empty) to one accumulator per AggExpr — hashing groups equal keys together without any sort, which is exactly why databases hash for GROUP BY.7 Accumulators are small state machines: COUNT keeps a count; SUM a running total; AVG keeps sum and count and divides only when emitting; MIN/MAX keep the best value via sql_cmp. Feed an accumulator only non-null inputs (COUNT(*) excepted) — aggregates ignore nulls.8 Then the empty-input rule: with GROUP BY and zero input rows, emit zero groups; without GROUP BY, emit exactly one row — COUNT is 0, everything else is NULL.8
  8. ExternalSorter: run generation. Follow the CS186 structure: “pass 0” fills your entire memory budget with input, sorts it in place, and writes one sorted run, giving ⌈N/B⌉ runs from N pages of input with a budget of B pages.5 
    -- run generation ("pass 0"), B = memory_pages       (CS186 note 8)
while input has rows:
    read rows until the budget (B pages of tuple bytes) is full
    sort them in memory
    write the run to freshly allocated pages       -- the final partial run too!

-- merge passes: k = max(2, B - 1) so run count always shrinks
while more than one run remains:
    take up to k runs; open one cursor per run (1 page each)
    repeatedly move the smallest head tuple to the output page
    flush the output page as it fills              -- the B-th page (for B >= 3)
    Account for the budget in bytes of serialized tuples against B × PAGE_SIZE (using ferricdb_storage::tuple::serialize with the schema passed to ExternalSorter::new), not in row counts — rows vary in width. Track how many runs have been written to disk so spilled_runs() returns 0 when the whole input fits in one batch and a positive count whenever spilling occurred. For the run pages themselves, you already own a fine format: a run is a chain of slotted pages (HeapPage) allocated through the PageStore, so runs flow through the buffer pool like any other page (PostgreSQL spills sort data to temporary files instead;3 using ordinary pages is a course simplification — whether you reclaim them afterwards is up to you, the tests don’t check). Sort with a comparator built from sql_cmp, the per-key desc flags, and FerricDB’s NULLs-last in both ASC and DESC rule — that combination is total, so sort_by and BinaryHeap are both happy.
  9. ExternalSorter: k-way merge. Open a cursor per run, each holding one page in memory; repeatedly emit the minimum (a BinaryHeap<Reverse<…>> keyed by your comparator works well); when a cursor exhausts its page, load that run’s next page.5 Set the merge fan-in to k = max(2, B − 1) (clamped to at least 2 so even an artificially tiny budget cannot infinite-loop with fan-in 1; textbook (B − 1)-way merging requires memory_pages >= 3, and ms6_external_sort_under_tiny_budget uses memory_pages = 4 for a 3-way merge). If pass 0 produced more than k runs, merge in multiple passes: total passes are 1 + ⌈logk⌈N/B⌉⌉ and total I/O is 2N × that,5 which the tiny-budget test will make you feel. Figure 3 walks through B = 4, N = 24.
  10. Wire it into the planner and Sort executor. Fold the bound FROM tree into a left-deep join chain. For each ON clause, split top-level ANDs into conjuncts; if every conjunct is left-column = right-column (one side each), plan a HashJoin with the paired key lists; otherwise plan a NestedLoopJoin (equality conjuncts can still become hash keys with the leftovers as a Filter on top — a nice refinement, not required). Plan Aggregate whenever group_by is non-empty or any aggregate appears in the projection. The Sort executor buffers its child while the accumulated tuple bytes fit the budget and sorts in memory; the moment the budget overflows, hand everything to ExternalSorter. The provided tests compare both paths on the same input — they must agree exactly. Finally, run the slt file (small customer and orders tables, TPC-H-flavored queries) end to end.
Optional stretch: merge join and spilling hash operators

With ExternalSorter done, a merge join is close: sort both inputs on the join keys and advance two cursors. It handles only equi-joins,3 and duplicate keys force you to mark the inner position and backtrack to it for the next outer row.6 Similarly, a build side that overflows the budget can be partitioned to temp pages and joined batch by batch — that is Grace hash join,6 and PostgreSQL’s production variant (hybrid hash join with a skew batch) keeps the hottest keys in memory.4 Both are excellent extensions after the milestone is green; neither is graded.

Common pitfalls

Pitfall — NULL join keys “match” in your hash table

Why: in SQL, NULL = NULL yields unknown — “it is not known whether two unknown values are equal”9 — but a hash map you key on serialized values will happily equate two NULL encodings. Build and probe must skip (or segregate) NULL keys explicitly. Symptom: extra output rows pairing null-keyed rows with each other; the slt queries over nullable columns fail while non-null fixtures pass, and hash-join results disagree with nested-loop results on the same data.

Pitfall — AVG on integers, computed as an integer

Why: summing into an i64 and dividing with integer division truncates (AVG of 1 and 2 becomes 1); updating a running f64 mean row-by-row accumulates error instead. Keep sum and count, divide once at emit time, and return the documented result type — Float, a course choice where PostgreSQL returns numeric for integer inputs.8 Symptom: off-by-a-fraction aggregate values; slt expected-output diffs on any AVG over an integer column that doesn’t divide evenly.

Pitfall — aggregates over zero rows

Why: with no input and no GROUP BY, SQL still returns one row: COUNT is 0, while SUM/AVG/MIN/MAX are NULL — “sum of no rows returns null, not zero as one might expect.”8 With GROUP BY, zero input rows mean zero output groups. A map-based implementation naturally emits nothing for an empty input — you must special-case the global aggregate. Symptom: SELECT COUNT(*) FROM empty_table returns no rows instead of 0, or returns SUM = 0 instead of NULL.

Pitfall — the final run never gets spilled

Why: run generation spills whenever the buffer fills, so the loop’s natural shape leaves the last, partially-filled buffer in memory at end-of-input. Either spill it as a (shorter) run like the others, or treat it as an in-memory run in the merge — but if your merge phase only enumerates on-disk runs, those buffered rows silently vanish. Symptom: sorted output is missing up to one budget’s worth of rows — always the ones that would have formed the last run; row-count assertions fail under the tiny-budget test but pass when everything fits in memory.

Pitfall — budgeting in tuples instead of pages

Why: the budget is memory_pages buffer pages — a byte limit of B × PAGE_SIZE — because that is the unit the buffer pool actually manages, and it is how the sort cost model counts (N and B are both in pages).5 “1,000 rows” is meaningless when a Text column can be 3 bytes or 3 KB wide. Track the serialized size of what you hold. Symptom: memory use explodes on wide rows (or you spill absurdly early on narrow ones), and the tiny-budget test produces a different number of runs than the pass-count math predicts.

Pitfall — join output schema: ordering, table_idx resolution, and duplicate names

Why: Binder keeps every column reference as (table_idx, col_idx) (each table's own schema ordinal), and Planner::create_executor resolves those pairs into flat row offsets against each operator's input layout. If a join executor concatenates right-then-left while create_executor assumes left-then-right — or if you offset right-side columns in the binder instead of at lowering time, breaking HashJoin::right_keys and Milestone 7 join reordering — every reference to the right table reads the wrong slot. And both children may legitimately contain a column named id; the combined schema keeps both, disambiguated only by qualifier at bind time. Symptom: out-of-bounds panics in HashJoin key evaluation, values from the wrong table in query results, type errors deep in expression evaluation, or projections that “work” on SELECT * but break the moment column order changes.

  • NestedLoopJoin produces correct results for non-equality ON predicates and for cross joins; the planner routes pure equi-join ON clauses to HashJoin (build left, probe right) and everything else to NestedLoopJoin.
  • Aggregates ignore NULL inputs, COUNT(*) counts rows, and a global aggregate over zero rows returns one row of COUNT = 0 and NULLs.8
  • ExternalSorter never holds more than memory_pages pages’ worth of tuple bytes, spills every run — including the final partial one — through the PageStore, and merges up to k = max(2, B − 1) runs per pass.
  • Earlier ms1_–ms5_ suites (via --include-ignored) and the baseline cargo test --workspace stay green: no regressions in Milestones 0–5.
