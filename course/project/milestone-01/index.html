Milestone 1 · Pages, Tuples, and Heap Storage

Build the bottom of the system: fixed-size 8 KB pages, slotted heap pages with tombstone deletes, tuple serialization with a null bitmap, a page-granular disk manager, and a multi-page heap file with a scan iterator.

Everything FerricDB will ever do — parse SQL, plan joins, commit transactions, recover from a crash — eventually turns into reading and writing bytes inside 8 KB pages. In this milestone you build that layer: the code you write here is exercised by every later milestone, unmodified. It is mostly careful byte accounting rather than clever algorithms, and that is exactly why it deserves care: an off-by-two in a page header is invisible today and a corrupted B+Tree in Milestone 5. Budget a solid weekend. The provided tests are thorough, and once they are green you will trust this layer for the rest of the course.

Learning objectives

  • Explain the slotted-page layout — header, line-pointer array growing forward, tuple data growing backward, free space in between — and why the line-pointer indirection makes tuple addresses stable.14
  • Implement a fixed-size Page type with a 16-byte reserved header (pageLSN + type tag) and safe, alignment-proof byte accessors.
  • Implement HeapPage: insert, get, metadata update, and tombstone delete over a slotted page.
  • Design and implement a tuple wire format for BOOLEAN / INTEGER / FLOAT / TEXT values with a null bitmap and length-prefixed UTF-8 text.
  • Implement page-granular file I/O (DiskManager) and a multi-page HeapFile addressed by RecordId, including a full-table scan iterator.
  • Map your implementation onto PostgreSQL's page layout: pd_lsn, pd_lower/pd_upper, line pointers, and heap tuple headers.2

Required reading

  • M02 · Storage: Files, Pages, Tuples — the concept module for this milestone. Read it first; this page assumes it.
  • Hironobu Suzuki, The Internals of PostgreSQL, Chapter 1, §1.3 “Internal Layout of a Heap Table File” and §1.4 “Writing and Reading Tuples” — line pointers, the hole, how tuples are written and read.17
  • PostgreSQL documentation, “Database Page Layout” — the exact page header fields and the heap tuple header your design is a simplification of.2 Skim the parent chapter “Database Physical Storage” for context.3
  • Berkeley CS186 notes, “Disks and Files” — heap files (linked list vs. page directory) and the slotted-page layout for variable-length records.4

Where this fits

Note the seam deliberately built into this milestone: HeapFile talks to a PageStore trait, not to DiskManager directly. In Milestone 2 the buffer pool implements the same trait and slots in between — with zero changes to the heap code you write now.

Provided: crates/common

The ferricdb-common crate ships complete in the starter workspace — you do not implement anything in it, but read it before you start. The pieces that matter for this milestone:

// crates/common — provided (excerpt; FrameId, Oid, and Error are elided here)

pub const PAGE_SIZE: usize = 8192;          // matches PostgreSQL default block size
pub type PageId = u32;
pub const INVALID_PAGE_ID: PageId = u32::MAX;
pub type TxnId = u64;                        // 0 = frozen / none
pub type Lsn = u64;                          // 0 = no LSN yet; real WAL records >= 1

#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub enum DataType { Boolean, Integer, Float, Text }

#[derive(Clone, PartialEq, Debug)]
pub enum Value { Null, Boolean(bool), Integer(i64), Float(f64), Text(String) }
impl Value {
    pub fn data_type(&self) -> Option<DataType>;   // None for Null
    /// SQL comparison: returns None when either side is NULL (three-valued logic).
    pub fn sql_cmp(&self, other: &Value) -> Option<std::cmp::Ordering>;
}

#[derive(Clone, PartialEq, Eq, Debug)]
pub struct Column { pub name: String, pub data_type: DataType, pub nullable: bool }
#[derive(Clone, PartialEq, Eq, Debug, Default)]
pub struct Schema { pub columns: Vec<Column> }
impl Schema {
    pub fn index_of(&self, name: &str) -> Option<usize>;
    pub fn column(&self, i: usize) -> &Column;
}

/// Tuple version metadata, present in every stored tuple header from
/// Milestone 1 (written as 0 until Milestone 8; xmin == 0 = frozen/bootstrap).
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
pub struct TupleMeta { pub xmin: TxnId, pub xmax: TxnId }

/// Physical tuple address: (page, slot) — Postgres calls this the ctid.
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash, Debug)]
pub struct RecordId { pub page_id: PageId, pub slot: u16 }

Semantic notes on the provided types:

  • PAGE_SIZE = 8192 is a course choice, matching PostgreSQL's default block size of 8192 bytes.12
  • TupleMeta mirrors the t_xmin/t_xmax insert- and delete-transaction stamps in PostgreSQL's heap tuple header,2 except we use u64 transaction ids (a course choice: Postgres uses 32-bit XIDs and has to manage wraparound; 64-bit IDs avoid wraparound altogether). You store and return it faithfully from Milestone 1 but always write zeros until Milestone 8.
  • RecordId is FerricDB's tuple identifier — the analog of a Postgres TID, which is a (block number, offset number) pair used by indexes to locate tuples.1
  • common::Error already defines the variants you need here: Io (with #[from] std::io::Error), PageFull, InvalidPage(PageId), InvalidSlot(RecordId), and Execution(String) (used by tuple::serialize / tuple::deserialize on schema/byte mismatches), plus pub type Result<T>.

You build: crates/storage

The public surface of ferricdb-storage, quoted verbatim from course/ferricdb/docs/api-spec.md. Your implementation must match these signatures exactly — the provided tests compile against them.

pub const PAGE_TYPE_UNINIT: u32 = 0;
pub const PAGE_TYPE_HEAP: u32 = 1;
pub const PAGE_TYPE_BTREE_LEAF: u32 = 2;
pub const PAGE_TYPE_BTREE_INTERNAL: u32 = 3;

/// One 8 KB page in memory. First 16 bytes of every page are reserved:
/// pageLSN (u64) + page type tag (u32) + reserved (u32).
pub struct Page { /* [u8; PAGE_SIZE] */ }
impl Page {
    pub fn new() -> Self;
    pub fn lsn(&self) -> Lsn;
    pub fn set_lsn(&mut self, lsn: Lsn);
    pub fn page_type(&self) -> u32;
    pub fn set_page_type(&mut self, tag: u32);
    pub fn data(&self) -> &[u8; PAGE_SIZE];
    pub fn data_mut(&mut self) -> &mut [u8; PAGE_SIZE];
}

/// Read-only slotted-page view over `&Page` (use inside `PageStore::with_page`
/// so reads never dirty buffer-pool frames).
pub struct HeapPageRef<'a> { /* &'a Page */ }
impl<'a> HeapPageRef<'a> {
    pub fn is_initialized(page: &Page) -> bool;
    pub fn attach(page: &'a Page) -> Self;
    pub fn get(&self, slot: u16) -> Option<(TupleMeta, &[u8])>;
    pub fn slot_count(&self) -> u16;
    pub fn free_space(&self) -> usize;
    pub fn next_page(&self) -> PageId;
}

/// Mutable slotted-page view over `&mut Page`: 28-byte header (16B reserved +
/// 4B next_page + 2B lower + 2B upper + 2B slot_count + 2B flags),
/// line-pointer array growing forward, tuple data growing backward.
pub struct HeapPage<'a> { /* &'a mut Page */ }
impl<'a> HeapPage<'a> {
    pub fn init(page: &'a mut Page) -> Self;       // format an empty heap page
    pub fn attach(page: &'a mut Page) -> Self;     // view an already-formatted page
    pub fn as_ref(&self) -> HeapPageRef<'_>;
    pub fn insert(&mut self, meta: TupleMeta, tuple: &[u8]) -> Option<u16>; // slot
    pub fn get(&self, slot: u16) -> Option<(TupleMeta, &[u8])>;             // None if dead/absent
    pub fn set_meta(&mut self, slot: u16, meta: TupleMeta) -> Result<()>;   // MVCC updates xmin/xmax
    pub fn delete(&mut self, slot: u16) -> Result<()>;                      // mark dead (tombstone)
    pub fn slot_count(&self) -> u16;
    pub fn free_space(&self) -> usize;
    pub fn next_page(&self) -> PageId;
    pub fn set_next_page(&mut self, next: PageId);
    pub fn compact(&mut self) -> usize;                                     // MS8 VACUUM
    pub fn put_at(&mut self, slot: u16, meta: TupleMeta, tuple: &[u8]) -> Result<()>; // MS9 ARIES
}

pub mod tuple {
    /// Format: null bitmap (bit 1 = NULL), then fixed-width values in schema order;
    /// TEXT as u32 length prefix + UTF-8 bytes.
    pub fn serialize(schema: &Schema, values: &[Value]) -> Result<Vec<u8>>;
    pub fn deserialize(schema: &Schema, bytes: &[u8]) -> Result<Vec<Value>>;
}

/// Page-granular file I/O. One file holds all pages of one database.
pub struct DiskManager { /* file handle, page counter */ }
impl DiskManager {
    pub fn open(path: &std::path::Path) -> Result<Self>;
    pub fn read_page(&self, id: PageId, out: &mut Page) -> Result<()>;
    pub fn write_page(&self, id: PageId, page: &Page) -> Result<()>;
    pub fn allocate_page(&self) -> Result<PageId>;
    pub fn num_pages(&self) -> u32;
}

/// How higher layers reach pages. DiskManager implements it directly
/// (Milestone 1); BufferPoolManager supersedes it (Milestone 2).
pub trait PageStore: Send + Sync {
    // Closures return nothing so the trait stays object-safe (the whole
    // system holds Arc<dyn PageStore>); capture results through the
    // closure's environment: let mut n = 0; store.with_page(id, &mut |p| n = …)?;
    fn with_page(&self, id: PageId, f: &mut dyn FnMut(&Page)) -> Result<()>;
    fn with_page_mut(&self, id: PageId, f: &mut dyn FnMut(&mut Page)) -> Result<()>;
    fn allocate_page(&self) -> Result<PageId>;
    fn num_pages(&self) -> u32;
    fn flush_all(&self) -> Result<()>;
}

/// A linked/sequential collection of heap pages storing one table.
pub struct HeapFile { /* Arc<dyn PageStore>, first_page */ }
impl HeapFile {
    pub fn create(store: std::sync::Arc<dyn PageStore>) -> Result<Self>;
    pub fn open(store: std::sync::Arc<dyn PageStore>, first_page: PageId) -> Self;
    pub fn first_page(&self) -> PageId;
    pub fn insert(&self, meta: TupleMeta, tuple: &[u8]) -> Result<RecordId>;
    pub fn get(&self, rid: RecordId) -> Result<Option<(TupleMeta, Vec<u8>)>>;
    pub fn set_meta(&self, rid: RecordId, meta: TupleMeta) -> Result<()>;
    pub fn delete(&self, rid: RecordId) -> Result<()>;
    pub fn scan(&self) -> HeapScan;   // Iterator<Item = Result<(RecordId, TupleMeta, Vec<u8>)>>
}

Semantic requirements

  • Page is a dumb 8192-byte buffer. Its first 16 bytes are reserved in every page of every kind: pageLSN (u64), a page-type tag (u32), and a reserved u32. This is a course-chosen simplification of PostgreSQL's 24-byte PageHeaderData, whose first field is likewise the page's LSN — “next byte after last byte of WAL record for last change to this page.”2 The LSN stays 0 until Milestone 9; reserving it now means the on-disk format never has to change when logging arrives. Page::new() returns an all-zero page.
  • HeapPage and HeapPageRef are views, not containers: HeapPage<'a> borrows &'a mut Page and HeapPageRef<'a> borrows &'a Page, interpreting bytes 16.. as heap-page structure (read paths use HeapPageRef inside PageStore::with_page so reads never dirty buffer-pool frames in Milestone 2). init formats a fresh header (setting PAGE_TYPE_HEAP, next_page = INVALID_PAGE_ID, lower = 28, upper = PAGE_SIZE, slot_count = 0, flags = 0); attach trusts the existing bytes. insert returns None when the tuple plus TupleMeta and one line pointer cannot fit — the caller (HeapFile) treats that as “try another page,” which is why this returns Option rather than Err(PageFull). Slots are never renumbered and never reused: delete only marks the slot dead, and slot_count still counts dead slots. get on a dead or out-of-range slot returns None; set_meta/delete on an absent or dead slot return Err(InvalidSlot). free_space reports the maximum payload byte length of a single new tuple that currently fits (deducting both the line pointer and the 16-byte TupleMeta). Leave compact stubbed for Milestone 8 (VACUUM) and put_at stubbed for Milestone 9 (ARIES redo/undo).
  • tuple format — the parts fixed by the spec: a null bitmap first, then values in schema order; BOOLEAN as 1 byte, INTEGER as i64 (8 bytes), FLOAT as f64 (8 bytes), TEXT as a u32 byte-length prefix followed by that many UTF-8 bytes. FerricDB's course conventions (documented in crates/storage/src/lib.rs): all integers little-endian via to_le_bytes/from_le_bytes;6 NULL values occupy zero bytes in the body (only their bitmap bit); the bitmap is ⌈columns/8⌉ bytes and is always present, with bit 1 = NULL (and 0 = present). PostgreSQL, by contrast, stores its null bitmap only when the row has at least one NULL (the HEAP_HASNULL flag) and uses the opposite polarity, 1 = present (not-null).2
  • DiskManager maps PageId n to byte offset n × PAGE_SIZE in a single file. open creates the file if absent and derives num_pages from the file length on reopen. allocate_page hands out the next id (never recycles). read_page/write_page with an id ≥ num_pages() is Err(InvalidPage). All methods take &self — see the guidance for how.
  • PageStore is the layering seam. The closure-passing shape is deliberate: today the closure runs over a freshly read scratch page; in Milestone 2 it runs over a pinned buffer-pool frame, and the closure's scope becomes the pin's lifetime. with_page_mut must persist the closure's changes (for DiskManager: write the page back).
  • HeapFile chains heap pages: each heap page's header stores the next page's id (INVALID_PAGE_ID terminates). This is the linked-list heap file from the CS186 notes; the notes also describe the page-directory alternative, which finds free space faster but needs extra pages4 — the chain is a course choice for simplicity (PostgreSQL uses a separate free space map for this job3). scan visits pages in chain order and slots in slot order, skipping dead slots, and yields Result items so I/O errors surface mid-iteration.

A worked capacity example with real numbers, using the standardized 12-byte heap header after the 16-byte reserved page header (4-byte next_page, 2-byte lower, 2-byte upper, 2-byte slot_count, 2-byte flags — 28 bytes total), 4-byte line pointers, and the 16-byte TupleMeta prefix stored in front of each tuple's bytes: usable space is 8192 − 16 − 12 = 8164 bytes, and a 19-byte tuple (Figure 3) costs 4 + 16 + 19 = 39 bytes, so one page holds ⌊8164 / 39⌋ = 209 such tuples. For comparison, PostgreSQL pays a 24-byte page header, 4-byte line pointers, and a 23-byte fixed tuple header per row.2

Step-by-step guidance

Build inside-out; every step is independently testable before the next begins. Signatures come from the spec above — the steps only add design hints, never solutions.

  1. Read the stubs, then finish Page. Skim course/ferricdb/crates/storage/src/lib.rs and tests/storage.rs to see what is already provided and what is stubbed. Page { data: [u8; PAGE_SIZE] } already ships with new(), data(), data_mut(), page_type(), and set_page_type() implemented; your job on Page is implementing lsn() and set_lsn() on bytes 0..8 (little-endian u64). Write private helpers now — read_u16(buf, off), write_u32(buf, off, v), and friends — built on copy_from_slice plus from_le_bytes/to_le_bytes,6 and use them for every multi-byte access in this crate (see the alignment pitfall).
  2. Implement the standardized 28-byte heap-page header. Directly after the 16-byte reserved page header sit the 12 heap-header bytes defined in crates/storage/src/lib.rs: next_page (u32 at 16..20), lower (u16 at 20..22, initialized to 28), upper (u16 at 22..24, initialized to PAGE_SIZE), slot_count (u16 at 24..26), and flags (u16 at 26..28). This mirrors PostgreSQL's pd_lower (start of free space) and pd_upper (end of free space).2 Define each offset as a named constant at the top of the file — future-you debugging a hexdump will be grateful.
  3. Line pointers and insert. Each line pointer needs the tuple's byte offset, its length, and a dead flag. PostgreSQL bit-packs offset, flags, and length into 4 bytes;2 a u16 offset + u16 length pair is simpler and enough here (one workable dead-flag encoding: offset 0 is impossible for a real tuple, since the header occupies it). The write path, as interdb describes it for Postgres — tuple placed at the falling end, line pointer appended, lower/upper updated7 — in pseudocode: 
    insert(meta, tuple):
    need ← META_SIZE + len(tuple)            // 16-byte meta prefix + payload
    if lower + LP_SIZE + need > upper:       // must fit pointer AND data
        return None
    upper ← upper − need
    write meta at upper, tuple at upper + META_SIZE
    write line pointer {offset: upper, len: need} at lower
    lower ← lower + LP_SIZE;  slot_count ← slot_count + 1
    return slot_count − 1
    Storing the TupleMeta as a fixed 16-byte prefix in front of the tuple bytes (like Postgres's t_xmin/t_xmax living in the tuple header2) makes set_meta a trivial in-place overwrite later.
  4. HeapPageRef plus get, set_meta, delete. Implement the Copy read-only getters (slot_count, free_space, next_page) once on HeapPageRef and have HeapPage delegate to them via self.as_ref() (already provided). For get, delegate both HeapPageRef::get and HeapPage::get to one shared private helper fn page_get(page: &Page, slot: u16) -> Option<(TupleMeta, &[u8])> (calling self.as_ref().get(slot) inside HeapPage::get will not compile because HeapPageRef::get borrows the temporary HeapPageRef rather than self.page). get bounds-checks the slot, returns None for dead or out-of-range, else decodes the meta prefix and returns it with a borrow of the payload bytes. set_meta overwrites the 16-byte prefix in place. delete flips the dead flag and nothing else — no compaction, no slot-count decrement, no byte reclamation. That is the tombstone contract (see the pitfall on slot reuse).
  5. tuple::serialize / deserialize. Compute the bitmap size as ⌈columns/8⌉ (initially all zero), set bit i (bitmap[i / 8] |= 1 << (i % 8)) for each Value::Null while walking schema.columns and values in lockstep (rejecting wrong arity, type mismatches, and NULL in non-nullable columns with Err(Error::Execution)), then append each non-null value's bytes at its fixed width (TEXT: u32 byte length, then the bytes). deserialize is the mirror image: read the bitmap, then consume exactly the bytes each non-null column implies. Validate as you go — a truncated slice or length prefix running past the input is Err(Error::Execution), not a panic. Check Figure 3 by hand against your implementation: serializing (7, "naïve", NULL) must produce 0b0000_0100 in byte 0 and 19 bytes total.
  6. DiskManager. Open the file read/write, creating it if needed; recover the page count from file length / PAGE_SIZE. Keep the count in an AtomicU32 so allocate_page(&self) can bump it without &mut. For positional I/O without seeking, std::os::unix::fs::FileExt gives you read_at/write_at on &File;5 (portable fallback: a Mutex<File> around seek-then-read). Reject out-of-range ids with Err(InvalidPage), and handle the read of a freshly allocated, never-written page (simplest: have allocate_page extend the file with a zero page immediately).
  7. PageStore for DiskManager. with_page: read the page into a local scratch Page and run the closure over it. with_page_mut: read, run, then write the page back — forgetting the write-back is the classic bug here, and it makes every mutation silently vanish. flush_all maps to File::sync_data (or sync_all). Yes, this rereads 8 KB from disk on every access; that is deliberate. Milestone 2 replaces it with cached frames behind the same trait.
  8. HeapFile. create allocates and formats the first page. insert checks whether the tuple could ever fit in an empty heap page (returning Err(Error::PageFull) immediately for oversized tuples), then walks the chain trying HeapPage::insert on each page; when the tail rejects the tuple, allocate a fresh page, link it via set_next_page, and insert there. A chain walk per insert is O(pages) — caching the last page id in HeapFile is a worthwhile upgrade, and the CS186 notes' page directory shows the fully general fix4 (not required here). get uses with_page + HeapPageRef::attach so reads stay read-only; set_meta and delete use with_page_mut + HeapPage::attach. Translate a dead-slot get to Ok(None), and an out-of-range page to Err.
  9. HeapScan and the reopen loop. The iterator holds the current page id and next slot; it reads each page through with_page + HeapPageRef, advances slot-by-slot in (page_id, slot) order along the page chain, skips dead slots, follows next_page() links, and stops at INVALID_PAGE_ID. Then close the loop end-to-end: create a database file, insert a few hundred random tuples through HeapFile, flush_all, drop everything, reopen the same path, and verify every RecordId and a full scan return identical data.
  10. REPL continuity: .open <path>. In Milestone 0, .open <path> printed a placeholder message because no disk storage existed yet. Once DiskManager passes its tests, you can wire .open <path> in crates/ferricdb/src/repl.rs to validate and open the target file via DiskManager::open — or defer wiring the full ExecContext until Milestone 2/3, when BufferPoolManager and Catalog snap into place above it.

Test plan

The starter workspace ships this milestone's tests in crates/storage/tests/storage.rs marked #[ignore = "milestone 1"] and named with the ms1_ prefix. The ms1_ argument below is a name filter selecting them; --include-ignored runs them despite the attribute:

cargo test -p ferricdb-storage -- --include-ignored ms1_

Work toward the provided tests in this order:

  • Pages & slotted layout: ms1_page_lsn_roundtrip checks Page::lsn/set_lsn; ms1_slotted_page_roundtrip checks HeapPage::init, insert, get with TupleMeta, and read-only HeapPageRef access; ms1_tombstone_semantics checks dead-slot delete and Error::InvalidSlot on double/out-of-range deletes; ms1_set_meta_updates_in_place checks in-place TupleMeta overwrites; and ms1_free_space_decreases_and_bounds_inserts fills a page until insert returns None and checks attach.
  • Tuple serialization: ms1_tuple_serde_all_types_and_nulls checks all four types, NULLs, IEEE 754 -0.0 bit identity, and non-ASCII UTF-8; ms1_tuple_serde_wide_schema_multi_byte_bitmap tests a 12-column schema (2-byte null bitmap); ms1_tuple_serde_rejects_bad_inputs verifies errors on wrong arity, NULL in a non-nullable column, type mismatch, and truncated slices; and ms1_tuple_serde_property_seeded round-trips 200 deterministic random rows generated with the dev-only rand dependency (fixed seed — print any failing row to debug).
  • Disk manager & heap file: ms1_disk_manager_persistence_across_reopen and ms1_disk_manager_rejects_out_of_range_reads test file I/O and bounds checking; ms1_heapfile_roundtrip_and_scan inserts 500 multi-page rows, verifies point reads, deletes every 10th row, and asserts scan() yields all survivors in (page_id, slot) order; ms1_heapfile_survives_reopen checks durability across close/reopen; and ms1_heapfile_rejects_oversized_tuple asserts that a PAGE_SIZE-byte tuple returns Err(Error::PageFull).

Do not delete the #[ignore] attributes: per the workspace README.md, keeping them leaves plain cargo test --workspace green in CI while --include-ignored ms1_ runs this milestone's regression suite whenever you want. Add your own unit tests freely alongside — the byte helpers from step 1 and the header round-trip from step 2 deserve their own.

Common pitfalls

Pitfall — unaligned reads via pointer casts

A tuple's bytes land at whatever offset the free-space math produced, so an i64 inside a page is almost never 8-byte aligned. Casting &buf[off] to &i64 (or any transmute/pointer-cast trick) is undefined behavior in Rust, because references must be aligned — Postgres avoids the issue by padding user data to MAXALIGN boundaries via t_hoff,2 but we don't pad. Symptom: everything passes on x86-64 (which tolerates unaligned loads), then Miri flags UB or an ARM target crashes. Fix: always copy_from_slice into a [u8; N] and use from_le_bytes6 — the compiler turns this into the same single load where legal, so there is no performance excuse.

Pitfall — reusing dead slots or compacting early

It is tempting to make insert recycle a tombstoned slot or to slide live tuples over dead ones. Don't. A RecordId must stay valid for the life of the row: Milestone 5 stores RecordIds inside B+Tree leaves, and Milestone 8 needs dead versions to remain addressable for MVCC visibility checks. The CS186 notes describe compaction and slot-null reuse as valid maintenance for generic slotted pages,4 but in this course that reclamation is exclusively VACUUM's job in Milestone 8. Symptom: nothing — today. The bug detonates milestones later as an index probe returning the wrong row. Fix: tombstone only; slot_count never decreases in this milestone.

Pitfall — off-by-one where lower meets upper

An insert consumes space at both ends of the hole: LP_SIZE bytes at lower and the tuple's bytes below upper. The page is full exactly when lower + LP_SIZE + need > upper; forget the LP_SIZE term, or use >= where you mean >, and the last insert that “fits” writes its line pointer over the first tuple byte. Symptom: ms1_slotted_page_roundtrip passes for a handful of tuples, then ms1_free_space_decreases_and_bounds_inserts corrupts the last tuple when a page fills — or free_space underflows a usize subtraction and panics. Fix: one function computes the fit decision and free_space from the same expression; test it at the exact boundary (a tuple that fits with 0 bytes to spare, then one byte more).

Pitfall — TEXT length prefix counts bytes, not chars

The u32 prefix is the UTF-8 byte length. "naïve" is 5 characters but 6 bytes (Figure 3); Rust's String::len already returns bytes, so the bug arrives when someone “helpfully” writes s.chars().count() instead. Symptom: ASCII-only tests pass, then ms1_tuple_serde_all_types_and_nulls (which round-trips "héllo → 世界") fails with a UTF-8 decode error or a shifted read of the next column. Fix: use len(), and in deserialize validate with String::from_utf8 rather than the unchecked variant.

Note — page checksums are a stretch goal, not this milestone

PostgreSQL reserves a pd_checksum field in every page header, filled in only when data checksums are enabled for the cluster.2 FerricDB's reserved u32 in the 16-byte page header leaves room for the same idea, and detecting torn or corrupted pages is a genuinely interesting extension — but it is strictly optional stretch work. Do not spend Milestone 1 time on it; the tests neither require nor check it.

Definition of done

  • cargo test -p ferricdb-storage -- --include-ignored ms1_ passes with all 14 ms1_ tests green — including the seeded property test, wide multi-byte bitmap test, bad-input rejection, and oversized-tuple rejection.
  • A fresh database file survives close and reopen with identical contents: insert through HeapFile, flush_all, drop the DiskManager, reopen the same path, and every stored RecordId returns the same meta and bytes, with a full scan yielding all surviving rows in (page_id, slot) order.
  • #[ignore] attributes remain intact and cargo test --workspace stays green.
  • Your heap-page byte map is documented as a comment table in the source, and free_space's convention is stated in its doc comment.
