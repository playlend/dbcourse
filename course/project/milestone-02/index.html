Milestone 2 · Buffer Pool Manager

Put a cache in front of the disk: fixed frames, a page table, RAII pin guards, CLOCK eviction — and from this milestone on, every page in FerricDB flows through it.

Milestone 1 gave FerricDB correct storage with the performance profile of a filing cabinet: one disk round trip per page touch. This milestone builds the layer that makes the next eight milestones fast enough to enjoy — and it is the first piece of real concurrent systems code in the course. The multi-threaded stress test at the end has ended many first drafts; the guidance below is ordered to keep yours out of that statistic.

Learning objectives

  • Implement a fixed-size buffer pool: page table, frames, and miss handling that reads through the DiskManager from Milestone 1.1
  • Implement pin counting as an RAII guard type, so a page can never be evicted while in use and pins can never leak.1
  • Implement the CLOCK replacement policy behind a trait, with LRU-2 as a stretch goal.2
  • Enforce the dirty-victim rule: a modified page is written back before its frame is reused, never silently dropped.1
  • Reason about latch scope: what the pool-wide latch protects, what it must never be held across, and why.3

Specification

You implement crates/buffer. The public surface (from the workspace API contract; the stubs carry the full rustdoc):

pub trait Replacer: Send {
    fn record_access(&mut self, frame: FrameId);
    fn set_evictable(&mut self, frame: FrameId, evictable: bool);
    fn evict(&mut self) -> Option<FrameId>;
    fn evictable_count(&self) -> usize;
}
pub struct ClockReplacer { /* ref bits + hand */ }
impl ClockReplacer { pub fn new(num_frames: usize) -> Self; }
pub struct LruKReplacer { /* stretch: history of last K accesses */ }
impl LruKReplacer { pub fn new(num_frames: usize, k: usize) -> Self; }

/// Log hook for the WAL rule (Milestone 9): before a dirty page with
/// pageLSN = L is written out, flush_until(L) must succeed.
pub trait LogFlusher: Send + Sync {
    fn flush_until(&self, lsn: Lsn) -> Result<()>;
}

pub struct BufferPoolManager { /* frames, page table, replacer, disk, log hook */ }
impl BufferPoolManager {
    pub fn new(pool_size: usize, disk: DiskManager, replacer: Box<dyn Replacer>) -> Self;
    pub fn set_log_flusher(&self, log: std::sync::Arc<dyn LogFlusher>); // wired in MS9
    pub fn fetch_page(&self, id: PageId) -> Result<PageGuard>;   // pins
    pub fn new_page(&self) -> Result<(PageId, PageGuard)>;       // allocate + pin
    pub fn flush_page(&self, id: PageId) -> Result<()>;
    pub fn flush_all(&self) -> Result<()>;
    pub fn pool_size(&self) -> usize;
}
impl ferricdb_storage::PageStore for BufferPoolManager { /* via fetch/guards */ }

/// RAII pin. Deref/DerefMut to Page; DerefMut marks the frame dirty;
/// Drop unpins.
pub struct PageGuard<'a> { /* pool ref, frame */ }

Semantics you must honor (they are what the tests check):

  • fetch_page on a resident page pins it and touches the replacer's access history — no disk I/O.1
  • fetch_page on a non-resident page finds a frame (free, else victim). A dirty victim is written to disk before the frame is reused. Then the requested page is read in, the page table is updated (old mapping out, new mapping in), and the frame comes back pinned.1
  • A frame with pin count > 0 is not evictable — set_evictable(frame, false) on first pin, true again when the count returns to zero.2
  • If every frame is pinned, fetch_page/new_page fail with Error::BufferPoolExhausted — never block forever, never evict a pinned page.1
  • CLOCK: one reference bit per frame, set on access; the hand clears set bits as it sweeps and evicts at the first evictable frame with a clear bit.2
  • flush_page/flush_all write dirty frames through and clear dirty bits; they do not evict. Once set_log_flusher is wired (Milestone 9), every dirty-page write is preceded by flush_until(page_lsn) — build the call site now, as a no-op when the hook is absent.
  • The PageStore impl makes the pool a drop-in replacement for DiskManager: from this milestone on, HeapFile::create/open in your tests and in the REPL take Arc<BufferPoolManager>.

Step-by-step guidance

  1. Start with ClockReplacer in isolation. It is a pure data structure: ref bits, an evictable set, a hand index. Get its unit behavior right against the M03 simulator before any latching exists to confuse the picture.
  2. Design the shared state as one struct. Page table, frame metadata (pin count, dirty, the Page itself), and the replacer live together behind one Mutex (or the frames' bytes behind per-frame RwLocks if you want finer grain — see the pitfall on latch scope first). Resist premature cleverness: the stress test rewards correct, not fastest.
  3. Write fetch_page as a state machine. Hit → pin, record access, return guard. Miss with free frame → read, install, pin. Miss with victim → evict (flush if dirty), install, pin. Miss with nothing evictable → error. Make each arm a few lines and test them separately.
  4. Do disk I/O outside the latch if you can. The straightforward version holds the pool latch across read_page/write_page; it passes the tests but serializes all misses. The better shape marks the frame "busy", drops the latch, does I/O, re-takes the latch to finish installation. Attempt it after the simple version is green — with the tests as your safety net.
  5. Make PageGuard boring. It stores the pool reference and frame id; Deref hands out &Page; DerefMut sets the dirty flag then hands out &mut Page; Drop decrements the pin and flips evictability at zero. All the subtlety belongs to the pool, not the guard.
  6. Wire PageStore and re-run Milestone 1. The ms1_ suite must still pass with HeapFile running over the pool — that regression is the whole point of the trait.
  7. Only then run the stress test. ms2_stress_multithreaded hammers fetch_page/writes/drops from many threads. When it fails, shrink: 2 threads, 2 frames, 3 pages reproduces almost every latching bug in miniature.
  8. Stretch — LRU-2. Implement LruKReplacer per the backward k-distance rule (max distance evicted; fewer than k accesses ⇒ infinite, ties by oldest overall access).2 The replacer trait means the pool doesn't change at all — that was the point of the trait, too.

Test plan

# the milestone group
cargo test -p ferricdb-buffer -- --include-ignored ms2_

# regression: Milestone 1 must still pass over the pool
cargo test -p ferricdb-storage -- --include-ignored ms1_

# after everything is green: the hit-rate benchmark
cargo bench -p ferricdb-buffer

The group starts with ms2_clock_evicts_unpinned — CLOCK ordering with pins in play — then covers: pinned pages surviving full-pool pressure (expect BufferPoolExhausted), dirty victims being readable after eviction, resident fetches doing no I/O, pins releasing on guard drop, and the multi-threaded stress test. The criterion bench in benches/hit_rate.rs reports fetch throughput on a skewed workload; record the number in your notes — the Definition of Done asks for it, and it becomes your baseline when you tune later.

Common pitfalls

Evicting a pinned page

Symptom: data corruption that reproduces only under load, when a page's bytes change under a live guard. Cause: the replacer saw a frame the pool considered pinned. Keep evictability inside the replacer (via set_evictable) and update it on every pin-count edge — first pin and last unpin — not on every access.2

Dropping a dirty victim

Symptom: a value written moments ago reads back stale after unrelated activity. Cause: the eviction path forgot the write-back. The test constructs exactly this: write page A, evict it via pressure, fetch it again. The rule is unconditional — and in Milestone 9 it grows the WAL prefix (flush_until(pageLSN) first), which is why the spec asks you to shape the call site now.1

Holding the pool latch across disk I/O — then adding a second latch

Symptom: deadlock under the stress test; threads parked forever. The classic shape: thread 1 holds the pool latch and waits on a frame latch; thread 2 holds that frame latch and calls back into the pool. Pick a strict order (pool before frame, never the reverse), or stay with the single coarse latch — a slow pool passes; a deadlocked one does not.3

Page table desync

Symptom: two frames both claim page N, or a fetch returns an evicted page's stale frame. Cause: eviction removed the victim's mapping but installation of the new mapping happened outside the same critical section. Table-out and table-in must be atomic with respect to other fetches of either page.

Definition of done

  • ms2_ tests all pass, including ms2_stress_multithreaded, run at least five times in a row (latching bugs are shy).
  • ms1_ tests still pass with HeapFile over BufferPoolManager.
  • cargo bench -p ferricdb-buffer runs and you have written down the hit-rate benchmark number.
  • You can explain, out loud, why fetch_page of a resident page must not touch the disk and what would break if flushing skipped the dirty check.
