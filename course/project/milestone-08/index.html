Since Milestone 1, every tuple you have written carried two silent u64s: xmin and xmax, faithfully stored as zero. Today they wake up. The remarkable thing about this milestone is how little machinery it takes — a transaction manager, a snapshot struct, one pure visibility function threaded through your scans — to turn a single-user engine into one where concurrent sessions each see a consistent world. The design is PostgreSQL's, simplified; the honesty requirement (write skew!) is toyDB's.3

Learning objectives

  • Implement transaction lifecycle: BEGIN / COMMIT / ROLLBACK plus autocommit for bare statements.
  • Implement snapshots (xmin, xmax, active set) captured at BEGIN.1
  • Implement the interdb Ch. 5 visibility rules as a pure function and apply them in every scan.1
  • Implement MVCC writes: insert stamps xmin; delete stamps xmax; update = delete + insert.1
  • Implement first-committer-wins conflict detection returning Error::Serialization (SQLSTATE 40001 spirit).2
  • Implement VACUUM against the oldest-active-snapshot horizon.4
  • Demonstrate — with tests — which anomalies snapshot isolation prevents and that write skew survives.3

Where this fits

Specification

You implement crates/txn and thread it through exec and the storage write paths:

#[derive(Clone, Debug)]
pub struct Snapshot { pub xmin: TxnId, pub xmax: TxnId,
                      pub active: std::collections::BTreeSet<TxnId> }
impl Snapshot {
    /// MVCC visibility of a tuple version to this snapshot, given the
    /// commit state oracle. Mirrors the interdb Ch.5 rules.
    pub fn is_visible(&self, meta: &TupleMeta,
                      committed: &dyn Fn(TxnId) -> bool) -> bool;
}

pub enum TxnState { Active, Committed, Aborted }
pub struct Transaction { /* id, snapshot, write set */ }
impl Transaction {
    pub fn id(&self) -> TxnId;
    pub fn snapshot(&self) -> &Snapshot;
}

pub struct TransactionManager { /* next txid, states, active set */ }
impl TransactionManager {
    pub fn new() -> Self;
    pub fn begin(&self) -> std::sync::Arc<Transaction>;
    /// First-committer-wins: Err(Error::Serialization) if the write set
    /// intersects a concurrently-committed transaction's writes.
    pub fn commit(&self, txn: &Transaction) -> Result<()>;
    pub fn abort(&self, txn: &Transaction);
    pub fn is_committed(&self, id: TxnId) -> bool;
    pub fn record_write(&self, txn: &Transaction, rid: RecordId);
    /// Oldest xmin any active snapshot can still see (VACUUM horizon).
    pub fn oldest_visible_xid(&self) -> TxnId;
}

Semantics contract:

  • Snapshot capture is atomic with txid assignment: begin() assigns the next id and captures {xmin = oldest active, xmax = next unassigned, active = in-flight ids} under one lock, so no transaction is ever missing from a snapshot that should contain it.1
  • Visibility follows the module's rules 1–10 exactly, including the own-transaction cases (my insert visible; my delete invisible to me) and the active-in-snapshot exceptions (rules 5 and 9). "Active in snapshot" = in the active set or ≥ snapshot xmax.1
  • Writes: INSERT stamps xmin = my id; DELETE stamps xmax = my id via HeapFile::set_meta (tuple body untouched); UPDATE writes a new version and stamps the old one's xmax — never in-place. Index entries are added for new versions; old entries stay until VACUUM.
  • Conflicts: every write also calls record_write; at commit(), if any rid in my write set was written by a transaction that committed after my snapshot, I abort with Error::Serialization — the first committer wins. ROLLBACK marks aborted; rule 1 instantly hides everything the transaction wrote (no undo needed — that elegance is MVCC's gift; contrast Milestone 9).
  • REPL / execute(): BEGIN opens a transaction bound to the session; COMMIT/ROLLBACK close it; bare statements run in a one-statement autocommit transaction. Scans without any explicit transaction still see committed-only data.
  • VACUUM scans heaps and removes versions whose deleter is committed and < oldest_visible_xid() (and aborted-insert corpses), compacting slots via your Milestone 1 tombstone machinery.4

Step-by-step guidance

  1. is_visible first, as a pure function. No manager, no storage — just (meta, snapshot, oracle) → bool, structured as the module's three cases by creator status. The provided table-driven test enumerates all ten rules; make it green before touching anything stateful. This function is 40 lines and the heart of the milestone.
  2. TransactionManager next. One mutex over {next_id, states map, active set, write sets}. begin/commit/abort are small critical sections; keep the commit-time conflict check inside the same lock that flips the state to Committed, or two racing commits can both pass the check.
  3. Thread the snapshot through ExecContext. The context gains a current transaction slot; SeqScan and IndexScan filter every tuple through snapshot.is_visible(meta, oracle) before anything else sees it. The oracle is a closure over TransactionManager::is_committed.
  4. Stamp the write paths. Insert/Delete/Update executors take the current txid from the context. Update is delete-then-insert on the same heap — resist any "small update optimization"; version history is the feature.
  5. Wire BEGIN/COMMIT/ROLLBACK. They have parsed since Milestone 3; execution is a session-state change plus manager calls. Autocommit wraps everything else.
  6. Conflict detection. Record writes as you stamp them; implement the commit check; surface Error::Serialization through the REPL as a clean retryable message, the way Postgres tells applications to treat 40001.2
  7. Anomaly scripts. Now run the provided ms8_ scenario tests: they script two interleaved transactions through the manager exactly like the module's anomaly zoo — lost update prevented, fuzzy read prevented, phantom prevented, and ms8_write_skew_is_documented asserting the skew succeeds. When that last one passes, read its doc comment out loud; it is the course's honesty pledge.3
  8. VACUUM last. Compute the horizon, sweep the heaps, drop dead index entries. Verify with the before/after page-count assertions and re-run the whole slt_all suite — vacuum must be invisible to correctness.

Common pitfalls

A transaction that can't see its own writes

Symptom: INSERT then SELECT in the same transaction returns nothing. Cause: treating in-progress creators as invisible unconditionally — rule 4 without rule 2's own-transaction exception. The symmetric bug (rule 7) makes your own deletes visible to you. Both are single branches in is_visible; the table test names them.

Snapshot race at begin

Symptom: rare test flakes where a transaction sees a "future" commit. Cause: assigning the txid and reading the active set in separate critical sections — a transaction that starts between them is missing from your active list, so its later commit looks like the past (rule 5 never fires). One lock, one capture.

Conflict check outside the commit lock

Symptom: two transactions updating the same row both commit under stress. Cause: check-then-commit as two steps. The check and the state flip must be atomic; otherwise both pass the check against the same "nobody committed yet" world.

Vacuum eats a row someone can still see

Symptom: a long-running transaction's second read of the same row returns nothing. Cause: using "deleter committed" as the reclaim condition instead of "deleter committed AND below every active snapshot's horizon". The watermark exists precisely for this.4

Definition of done

  • All ms8_ tests pass, including the write-skew documentation test; slt_all and earlier groups still pass.
  • Two REPL sessions demonstrate live: session A begins and reads a row; session B updates it and commits; A re-reads the old value; after A commits and re-reads, the new value appears.
  • Two sessions updating the same row: the second committer gets a serialization error and succeeds on retry.
  • After a bulk UPDATE, VACUUM reclaims space (visible via a page-count or free-space report) and nothing changes semantically.
  • You can state from memory which anomalies your database now prevents and the one it documents instead of preventing.
