Since Milestone 1, every tuple you wrote into a HeapPage carried two quiet 64-bit integers in its 16-byte TupleMeta header: xmin and xmax, faithfully stored as zero. Today they wake up. By adding a compact transaction manager, an atomic snapshot captured at BEGIN, one pure visibility function threaded through both scan operators, and out-of-place versioned writes, FerricDB graduates from a single-user engine into a multi-version database where readers never block writers and writers never block readers.1

The concurrency model is PostgreSQL's Snapshot Isolation (which PostgreSQL calls REPEATABLE READ): one snapshot per transaction, tuple-level xmin/xmax versioning, and first-committer-wins conflict detection returning Error::Serialization.12 The honesty pledge is toyDB's: dirty reads, dirty writes, lost updates, fuzzy reads, and phantoms are all eliminated, while write skew remains permitted under snapshot isolation and is explicitly pinned down by a provided test until you close it with Serializable Snapshot Isolation in Stretch Milestone S2.3

Learning objectives

  • Implement the ten interdb Ch. 5 MVCC visibility rules (plus xmin == 0 frozen/bootstrap tuples) as a pure function Snapshot::is_visible.1
  • Implement TransactionManager with atomic transaction-id assignment and snapshot capture, commit-state tracking, first-committer-wins conflict detection, and the oldest_visible_xid() garbage-collection horizon.14
  • Implement out-of-place MVCC writes (INSERT, DELETE, UPDATE) with first-updater-wins protection on meta.xmax, seamlessly paired with Milestone 5's composite (key, rid) B+Tree.
  • Wire session transaction lifecycle (BEGIN, COMMIT, ROLLBACK, autocommit, and PostgreSQL-style failed_txn error state) through ExecContext and execute().2
  • Implement VACUUM parsing in crates/sql, slot-preserving heap compaction in HeapPage::compact(), and horizon-safe dead tuple and index cleanup.4

Where this fits

Notice how earlier architectural choices pay off today. In Milestone 1 you reserved TupleMeta { xmin, xmax } in every heap slot and kept tombstoned line pointers so slot numbers never shifted. In Milestone 5 you keyed the B+Tree on composite (key, rid) pairs rather than bare keys, specifically so two versions of an updated row can coexist under the same indexed key. And in Milestone 4 you designed ExecContext::new_session() to clone the shared database Arcs while giving each session its own isolated current_txn and failed_txn slots. Milestone 8 connects all of those hooks together.

Specification

1. Transaction manager and snapshots (crates/txn)

From course/ferricdb/docs/api-spec.md and course/ferricdb/crates/txn/src/lib.rs — implement every public type and method verbatim (note that TransactionManager::restore is stubbed for Milestone 9 WAL recovery and stays todo!("Milestone 9") for now):

// crates/txn/src/lib.rs — verbatim public surface

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct Snapshot {
    pub owner: TxnId,
    pub xmin: TxnId,
    pub xmax: TxnId,
    /// Other in-flight transactions (excluding `owner`).
    pub active: std::collections::BTreeSet<TxnId>,
}
impl Snapshot {
    /// MVCC visibility of a tuple version to this snapshot, given the
    /// commit state oracle. `xmin == 0` is treated as frozen/committed.
    pub fn is_visible(&self, meta: &TupleMeta,
                      committed: &dyn Fn(TxnId) -> bool) -> bool;
}

pub enum TxnState { Active, Committed, Aborted }
pub struct Transaction { /* id, snapshot, write set */ }
impl Transaction {
    pub fn id(&self) -> TxnId;
    pub fn snapshot(&self) -> &Snapshot;
}

pub struct TransactionManager { /* next txid (>= 1), states, active set */ }
impl TransactionManager {
    pub fn new() -> Self;
    pub fn begin(&self) -> std::sync::Arc<Transaction>;
    /// First-committer-wins: aborts and returns Err(Error::Serialization) if
    /// the write set intersects a concurrently-committed transaction's writes.
    pub fn commit(&self, txn: &Transaction) -> Result<()>;
    pub fn abort(&self, txn: &Transaction);
    pub fn is_committed(&self, id: TxnId) -> bool;
    pub fn is_active(&self, id: TxnId) -> bool;
    pub fn record_write(&self, txn: &Transaction, rid: RecordId);
    /// Oldest xmin any active snapshot can still see (VACUUM horizon).
    pub fn oldest_visible_xid(&self) -> TxnId;
    /// Restore committed txns and advance next_txid after WAL recovery (MS9).
    pub fn restore(&self, max_txn_id: TxnId, committed: impl IntoIterator<Item = TxnId>);
}

Pay close attention to Snapshot's four fields. Unlike a fragile xmax - 1 heuristic, Snapshot carries an explicit pub owner: TxnId field so any snapshot knows unequivocally which transaction owns it — even when other transactions started concurrently before or after it. Equally important: active contains all other in-flight transactions (excluding owner), while xmin is the oldest active transaction id including owner, and xmax is the first unassigned transaction id at capture time (owner < xmax). Transaction ids start at 1 because 0 is reserved for "none" (on xmax) and "frozen / bootstrap" (on xmin).

3. Semantics contract

  • Atomic snapshot capture: TransactionManager::begin() acquires the internal mutex once to allocate id = next_txid (starting at 1), snapshot active (all currently active ids before inserting id), compute xmin = active.first().copied().unwrap_or(id), set xmax = id + 1, insert id into the active set with state TxnState::Active, and increment next_txid. Splitting id assignment and snapshot capture across two locks opens a race where a concurrent transaction vanishes from your active set.1
  • First-updater-wins AND first-committer-wins: write conflicts are guarded at both write time and commit time:
    • Write time (first-updater-wins): before an UPDATE or DELETE stamps meta.xmax = my_id on an existing tuple at rid, inspect its current meta.xmax atomically inside one store.with_page_mut(rid.page_id, ...) latch using HeapPage::attach. If meta.xmax != 0 and meta.xmax != my_id, and either txn_manager.is_active(meta.xmax) or txn_manager.is_committed(meta.xmax) holds, abort immediately with Err(Error::Serialization(...)). Why is this essential? A heap tuple header holds only one xmax slot. Without first-updater-wins (and without holding the page latch across the check and stamp), transaction T1 could stamp xmax = T1 and commit while concurrent T2 overwrites xmax = T2 and later aborts — silently resurrecting T1's deleted tuple under Rule 6b! If neither is_active nor is_committed is true, meta.xmax belongs to an already-aborted transaction and overwriting xmax is completely safe.
    • Commit time (first-committer-wins): every INSERT, UPDATE, and DELETE calls txn_manager.record_write(&txn, rid). Inside TransactionManager::commit(&txn), under the same lock that marks txn committed, check whether txn's write set intersects the write set of any transaction c that committed concurrently with txn (i.e., c was in txn.snapshot().active or c >= txn.snapshot().xmax). If any rid collides, mark txn as TxnState::Aborted, remove it from the active set so oldest_visible_xid() advances, and return Err(Error::Serialization(...)).2
  • Seamless MVCC UPDATE with composite B+Trees: an UPDATE never edits a tuple in place and never deletes the old index entry at update time. Instead, it stamps xmax = my_id on old_rid via HeapFile::set_meta, inserts the new tuple bytes with TupleMeta { xmin: my_id, xmax: 0 } producing new_rid, records both old_rid and new_rid in the write set, and inserts (new_key, new_rid) into every index on the table while keeping (old_key, old_rid) intact! Because Milestone 5's BPlusTree orders entries by composite (key, rid), both (key, old_rid) and (key, new_rid) coexist cleanly even when the indexed column's value did not change. Every IndexScan resolves each candidate rid from the heap and filters by snapshot.is_visible(&meta, &oracle) (Figure 2).
  • ROLLBACK now vs. Milestone 9: in Milestone 8 (before the write-ahead log exists), ROLLBACK calls txn_manager.abort(&txn) and clears current_txn and failed_txn. Under visibility rules 1 and 6b, every version created by the aborted transaction vanishes immediately and every xmax it stamped is ignored; physical reclamation happens later when VACUUM runs. In Milestone 9, adding ARIES write-ahead logging layers physical undo + Compensation Log Records (CLRs) on abort and crash recovery, plus TransactionManager::restore so committed states survive process restarts — giving you full ACID durability without changing a single visibility rule.
  • Session transaction state & autocommit: BEGIN starts a transaction and stores it in ctx.current_txn (erroring if already inside one); COMMIT commits it and clears current_txn; ROLLBACK aborts it and clears both current_txn and failed_txn. If any statement inside an explicit transaction fails (including a serialization failure), set ctx.failed_txn = true so subsequent statements fail until ROLLBACK (matching PostgreSQL's ReadyForQuery('E') protocol state in Milestone 10). Any statement executed when current_txn is None runs in an implicit single-statement autocommit transaction (begin → run → commit on Ok or abort on Err).
  • VACUUM horizon safety: TransactionManager::oldest_visible_xid() returns the minimum snapshot.xmin across all currently active transactions (or next_txid when no transactions are active).4 VACUUM reclaims only tuples that are guaranteed invisible to every current and future snapshot: aborted inserts (xmin != 0, not committed, and xmin < horizon) and old committed deletes (xmax != 0, committed, and xmax < horizon).

The ten visibility rules (plus frozen tuples)

Snapshot::is_visible(&self, meta, committed) is a pure function with zero shared state. Define one helper predicate for whether another transaction x is in this snapshot's "future": is_in_future(x) = self.active.contains(&x) || x >= self.xmax. Notice that committed(x) returns true only when x is committed, and false when x is either in progress or aborted; combining it with self.owner and is_in_future(x) resolves every single one of interdb §5.6's ten rules plus FerricDB's xmin == 0 frozen-tuple rule:1

Rule Creator (meta.xmin) Deleter (meta.xmax) Visible? Example in snapshot_100
owner=100, xmin=98, xmax=101, active={98}
Frozen xmin == 0 (bootstrap / pre-MS8 tuple) Treat creator as committed in distant past → evaluate xmax via R6–R10 By xmax (0, 0) → true; (0, 96) → false; (0, 100) → false
R1 Aborted (!committed(xmin), xmin != owner, not in future) Any false (99, 0) → false (T99 aborted)
R2 xmin == owner (my own insert) xmax == 0 (or aborted) true (100, 0) → true
R3 xmin == owner (my own insert) xmax == owner (deleted by me) false (100, 100) → false
R4 Other in-progress (!committed(xmin), xmin != owner, in future) Any false (98, 0) → false (T98 still running)
R5 committed(xmin) AND is_in_future(xmin) Any false (98, 0) after T98 commits, or (105, 0) → false
R6 committed(xmin) AND !is_in_future(xmin) xmax == 0 (not deleted) true (95, 0) → true
R6b committed(xmin) AND !is_in_future(xmin) xmax != 0, aborted (!committed(xmax), xmax != owner) true (95, 99) → true (T99 aborted delete)
R7 committed(xmin) AND !is_in_future(xmin) xmax == owner (deleted by me) false (95, 100) → false
R8 committed(xmin) AND !is_in_future(xmin) Other in-progress (!committed(xmax), xmax != owner, in future) true (95, 98) → true (T98 delete uncommitted)
R9 committed(xmin) AND !is_in_future(xmin) committed(xmax) AND is_in_future(xmax) true (95, 98) after T98 commits → true (future delete!)
R10 committed(xmin) AND !is_in_future(xmin) committed(xmax) AND !is_in_future(xmax) false (95, 96) → false (T96 deleted before snapshot)

Look closely at the symmetry between creator and deleter. A creator is visible to this snapshot if and only if meta.xmin == 0 (frozen), meta.xmin == self.owner (mine), or committed(meta.xmin) && !is_in_future(meta.xmin) (committed before my snapshot). Once the creator passes, the deletion is visible to this snapshot — hiding the tuple — if and only if meta.xmax != 0 AND (meta.xmax == self.owner OR (committed(meta.xmax) && !is_in_future(meta.xmax))). Every single one of the twelve rows above collapses cleanly into those two symmetric checks, and every rule maps one-to-one onto the cases in ms8_visibility_rules_table, ms8_frozen_tuple_xmin_zero_is_visible, and ms8_visibility_active_in_snapshot_rules.1

Step-by-step guidance

Build from the pure logic outward to storage compaction and SQL integration, turning each crate's ms8_ tests green as you go.

  1. Implement Snapshot::is_visible first. It is roughly 30 lines of pure Rust with zero locks and zero I/O. Structure it cleanly around the two symmetric helpers from the table above (creator visibility with the xmin == 0 frozen fast path, then deleter visibility). Run cargo test -p ferricdb-txn -- --include-ignored ms8_visibility and ms8_frozen until all three visibility tests pass.

  2. Build TransactionManager behind one mutex. Inside ManagerState (guarded by self.inner: Mutex<ManagerState>), keep: next_txid: TxnId (initialized to 1), states: HashMap<TxnId, TxnState>, active: BTreeMap<TxnId, TxnId> (mapping each active txn id to its captured snapshot.xmin, so both the active set and oldest_visible_xid() are O(active) or O(1)), in_flight_writes: HashMap<TxnId, HashSet<RecordId>>, and committed_writes: Vec<(TxnId, HashSet<RecordId>)> (or map keyed by TxnId).

    • begin(): lock once; allocate id = next_txid; next_txid += 1; build active: BTreeSet<TxnId> from the keys currently in state.active (which does not include id); compute xmin = active.first().copied().unwrap_or(id); set xmax = id + 1; insert id into states as Active and into state.active with value xmin; return Arc::new(Transaction { id, snapshot }).
    • record_write(txn, rid): lock and insert rid into in_flight_writes[txn.id()].
    • commit(txn): lock once; take my_writes; scan every (cid, c_writes) in committed_writes where cid was concurrent with txn (i.e., txn.snapshot().active.contains(&cid) || cid >= txn.snapshot().xmax). If my_writes shares any RecordId with c_writes, set states[id] = TxnState::Aborted, remove id from state.active, and return Err(Error::Serialization(...)). Otherwise set states[id] = TxnState::Committed, remove id from state.active, store (id, my_writes) in committed_writes, and return Ok(()).
    • abort(txn): lock once; set states[id] = TxnState::Aborted, remove id from state.active, and discard in_flight_writes.remove(&id) so aborted writers never conflict with anyone.
    • oldest_visible_xid(): lock once; return the minimum snapshot.xmin stored in state.active.values(), or state.next_txid if no transactions are active.4

    Run cargo test -p ferricdb-txn -- --include-ignored ms8_ — all 11 transaction-manager tests (including ms8_write_skew_is_documented and the 8-thread ms8_concurrent_begins_are_atomic stress test) should now pass!

  3. Implement HeapPage::compact() and parse VACUUM. In crates/storage/src/lib.rs, implement HeapPage::compact(&mut self) -> usize: read old_upper; iterate slot in 0..self.slot_count() collecting every live slot's (slot, meta, payload.to_vec()); reset upper = PAGE_SIZE; rewrite each live entry tightly backward from PAGE_SIZE, updating that exact slot's line pointer offset while keeping dead slots tombstoned and slot_count untouched; write the updated upper to the 28-byte header and return new_upper.saturating_sub(old_upper). Verify with cargo test -p ferricdb-storage -- --include-ignored ms8_.

    In crates/sql/src/lib.rs, add the one-line parser branch mapping Keyword::Vacuum to ast::Statement::Vacuum (and wire BoundStatement::Vacuum in crates/exec/src/binder.rs). Verify with cargo test -p ferricdb-sql -- --include-ignored ms8_.

  4. Thread snapshots through SeqScan and IndexScan. Every query executing through execute() now runs inside an active Arc<Transaction> — either the session's explicit transaction in ctx.current_txn, or a fresh autocommit transaction created at the start of the statement. Pass that Arc<Transaction> (or clone its Snapshot) into SeqScan and IndexScan. Before deserializing or evaluating a filter predicate on any heap tuple, check snapshot.is_visible(&meta, &|x| txn_manager.is_committed(x)) and skip invisible versions. Because Catalog::bootstrap and earlier DDL wrote system tuples with xmin == 0, the frozen-tuple rule ensures system tables and pre-existing rows remain visible automatically.

  5. Convert DML executors to MVCC writes with first-updater-wins.

    • Insert: write every new tuple with TupleMeta { xmin: my_id, xmax: 0 }, call txn_manager.record_write(&txn, rid), and insert (key, rid) into every index in table.indexes (for non-NULL keys).
    • Delete: materialize target RecordIds from the child scan first (preserving the Halloween guard). For each rid, check first-updater-wins and stamp xmax atomically inside a single ctx.store.with_page_mut(rid.page_id, ...) call via HeapPage::attach: read (meta, _), abort with Error::Serialization if meta.xmax != 0 && meta.xmax != my_id && (txn_manager.is_active(meta.xmax) || txn_manager.is_committed(meta.xmax)), otherwise call page.set_meta(rid.slot, TupleMeta { xmin: meta.xmin, xmax: my_id }) before releasing the latch, then call txn_manager.record_write(&txn, rid). Do not call heap.delete(rid) or remove index entries here — older snapshots may still need that version!
    • Update: materialize target (old_rid, old_values) pairs first. For each row, perform the exact same atomic check-and-stamp on old_rid via with_page_mut + HeapPage::attach (first-updater-wins check, then set_meta with xmax = my_id), serialize the updated row and call heap.insert(TupleMeta { xmin: my_id, xmax: 0 }, &new_bytes) to obtain new_rid, record both old_rid and new_rid with record_write, and insert (new_key, new_rid) (for non-NULL keys) into every index on the table (leaving (old_key, old_rid) untouched for older snapshots).

  6. Wire BEGIN, COMMIT, ROLLBACK, and failed_txn in execute(). Check *ctx.failed_txn.lock().unwrap() at the top of each statement inside an explicit transaction: if true and the statement is not Rollback, return Err(Error::Execution("current transaction is aborted; run ROLLBACK".into())). On BEGIN, call txn_manager.begin() and store the result in ctx.current_txn (tag "BEGIN"). On COMMIT, take the transaction out of ctx.current_txn and call txn_manager.commit(&txn) — if it returns Err(Error::Serialization(e)), the transaction has already been marked aborted by the manager, so clear failed_txn = false and propagate the error (tag "COMMIT" on success). On ROLLBACK, take any open transaction, call txn_manager.abort(&txn), reset failed_txn = false, and return tag "ROLLBACK". For any error during a statement inside an explicit transaction (such as a bind error or first-updater-wins Error::Serialization), mark failed_txn = true (and if it was a serialization conflict, aborting immediately or waiting for explicit ROLLBACK must be consistent — ensure ms8_sql_transactions_commit_rollback_isolation and PostgreSQL error semantics stay clean).

  7. Implement VACUUM execution. Dispatch BoundStatement::Vacuum in execute() (disallowing it inside an explicit transaction, just as PostgreSQL does, and running against horizon = ctx.txn_manager.oldest_visible_xid()). For each table in ctx.catalog.tables()?, walk the table's heap page chain page by page. For each live slot on a page with (meta, bytes), check whether it is dead and below the horizon:

    // Reclaim condition for a tuple version at (page_id, slot) with meta:
let aborted_insert = meta.xmin != 0
    && !txn_manager.is_committed(meta.xmin)
    && meta.xmin < horizon;
let old_committed_delete = meta.xmax != 0
    && txn_manager.is_committed(meta.xmax)
    && meta.xmax < horizon;
if aborted_insert || old_committed_delete {
    // 1. Deserialize tuple and remove (key, rid) from every index via BPlusTree::delete
    //    (skipping Value::Null keys, matching Insert — BPlusTree rejects NULL)
    // 2. Tombstone slot via HeapPage::delete(slot)
}
// 3. After sweeping the page, call HeapPage::compact() if any slot was tombstoned

    Return tag "VACUUM". Notice why step 1 must delete the exact (key, rid) pair: the newer live version of the same row may share key under a different new_rid, and composite BPlusTree::delete(&key, old_rid) removes only the dead pointer without disturbing the live one!

Common pitfalls

Pitfall — a transaction cannot see its own writes or still sees its own deletes

Symptom: INSERT followed by SELECT inside the same BEGIN ... COMMIT block returns zero rows, or DELETE followed by SELECT still shows the deleted row. Cause: forgetting to check self.owner before checking committed(xid) (missing Rules 2, 3, and 7). Because Snapshot carries owner explicitly, handle meta.xmin == self.owner and meta.xmax == self.owner first — and never include owner inside snapshot.active.

Pitfall — single-xmax clobbering on concurrent writes

Symptom: a committed DELETE or UPDATE mysteriously comes back to life after a concurrent transaction aborts. Cause: relying solely on commit-time first-committer-wins without checking meta.xmax before calling HeapFile::set_meta. When T1 stamps xmax = T1 and T2 overwrites it with xmax = T2 and then aborts, T1's stamp is lost forever. Enforce first-updater-wins before modifying meta.xmax.

Pitfall — snapshot race or split commit lock

Symptom: intermittent failures under ms8_concurrent_begins_are_atomic or two concurrent writers both committing. Cause: allocating next_txid and reading active under separate locks, or checking write-set conflicts before releasing and re-acquiring the mutex to mark Committed. Keep both begin() and commit() atomic inside a single critical section.

Pitfall — forgetting to remove aborted losers from the active set

Symptom: ms8_first_committer_wins fails its horizon assertion, or VACUUM permanently stops reclaiming dead rows after a single conflict. Cause: returning Err(Error::Serialization) from commit() without flipping the loser to TxnState::Aborted and removing its id from state.active. A stalled active entry pins oldest_visible_xid() forever.4

Pitfall — HeapPage::compact() renumbering slots or VACUUM ignoring indexes

Symptom: IndexScan returns wrong rows or crashes after VACUUM. Cause: shifting live entries down to lower slot indexes during compaction (invalidating every RecordId stored in B+Trees), or tombstoning dead heap slots without calling BPlusTree::delete(&key, rid) first. Always keep each live tuple at its original slot index and remove dead (key, rid) pairs from every index before tombstoning the slot.

Definition of done

  • All ms8_ tests pass across all four crates (ferricdb-txn, ferricdb-storage, ferricdb-sql, ferricdb-exec), including ms8_write_skew_is_documented; slt_all and earlier milestone suites still pass.
  • Multi-session integration tests using ExecContext::new_session() demonstrate live in one process: session A begins and reads a row; session B updates it and commits; session A re-reads the old value; after session A commits, a fresh read observes the new value. (Note: two separate REPL OS processes do not share an in-memory TransactionManager or buffer pool — interactive multi-client sessions over TCP come alive in Milestone 10.)
  • Two concurrent sessions updating the same row trigger Error::Serialization for the loser while preserving the winner's committed update intact, and a retry succeeds.
  • After a bulk UPDATE on an indexed table (and closing old snapshots), VACUUM reclaims dead tuple bytes via HeapPage::compact() and prunes dead (key, rid) entries from the B+Tree with zero semantic change.
  • You can state from memory the five anomalies FerricDB now prevents (dirty write, dirty read, lost update, fuzzy read, phantom read) and the one anomaly it honestly documents instead of preventing (write skew).3
