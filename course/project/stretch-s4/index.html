Stretch pages are deliberately lower-detail: this one maps toyDB's documentation onto FerricDB rather than re-deriving consensus theory.

The goal

One FerricDB process is one failure away from downtime. The distributed answer is to replicate the database as a state machine behind a consensus log: toyDB uses Raft for exactly this — linearizable state machine replication over its MVCC SQL engine.1 This stretch builds the miniature: a three-process local FerricDB cluster that elects a leader, replicates writes through a Raft log, applies committed entries to each node's engine, and survives killing any single node. toyDB is Apache-2.0 — attribute anything you adapt.1

Where this fits

The toyDB map

Read toyDB's architecture guide front to back once — it is a guided tour written for exactly this purpose1 — then study its Raft documentation in this order: log storage; the state machine interface; node roles (leader/follower/candidate); leader election and terms; client request forwarding; and write replication and application.2 The state machine interface is the piece to internalize: Raft neither knows nor cares that the entries are SQL — it delivers committed byte blobs to an apply() function in log order, one at a time, on every node.

Integration plan

  1. Define the state machine. trait StateMachine { fn apply(&mut self, entry: &[u8]) -> Result<Vec<u8>>; } — start with auto-commit write statements wrapped in execute(), then handle multi-statement transactions (BEGIN ... COMMIT) by replicating either a session-tagged command sequence or an atomic commit-time write-set batch so open transactions do not interleave inconsistently across nodes. Reads can bypass the Raft log on the leader only when paired with a linearizable leadership check (Raft's ReadIndex / quorum heartbeat round, or a bounded-clock leader lease — see pitfalls).
  2. Implement Raft small. Follow toyDB's decomposition: a node struct with role state, a persisted log, election timers with randomized timeouts, AppendEntries heartbeats, and commit-index advancement on majority acknowledgment.2 Keep transport simple: length-prefixed messages over tokio TCP between the three fixed peers.
  3. Route writes through the leader. The wire-protocol server on a follower forwards write statements to the leader (toyDB documents this client-forwarding pattern) and returns the applied result.2
  4. Persist the applied index. Each node stores how far it has applied, so restart re-applies only newer committed entries.
  5. Cluster harness. A test script that launches three processes on different ports, drives psql at whichever is leader, kills nodes, and asserts convergence.

Pitfalls

Non-deterministic entries

Every node applies every entry independently — entries must be deterministic. Anything involving randomness, time, or per-node state (even txid assignment!) must be resolved by the leader before the entry enters the log, or the replicas diverge silently.

Applying entries twice after restart

If the applied index isn't persisted atomically with application effects, a crash between them replays an entry. Make apply idempotent or gate it on the stored index — this is the ARIES pageLSN lesson wearing a distributed costume.

Two logs, different jobs

The Raft log orders commands across nodes; the Milestone 9 WAL protects each node's local storage. They are not interchangeable and you likely keep both — decide and document whether snapshot reads on followers are allowed (stale) or forbidden (leader-only reads, which are linearizable only if the leader confirms leadership via a ReadIndex quorum heartbeat check or a bounded-clock lease rather than serving local state unchecked during a network partition).

Definition of done

  • A three-node local cluster elects a leader and serves psql through it.
  • Writes are visible on all nodes; a killed-and-restarted follower catches up automatically.
  • Killing the leader elects a new one, and reads after failover see all previously committed writes.
  • A design note records determinism decisions, applied-index persistence, and the follower-read policy.
