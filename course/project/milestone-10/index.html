Ten milestones of internals, and not one of them is visible from the outside. This one is nothing but outside: a byte-exact implementation of somebody else's contract, judged by the least forgiving integration test imaginable — real clients you didn't write. Two paths are offered. Hand-rolling the message codec from the spec is the recommended one: it is a weekend of exacting, satisfying work. The pgwire crate is the honorable escape hatch — it implements the startup, simple-query, and extended-query sub-protocols and ships a complete SQLite-backed example server.2

Learning objectives

  • Implement the protocol codec: framing, StartupMessage's special case, the frontend and backend message set.3
  • Implement the session state machine: startup → auth → query cycles → termination, with correct ReadyForQuery discipline.1
  • Build a tokio accept loop giving each connection its own session and its own transaction state.
  • Map FerricDB results and errors onto RowDescription/DataRow, CommandComplete tags, and SQLSTATE codes.
  • Prove it with psql and the full sqllogictest suite over the wire.

Required reading

  • M11 · The Postgres Wire Protocol — the concept module; its byte explorer and sequence diagrams are your codec's reference behavior.
  • PostgreSQL "Message Formats" — keep it open in a tab the entire milestone; your codec matches it byte for byte. postgresql.org/docs/current/protocol-message-formats.html
  • PostgreSQL "Message Flow" — the state machine. postgresql.org/docs/current/protocol-flow.html

Where this fits

Specification

You implement crates/server and the --serve flag:

pub mod protocol {
    pub enum FrontendMessage { StartupMessage { params: Vec<(String, String)> },
        Query { sql: String }, Parse {..}, Bind {..}, Execute {..},
        Describe {..}, Sync, Terminate, PasswordMessage { password: String } }
    pub enum BackendMessage { AuthenticationOk, AuthenticationCleartextPassword,
        ParameterStatus { name: String, value: String }, BackendKeyData {..},
        ReadyForQuery { txn_status: u8 }, RowDescription { fields: Vec<FieldDescription> },
        DataRow { values: Vec<Option<Vec<u8>>> }, CommandComplete { tag: String },
        ErrorResponse { severity: String, code: String, message: String },
        EmptyQueryResponse, ParseComplete, BindComplete }
    pub struct FieldDescription { pub name: String, pub type_oid: u32,
                                  pub type_len: i16 }
    pub fn read_message(...) -> Result<FrontendMessage>;
    pub fn write_message(...) -> Result<()>;
}

pub struct ServerConfig { pub addr: String /* default 127.0.0.1:5433 */,
                          pub password: Option<String> }
pub struct Server { /* ExecContext factory */ }
impl Server {
    pub fn new(config: ServerConfig, ctx: std::sync::Arc<ExecContext>) -> Self;
    pub async fn run(self) -> Result<()>;   // tokio TCP accept loop
}

Behavioral contract:

  • Framing: type byte + self-inclusive Int32 length, big-endian, except StartupMessage (length-only). Reject SSL requests politely (respond 'N') and ignore CancelRequest connections gracefully.3
  • Startup: trust auth by default (AuthenticationOk immediately); cleartext password when configured. Then at least two ParameterStatus messages (server_version — report a Postgres-compatible string —, client_encoding UTF8), BackendKeyData (any values), ReadyForQuery('I').1
  • Simple query: route the SQL through execute(); SELECTs produce RowDescription (type OIDs: bool 16, int8 20, float8 701, text 25; values in text format) then DataRows (NULL as length −1) then CommandComplete (SELECT n, INSERT 0 n, UPDATE n, DELETE n); every cycle ends with ReadyForQuery carrying the true transaction status (I/T/E).3 Empty query string → EmptyQueryResponse. Errors → ErrorResponse with mapped SQLSTATE (Serialization → 40001, parse → 42601, everything else → XX000-style fallback), then ReadyForQuery — always.
  • Sessions: one tokio task per connection, each with its own transaction slot; BEGIN/COMMIT work per session exactly as in the REPL; a dropped connection with an open transaction rolls it back.
  • Extended protocol (optional): Parse/Bind/Execute/Describe/Sync for the unnamed statement and portal is enough to satisfy most drivers' simple use.1

Step-by-step guidance

  1. Codec first, offline. Implement read_message/write_message over byte buffers (the bytes crate earns its keep here) and drive them with the ms10_ round-trip tests. Get the length arithmetic perfect now: the tests assert exact byte sequences for Query("SELECT 1") among others, straight from the module's byte explorer.
  2. The session state machine as plain code. A per-connection async function: read startup, answer the auth dance, then loop { read message, dispatch }. Keep it a function of (socket, ExecContext) with no shared mutable state beyond what Milestone 8 already synchronizes.
  3. Wire execute(). The result-mapping layer is mechanical: Schema → RowDescription (name + OID per column), rows → text-encoded DataRows, affected counts → tags. Reuse the REPL's value-formatting code — pull it into a shared helper rather than duplicating it.
  4. First contact. cargo run -- --serve then psql -h 127.0.0.1 -p 5433 -U ferric. Expect failure; enjoy it. psql's PGDEBUG-style tracing and a packet capture (tcpdump -X port 5433) are your microscopes. The classic first crash: psql immediately sends a parameterized startup you didn't expect, or an SSLRequest you forgot to decline.
  5. Transaction status discipline. Thread the session's real state into every ReadyForQuery. psql renders it in the prompt (=>, *=>, !=>) — free UI for your MVCC layer.
  6. The suite over the wire. Run the sqllogictest files through a real session: simplest is a small runner mode that pipes each statement through psql (psql -At -c) and compares; if you implemented the extended protocol, run the harness through a Rust Postgres driver instead. Same files, fourth transport — the point of the course's testing pyramid.
  7. Concurrency check. Two psql sessions: BEGIN in both, update the same row, watch first-committer-wins deliver a real 40001 over the wire to the loser. Your whole stack, end to end, standing on every milestone at once.

Test plan

cargo test -p ferricdb-server -- --include-ignored ms10_   # codec round-trips
cargo run -- --db /tmp/wire.db --serve &
psql -h 127.0.0.1 -p 5433 -U ferric -c "SELECT 1;"          # the handshake proof
# then the full slt suite through a live session (see guidance step 6)

The ms10_ group is pure codec: encode/decode round-trips for every message, exact-byte assertions (length includes itself, excludes type byte; StartupMessage typeless; DataRow NULL as −1), and malformed-length rejection. Everything beyond the codec is validated live — this milestone's definition of done is unusually external.

Common pitfalls

Length-field off-by-one

Symptom: psql connects then hangs or reports garbled messages. Cause: counting the type byte in the length, or not counting the length field itself. One wrong constant desynchronizes every subsequent message on the stream. The exact-byte tests exist to catch this before psql does.3

Missing ReadyForQuery after an error

Symptom: the first bad statement freezes the session. Cause: the error path returns early. ErrorResponse tells the client what went wrong; ReadyForQuery tells it that it may speak again. Both, every time.1

Forgetting the SSLRequest and empty query

Symptom: psql fails before authentication, or a bare semicolon kills the session. Modern psql opens with an SSLRequest (answer 'N' and it retries plaintext) and really does send empty query strings (answer EmptyQueryResponse).1

Sharing one transaction across sessions

Symptom: one client's BEGIN puts every client in a transaction. Cause: the transaction slot living in the shared ExecContext instead of per-session state. The two-psql concurrency check in the guidance catches it immediately.

Definition of done

  • ms10_ codec tests pass.
  • psql -h localhost -p 5433 connects, runs CREATE/INSERT/SELECT/UPDATE/DELETE with correct output and tags, survives SQL errors, and shows transaction state in its prompt.
  • The full sqllogictest suite passes through a real psql session.
  • Two concurrent psql sessions demonstrate snapshot isolation and a wire-delivered 40001 on write conflict.
  • Kill the server mid-transaction, restart with recovery (Milestone 9), reconnect: committed data present, uncommitted gone — the whole course in one demo.
