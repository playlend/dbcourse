Ten milestones of storage, indexing, planning, MVCC, and ARIES recovery, and until today only your own REPL has ever spoken to the engine. This milestone turns FerricDB into a real network server speaking the PostgreSQL frontend/backend wire protocol version 3 — judged by the strictest integration test available: real PostgreSQL clients you did not write.1

In line with FerricDB's crate policy, you implement the protocol codec by hand using bytes::BytesMut and big-endian integer framing, with no external PostgreSQL protocol crate. The provided ms10_ suite tests your exact incremental codec functions byte for byte before driving a live TCP connection through Server::serve. Once those tests pass and --serve is wired in crates/ferricdb/src/main.rs, plain psql -h 127.0.0.1 -p 5433 connects without special flags, renders your query tables, displays live MVCC transaction status in its prompt, and receives real SQLSTATE 40001 serialization errors when two terminals race on the same row.13

Learning objectives

  • Implement all four incremental, non-blocking PostgreSQL v3 codec functions over bytes::BytesMut: framing, typeless startup/SSL packets, signed i32 length validation, and exact wire encodings for all 10 frontend and 12 backend message variants.24
  • Implement the per-connection session state machine inside Server::serve: SSLRequest decline (b'N'), startup and trust/cleartext authentication, startup parameter burst, simple-query loop, and clean Terminate / disconnect cleanup.1
  • Isolate concurrent clients with ExecContext::new_session() and bridge synchronous query execution onto tokio::task::spawn_blocking so disk I/O and mutex locks never stall async worker threads.4
  • Map FerricDB QueryResults and Errors onto PostgreSQL type OIDs, text-format DataRow values (including "t" / "f" booleans and -1 NULLs), CommandComplete tags, SQLSTATE codes, and ReadyForQuery transaction status bytes.23
  • Wire ferricdb --db <path> --serve [addr] in crates/ferricdb/src/main.rs (with Milestone 9 WAL recovery on startup) and validate end to end with live psql sessions.

Where this fits

The server crate sits at the top of the dependency DAG: ferricdb-server depends on ferricdb-common, ferricdb-exec, ferricdb-catalog, ferricdb-txn, tokio, and bytes. It knows nothing about slotted pages, B+Trees, or WAL records — every SQL string flows straight into ferricdb_exec::execute on a per-connection ExecContext session, and every result or error translates back into PostgreSQL wire frames.

Specification

From course/ferricdb/docs/api-spec.md, course/ferricdb/crates/server/src/protocol.rs, and course/ferricdb/crates/server/src/lib.rs — the complete verbatim public API to implement in course/ferricdb/crates/server:

// crates/server/src/protocol.rs — verbatim public surface

/// PostgreSQL frontend/backend protocol v3, hand-rolled incremental framing.
pub mod protocol {
    pub const PROTOCOL_VERSION: u32 = 196608; // 3.0
    pub const SSL_REQUEST_CODE: u32 = 80877103;

    #[derive(Clone, Debug, PartialEq, Eq)]
    pub enum FrontendMessage {
        SslRequest,
        StartupMessage { params: Vec<(String, String)> },
        Query { sql: String },
        Parse { statement: String, sql: String, param_types: Vec<u32> },
        Bind { portal: String, statement: String, params: Vec<Option<Vec<u8>>> },
        Execute { portal: String, max_rows: i32 },
        Describe { kind: u8, name: String },
        Sync,
        Terminate,
        PasswordMessage { password: String },
    }

    #[derive(Clone, Debug, PartialEq, Eq)]
    pub enum BackendMessage {
        AuthenticationOk,
        AuthenticationCleartextPassword,
        ParameterStatus { name: String, value: String },
        BackendKeyData { process_id: u32, secret_key: u32 },
        ReadyForQuery { txn_status: u8 },
        RowDescription { fields: Vec<FieldDescription> },
        DataRow { values: Vec<Option<Vec<u8>>> },
        CommandComplete { tag: String },
        ErrorResponse { severity: String, code: String, message: String },
        EmptyQueryResponse,
        ParseComplete,
        BindComplete,
    }

    #[derive(Clone, Debug, PartialEq, Eq)]
    pub struct FieldDescription {
        pub name: String,
        pub type_oid: u32,
        pub type_len: i16,
    }

    // Incremental non-blocking wire codecs (Ok(None) = need more bytes)
    pub fn read_message(buf: &mut bytes::BytesMut, startup: bool) -> Result<Option<FrontendMessage>>;
    pub fn write_message(buf: &mut bytes::BytesMut, msg: &BackendMessage) -> Result<()>;
    pub fn write_frontend_message(buf: &mut bytes::BytesMut, msg: &FrontendMessage) -> Result<()>;
    pub fn read_backend_message(buf: &mut bytes::BytesMut) -> Result<Option<BackendMessage>>;
}

// crates/server/src/lib.rs — verbatim public surface
pub struct ServerConfig {
    pub addr: String,               // default "127.0.0.1:5433"
    pub password: Option<String>,
}
pub struct Server { /* config, Arc<ExecContext> */ }
impl Server {
    pub fn new(config: ServerConfig, ctx: std::sync::Arc<ExecContext>) -> Self;
    pub async fn run(self) -> Result<()>;                                 // bind config.addr + serve
    pub async fn serve(self, listener: tokio::net::TcpListener) -> Result<()>;
}

Key requirements across the codec and live server:

  • All four codec functions are required. read_message and write_message drive the server; write_frontend_message and read_backend_message are their client-side mirrors used by the provided round-trip and live-TCP tests. Every extended-protocol variant (Parse, Bind, Execute, Describe, Sync, ParseComplete, BindComplete) must encode and decode accurately in the codec (tested by ms10_frontend_roundtrips and ms10_backend_roundtrips); wiring extended-protocol execution inside Server::serve is an optional stretch once simple queries pass.
  • Incremental, non-destructive decoding: when buf holds fewer bytes than a complete frame requires, read_message and read_backend_message return Ok(None) and leave buf completely untouched (do not call advance() until you know the entire message is present and valid!). When a full message is available, parse it and consume its exact byte count from the front of buf.4
  • Strict validation: decode every wire length header as a signed i32 (big-endian). Reject any length < 4 (including negative values like -1) immediately with Err(Error::Protocol(_)) rather than casting to u32 and hanging for 4 GiB. For startup == true, lengths < 8 and codes other than PROTOCOL_VERSION (196608) or SSL_REQUEST_CODE (80877103) return Err(Error::Protocol(_)). In both encoders, reject C-string fields containing interior NUL (\0) bytes or column/parameter counts exceeding i16::MAX with Err(Error::Protocol(_)).
  • Server lifecycle: Server::run binds self.config.addr (course default 127.0.0.1:5433 — one port above PostgreSQL's default 5432 so both run side by side) and delegates to self.serve(listener). Splitting serve(listener) out lets ms10_server_ssl_decline_and_simple_query_over_tcp bind an ephemeral port 127.0.0.1:0 cleanly in tests.

Wire format quick reference

Every integer is big-endian (network byte order); every string is UTF-8 followed by a 0x00 NUL byte unless noted; and every length field counts itself (4 bytes) plus the body, excluding any leading type byte.2 Keep this summary table beside you while writing protocol.rs:

Direction / TypeMessageExact body layout & rules
FE · no type byte SslRequest Int32(8), Int32(80877103) (8 bytes total; decoded when startup == true).
FE · no type byte StartupMessage Int32(len), Int32(196608), repeated key\0value\0, final \0.
FE · 'Q' / 'p' Query / PasswordMessage Single C-string (sql\0 or password\0). Note lowercase 'p' for password!
FE · 'P' / 'B' / 'D' / 'E' / 'S' / 'X' Extended & control Parse: stmt\0, sql\0, i16(n), n × u32 OIDs. Bind: portal\0, stmt\0, i16(0) param fmts, i16(n), n × (i32(-1) | i32(len)+bytes), i16(0) result fmts. Describe: u8 ('S'/'P'), name\0. Execute: portal\0, i32(max_rows). Sync / Terminate: empty body (len = 4).
BE · 'R' AuthenticationOk / Cleartext Int32(0) for Ok; Int32(3) for CleartextPassword (len = 8).
BE · 'S' / 'K' / 'Z' ParameterStatus / BackendKeyData / ReadyForQuery 'S': name\0, value\0 (send at least server_version & client_encoding = UTF8). 'K': u32(pid), u32(secret). 'Z': 1 byte — b'I' idle, b'T' in txn, b'E' failed txn.
BE · 'T' RowDescription i16(n), then per field: name\0 + 18 fixed bytes: table_oid: i32 = 0, attr_num: i16 = 0, type_oid: u32, type_len: i16, type_mod: i32 = -1, format_code: i16 = 0 (text).
BE · 'D' DataRow i16(n), then per column: i32(-1) for SQL NULL (no bytes), or i32(bytes.len()) followed by raw UTF-8 text bytes (empty string is i32(0)).
BE · 'C' / 'I' / '1' / '2' CommandComplete / empties 'C': QueryResult::tag + \0 (e.g. "SELECT 3\0", "INSERT 0 2\0"). 'I', '1', '2': empty body (len = 4).
BE · 'E' ErrorResponse b'S' + severity\0, b'C' + code\0, b'M' + message\0, final \0.

SSL negotiation and going further with TLS

Real PostgreSQL clients — including psql with its default sslmode=prefer and libpq drivers — do not send StartupMessage first. Instead, they open every TCP connection with an 8-byte SSLRequest packet: [0x00, 0x00, 0x00, 0x08, 0x04, 0xD2, 0x16, 0x2F] (length 8, code 80877103).12

Because read_message(&mut buf, true) decodes this natively as FrontendMessage::SslRequest, handling it in Server::serve takes only a few lines: loop while in the startup phase; if the decoded message is FrontendMessage::SslRequest, write the single unframed byte b'N' to the socket and stay in the startup = true loop to read the real StartupMessage that the client sends next. That single byte lets plain psql -h 127.0.0.1 -p 5433 -U ferric connect immediately without forcing users to type sslmode=disable.

Going further: real TLS ('S')

Declining SSL with b'N' is standard for local loopback development, but sending PasswordMessage (cleartext password auth) or sensitive SQL over a real network requires transport encryption. PostgreSQL's wire protocol upgrades cleanly in place: when your server wants TLS, reply with a single byte b'S' instead of b'N', immediately run a TLS server handshake over the same TcpStream (for example, wrapping it with tokio-rustls and a local self-signed certificate generated via openssl or rcgen), and then run the exact same startup and query codec over the resulting encrypted AsyncRead + AsyncWrite stream! Once upgraded, psql displays an active TLS cipher banner on connect and protects both passwords and query payloads in transit.1 (Keep b'N' as the default when no certificate is configured so ms10_server_ssl_decline_and_simple_query_over_tcp stays green.)

Step-by-step guidance

Follow this build order: finish the pure byte codec first while every test runs offline in milliseconds, then build the async session loop, and finally wire --serve and test with live psql.

  1. Implement the byte codec in crates/server/src/protocol.rs. Use bytes::{Buf, BufMut, BytesMut} to avoid manual slice index arithmetic.4

    • Encoder helper pattern: for standard framed messages, reserve or build the body in a small scratch BytesMut (or record the length-field offset, append the body, and back-patch the i32 length). Check that 4 + body.len() fits in i32, write the type byte (omitted for SslRequest and StartupMessage), write (4 + body.len()) as i32 in big-endian, then append the body. Write a small helper put_cstring(buf, s) that rejects any interior 0x00 byte with Err(Error::Protocol(_)) before appending s.as_bytes() and 0u8.
    • Decoder peek-before-consume pattern: never mutate buf until the entire frame has arrived (Figure 3):
      • When startup == true: if buf.len() < 4, return Ok(None). Peek len = i32::from_be_bytes(...). If len < 8, return Err(Error::Protocol(_)). If buf.len() < len as usize, return Ok(None). Now consume let mut frame = buf.split_to(len as usize);, skip the 4-byte length, read code = frame.get_u32(): match SSL_REQUEST_CODE (verify len == 8 → SslRequest) or PROTOCOL_VERSION (parse key\0value\0 pairs up to the trailing 0x00 → StartupMessage); any other code returns Err(Error::Protocol(_)).
      • When startup == false: if buf.len() < 5, return Ok(None). Peek tag = buf[0] and len = i32::from_be_bytes(buf[1..5]). If len < 4, return Err(Error::Protocol(_)). Total frame bytes = 1 + len as usize; if buf.len() < total, return Ok(None). Consume let mut frame = buf.split_to(total);, advance past the 5-byte header, and decode the body by tag (mirroring the exact same pattern in read_backend_message).

    Run cargo test -p ferricdb-server -- --include-ignored ms10_ — the first 10 codec tests (all except the live TCP test) should pass immediately!

  2. Build the per-connection session loop in crates/server/src/lib.rs. Inside Server::serve(self, listener), loop on let (socket, _) = listener.accept().await?;. Clone the config password and create an isolated session: let session = Arc::new(self.ctx.new_session());, then tokio::spawn an async handler task per connection (logging any unexpected connection error cleanly without crashing the accept loop). Inside the connection task:

    1. Maintain two buffers: read_buf = BytesMut::with_capacity(4096) and write_buf = BytesMut::with_capacity(4096).
    2. Startup loop (startup = true): read from the socket with socket.read_buf(&mut read_buf).await? (return cleanly on 0 bytes EOF) and call read_message(&mut read_buf, true)?. On SslRequest, write &[b'N'] to the socket and continue the startup loop. On StartupMessage, exit the startup loop.
    3. Authentication: if password is None, encode AuthenticationOk. If Some(expected), encode AuthenticationCleartextPassword, flush write_buf so the client actually receives the challenge, read a PasswordMessage (startup = false), and either encode AuthenticationOk on match or send ErrorResponse { severity: "FATAL", code: "28P01", ... } (flushed) and close the connection on mismatch.
    4. Startup burst: encode ParameterStatus("server_version", "16.0 (FerricDB)"), ParameterStatus("client_encoding", "UTF8"), BackendKeyData { process_id, secret_key }, and ReadyForQuery { txn_status: b'I' }, then flush write_buf.
    5. Query loop (startup = false): drain every complete message already sitting in read_buf via while let Some(msg) = read_message(&mut read_buf, false)? before issuing another socket.read_buf (Figure 3 — a client may pipeline Query and Terminate in a single TCP segment!). On Terminate or TCP EOF, break out of the loop and execute cleanup: if session.current_txn holds an open transaction, run ferricdb_exec::execute("ROLLBACK", &session) inside spawn_blocking so the engine's normal rollback path aborts the transaction (and runs WAL physical undo + CLRs when attached) and dropped clients never leak active snapshots that stall VACUUM.

  3. Bridge ferricdb_exec::execute cleanly with spawn_blocking. ferricdb_exec::execute performs synchronous buffer-pool I/O, disk fsyncs, and std::sync::Mutex locking. Never invoke it directly inside an async task on a tokio worker thread — doing so stalls other concurrent client connections! Instead, clone Arc::clone(&session) and await tokio::task::spawn_blocking(move || ferricdb_exec::execute(&sql, &s)).await.4

    Translate the result onto the wire:

    • Empty or whitespace/semicolon-only sql (where execute returns an empty Vec<QueryResult>): send EmptyQueryResponse.
    • For each QueryResult in the returned vector:
      • If res.explain is Some(plan_text): emit a single-column RowDescription (FieldDescription { name: "QUERY PLAN".into(), type_oid: 25, type_len: -1 }), one DataRow per line of plan_text, and CommandComplete { tag: "EXPLAIN".into() } — just like real PostgreSQL so psql prints EXPLAIN plans as a clean table!
      • Else if !res.schema.columns.is_empty(): emit RowDescription using the OID table above, one DataRow per row (rendering Value::Null as None and Value::Boolean(b) as "t" / "f"), and CommandComplete { tag: res.tag }.
      • Else (DDL / DML / TCL): emit CommandComplete { tag: res.tag }.
    • On Err(e): map e to ErrorResponse with the matching SQLSTATE (42601, 42P01/42703, 40001, or XX000).
    • Always finish the query cycle by computing the session's live transaction status byte — b'E' if *session.failed_txn.lock().unwrap(), else b'T' if session.current_txn.lock().unwrap().is_some(), else b'I' — and appending ReadyForQuery { txn_status }, then flushing write_buf to the socket.1

    Now re-run cargo test -p ferricdb-server -- --include-ignored ms10_ — all 11 tests including ms10_server_ssl_decline_and_simple_query_over_tcp should now pass!

  4. Wire --serve in crates/ferricdb/src/main.rs. Open course/ferricdb/crates/ferricdb/src/main.rs around lines 41–47. Because main() stays synchronous for the interactive rustyline REPL, build a tokio::runtime::Runtime::new() inside the if let Some(addr) = serve branch: open the database (using db_path or a temp file), run Milestone 9 WAL recovery + TransactionManager::restore + WalHook wiring, wrap the resulting ExecContext in Arc::new(ctx), construct Server::new(ServerConfig { addr, password: None }, ctx), print the listening address to stderr, and call rt.block_on(server.run()).

  5. First live contact with psql and concurrent sessions. Start FerricDB in one terminal with cargo run -p ferricdb -- --db /tmp/ferric_wire.db --serve, then connect from a second terminal with psql -h 127.0.0.1 -p 5433 -U ferric. Watch the prompt change from => to *=> after BEGIN; and to !=> after an error inside a transaction until ROLLBACK; — free UI confirming your ReadyForQuery state machine! If anything hangs or desynchronizes, inspect raw bytes with tcpdump -i lo0 -X port 5433 (macOS) or tcpdump -i lo -X port 5433 (Linux).

Common pitfalls

Pitfall — signed vs. unsigned length decoding and off-by-one framing

Symptom: ms10_negative_length_and_bad_startup_version_error hangs or returns Ok(None) instead of Err(Error::Protocol), or psql stalls after the first message. Cause: decoding the 4-byte length as u32 (so -1 looks like a 4 GiB partial frame waiting for more bytes), or counting the type byte inside the length field. Always decode lengths as big-endian i32, reject < 4 immediately, and remember the length counts itself plus body, never the type byte.2

Pitfall — omitting ReadyForQuery after an error or empty query

Symptom: psql freezes forever after the first syntax error, failed transaction, or bare ;. Cause: returning early on Err(e) or empty SQL without emitting ReadyForQuery. Both ErrorResponse and EmptyQueryResponse must always be followed by ReadyForQuery with the session's true transaction status ('I', 'T', or 'E').1

Pitfall — blocking tokio workers or sharing one ExecContext

Symptom: one client's BEGIN puts every connected psql session inside the same transaction, or a slow query freezes every other client's handshake. Cause: passing self.ctx directly instead of calling self.ctx.new_session() per accepted TCP connection, or calling synchronous ferricdb_exec::execute directly on a tokio worker thread instead of wrapping it in tokio::task::spawn_blocking.4

Pitfall — forgetting to drain multiple buffered messages or encoding booleans as "true"

Symptom: ms10_two_messages_in_one_buffer_parse_in_order fails, a pipelined Terminate hangs until timeout, or Postgres drivers fail to parse boolean columns. Cause: calling read_message once per read_buf instead of looping while let Some(msg) = read_message(...), or formatting Value::Boolean with Rust's to_string() instead of PostgreSQL's wire text representation "t" / "f" for OID 16.

Pitfall — leaking an active transaction when a client disconnects

Symptom: killing a psql terminal with Ctrl-C / kill while inside BEGIN permanently pins oldest_visible_xid() so VACUUM never reclaims dead versions. Cause: breaking out of the connection loop on TCP EOF without checking session.current_txn and calling txn_manager.abort(&txn).
