Until now, Planner::optimize has been the identity function: whatever tree Planner::plan transcribed from the bound query went straight to execution, and Milestone 5's rule picked an index blindly whenever one matched a predicate. On a tiny table that habit hides in the noise. On a multi-table join or a non-selective range filter over thousands of rows, the difference between a good plan and a naive one is orders of magnitude in page reads.15

This milestone gives your planner a real optimizer modeled on System R and PostgreSQL. The work decomposes cleanly into four independent layers that you can build and verify in order: (1) parser and catalog plumbing for ANALYZE, EXPLAIN, and persisted statistics; (2) semantics-preserving logical rewrites that need no statistics at all; (3) selectivity estimation and a dimensionless cost model; and (4) cost-based access-path selection, join strategy and ordering, and the EXPLAIN / EXPLAIN ANALYZE renderer. Build and test each layer before moving to the next, and the optimizer stays understandable from top to bottom.

Learning objectives

  • Extend the SQL parser in crates/sql to accept ANALYZE [table] and EXPLAIN [ANALYZE] <statement>, and wire both through the binder and dispatcher in crates/exec.
  • Implement durable table and column statistics in crates/catalog (row_count, page_count, per-column min, max, distinct_estimate, and null_count) gathered by ANALYZE.
  • Implement rule-based logical plan rewrites: constant folding (honoring SQL three-valued logic and NULL propagation), predicate pushdown across joins using table_idx containment, and redundant-projection cleanup.
  • Implement Selinger-style selectivity estimation and a PostgreSQL-style cost model (SEQ_PAGE_COST, RANDOM_PAGE_COST, CPU_TUPLE_COST) in crates/exec/src/cost.rs.12
  • Replace Milestone 5's always-index heuristic with cost-based SeqScan vs. IndexScan selection, and choose between HashJoin (building on the smaller left input) and NestedLoopJoin within a left-deep join orderer.13
  • Implement EXPLAIN (plan-only, zero side effects) and EXPLAIN ANALYZE (real execution with actual row counts and timing).4

Where this fits

Every physical building block the optimizer needs is already implemented below it: HeapFile and BPlusTree give you two access paths per indexed table, and Milestone 6 gave you two join operators — NestedLoopJoin (which accepts any join predicate or cross product) and HashJoin (which executes equi-joins by building a hash table on its left child and probing with its right child). Notice that FerricDB's LogicalPlan intentionally omits sort-merge join, so your optimizer has a tight, concrete physical search space: two scan methods and two join methods, priced against statistics stored in the catalog.

Specification

1. SQL parser extensions (crates/sql)

The keywords Keyword::Analyze and Keyword::Explain and the two AST variants already exist in course/ferricdb/crates/sql/src/ast.rs, but Milestone 3 did not parse them yet. Extend Parser::parse in course/ferricdb/crates/sql/src/lib.rs to recognize these two productions:

// crates/sql/src/ast.rs — already declared; wire into Parser::parse in MS7:
Analyze { table: Option<String> },                                  // MS7
Explain { analyze: bool, inner: Box<Statement> },                   // MS7

// Grammar in crates/sql/src/lib.rs:
//   analyze := "ANALYZE" [ ident ]
//   explain := "EXPLAIN" [ "ANALYZE" ] statement

ANALYZE with no table name parses as Analyze { table: None } (meaning analyze every user table); ANALYZE users parses as Analyze { table: Some("users".into()) }. EXPLAIN parses an optional ANALYZE keyword and then recursively parses the inner statement (any valid statement, such as SELECT, UPDATE, or DELETE). In crates/exec/src/binder.rs, bind Statement::Analyze into BoundStatement::Analyze { table: Option<TableInfo> } (rejecting an unknown table name with Error::Bind) and Statement::Explain into BoundStatement::Explain { analyze, inner } by recursively binding the inner statement.

2. Persisted statistics (crates/catalog)

From course/ferricdb/docs/api-spec.md and course/ferricdb/crates/catalog/src/lib.rs, implement the statistics persistence surface:

// crates/catalog/src/lib.rs — verbatim public surface for Milestone 7

/// Per-column statistics gathered by ANALYZE (Milestone 7).
#[derive(Clone, Debug, Default)]
pub struct ColumnStats {
    pub min: Option<Value>,
    pub max: Option<Value>,
    pub distinct_estimate: u64,
    pub null_count: u64,
}

#[derive(Clone, Debug, Default)]
pub struct TableStats {
    pub row_count: u64,
    pub page_count: u32,
    pub columns: Vec<ColumnStats>,
}

impl Catalog {
    pub fn stats(&self, table: &str) -> Result<Option<TableStats>>;         // MS7
    pub fn set_stats(&self, table: &str, stats: TableStats) -> Result<()>;  // MS7
}

Behavioral contract for catalog statistics:

  • Existing, never-analyzed table: catalog.stats("users") returns Ok(None). Analyzing one table must never synthesize statistics for any other table.
  • Unknown table: both stats("ghost") and set_stats("ghost", ...) return Err(Error::Catalog(_)), never Ok(None).
  • Overwrite semantics: a subsequent set_stats for the same table replaces the previous statistics cleanly (both in the in-memory cache and on disk).
  • Durability across reopen: persist statistics in the catalog's own heap storage (for example, a dedicated fixed-page __stats system table bootstrapped alongside __tables and __columns, or a stats-root pointer in your catalog header) so closing and reopening the database via Catalog::bootstrap restores row_count, page_count, and every column's min, max, distinct_estimate, and null_count verbatim.

3. Cost model & optimizer (crates/exec)

From course/ferricdb/docs/api-spec.md, course/ferricdb/crates/exec/src/cost.rs, and course/ferricdb/crates/exec/src/lib.rs:

// crates/exec/src/cost.rs — verbatim public surface
pub mod cost {                                                 // MS7
    pub const SEQ_PAGE_COST: f64 = 1.0;      // matches Postgres defaults
    pub const RANDOM_PAGE_COST: f64 = 4.0;
    pub const CPU_TUPLE_COST: f64 = 0.01;
    pub struct CostModel<'a> { /* &'a Catalog */ }
    impl<'a> CostModel<'a> {
        pub fn new(catalog: &'a Catalog) -> Self;
        pub fn plan_cost(&self, plan: &LogicalPlan) -> f64;
        pub fn selectivity(&self, table: &TableInfo, pred: &BoundExpr) -> f64;
    }
}

// crates/exec/src/lib.rs — verbatim public surface
impl<'a> Planner<'a> {
    pub fn new(ctx: &'a ExecContext) -> Self;
    pub fn plan(&self, stmt: binder::BoundStatement) -> Result<plan::LogicalPlan>;
    /// MS4: identity; MS7: rewrite rules + cost-based access path & join order.
    pub fn optimize(&self, plan: plan::LogicalPlan) -> Result<plan::LogicalPlan>;
    pub fn create_executor(&self, plan: &plan::LogicalPlan) -> Result<Box<dyn Executor>>;
}

The optimizer's behavioral contract:

  • Constant folding: evaluate constant subexpressions inside BoundExpr down to BoundExpr::Literal at plan time (e.g., 2 * (3 + 4) becomes Literal(Integer(14))), propagating SQL NULL according to three-valued logic (NULL + 1 -> NULL, false AND NULL -> false, true OR NULL -> true). Do not panic on constant division or modulo by zero during optimization — leave it unfolded so the executor raises the runtime error if that expression is actually evaluated. Folding must preserve the surrounding plan node (a Projection remains a Projection).
  • Predicate pushdown: split conjunctive AND predicates into individual conjuncts and push each conjunct as far down the plan tree as is semantically legal. A conjunct may move below a join into its left or right child only if every BoundExpr::Column { table, .. } it references belongs to a scan inside that child. A single-table conjunct reaching a SeqScan lands either fused into SeqScan::filter or in a Filter node directly above that SeqScan; a conjunct referencing columns from both join sides stays at the join (or above it).
  • Selectivity estimation: CostModel::selectivity(table, pred) returns a finite f64 clamped to [0.0, 1.0]. Use System R's formulas when catalog statistics exist and fall back to Selinger's documented guesses when Catalog::stats returns Ok(None) or a column is not interpolatable:1
    • Equality col = lit: 1.0 / distinct_estimate when distinct_estimate > 0; fallback 0.1 (1/10) without stats.
    • Inequality col != lit: 1.0 - sel(col = lit).
    • Range col > lit / col >= lit: (max - lit) / (max - min) for numeric columns when max > min; symmetric (lit - min) / (max - min) for < / <=; fallback 1.0 / 3.0 when stats are absent or the column is Text. Handle degenerate bounds cleanly (if lit <= min for >, return 1.0; if lit >= max, return a tiny floor or 0.0; if min == max, avoid dividing by zero!).
    • Null checks: col IS NULL ⇒ null_count / row_count (fallback 0.05); col IS NOT NULL ⇒ complement.
    • Boolean connectives: A AND B ⇒ sel(A) * sel(B) (independence assumption); A OR B ⇒ sel(A) + sel(B) - sel(A) * sel(B); NOT A ⇒ 1.0 - sel(A).
    • Document the uniformity and independence assumptions explicitly in your rustdoc for CostModel, because violating them on skewed or correlated columns is the exact phenomenon EXPLAIN ANALYZE exposes.5
  • Access-path selection: for each base scan whose filter yields usable bounds on an indexed column in table.indexes, construct both candidate plans (SeqScan with the filter, and IndexScan plus any residual Filter for predicates not enforced by the index bounds), price both with CostModel::plan_cost, and keep the cheaper plan. This replaces Milestone 5's always-use-index rule.
  • Join method and ordering: choose HashJoin whenever an equi-join predicate connects two join inputs — placing the smaller estimated input on the left (build) side and the larger input on the right (probe) side — and NestedLoopJoin for non-equi or cross joins. For queries joining multiple tables, order them as a left-deep tree via Selinger subset dynamic programming (or greedy for > 8 tables), preferring connected pairs with a join predicate over cross products.13

4. Exact EXPLAIN and EXPLAIN ANALYZE contract

The provided test suite inspects QueryResult::explain directly. Match the exact contract documented in course/ferricdb/crates/exec/src/lib.rs:

  • Line-oriented structural format: render the optimized LogicalPlan tree with one plan node per line, indented by tree depth (two spaces per level is clean and readable). Each line must start (immediately after indentation) with the verbatim LogicalPlan variant name — Projection, Filter, SeqScan, IndexScan, HashJoin, NestedLoopJoin, Aggregate, Sort, Limit, Insert, Update, Delete, Values — followed by helpful details such as table name, index name, estimated cost, and estimated row count. Example shape: 
    Projection (cost=16.02 rows=1)
  IndexScan on t using t_id (cost=16.01 rows=1)
  • EXPLAIN <stmt> does NOT execute <stmt>: plan and optimize the inner statement, render the plan string into QueryResult::explain = Some(text), leave rows empty and affected = 0, and set tag = "EXPLAIN".into(). Running EXPLAIN DELETE FROM t must leave every row of t untouched.4
  • EXPLAIN ANALYZE <stmt> DOES execute <stmt>: lower the optimized plan to executors wrapped in a lightweight timing-and-counting instrumented executor, run the tree to completion (performing all side effects on INSERT/UPDATE/DELETE, just as PostgreSQL does4), discard the result rows (keeping QueryResult::rows empty), and return the rendered tree in QueryResult::explain = Some(text) annotated with each node's actual row count and elapsed time in milliseconds. Print a clear reminder in the REPL whenever a user runs EXPLAIN ANALYZE on a data-modifying statement.

Worked selectivity and cost example

Before writing code, trace the exact scenario tested by ms7_analyze_then_explain_picks_access_path in crates/exec/tests/exec.rs by hand. Doing the arithmetic once guarantees your constants, page counts, and crossover point agree with reality.2

Suppose table t (id INTEGER PRIMARY KEY, grp INTEGER) holds N = 2,000 rows with id ∈ [0, 1999] and grp = id % 4, with B+Tree index t_id on id. Each heap tuple carries a 16-byte TupleMeta header, a 1-byte null bitmap, and two 8-byte INTEGER values (33 bytes) plus a 4–6 byte line pointer — about 39 bytes per row. Inside an 8,192-byte heap page (minus 28 bytes of header), roughly 205 rows fit per page, so the heap spans P = 10 pages. Running ANALYZE t stores:

StatisticTable tColumn id (col 0)Column grp (col 1)
row_count / page_count2000 rows / 10 pages——
min / max—0 / 19990 / 3
distinct_estimate / null_count—2000 / 04 / 0

Now price the two queries from the test suite using FerricDB's course constants (chosen to match PostgreSQL's defaults:2 SEQ_PAGE_COST = 1.0, RANDOM_PAGE_COST = 4.0, CPU_TUPLE_COST = 0.01). For a sequential scan, every page and every tuple is visited regardless of selectivity: cost(SeqScan) = SEQ_PAGE_COST · P + CPU_TUPLE_COST · N = 1.0 · 10 + 0.01 · 2000 = 30.0. For an unclustered B+Tree index scan of height h ≈ 2 over an index of roughly L ≈ 4 leaf pages (510 integer entries per leaf), matching M = s · N rows requires descending h internal levels, reading ⌈s · L⌉ leaf pages, and performing up to M random heap fetches: cost(IndexScan) = RANDOM_PAGE_COST · (h + ⌈s · L⌉ + M) + CPU_TUPLE_COST · M.

Query predicateSelectivity sEst. rows MSeqScan costIndexScan costWinner
WHERE id = 42 1 / 2000 = 0.0005 1 1.0·10 + 0.01·2000 = 30.0 4.0·(2 + 1 + 1) + 0.01·1 = 16.01 IndexScan
WHERE id > 2 (1999 − 2) / 1999 ≈ 0.999 1998 1.0·10 + 0.01·2000 = 30.0 4.0·(2 + 4 + 1998) + 0.01·1998 ≈ 8,036 SeqScan

Even if you cap heap fetches at min(M, P) = 10 pages (assuming a lucky buffer pool), IndexScan for id > 2 still pays 4.0 · (2 + 4 + 10) + 19.98 = 83.98 > 30.0 because random I/O costs 4× sequential I/O and the scan also reads the index leaves. Notice where the crossover lies: setting 4.0 · (3 + M) + 0.01 · M = 30.0 solves to M ≈ 4.5 rows (s ≈ 0.22%) on a 10-page table. On a 1,000-page table the crossover shifts higher, but the shape is identical: a flat sequential line intersected by a steep index line (Figure 2).

Step-by-step guidance

Work through these steps in sequence. Each step unlocks a specific subset of the provided tests before you build the next layer on top of it.

  1. Parse ANALYZE and EXPLAIN, and persist catalog stats. Start in crates/sql/src/lib.rs: dispatch on Keyword::Analyze (optional identifier → Statement::Analyze) and Keyword::Explain (optional Keyword::Analyze, then recursive statement parse → Statement::Explain). Run cargo test -p ferricdb-sql -- --include-ignored ms7_ until ms7_analyze_and_explain_parse passes. Next, wire Binder::bind for both statements in crates/exec/src/binder.rs.

    Then implement Catalog::stats and Catalog::set_stats in crates/catalog/src/lib.rs. Store statistics in your catalog's own page-backed storage — for example, a fixed-page __stats heap file allocated at bootstrap alongside __tables and __columns (or chained off your catalog metadata page if your bootstrap already allocated fixed page IDs 0..N; if you add a new page on an existing database file, handle stores created before stats existed cleanly). Serialize TableStats (table name, row_count, page_count, column count, and each ColumnStats with tagged Option<Value> min/max). On overwrite, tombstone the old stats row and insert the new one, and update the in-memory CatalogCache::stats map. Verify with cargo test -p ferricdb-catalog -- --include-ignored ms7_.

  2. Implement ANALYZE execution. In crates/exec/src/lib.rs, dispatch BoundStatement::Analyze { table } directly inside execute() (bypassing Planner::plan). Resolve the target list: either vec![table_info] or all tables from ctx.catalog.tables()?. For each table, scan its HeapFile once, counting live rows and distinct heap pages visited (walking the page chain via HeapPageRef::next_page so even an empty table reports page_count >= 1). Per column, track null_count, running min and max via Value::sql_cmp, and distinct non-NULL values. At course scale, an exact HashSet (normalizing Float via to_bits() or converting to a comparable key) is fast and exact; note in a doc comment that production systems sample blocks and use sketches such as HyperLogLog to bound memory. Persist with ctx.catalog.set_stats and return QueryResult with tag = "ANALYZE".into().

  3. Build rule-based rewrites before touching costs. Organize Planner::optimize as an explicit multi-pass pipeline over LogicalPlan:

    1. Constant folding: write a recursive helper fold_expr(expr: BoundExpr) -> BoundExpr that folds children first and evaluates Unary, Binary, IsNull, and Cast nodes whose operands are all BoundExpr::Literal. Reuse your Milestone 4 expression evaluator so NULL propagation and SQL three-valued logic stay identical in one place. Apply fold_expr across every expression in every LogicalPlan variant without changing node kinds (so ms7_constant_folding sees its Projection intact).
    2. Predicate pushdown: write a helper referenced_tables(expr: &BoundExpr) -> BTreeSet<usize> collecting every BoundExpr::Column { table, .. }, and a companion output_tables(plan: &LogicalPlan) -> BTreeSet<usize> collecting the table_idx of every SeqScan / IndexScan in a subtree. Split a Filter's predicate on top-level AND into a list of conjuncts. When pushing a conjunct down through a NestedLoopJoin or HashJoin: if its referenced tables are a subset of output_tables(left), push it onto left; if a subset of output_tables(right), push it onto right; otherwise keep it at the join (for NestedLoopJoin, you may merge it into on). When a conjunct reaches a SeqScan, combine it into SeqScan::filter (or leave a Filter right above the scan). Never push a predicate containing BoundExpr::InputRef below an Aggregate or Projection that produces that ref.
    3. Projection cleanup: if your planner ever stacks redundant pass-through Projection nodes, collapse them; otherwise keep the top-level Projection schema untouched so column names and aliases remain exact.

    Verify right now with ms7_constant_folding and ms7_predicate_pushdown_single_side.

  4. Implement CostModel::selectivity and CostModel::plan_cost. In crates/exec/src/cost.rs, build selectivity(table, pred) first as a recursive match on BoundExpr:

    • Handle normalized column-literal comparisons regardless of operand order (rewrite 42 = id to id = 42 by flipping the comparison operator).
    • Look up self.catalog.stats(&table.name); if Ok(Some(stats)) and stats.row_count > 0, compute exact Selinger fractions from stats.columns[col_idx]; otherwise use the honest fallback guesses (0.1 for =, 1.0 / 3.0 for ranges, 0.05 for IS NULL).
    • Guard every denominator: if distinct_estimate == 0, fall back to 0.1; if min == max in range interpolation, return 1.0 or 0.0 by comparing the literal directly against min; and clamp the final return value with .clamp(0.0, 1.0) so NaN or negative values can never poison downstream costs.

    Next, write an internal helper estimate(&self, plan: &LogicalPlan) -> (f64 /*cost*/, f64 /*rows*/) that plan_cost delegates to. Price every node recursively:

    • SeqScan { table, filter, .. }: fetch (rows, pages) from catalog stats (fallback e.g. 1000 rows, 10 pages when unanalyzed); cost = SEQ_PAGE_COST * pages + CPU_TUPLE_COST * rows; output rows = (rows * filter_sel).max(1.0) (or 0.0 if rows == 0).
    • IndexScan { table, lower, upper, .. }: convert the lower / upper bounds back into a selectivity s (using 1/distinct when lower == upper is an equality point lookup, or range interpolation for open/closed intervals); matching rows M = (rows * s).max(1.0); approximate B+Tree height h = (rows.max(2.0).log(256.0)).ceil().max(1.0) and leaf pages L = (rows / 256.0).ceil().max(1.0); cost = RANDOM_PAGE_COST * (h + (s * L).ceil() + M) + CPU_TUPLE_COST * M. State your unclustered-heap assumption in the rustdoc.2
    • Filter { input, predicate }: child cost + CPU_TUPLE_COST * child_rows; output rows scaled by selectivity.
    • NestedLoopJoin { left, right, on }: left_cost + left_rows * right_cost + CPU_TUPLE_COST * left_rows * right_rows (reflecting the outer loop re-scanning the inner relation per outer row).
    • HashJoin { left, right, .. }: left_cost + right_cost + CPU_TUPLE_COST * (2.0 * left_rows + right_rows) plus a small build-side penalty (e.g., 1.5 * CPU_TUPLE_COST * left_rows) so the cost model strictly prefers placing the smaller relation on the left build side!
    • Projection, Sort (N log₂ N · CPU_TUPLE_COST), Aggregate, Limit: child cost plus linear/log CPU work.

  5. Cost-based access path selection. First, remove Milestone 5's unconditional IndexScan branch from Planner::plan (so plan() always emits SeqScan + Filter, letting optimize() own every access-path decision; alternatively, also evaluate SeqScan whenever optimize() visits an existing IndexScan). Otherwise selective-vs-unselective tests like ms7_analyze_then_explain_picks_access_path (WHERE id > 2) will stay pinned on IndexScan. Next, walk the rewritten plan bottom-up. Whenever you visit a SeqScan { table_idx, table, filter: Some(pred) } (or a Filter directly above a SeqScan), inspect each index in table.indexes. Extract the tightest (lower, upper) bounds on that index's column from the conjunctive terms of pred, keeping any remaining conjuncts as a residual filter. Build the candidate IndexScan { table_idx, table, index, lower, upper } (wrapped in a Filter if residual conjuncts remain), compare cost_model.plan_cost(&idx_candidate) against cost_model.plan_cost(&seq_candidate), and keep whichever has the lower cost. Remember to guard against Value::Null and Float(NaN) bounds (B+Tree rejects them, so those predicates stay on SeqScan).

  6. Join strategy selection and Selinger left-deep join ordering. First, handle single joins cleanly: given a join of left and right with predicate on, extract equi-join conjuncts of the form left_col = right_col (where one side references only left's table_idxs and the other only right's). If at least one equi-pair exists, build HashJoin with the smaller estimated child on the left (build side) and the larger on the right (probe side), wrapping any leftover non-equi conjuncts in a Filter above the join; otherwise keep NestedLoopJoin.

    Next, generalize to multi-table inner/cross join trees (up to ~8 tables) using Selinger subset dynamic programming (Figure 3).1 Flatten contiguous inner/cross joins into a vector of base scan plans scans[0..n] (each already carrying its winning single-table access path and its original table_idx!) plus the list of all inter-table join conjuncts. Because every SeqScan and IndexScan carries its own table_idx, reordering tables inside the join tree never breaks BoundExpr::Column { table, column } — Planner::create_executor resolves column offsets dynamically from each subtree's table_idx layout! Here is the published System R subset-DP structure in pseudocode:13

    // Published System R subset-DP (Selinger et al. 1979) — left-deep join order
memo: Map<Bitmask, (LogicalPlan, cost: f64, est_rows: f64)>
for i in 0..n:
    memo[1 << i] = (best_scan[i], plan_cost(best_scan[i]), est_rows(best_scan[i]))

for subset_size in 2..=n:
    for each mask with popcount(mask) == subset_size:
        best = None
        for each i in mask:                        // try adding base table i last
            prev = mask ^ (1 << i)
            let (prev_plan, _, prev_rows) = memo[prev]
            let (scan_plan, _, scan_rows) = memo[1 << i]
            connecting_preds = preds touching BOTH prev and {i} (and nothing outside mask)
            // Keep cross-product candidates priced honestly (or only skip i when some
            // other j ∉ prev still has a predicate connecting to prev) so disconnected
            // queries like `(a JOIN b) CROSS JOIN c` still explore `(a ⋈ b) × c`.
            candidate = build_best_join(prev_plan, scan_plan, connecting_preds)
            // Inside build_best_join: if equi-preds exist, emit HashJoin with
            // min(prev_rows, scan_rows) on the LEFT build side; else NestedLoopJoin.
            c = plan_cost(candidate)
            if best is None or c < best.cost:
                best = Some((candidate, c, est_join_rows(prev_rows, scan_rows, connecting_preds)))
        memo[mask] = best

return memo[(1 << n) - 1].plan

    Notice one subtle detail in the pseudocode: inside build_best_join, HashJoin builds its hash table on the left child, so when scan_rows < prev_rows you may place scan_plan on the left and prev_plan on the right (turning that single step into a smaller hash build) — or if you keep strictly left-deep shape where prev_plan stays on the left, still compare both orientations at size 2 so the smaller base table builds the first hash table. For queries with more than ~10 tables, fall back to a greedy loop that repeatedly attaches the remaining table producing the smallest estimated intermediate result.

  7. Wire EXPLAIN and EXPLAIN ANALYZE. In execute(), handle BoundStatement::Explain { analyze, inner }: plan and optimize *inner via planner.plan → planner.optimize. Write a recursive formatter over &LogicalPlan that prints two spaces per depth level, the exact LogicalPlan variant name, target table/index/keys, and cost + estimated rows from CostModel. When analyze == false, return immediately without calling create_executor. When analyze == true, wrap each lowered Box<dyn Executor> in a tiny InstrumentedExecutor struct holding a shared Arc<Mutex<NodeStats>> (actual_rows: u64, elapsed: Duration) that times open/next/close and increments actual_rows on every Ok(Some(_)); drain the root executor to completion, then format the plan tree with both estimates and actuals side by side.4

Tests you should write yourself: the provided suite deliberately leaves four critical edge cases for your own unit tests — add them to crates/exec while building so bugs surface early:

  • ANALYZE on an empty table and a constant column: verify row_count == 0, min == max == None, and a column where every row has value 7 (min == max) never produces NaN or inf in CostModel::selectivity or plan_cost.
  • Cross-side predicate non-pushdown: assert that Filter(t0.a + t1.b = 10) above a join stays at or above the join rather than being pushed into either child.
  • Multi-table join ordering: seed three or four tables with skewed sizes (e.g., 100 / 1,000 / 5,000 rows) and assert that Planner::optimize produces a strictly lower CostModel::plan_cost than the naive left-to-right cross/join plan, and that executing both plans returns identical sorted rows.
  • NULL constant folding: verify 1 + NULL folds to Literal(Null), false AND NULL folds to Literal(Boolean(false)), and true OR NULL folds to Literal(Boolean(true)).

Common pitfalls

Pitfall — pushing a predicate across the wrong boundary

Symptom: runtime index-out-of-bounds panics in expression evaluation, or silently wrong join answers. Cause: pushing a predicate below an operator whose subtree does not contain every table_idx referenced by the predicate (most commonly pushing a two-table predicate like t0.x = t1.y into one child, or pushing a post-aggregate filter below Aggregate). Compute output_tables(child) from each scan's table_idx and push only when referenced_tables(conjunct).is_subset(&output_tables(child)).

Pitfall — NaN or division by zero on empty or constant columns

Symptom: the planner picks arbitrary plans because every NaN < cost comparison evaluates to false. Cause: interpolating (max - lit) / (max - min) when min == max, dividing 1.0 / distinct_estimate when distinct_estimate == 0, or dividing null_count / row_count on an empty table. Guard every denominator, treat min == max explicitly, and clamp selectivity to [0.0, 1.0].

Pitfall — forgetting residual predicates on IndexScan

Symptom: slt_all fails after enabling cost-based index scans. Cause: replacing SeqScan(filter: id > 10 AND grp = 2) with IndexScan(id > 10) and dropping grp = 2! Only the bounds enforced by the index belong in IndexScan::{lower, upper}; every other conjunct must stay wrapped in a Filter node above the IndexScan.

Pitfall — building HashJoin on the larger side or enumerating permutations

Symptom: join planning blows up on 6+ tables, or HashJoin builds a huge hash table when a tiny table was available. Cause: memoizing on ordered sequences (n!) instead of subset bitmasks (2ⁿ),1 or forgetting that FerricDB's HashJoin builds on left and probes with right. Key the DP table by bitmask, and swap left/right (along with left_keys/right_keys) whenever the right child has fewer estimated rows.

Pitfall — fragile EXPLAIN assertions or wrong variant names

Symptom: ms7_analyze_then_explain_picks_access_path fails even though your optimizer chose the right scan. Cause: printing Postgres-style spaced names like "Index Scan" or "Seq Scan" instead of FerricDB's verbatim LogicalPlan variant names (IndexScan, SeqScan, HashJoin). Match the variant names in crates/exec/src/lib.rs, and in your own tests assert structural markers rather than exact floating-point cost strings.

Definition of done

  • All three ms7_ test groups pass (ferricdb-sql, ferricdb-catalog, ferricdb-exec), and slt_all plus all earlier milestone suites remain green.
  • In the REPL, on a 2,000+ row table with an index on id: after ANALYZE, EXPLAIN SELECT ... WHERE id = 42 prints IndexScan, while EXPLAIN SELECT ... WHERE id > 2 prints SeqScan; closing and reopening the database preserves those statistics and choices without re-running ANALYZE.
  • EXPLAIN DELETE FROM t leaves t unchanged; EXPLAIN ANALYZE SELECT ... prints both estimated and actual row counts plus elapsed time per node, and you can construct one skewed or correlated query where estimated and actual rows diverge and explain why.5
  • A 3- or 4-table equi-join query's EXPLAIN shows HashJoin nodes avoiding unnecessary cross products and placing the smaller estimated input on the left build side, returning the exact same rows as an unoptimized nested-loop plan.
