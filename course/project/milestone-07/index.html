Milestone 7 · Query Optimization

Until now your planner has been a stenographer: it transcribes the bound statement into the one plan shape it knows. This milestone makes it opinionated. The work divides into three independent layers — rewrites (no statistics needed), statistics (ANALYZE), and cost-based choice (access paths, join order) — and each layer is testable on its own before the next exists. Build them in that order and the milestone stays calm.

Learning objectives

  • Implement plan rewrites as tree-to-tree transformations: predicate pushdown, projection pruning, constant folding.
  • Implement ANALYZE: row counts, per-column min/max, distinct and null estimates, persisted through the catalog.
  • Implement a cost model in the spirit of Postgres's — page I/O plus per-tuple CPU, with the documented default constants.2
  • Implement Selinger-style selectivity estimation and cost-based seq-vs-index access path selection.1
  • Implement join ordering — greedy or subset-DP — for up to ~6 tables, left-deep.1
  • Implement EXPLAIN and EXPLAIN ANALYZE.4

// crates/exec

    /// constant folding) then cost-based access path + join order.
    pub fn optimize(&self, plan: plan::LogicalPlan) -> Result<plan::LogicalPlan>;

    pub const SEQ_PAGE_COST: f64 = 1.0;      // matches Postgres defaults
    pub const RANDOM_PAGE_COST: f64 = 4.0;
    pub const CPU_TUPLE_COST: f64 = 0.01;
    pub struct CostModel<'a> { /* &'a Catalog */ }
    impl<'a> CostModel<'a> {

Behavioral contract:

  • Rewrites are semantics-preserving and run before costing. Pushdown may move a predicate below an operator only if every column it references is available there.
  • Selectivity follows the Selinger defaults where statistics exist: equality ⇒ 1/distinct; range ⇒ linear interpolation between min and max; fall back to the paper's honest guesses (1/10, 1/3) where they don't.1 Document the uniformity and independence assumptions in the rustdoc.
  • Access path: for each base table with a usable index predicate, cost both scans and keep the cheaper — replacing the Milestone 5 always-index rule.
  • Join order: left-deep; either greedy (smallest estimated intermediate result first) or the Selinger subset-DP. The DP earns you the crossed-out cross products in the M08 explorer; greedy passes the tests with a documented caveat.
  • EXPLAIN prints the optimized plan tree, one node per line with estimated cost and rows; EXPLAIN ANALYZE executes it and adds actual rows and wall time per node — and, like the real one, performs the statement's side effects, so the REPL warns on data-modifying statements.4

Step-by-step guidance

  1. Rewrites first — they need no statistics. Write each rule as a function LogicalPlan -> LogicalPlan and a driver that applies rules bottom-up until a fixpoint. Constant folding is a good warm-up (fold inside BoundExpr); pushdown is the one with the correctness rule — test it on a predicate referencing both join sides (must NOT push) and one side (must push).
  2. ANALYZE next. One pass per table through your own SeqScan: count rows and pages, track min/max per column, estimate distincts. For distinct estimation a HashSet is fine at course scale; note in the rustdoc that real systems sample and use sketches (HyperLogLog) instead. Persist with set_stats; verify with the catalog round-trip test.
  3. Selectivity, then cost. Implement selectivity() as a match over the predicate shape, then plan_cost() recursively: SeqScan = SEQ_PAGE_COST·pages + CPU_TUPLE_COST·rows; IndexScan = RANDOM_PAGE_COST·(height + matching leaves + matching heap fetches) + cpu (state your clustering assumption — all-random is honest and simple); joins from the M07 formulas over estimated input cardinalities. Check your arithmetic against interdb §3.2's worked examples with the same constants.2
  4. Access path selection. Where a filter predicate hits an indexed column with = or a range, build both candidate scans, cost them, keep the winner. This is ten lines once the cost model exists — the leverage is all in step 3.
  5. Join ordering. Greedy: start from the pair with the smallest estimated output, attach the table producing the smallest next output, repeat. DP: memo from table-bitmask to best (plan, cost, rows) per subset, built by subset size, exactly the M08 explorer.1 Either way, join inputs keep their chosen access paths from step 4.
  6. EXPLAIN last. A pretty-printer over the optimized plan plus per-node estimates you already computed; ANALYZE mode wraps each executor with counters and a timer. Keep the format line-oriented and stable — the tests match structural markers (operator names, indentation), not exact costs.

Test plan

cargo test -p ferricdb-exec    -- --include-ignored ms7_
cargo test -p ferricdb-catalog -- --include-ignored ms7_

The exec group: rewrite unit tests on plan trees (pushdown legality both ways, folding); the crossover test — after ANALYZE, EXPLAIN must choose IndexScan for a selective predicate and SeqScan for a non-selective one on the same table; join-order tests asserting the chosen order's estimated cost, not its text. The catalog group: stats round-trip and the never-analyzed None case. Regressions: the whole slt_all suite must still pass — an optimizer that changes results has a bug worth finding today, not in Milestone 8.

Common pitfalls

Pushdown across the wrong boundary

Symptom: "column not found" panics at execution, or silently wrong join results. Cause: pushing a predicate below the operator that produces one of its columns (classically: below the join whose output it references from both sides). The legality check is column-set containment — compute each node's output columns once and consult it.

Selectivity of an empty or constant column

Symptom: NaN costs, or division by zero on min == max. Cause: interpolation over a zero-width range or stats from an empty table. Clamp selectivity to [0, 1] at the end of selectivity() and special-case empty tables — the ms7_ suite includes an ANALYZE-on-empty test for exactly this.

Enumerating permutations instead of subsets

Symptom: planning time explodes at 6 tables. Cause: memoizing on ordered sequences. The Selinger insight is that the memo key is the set — for any order of the same set, the ways to extend it are identical.1 Use a bitmask key and the space is 2⁶, not 6!.

Brittle EXPLAIN tests

Symptom: every cost-model tweak breaks a dozen tests. Cause: asserting exact EXPLAIN text. Assert structure (which scan, which join, nesting) and let numbers float — the provided tests model this; keep your own tests to the same discipline.

Definition of done

  • ms7_ groups pass in both crates; slt_all and all earlier groups still pass.
  • In the REPL, on a 10k-row table with an index: EXPLAIN SELECT … WHERE id = k shows IndexScan; WHERE id > tiny_value (matching ~everything) shows SeqScan; dropping the index flips the first to SeqScan; running ANALYZE after bulk changes updates the choice.
  • EXPLAIN ANALYZE shows estimated vs actual rows, and you can point at a query where they diverge and say why (skew or correlation).
  • A 4-table join query's EXPLAIN shows an order that starts from the most selective join — and you can defend it with the estimated cardinalities.
