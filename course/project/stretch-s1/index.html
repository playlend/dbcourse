Stretch S1 · Lock Manager and Row Locks (SELECT FOR UPDATE)

Add pessimistic concurrency control to FerricDB: a shared/exclusive row-lock manager with wait queues, SELECT ... FOR UPDATE from SQL, and deadlock handling on top of the MVCC engine you built in Milestone 8.

Milestone 8 gave FerricDB optimistic concurrency control: every transaction reads from its own snapshot, and write-write conflicts are caught at commit time by first-committer-wins. That is also the shape of CMU's current concurrency-control project, which detects conflicts through tuple timestamps instead of locks.5 This stretch builds the pessimistic counterpart that earlier editions of the same project made famous:2 a centralized lock manager that grants shared and exclusive row locks, queues the transactions it cannot yet serve, and breaks the deadlocks that queuing inevitably creates.

Fair warning: this is concurrent systems programming. The failure modes are hangs, races, and tests that pass 99 times out of 100 — not wrong answers. It is also one of the most satisfying pieces of the whole project to get right. Unlike the core milestones, this page is a spec with pointers rather than a walkthrough: you design the internals.

Learning objectives

  • Implement a lock manager that grants shared and exclusive row locks, with a per-row wait queue and strict two-phase release at commit/abort.
  • Extend the lexer, parser, planner, and executor so SELECT ... FOR UPDATE acquires exclusive row locks on the rows it returns.
  • Explain how row locks coexist with MVCC snapshot reads: plain readers never block, while writers and lockers of the same row serialize.
  • Handle deadlocks by waits-for-graph detection or wound-wait prevention, aborting a victim transaction with a clear, retryable error.
  • Distinguish latches (short-term, protect the lock manager's own structures) from locks (transaction-lifetime, protect database rows) — and never hold the former while waiting for the latter.
  • Write multi-threaded tests that assert blocking, parallelism, deadlock recovery, and lock release without depending on timing luck.

Where this fits

Nothing new appears on the diagram because a lock manager is invisible plumbing: it is a service the executor and transaction manager call into. The lock manager's state is pure memory and deliberately non-durable — any transaction still active at a crash is aborted by recovery anyway, so there is nothing to persist.1

Specification

Scope

Real lock managers support a granularity hierarchy — database, table, page, tuple — glued together with intention locks (IS, IX, SIX) so that coarse and fine locks can coexist,1 and the BusTub project requires all five modes plus table/row leveling.2 FerricDB scopes this down as a course choice: row locks only, two modes (Shared, Exclusive). Our DDL is not concurrency-safe anyway, so table-level protection buys little here; the interesting machinery — queues, blocking, deadlocks — is all present at row granularity.

  • Modes. A shared lock lets multiple transactions hold it on the same row simultaneously; an exclusive lock admits exactly one holder and conflicts with every other request.1
  • Release policy. Strong strict 2PL: a transaction releases locks only when it commits or aborts, never earlier. This forgoes some concurrency but rules out cascading aborts.1
  • Plain SELECT never locks. Snapshot visibility already gives consistent reads; this mirrors Postgres, where “row-level locks do not affect data querying; they block only writers and lockers to the same row”.4
  • SELECT ... FOR UPDATE takes exclusive locks on the rows it returns, so a read-modify-write sequence holds the row from the read onward. In Postgres, FOR UPDATE is the strongest of four row modes and conflicts with all of them.4 We implement only this one (course choice; FOR SHARE maps onto lock_shared if you want it).
  • UPDATE/DELETE also lock. Give them exclusive locks on the rows they modify, or FOR UPDATE would exclude other lockers but not actual writers. First-committer-wins stays on as the commit-time backstop.
  • Lock table lives in memory. Postgres avoids a per-row lock table by marking locked tuples on disk, which is why it can lock unlimited rows at the cost of disk writes;4 FerricDB keeps an in-memory map — simpler, bounded by memory, fine at our scale (course choice).

Suggested API additions (design sketch — not a provided stub)

The starter workspace ships no lock-manager code and no S1 tests. The sketch below is one reasonable surface, in the style of api-spec.md; you own this design and may change anything about it.

// crates/txn — SUGGESTED design sketch for Stretch S1 (you own this API)

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum LockMode { Shared, Exclusive }

/// Row-granularity lock manager: strong strict 2PL over RecordIds.
/// Locks are held until commit/abort and released all at once.
pub struct LockManager { /* latched map: RecordId -> per-row queue */ }

impl LockManager {
    pub fn new() -> Self;

    /// Block until `txn` holds a shared lock on `rid`. Returns
    /// Err(Error::Serialization) if `txn` is chosen as a deadlock
    /// victim while waiting.
    pub fn lock_shared(&self, txn: TxnId, rid: RecordId) -> Result<()>;

    /// Block until `txn` holds an exclusive lock on `rid`.
    /// Same error contract as lock_shared.
    pub fn lock_exclusive(&self, txn: TxnId, rid: RecordId) -> Result<()>;

    /// Release every lock `txn` holds and wake affected waiters.
    /// Called from TransactionManager::commit and ::abort so that
    /// every exit path releases locks.
    pub fn unlock_all(&self, txn: TxnId);
}

// crates/sql — suggested AST change: one new field
pub struct Select {
    /* existing fields unchanged (see api-spec.md) */
    pub for_update: bool,    // SELECT ... FOR UPDATE
}

Semantic notes on the sketch:

  • Reusing Error::Serialization for deadlock victims is a course choice: it is already FerricDB's “retry the transaction” error, matching how Postgres clients are told to handle serialization failures (SQLSTATE 40001) by retrying from the start.3 Make the message unmistakable, e.g. "deadlock detected: transaction 42 aborted".
  • Both lock_* calls must be idempotent for a lock already held by txn, and &self throughout — the manager is shared across threads behind an Arc, like the other managers in ExecContext.
  • In BusTub's version, any failed lock request implicitly aborts the transaction;2 mirror that: once lock_* returns an error, the executor stops and the session runs TransactionManager::abort.

Interaction with MVCC

Locking a row and reading a version of it are different things, and the seam between them is where the design work lives. When your FOR UPDATE finally gets its lock, the row may have been updated by the transaction you were waiting on. Postgres resolves this per isolation level, and both behaviors are worth knowing:3

  • Read Committed: the waiter re-evaluates the WHERE clause against the updated version of the row, and if it still matches, it is the updated version that gets locked and returned.3
  • Repeatable Read: if the transaction you waited on committed a real change to the row, you fail with ERROR: could not serialize access due to concurrent update and must retry the whole transaction.3

Course choice: implement the Repeatable Read rule. FerricDB transactions read from a fixed snapshot (Milestone 8), which is Repeatable Read's model, and the rule is much simpler: after the lock is granted, re-read the tuple's TupleMeta; if a committed transaction set xmax on the version your snapshot saw, return Error::Serialization. No WHERE re-evaluation machinery needed.

Step-by-step guidance

  1. Write your scope down first. One paragraph in crates/txn/src/lock.rs: modes, granularity, release policy, deadlock strategy, and what happens to a victim. Every hang you debug later gets measured against this paragraph. Hint: decide now whether a transaction re-requesting a lock it already holds is a no-op (recommended) and what S-then-X on the same row does (see the pitfalls).
  2. Build the two-level lock table. An outer latched map from RecordId to a per-row queue; each queue has its own mutex, a condition variable, a granted set (txn + mode), and a FIFO list of waiters (Figure 2). This is BusTub's LockRequestQueue shape, condition variable included.2 Hint: wrap the queue in an Arc so you can clone it out of the map and drop the map latch before doing anything slow.
  3. Implement lock_shared / lock_exclusive. Grant when the mode is compatible with all granted requests and no one is ahead in the queue — plain FIFO (course choice) keeps writers from starving behind a stream of readers. Otherwise append a waiter and loop on the condition variable: wait → recheck grant condition → wait…. Hint: use Condvar::wait_while; spurious wakeups are real.
  4. Implement unlock_all and wire it into commit and abort. Strong strict 2PL means this is the only release path.1 Keep a per-transaction set of held RecordIds so release is O(locks held), then notify_all each affected queue and let waiters re-check. Call it from TransactionManager::commit (success and first-committer-wins failure) and TransactionManager::abort.
  5. Pick a deadlock strategy and build it. Both are acceptable; say which you chose in your scope paragraph.
    • Detection: build a waits-for graph — one node per transaction, an edge Ti → Tj when Ti waits for a lock Tj holds — and check it for cycles periodically from a background thread.1 On a cycle, abort a victim; BusTub mandates the youngest transaction.2 Outline, paraphrasing the lecture's description1 and BusTub's victim rule:2 
      every T ms (background thread):
    G ← empty digraph
    for each row queue Q:
        for each waiting request w in Q:
            for each granted g in Q incompatible with w:
                add edge (w.txn → g.txn) to G
    while G contains a cycle (DFS):
        v ← youngest txn on the cycle
        mark v as victim; notify v's queue
        remove v from G
    • Prevention (wound-wait, “young waits for old”): priorities come from transaction age — older means higher priority. If the requester is older than an incompatible holder, the younger holder is wounded (aborted) and releases its locks; otherwise the requester waits. A restarted transaction keeps its original timestamp so it cannot starve.1 FerricDB's monotonically increasing TxnId is a ready-made age.
    Hint: a victim is, by definition, blocked inside lock_*. Deliver the verdict through a victim flag on its wait entry, notify_all, and have the wait loop check the flag and return Err(Error::Serialization).
  6. Parse SELECT ... FOR UPDATE. Add a FOR keyword to the lexer (UPDATE already exists), accept the clause only at the end of a top-level SELECT, and set Select::for_update. Reject it inside subqueries or on aggregate queries — locking “the rows” of a GROUP BY result has no meaning (Postgres restricts the locking clause similarly).
  7. Acquire locks in the executor. Thread for_update through the binder and planner to the scan. For each row that passes visibility and the filter, call lock_exclusive(txn, rid), then apply the Repeatable Read re-check from the specification before emitting the row. Hint: lock after the predicate passes — locking every scanned row turns a selective query into a table lock in disguise.
  8. Give UPDATE and DELETE the same treatment. Exclusive-lock each target row before writing the new version. Watch what changes in the Milestone 8 conflict tests: write-write conflicts that used to abort at commit now mostly surface earlier as lock waits — one writer blocks, then hits the re-check or first-committer-wins. The final outcome (one winner, one Error::Serialization) must not change.
  9. Stress it. N threads, each: BEGIN; SELECT balance FROM acct WHERE id = 1 FOR UPDATE; add 1; UPDATE; COMMIT (retry on serialization errors). The final balance must be exactly N. This is the read-modify-write pattern FOR UPDATE exists for: taking the exclusive lock at the read means you never grab S first and then fail upgrading to X.1

Test plan

Stretch milestones ship no skeleton tests, so this suite is yours to write. Keep the workspace convention: core-milestone tests arrive marked #[ignore = "milestone N"] and get un-ignored per milestone with cargo test -- --include-ignored msN_; name your new tests with an s1_ prefix (no #[ignore] needed — you are writing them when you need them) and keep the Milestone 8 group green as your regression net.

cargo test -p ferricdb-txn s1_                        # your new suite
cargo test --workspace -- --include-ignored ms8_      # MVCC must still hold

Five scenarios that together cover the definition of done:

  1. s1_x_blocks_x — blocking. Thread A takes X on row r and parks; thread B requests X on r and must not return until A commits. Prove ordering with an mpsc channel of events ("B-requested", "A-committed", "B-granted"), not with sleeps.
  2. s1_no_conflict_parallelism — no false blocking. Two transactions take X on different rows concurrently; both grant immediately. Also: three transactions take S on the same row concurrently; all grant. A lock manager that serializes everything passes test 1 and fails this one.
  3. s1_deadlock_detected — the constructed deadlock. T1 locks r1 then r2; T2 locks r2 then r1, synchronized with a std::sync::Barrier after the first lock so the cycle is guaranteed. Assert exactly one transaction gets Error::Serialization (with a message naming the deadlock) and the other commits normally.
  4. s1_release_on_abort — the abort path. A takes X on r and aborts; B's pending request must grant promptly. Repeat with A being killed as a deadlock victim rather than aborting voluntarily — both paths must release.
  5. s1_for_update_stress — end to end through SQL. The counter-increment stress from guidance step 9, run through execute() with real BEGIN/COMMIT. Final value N proves lost updates are gone; as a control, document that the same loop without FOR UPDATE loses updates under first-committer-wins retries only if you don't retry — with retries it also reaches N, just slower. Timing note: never assert "B was still blocked after 50 ms"; assert event order, and give any genuine timeout seconds, not milliseconds.

Common pitfalls

Holding the map latch while you wait

Why it happens: the obvious implementation locks the outer HashMap mutex, finds the queue, sees a conflict, and calls Condvar::wait right there — still holding the map. Symptom: the entire database freezes: transactions touching completely unrelated rows hang, because nobody can even look up their queue. Remember the lecture's distinction: latches protect the DBMS's internal structures for short critical sections; locks protect database objects for transaction lifetimes.1 The map mutex is a latch. Clone the Arc to the row's queue, drop the map latch, and block only on the queue's own condition variable (Figure 2).

Upgrade deadlocks: S then X on the same row

Why it happens: two transactions both take S on a row (a read), then both request X on it (a write). Each upgrade must wait for the other's S to go away — a perfect two-cycle that pure FIFO queuing cannot resolve. Symptom: any two concurrent read-then-update transactions on the same row hang (or both die as victims, if your detector is eager), reliably, every run. This is precisely the failure FOR UPDATE exists to avoid: for read-modify-write, take the exclusive lock at the read instead of acquiring S and then failing to upgrade.1 Pick an explicit upgrade policy — simplest is to treat S→X by the same transaction as an error or as a fresh X request that waits for other S holders — and make sure your deadlock handler counts an upgrader as waiting for every other current S holder, so the cycle is visible.

Locks leak on abort paths

Why it happens: release is coded into the COMMIT handler, but transactions die in many other places — explicit ROLLBACK, a first-committer-wins failure inside commit(), a statement error mid-execution, a deadlock victim unwinding with ?. Miss one path and the dead transaction keeps its locks forever. Symptom: the system works, then minutes later an unrelated transaction hangs on a row nobody living holds; under test, suites pass alone and deadlock in CI. Fix: route every ending through TransactionManager::commit / abort and call unlock_all there and only there — that is what "release at transaction end" means in strong strict 2PL,1 and BusTub's spec likewise makes any failed lock request abort the whole transaction rather than limp on.2

Definition of done

  • Two concurrent SELECT ... FOR UPDATE on the same row serialize correctly: the second blocks until the first commits or aborts, then proceeds (or fails the version re-check with Error::Serialization) — never returns stale data, never interleaves.
  • A constructed deadlock (two transactions locking two rows in opposite order) is detected or prevented: exactly one transaction aborts with a clear, retryable error message; the other commits.
  • A plain SELECT never calls the lock manager and never blocks behind any writer.
  • unlock_all runs on every transaction ending — commit, rollback, conflict abort, deadlock victim — verified by s1_release_on_abort.
  • The FOR UPDATE counter stress reaches exactly N with N concurrent incrementers.
  • cargo test --workspace -- --include-ignored ms8_ still passes: MVCC snapshots and first-committer-wins are unchanged underneath the locks.
