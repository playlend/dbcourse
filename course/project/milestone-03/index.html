Milestone 3 · SQL Front-End: Lexer, Parser, AST, Catalog, Binder

Teach FerricDB to read: a hand-written lexer and parser, a system catalog stored inside the database itself, and a binder that turns names into checked references.

This is the widest milestone in the course — three crates get real code — but none of it touches concurrency or subtle byte layouts, so it moves faster than its size suggests. At the end, the REPL stops echoing: .ast SELECT 1 + 2 * 3; prints a real parse tree, CREATE TABLE writes real catalog rows into real heap pages through your buffer pool, and .tables finally has something to say.

Learning objectives

  • Implement a hand-written SQL lexer: case-insensitive keywords, maximal munch, SQL string escapes, positions for errors.
  • Implement a recursive-descent statement parser with a Pratt expression parser — the sqlparser-rs architecture in miniature.1
  • Design a catalog that stores table and column metadata in the database itself, bootstrap pages included.
  • Implement a binder that resolves names and types against the catalog and rejects nonsense with useful errors.
  • Wire the REPL: .ast, .tables, .schema, and executable CREATE TABLE/DROP TABLE.

Required reading

  • M05 · SQL Front-End — the concept module: Pratt parsing with a worked trace, AST design, the binder's contract. The live demo there is a reference implementation of a subset of your parser.
  • sqlparser-rs design notes — Pratt/TDOP expressions inside recursive-descent statements; the architecture you are reproducing. github.com/apache/datafusion-sqlparser-rs
  • SQLite, "Architecture of SQLite" — the contrasting front-end (Lemon-generated parser, bytecode output). sqlite.org/arch.html
  • cstack, Part 2 — the smallest possible front-end/engine split, worth 10 minutes before you build the real one. cstack.github.io/db_tutorial/parts/part2.html

Where this fits

Specification

Grammar scope

Exactly these statements (execution of the transaction statements waits for Milestone 8; parsing them costs you five lines now and saves a grammar migration later):

CREATE TABLE name (col type [NOT NULL] [PRIMARY KEY], …)
DROP TABLE name
INSERT INTO name [(cols…)] VALUES (exprs…) [, (exprs…)…]
SELECT exprs… FROM name [WHERE expr] [ORDER BY expr [ASC|DESC], …] [LIMIT n]
UPDATE name SET col = expr [, …] [WHERE expr]
DELETE FROM name [WHERE expr]
BEGIN | COMMIT | ROLLBACK

Types: BOOLEAN, INTEGER, FLOAT, TEXT. Expressions: literals, column references (optionally qualified), unary -/NOT, binary arithmetic/comparison/AND/OR, IS [NOT] NULL, CAST(expr AS type), parentheses.

Public API (crates/sql)

pub enum Token { /* keywords, idents, literals, operators, punctuation */ }
pub struct Lexer;
impl Lexer { pub fn tokenize(input: &str) -> Result<Vec<Token>>; }

pub mod ast { /* Statement, ColumnDef, Select, TableRef, Expr, UnaryOp, BinaryOp —
                 the full definitions live in the stubs and match the module page */ }

/// Recursive-descent statement parser + Pratt expression parser.
pub struct Parser;
impl Parser {
    pub fn parse(sql: &str) -> Result<Vec<ast::Statement>>;
    pub fn parse_expr(sql: &str) -> Result<ast::Expr>;   // test convenience
}

Public API (crates/catalog)

pub struct TableInfo { pub oid: Oid, pub name: String, pub schema: Schema,
                       pub first_page: PageId, pub indexes: Vec<IndexInfo> }

/// System catalog, itself stored in heap pages (bootstrap: fixed page ids
/// for __tables / __columns; the catalog reads itself at open).
pub struct Catalog { /* Arc<dyn PageStore>, cached maps */ }
impl Catalog {
    pub fn bootstrap(store: std::sync::Arc<dyn PageStore>) -> Result<Self>; // create-or-open
    pub fn create_table(&self, name: &str, schema: Schema) -> Result<Oid>;
    pub fn drop_table(&self, name: &str) -> Result<()>;
    pub fn table(&self, name: &str) -> Result<TableInfo>;
    pub fn tables(&self) -> Result<Vec<TableInfo>>;
}

Public API (crates/exec, binder module)

/// Name/type resolution against the catalog; produces bound statements
/// whose column references are (table index, column index) pairs.
pub struct Binder<'a> { /* &'a Catalog */ }
impl<'a> Binder<'a> {
    pub fn new(catalog: &'a Catalog) -> Self;
    pub fn bind(&self, stmt: ast::Statement) -> Result<BoundStatement>;
}

Behavioral contract: the parser never touches the catalog (grammatical nonsense about nonexistent tables must parse); the binder rejects unknown tables/columns, ambiguous or type-mismatched expressions, and INSERT arity errors, each with a message naming the offender.2 Escape hatch: you may swap your parser for the sqlparser-rs crate and translate its AST into ast::Statement — the rest of the milestone is unchanged — but the hand-written path is the recommended one; the module teaches everything you need.

Step-by-step guidance

  1. Lexer first, tests continuously. It is pure string processing — ms3_ lexer tests can be green within the hour. Get keyword case-insensitivity, >= maximal munch, and '' string escaping right here so the parser never sees the mess.
  2. Parser skeleton: peek/expect. Build the token cursor with peek()/next()/expect(tok) helpers, then parse_statement dispatching on the first keyword. Do CREATE TABLE first — flat clause structure, no expressions — and run .ast against it early for morale.
  3. Pratt core next. Implement parse_expr(min_bp) exactly as the module traces it: prefix position, then the infix loop with the binding-power table (OR 1, AND 2, NOT 3, comparisons 4, additive 5, multiplicative 6, unary minus 7), recursing with bp + 1 for left-associativity. The precedence tests encode the module's traces — 1 + 2 * 3, a OR b AND c, chains of minus.
  4. Finish the statement grammar. SELECT is the largest; take its clauses one at a time (projection with AS aliases, FROM, WHERE, ORDER BY, LIMIT). INSERT with multi-row VALUES, UPDATE with the SET list, DELETE, DROP, and the three one-keyword transaction statements follow quickly.
  5. Catalog: constants before code. Write down the fixed schemas of __tables (oid, name, first_page) and __columns (table_oid, ordinal, name, type, nullable) as Rust constants, and pin their page ids (this course: page 1 and page 2; page 0 is the database header). bootstrap then has two branches: fresh store → format both heaps and insert the rows describing the catalog tables themselves; existing store → scan both heaps and build the in-memory maps. That self-description is the chicken-and-egg — solved by the constants, exactly as Postgres solves it with compiled-in bootstrap schemas for pg_class and pg_attribute.2
  6. Everything through the pool. The catalog's heaps are ordinary HeapFiles over Arc<dyn PageStore> — your Milestone 2 buffer pool. No direct DiskManager access from here to the end of the course.
  7. Binder last. Walk each statement: resolve the table via catalog.table(), build a scope of (index, name, type) for its columns, resolve every Expr::Column against the scope, type expressions bottom-up, and emit BoundStatement. Boring by design — every interesting decision was made when you defined the AST and the catalog.
  8. Wire the REPL. .ast pretty-prints Parser::parse output (write a small indent-per-level Debug-style formatter — the M05 demo shows the shape). CREATE TABLE/DROP TABLE execute directly against the catalog: your first statements that do something. .tables and .schema read it back.

Test plan

cargo test -p ferricdb-sql     -- --include-ignored ms3_
cargo test -p ferricdb-catalog -- --include-ignored ms3_

# regressions
cargo test -p ferricdb-storage -- --include-ignored ms1_
cargo test -p ferricdb-buffer  -- --include-ignored ms2_

The sql group covers the lexer cases, a valid corpus asserting exact ASTs across the whole grammar scope, the precedence suite, and an invalid corpus (about ten broken statements) that must produce Err — a panicking parser fails the milestone even if everything else passes. The catalog group covers bootstrap-fresh vs bootstrap-reopen, create/list/drop round-trips, duplicate-name rejection, and schema fidelity across reopen (types and nullability intact). A handful of parses for Milestone 6 grammar (JOIN, GROUP BY, aggregate calls) sit in the same files marked #[ignore = "milestone 6"] — leave them; they are tomorrow's shopping list, not today's.

Common pitfalls

Precedence-table typos

Symptom: a OR b AND c groups the wrong way, or comparisons swallow arithmetic (a + 1 > b parsing as a + (1 > b)). One wrong integer in the table produces trees that look plausible in .ast and fail quietly at execution time in Milestone 4. Trust the precedence tests — they exist because everyone makes exactly this mistake once.

Consuming tokens on the error path

Symptom: error messages that point one token too far, or cascading bogus errors after the first. Cause: a helper called next() to inspect and then errored without backing up. Decide with peek(), consume with expect() — if every consumption is one of those two, this bug cannot exist.

Bootstrap reads the catalog to learn the catalog's schema

Symptom: bootstrap works on a fresh database and panics on reopen (or vice versa). Cause: using catalog lookups for __tables/__columns themselves. Their schemas and page ids are compile-time constants; only user tables are discovered by scanning. Write the reopen test first if you are unsure — it is the one that catches this.

Forgetting that catalog writes must persist

Symptom: .tables shows your table until the process restarts. Cause: catalog rows inserted through the buffer pool but never flushed — flush_all on clean shutdown (and after DDL, until the WAL exists) is part of this milestone's REPL wiring.

Definition of done

  • ms3_ groups pass in both crates; ms1_/ms2_ still pass.
  • In the REPL: .ast SELECT 1 + 2 * 3; shows multiplication nested under addition; CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT NOT NULL); succeeds; .tables lists it; .schema users shows both columns with types; all of it survives restart.
  • Binding SELECT ghost FROM users and SELECT name FROM nowhere both fail with errors that name the missing thing.
  • Invalid SQL never panics the REPL.
