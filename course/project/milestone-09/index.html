Milestone 9 · Write-Ahead Logging and ARIES-Style Recovery

Build the append-only log, enforce the log-before-data rule in the buffer pool, and implement the three-pass ARIES restart — then prove it by crashing your database hundreds of times.

Learning objectives

  • Implement an append-only log manager with monotonically increasing LSNs, a per-transaction prev_lsn chain, and a durable flushed_lsn watermark.
  • Design log records that carry before-images for undo and after-images for redo, plus compensation log records (CLRs) that make rollback itself restartable.
  • Enforce the WAL rule at the buffer-pool boundary via the LogFlusher hook, so a steal eviction policy is safe and commit is no-force.
  • Take fuzzy checkpoints that snapshot the active-transaction table (ATT) and dirty-page table (DPT) without stopping traffic.
  • Implement ARIES restart exactly: analysis, redo that repeats history, and undo of losers — and explain why redo consults the pageLSN while undo does not.
  • Build crash-injection tests, both simulated (drop unflushed state) and real (kill the process), and use them to argue durability empirically rather than by inspection.

Where this fits

The WAL is the last purely internal component of FerricDB. It sits beside the buffer pool and the transaction manager: executors log every heap change before applying it, the transaction manager logs begin/commit/abort, and the buffer pool refuses to write a dirty page until the log covering it is on disk. When this milestone is done, FerricDB stops being a program that usually keeps your data and becomes a database: you can kill it at any instant and no committed change is lost, no aborted change survives.

Specification

You implement course/ferricdb/crates/wal (package ferricdb-wal), which depends on common, storage, and buffer. The public surface, from the API spec:

// crates/wal — ferricdb-wal (Milestone 9)

pub enum LogRecord {
    Begin  { txn: TxnId },
    Commit { txn: TxnId },
    Abort  { txn: TxnId },
    Insert { txn: TxnId, rid: RecordId, tuple: Vec<u8>, meta: TupleMeta },
    Update { txn: TxnId, rid: RecordId,
             old_meta: TupleMeta, old: Vec<u8>,
             new_meta: TupleMeta, new: Vec<u8> },
    Delete { txn: TxnId, rid: RecordId, old_meta: TupleMeta, old: Vec<u8> },
    /// Compensation log record written during undo; undo_next points at
    /// the next record of the same txn still to undo.
    Clr    { txn: TxnId, rid: RecordId, redo: Vec<u8>, undo_next: Lsn },
    CheckpointBegin,
    CheckpointEnd { active_txns: Vec<(TxnId, Lsn /*lastLSN*/)>,
                    dirty_pages: Vec<(PageId, Lsn /*recLSN*/)> },
}

pub struct WalManager { /* append-only file, in-memory tail, flushed_lsn */ }
impl WalManager {
    pub fn open(path: &std::path::Path) -> Result<Self>;
    pub fn append(&self, prev_lsn: Lsn, rec: &LogRecord) -> Result<Lsn>;
    pub fn flush(&self, up_to: Lsn) -> Result<()>;
    pub fn flushed_lsn(&self) -> Lsn;
    pub fn iter_from(&self, lsn: Lsn) -> Result<WalIter>; // Iterator<Item=Result<(Lsn, Lsn /*prev*/, LogRecord)>>
    pub fn checkpoint(&self, active: &[(TxnId, Lsn)],
                      dirty: &[(PageId, Lsn)]) -> Result<Lsn>;
}
impl ferricdb_buffer::LogFlusher for WalManager { /* flush_until = flush */ }

pub struct RecoveryReport { pub redone: usize, pub undone: usize,
                            pub loser_txns: Vec<TxnId> }
/// ARIES: analysis (rebuild ATT+DPT from last checkpoint), redo
/// (repeat history from min recLSN, honoring pageLSN), undo (losers,
/// writing CLRs).
pub fn recover(wal: &WalManager, pool: &BufferPoolManager) -> Result<RecoveryReport>;

Semantics

  • LSNs are strictly increasing. append assigns and returns the record’s LSN. In ARIES an LSN is typically the logical address of the record in the log address space1; PostgreSQL likewise uses a byte position in an 8-byte log address space4. Using the record’s byte offset in the log file is the natural course choice. Lsn = 0 means “none” — never assign it.
  • prev_lsn chains a transaction’s records backward. Pass the LSN of the same transaction’s previous record (0 for its first). Rollback and the undo pass walk this chain; ARIES stores it as PrevLSN in every record.1
  • append buffers; only flush makes records durable. flush(up_to) must write every record with LSN ≤ up_to and fsync before returning. flushed_lsn() is the durability watermark: everything at or below it survives a crash, nothing above it is promised.
  • Update carries both images. The old tuple/meta is the undo information, the new one the redo information — ARIES’ Data field serves both roles.1 Insert needs no before-image (undo = delete the slot); Delete needs no after-image (redo = delete again).
  • Clr is redo-only. Its redo bytes describe the compensation so it can be re-applied by a later redo pass; it has no undo information because CLRs are never undone.1 undo_next holds the prev_lsn of the record it compensated.
  • checkpoint is fuzzy. It appends CheckpointBegin, then CheckpointEnd carrying the ATT (txn, lastLSN) and DPT (page, recLSN) snapshots supplied by the caller, flushes, and returns the begin record’s LSN. It must not write any data pages — that is the whole point.1
  • iter_from must survive a torn tail. A crash can truncate the file mid-record; iteration ends cleanly at the first incomplete or corrupt record instead of erroring the whole scan.
  • recover reads and writes pages only through the buffer pool, and returns how much work each phase did — the tests assert on RecoveryReport.

Step-by-step guidance

Honest difficulty note

This is the hardest milestone in the course, harder than the B+Tree. Not because any one pass is long — each is under a hundred lines — but because correctness is invisible until a crash lands in exactly the wrong microsecond. Build in the order below, keep every step under test before starting the next, and let the crash-injection loop, not your intuition, be the judge. Budget two weeks.

Step 1 — Encode records and append them

Pick a simple binary framing for one record on disk: a length prefix, the payload (prev_lsn, a type tag, then the fields), and a checksum. The checksum is not paranoia — it is how iter_from will distinguish “end of log” from “torn record at the crash point”. PostgreSQL splits its log into 16 MB segment files4; a single append-only file is a fine course simplification. Keep an in-memory tail buffer protected by a mutex: append assigns the next LSN (byte offset works), serializes into the tail, and returns without touching the disk. Write a round-trip unit test — every LogRecord variant through serialize → deserialize — before anything else.

Step 2 — flush, flushed_lsn, iter_from

flush(up_to) writes the buffered prefix of the log through up_to, calls sync_data, then advances flushed_lsn. Note the order: the watermark moves only after fsync returns. Because the log is one sequential file, this is cheap — the PostgreSQL docs make the same point: syncing a sequential log costs far less than flushing scattered data pages, and one fsync can commit many concurrent transactions.8 iter_from(lsn) seeks to a byte offset and yields (lsn, prev_lsn, record) triples until end-of-file or the first record whose length or checksum does not hold — stop there silently; that torn tail is a record that was never durable.

Step 3 — Stamp the pageLSN on every modification

ARIES keeps a page_LSN in every page: the LSN of the log record describing the latest update applied to that page.1 PostgreSQL’s page header has the same field, pd_lsn.3 Thread the WAL into the write paths that mutate heap pages (insert, update via set_meta, delete): append the log record first, then apply the change and call page.set_lsn(record_lsn) while still holding the page guard. Doing both under the same guard keeps log order identical to page-apply order, which ARIES requires for physical redo to work.1 Redo will also need to re-apply a tuple at the exact slot named in the record’s rid — a plain insert() that picks any free slot is not enough, so plan a crate-internal “place at slot” primitive.

Step 4 — Enforce the WAL rule in the buffer pool

Implement LogFlusher for WalManager (it is just flush) and wire it with pool.set_log_flusher(wal.clone()) at startup. In the buffer pool’s write-back path — eviction, flush_page, flush_all — call flush_until(page.lsn()) before the disk write. This is the WAL protocol: the buffer manager forces the log up to the dirty page’s LSN before the page goes out.1 PostgreSQL states the same invariant as its central rule: data files may be written only after the WAL records describing the changes are on permanent storage.8 With this one hook, a steal policy (evicting pages dirtied by uncommitted transactions) becomes safe, because the before-images needed to undo them are guaranteed to be in the durable log.1

Step 5 — Transaction lifecycle: Begin, Commit, Abort

Log Begin when the transaction manager hands out a transaction, and track its lastLSN as you append its records. Commit is two lines with a big meaning: append Commit, then flush(commit_lsn) — and only report success to the caller after the flush returns. That is no-force: no data page is written at commit; the flushed log alone carries durability.1 Abort during normal operation is a rehearsal for restart undo: walk the transaction’s prev_lsn chain from its lastLSN; for each undoable record apply the before-image, append a Clr whose undo_next is the undone record’s prev_lsn (and stamp the touched page with the CLR’s LSN); finish with an Abort record. Write this as one reusable routine — the undo pass in step 9 is the same loop; ARIES presents it once as ROLLBACK and reuses it.1

Step 6 — Fuzzy checkpoints

A checkpoint exists to bound how much log recovery must read; it must not stop the world. checkpoint(active, dirty) appends CheckpointBegin, then CheckpointEnd carrying the ATT (each active transaction with its lastLSN) and the DPT (each dirty page with its recLSN), then flushes. Record the begin record’s LSN in a small side file next to the log — the analog of ARIES’ master record and of PostgreSQL’s pg_control, which stores the location of the latest checkpoint so recovery knows where to start.15 Only update the side file after CheckpointEnd is durable: a checkpoint whose end record never reached disk is incomplete and must be ignored.1

The recLSN needs care: it is recorded by the buffer pool when a clean page first becomes dirty, as the end-of-log LSN at that moment — “from this point on, the log may contain updates not yet in the on-disk copy of this page”.1 When a page is written out, its DPT entry is dropped. You will need to surface the buffer pool’s dirty set with recLSNs to the caller assembling the checkpoint — a small crate-internal accessor; the public API stays as specified. Crucially, a fuzzy checkpoint forces no dirty pages1 — PostgreSQL’s checkpointer likewise dribbles dirty pages out gradually while traffic continues, on a timer that defaults to 300 seconds.5

Step 7 — Recovery I: the analysis pass

Analysis starts at the CheckpointBegin of the last complete checkpoint (from the side file; LSN 0 if none) and scans forward to the end of the log.1 Seed the ATT and DPT from CheckpointEnd when you pass it, then update both from every record you see:

  • Any record for a transaction not in the ATT adds it; every record updates that transaction’s lastLSN.
  • Any page-touching record (Insert/Update/Delete/Clr) whose page is not in the DPT adds it with recLSN = the record’s own LSN.
  • Commit and Abort remove the transaction from the ATT — both mark a finished outcome (an Abort record is only written after rollback completed, so there is nothing left to undo).

Whoever remains in the ATT at end of scan is a loser. The redo starting point is the minimum recLSN in the DPT; if the DPT is empty, redo can be skipped entirely.1

Step 8 — Recovery II: redo repeats history

Redo scans forward from the minimum recLSN and re-applies every missing page change — including those of loser transactions and including CLRs. This “repeating history” is the paradigm the paper is built on: first re-establish the exact state as of the crash, then roll losers back from that known state.1 The decision procedure, from ARIES Fig. 11 (pseudocode of the published algorithm — your Rust will differ):

for (lsn, _prev, rec) in wal.iter_from(min_recLSN):
    if rec touches a page
       and rec.page ∈ DPT
       and lsn ≥ DPT[rec.page].recLSN:        # filter 1: no disk read needed
        fetch the page via the buffer pool
        if page.pageLSN < lsn:                 # filter 2: is the effect present?
            re-apply the record's redo action
            page.pageLSN := lsn                # no new log records are written

Filter 1 uses only the DPT and skips records without touching the disk; filter 2 reads the page and asks whether the effect already made it out before the crash. Both are required and they are not the same test (see the pitfalls). Setting pageLSN := lsn after each application is what makes redo idempotent; nothing is logged during the redo pass.1 PostgreSQL’s recovery makes the identical comparison — a record is replayed only when its LSN beats the page’s pd_lsn, because replaying a change that is already present is not an idempotent operation.6

Step 9 — Recovery III: undo the losers

Undo rolls back all losers in one backward sweep, in reverse LSN order across transactions: repeatedly pick the loser with the largest next-LSN-to-undo and process that record.1 Adapted from ARIES Figs. 8 and 12:

undo_next[t] := lastLSN(t) for every loser t
while any undo_next[t] ≠ 0:
    t := loser with the largest undo_next[t];  rec := record at undo_next[t]
    match rec:
        Insert/Update/Delete →
            apply the before-image through the buffer pool
            clr := append Clr { redo: …, undo_next: rec.prev_lsn }
            page.pageLSN := clr.lsn
            undo_next[t] := rec.prev_lsn
        Clr   → undo_next[t] := rec.undo_next      # skip; CLRs are never undone
        Begin → append Abort { t };  undo_next[t] := 0

Two things are deliberately absent. Undo never consults the DPT, and never compares pageLSNs — because history was already repeated, the page state is exactly what the log says it is, so the undo applies unconditionally.1 And when undo meets a CLR (left over from a rollback that a crash interrupted, or from a previous recovery that itself crashed), it does not undo it — it follows undo_next straight past the work that was already undone. That single pointer is what bounds logging even across repeated failures: each undoable record produces at most one CLR, ever.1 Fill in RecoveryReport as you go: records re-applied in redo, records undone, and the loser list.

One contrast worth knowing: the recovery walkthrough in interdb Ch. 9.8 is redo-only — PostgreSQL replays from the REDO point and stops6, leaning on MVCC (your Milestone 8 machinery) to keep aborted rows invisible instead of erasing them at restart. FerricDB’s MVCC could justify the same shortcut; we implement the full ARIES undo as a course choice, because the canonical three-pass algorithm is the thing this milestone exists to teach — and it keeps the WAL correct independently of visibility rules.

Step 10 — The kill-the-process harness

The provided sim-crash tests fake a crash: run a workload, drop the buffer pool without flushing data pages (the WAL file survives), reopen, recover, check invariants. They are fast and seeded, and they will catch most bugs. But a simulated crash only loses what you remembered to throw away. The real harness — your job here — kills an actual process at an arbitrary instruction:

  1. Give the test binary a child mode. At the top of a harness test, check an environment variable (say FERRICDB_MS9_CHILD). If set, run the child role; otherwise run the parent role. The parent re-executes its own binary via std::process::Command::new(std::env::current_exe()?) with the variable set, plus a seed and a database path — a standard libtest re-exec pattern.
  2. Child: open the database, run a seeded workload of small transactions — inserts, updates, deletes; commit some, abort others; make each row’s values derivable from (txn number, seed) so the parent can validate content, not just counts. After each successful commit, print COMMITTED <n> to stdout and flush stdout. At a seeded random operation count, call std::process::abort() — no destructors, no flushes, no goodbye.
  3. Parent: wait for the child (expect an abnormal exit), collect the COMMITTED lines, reopen the database, run recover(), and assert the two invariants: every transaction acknowledged before the crash is fully present with correct contents, and no rows from aborted or unfinished transactions are visible. The check is deliberately one-sided: a commit that returned but whose stdout line was lost in the crash is allowed to survive — it must simply never be half-present.
  4. Loop over a hundred or more seeds, and for extra credit re-kill the child during recovery (child mode: recover, then abort at a random point) and recover again — recovery must be idempotent.

Common pitfalls

Appending to the log without stamping the pageLSN

If a page change is logged but set_lsn is skipped, redo’s filter 2 sees a stale pageLSN and re-applies a change that is already present. Redo of a slotted-page mutation is not idempotent — PostgreSQL guards replay with exactly this LSN comparison for the same reason.6 Symptom: duplicate rows or doubly-applied updates after recovery, and a database that gets worse each time you recover it again.

Undoing CLRs

Never. CLRs are redo-only; when undo encounters one it follows undo_next and moves on.1 If you “undo the undo”, a crash during rollback resurrects aborted data on the next restart, and repeated crashes make the log grow without bound — the exact failure ARIES cites in older systems that compensated compensations.1 Symptom: the crash-during-recovery loop flip-flops a row between states instead of converging.

Conflating the two redo filters

“Page not in the DPT (or LSN < recLSN)” and “pageLSN ≥ record LSN” are different tests with different jobs: the first prunes log records using only in-memory tables, the second is the ground truth read from the page itself.1 Skip the second and you double-apply to pages that were flushed just before the crash; skip the first and you are merely slow — until you “optimize” by treating recLSN as the application test, which corrupts pages whose on-disk state is newer than the DPT thinks. Symptom: corruption that only appears when a checkpoint, an eviction, and a crash interleave — i.e., only under the randomized loop.

Flushing the commit record without everything before it

flush(up_to) is a prefix operation: every record with LSN ≤ up_to goes out, in order, before the fsync. If your implementation flushes selected records — say, just the commit — the durable log can hold a commit whose updates are missing, and recovery will happily declare a winner it cannot redo. The WAL guarantee is stated over the whole prefix: changes are recoverable because all records describing them reached storage first.8 Symptom: committed rows vanish, but only when the crash lands between two partial flushes.

Treating the checkpoint as a barrier

A fuzzy checkpoint promises nothing about data pages — it forces none of them.1 It is where analysis starts, not where redo starts: redo begins at the minimum recLSN, which can lie far before the checkpoint (Figure 3), and records written between begin_chkpt and end_chkpt still need scanning.1 If you start redo at the checkpoint, every page dirtied before it and never flushed silently loses its changes. Symptom: committed data missing, but only in runs where a checkpoint happened while old dirty pages were still in the pool.

Recovery that assumes it will finish

A crash during recovery must leave the system recoverable again — that is the whole design: redo is guarded by pageLSN, and CLRs written by the undo pass carry undo_next so a second undo resumes rather than repeats.1 But the property only holds if your recovery honors the WAL rule too — the buffer manager follows the usual protocol while writing pages during recovery,1 so wire the LogFlusher hook before calling recover(). Symptom: recovering once works; killing the process mid-recovery and recovering again panics or loses data.

Definition of done

  • cargo test -p ferricdb-wal -- --include-ignored ms9_ passes — including ms9_crash_injection_no_lost_commits, the seeded randomized sim-crash loop: after hundreds of random crash points, zero committed transactions lost and zero aborted transactions resurrected.
  • Your process-kill harness (step 10) demonstrates the same two invariants across at least 100 seeded kills, including kills during recovery, and is documented in your repo so a grader can run it.
  • Recovery is idempotent: running recover() on an already-recovered database, or crashing mid-recovery and recovering again, converges to the same committed state.
  • The WAL rule is airtight: no code path writes a page whose pageLSN exceeds flushed_lsn() — add a debug assertion in the buffer pool’s write-back path and leave it on in tests.
  • COMMIT returns to the caller only after the log is flushed through the commit record’s LSN; no data pages are flushed at commit.
  • Checkpoints bound recovery: after a checkpoint plus more traffic, restart scans the log only from the checkpoint (analysis) and the minimum recLSN (redo) — verify by counting records scanned, not by vibes.
  • cargo test --workspace is still green — the WAL wiring must not regress earlier milestones.
