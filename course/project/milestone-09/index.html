Learning objectives

  • Implement an append-only log manager with monotonically increasing LSNs, a per-transaction prev_lsn chain, and a durable flushed_lsn watermark.
  • Design log records that carry before-images for undo and after-images for redo, plus compensation log records (CLRs) that make rollback itself restartable.
  • Enforce the WAL rule at the buffer-pool boundary via the LogFlusher hook, so a steal eviction policy is safe and commit is no-force.
  • Take fuzzy checkpoints that snapshot the active-transaction table (ATT) and dirty-page table (DPT) without stopping traffic.
  • Implement ARIES restart exactly: analysis, redo that repeats history, and undo of losers — and explain why redo consults the pageLSN while undo does not.
  • Build crash-injection tests, both simulated (drop unflushed state) and real (kill the process), and use them to argue durability empirically rather than by inspection.

Where this fits

The WAL is the last purely internal component of FerricDB. It sits beside the buffer pool and the transaction manager: executors log every heap change before applying it, the transaction manager logs begin/commit/abort, and the buffer pool refuses to write a dirty page until the log covering it is on disk. When this milestone is done, FerricDB stops being a program that usually keeps your data and becomes a database: you can kill it at any instant and no committed change is lost, no aborted change survives.

Specification

You implement course/ferricdb/crates/wal (package ferricdb-wal), which depends on common, storage, and buffer, plus four small MS9 hooks in storage, buffer, txn, and the ferricdb binary. The public surface, quoted verbatim from course/ferricdb/docs/api-spec.md:

// crates/wal — ferricdb-wal (Milestone 9)

#[derive(Clone, Debug, PartialEq)]
pub enum ClrAction {
    Tombstone,
    Restore { meta: TupleMeta, tuple: Vec<u8> },
}

#[derive(Clone, Debug, PartialEq)]
pub enum LogRecord {
    PageInit { page_id: PageId },
    Begin  { txn: TxnId },
    Commit { txn: TxnId },
    Abort  { txn: TxnId },
    Insert { txn: TxnId, rid: RecordId, tuple: Vec<u8>, meta: TupleMeta },
    Update { txn: TxnId, rid: RecordId,
             old_meta: TupleMeta, old: Vec<u8>,
             new_meta: TupleMeta, new: Vec<u8> },
    Delete { txn: TxnId, rid: RecordId, old_meta: TupleMeta, old: Vec<u8> },
    Clr    { txn: TxnId, rid: RecordId, action: ClrAction, undo_next: Lsn },
    CheckpointBegin,
    CheckpointEnd { active_txns: Vec<(TxnId, Lsn /*lastLSN*/)>,
                    dirty_pages: Vec<(PageId, Lsn /*recLSN*/)> },
}

pub struct WalManager { /* append-only file, in-memory tail, flushed_lsn */ }
impl WalManager {
    pub fn open(path: &std::path::Path) -> Result<Self>;
    pub fn append(&self, prev_lsn: Lsn, rec: &LogRecord) -> Result<Lsn>; // returns Lsn >= 1
    pub fn flush(&self, up_to: Lsn) -> Result<()>;
    pub fn flushed_lsn(&self) -> Lsn;
    pub fn iter_from(&self, lsn: Lsn) -> Result<WalIter>; // Iterator<Item=Result<(Lsn, Lsn /*prev*/, LogRecord)>>
    pub fn checkpoint(&self, active: &[(TxnId, Lsn)],
                      dirty: &[(PageId, Lsn)]) -> Result<Lsn>; // returns CheckpointEnd LSN
}
impl ferricdb_buffer::LogFlusher for WalManager { /* flush_until = flush */ }

pub struct RecoveryReport {
    pub redone: usize,
    pub undone: usize,
    pub loser_txns: Vec<TxnId>,
    pub committed_txns: Vec<TxnId>,
    pub max_txn_id: TxnId,
}
/// ARIES: analysis (seed pre-checkpoint commits/max_txn_id from checkpoint metadata,
/// rebuild ATT+DPT+post-checkpoint commits from last CheckpointBegin),
/// redo (repeat history from min recLSN, honoring DPT & pageLSN),
/// undo (losers in reverse LSN order, writing CLRs + Abort).
pub fn recover(wal: &WalManager, pool: &BufferPoolManager) -> Result<RecoveryReport>;
/// ARIES physical undo for a live ROLLBACK (shared undo loop with recover() Pass 3).
pub fn rollback_txn(wal: &WalManager, store: &dyn PageStore, txn: TxnId, last_lsn: Lsn) -> Result<()>;

Semantics

  • LSNs are strictly increasing and >= 1. append assigns and returns the record’s LSN. In ARIES an LSN is typically the logical address of the record in the log address space;1 PostgreSQL likewise uses a byte position in an 8-byte log address space.3 Because Lsn = 0 is reserved for “no LSN yet”, never assign LSN 0: if you derive LSNs from file byte offsets, use 1 + start_offset or end_offset so record 0 gets Lsn >= 1.
  • prev_lsn chains a transaction’s records backward. Pass the LSN of the same transaction’s previous record (0 for its first). Rollback and the undo pass walk this chain; ARIES stores it as PrevLSN in every record.1
  • append buffers; only flush makes records durable. flush(up_to) must write every record with LSN ≤ up_to and sync_data before advancing flushed_lsn. Flushing the entire pending in-memory tail buffer whenever up_to > flushed_lsn() is standard, valid, and idempotent. Everything at or below flushed_lsn() survives a crash; unflushed records above it vanish on reopen.
  • PageInit and tuple records. PageInit { page_id } logs formatting a brand-new heap page (HeapPage::init) so crash recovery can re-initialize an unflushed newly allocated page before replaying tuple inserts onto it. Update carries both images (old_meta/old for undo, new_meta/new for redo — ARIES’ Data field serves both roles1); Insert needs no before-image (undo = tombstone the slot via HeapPage::delete); Delete carries old_meta/old (redo = delete again; undo = resurrect via HeapPage::put_at).
  • Clr is redo-only with typed ClrAction. Its action is either ClrAction::Tombstone (undoing an Insert) or ClrAction::Restore { meta, tuple } (undoing an Update or Delete via HeapPage::put_at). CLRs are applied on redo and never undone;1 undo_next holds the prev_lsn of the record it compensated.
  • checkpoint is fuzzy and returns the CheckpointEnd LSN. It appends CheckpointBegin, then CheckpointEnd carrying the ATT (txn, lastLSN) and DPT (page, recLSN) snapshots supplied by the caller, flushes through CheckpointEnd, and returns the CheckpointEnd LSN. It must not write any data pages — that is the whole point.1
  • iter_from must survive a torn tail. A crash can truncate the file mid-record; iteration yields durable records with LSN ≥ lsn and ends cleanly at the first incomplete or corrupt record instead of erroring the whole scan.
  • recover completes full ACID on top of Milestone 8. It reads and writes pages only through the buffer pool, performs all three ARIES passes (flushing the WAL and pool before returning), and populates RecoveryReport — including committed_txns and max_txn_id so startup can call TransactionManager::restore(report.max_txn_id, report.committed_txns) and keep committed MVCC tuples visible after restart.
Wiring across the crate-graph boundary (crates/ferricdb)

In the workspace dependency graph, ferricdb-exec sits below ferricdb-wal so it cannot name WalManager directly. Instead, crates/ferricdb (the binary crate) ties the layers together: wrap Arc<WalManager> in a small newtype (required by Rust’s orphan rule) that implements ferricdb_exec::WalHook (tracking each active transaction’s lastLSN, with WalHook::rollback delegating directly to ferricdb_wal::rollback_txn(&self.wal, store, txn, last_lsn)), install it in ExecContext::wal, install the same Arc<WalManager> as the buffer pool’s LogFlusher via pool.set_log_flusher(...), and on startup run let report = recover(&wal, &pool)?; followed immediately by txn_manager.restore(report.max_txn_id, report.committed_txns);. With that in place, both normal ROLLBACK (calling wal.rollback(txn.id(), &*ctx.store)? inside execute()) and crash recovery share one ARIES physical undo routine (HeapPage::delete / HeapPage::put_at + CLRs + Abort), unifying Milestone 8’s MVCC visibility with crash-safe durability.

Step-by-step guidance

Honest difficulty note

This is the hardest milestone in the course, harder than the B+Tree. Not because any one pass is long — each is under a hundred lines — but because correctness is invisible until a crash lands in exactly the wrong microsecond. Build in the order below, keep every step under test before starting the next, and let the crash-injection loop, not your intuition, be the judge. Budget two weeks.

Step 1 — Encode records and append them

Pick a simple binary framing for one record on disk: a length prefix, the payload (lsn, prev_lsn, a type tag, then the fields for all ten LogRecord variants including PageInit and both ClrAction cases), and a checksum. The checksum is not paranoia — it is how iter_from will distinguish “end of log” from “torn record at the crash point”. PostgreSQL splits its log into 16 MB segment files;3 a single append-only file is a fine course simplification. Keep an in-memory tail buffer protected by a mutex: append assigns the next strictly increasing Lsn >= 1 (e.g. 1 + start_offset or end_offset, never 0!), serializes into the tail, and returns without touching the disk. On WalManager::open, scan existing durable records and truncate the file to the end of the last valid record (discarding any torn trailing bytes from a mid-write crash so future appends never sit behind corrupt bytes) so new appends continue with strictly larger LSNs. Verify with ms9_append_iter_roundtrip_every_variant.

Step 2 — flush, flushed_lsn, iter_from

flush(up_to) writes the pending tail through at least up_to (flushing the entire pending tail buffer whenever up_to > flushed_lsn() is standard and valid), calls sync_data, and advances flushed_lsn only after fsync returns. Because the log is one sequential file, this is cheap — the PostgreSQL docs make the same point: syncing a sequential log costs far less than flushing scattered data pages, and one fsync can commit many concurrent transactions.7 iter_from(lsn) iterates durable records with LSN ≥ lsn, yielding (lsn, prev_lsn, record) triples until end-of-file or the first record whose length or checksum does not hold — stop there silently; that torn tail was never durable.

Step 3 — HeapPage::put_at and stamping pageLSN

First implement the public HeapPage::put_at(slot, meta, tuple) method in crates/storage (tested by ms9_heap_page_put_at_redo_undo): redo and undo must place a tuple at the exact slot named in rid, extending the line-pointer array with dead entries if slot >= slot_count(), or replacing/resurrecting slot in place (compacting first if the new payload is longer than the old space).

ARIES keeps a page_LSN in every page: the LSN of the log record describing the latest update applied to that page.1 PostgreSQL’s page header has the same field, pd_lsn.2 Thread ExecContext::wal (the WalHook trait) into the write paths that initialize or mutate heap pages (PageInit, Insert, Update, Delete). Because HeapFile's convenience methods acquire and release with_page_mut internally, perform logged page mutations directly inside ctx.store.with_page_mut(page_id, |page| ...) using HeapPage::attach (or HeapPage::init on newly allocated pages): while holding that page write latch, mutate the page, append the log record via WalHook, and call page.set_lsn(record_lsn) before returning from the closure. Holding the page latch across mutation, log append, and set_lsn guarantees no steal eviction can write the dirty page before its pageLSN is set, and keeps log order identical to page-apply order — which ARIES requires for physical redo.1 (Flush catalog DDL pages directly — catalog metadata updates do not need WAL records in Milestone 9.)

Step 4 — Enforce the WAL rule in the buffer pool

Implement LogFlusher for WalManager (delegating to self.flush(lsn)) and wire it with pool.set_log_flusher(wal.clone()) at startup. In crates/buffer, update every dirty write-back path — eviction, flush_page, and flush_all — to call flush_until(page.lsn()) before writing the page to disk (verify with ms9_log_flusher_enforced_before_dirty_write). This is the WAL protocol: the buffer manager forces the log up to the dirty page’s LSN before the page goes out.1 PostgreSQL states the same invariant as its central rule: data files may be written only after the WAL records describing the changes are on permanent storage.7 With this one hook, a steal policy (evicting pages dirtied by uncommitted transactions) becomes safe, because the before-images needed to undo them are guaranteed to be in the durable log.1

Step 5 — Transaction lifecycle: Begin, Commit, Abort, and restore

Log Begin when a transaction starts, and track each transaction’s lastLSN as you append its records. Commit is two steps with a big meaning: append Commit, then flush(commit_lsn) — and only report success to the caller after the flush returns. That is no-force: no data page is written at commit; the flushed log alone carries durability.1 Normal ROLLBACK is a rehearsal for restart undo, exposed via ferricdb_wal::rollback_txn(wal, store, txn, last_lsn) and wired into ExecContext::wal via WalHook::rollback: walk the transaction’s prev_lsn chain from its lastLSN (including any unflushed records still sitting in WalManager's in-memory tail); for each undoable record apply the inverse via HeapPage::delete (for Insert) or HeapPage::put_at (for Update/Delete), append a Clr carrying ClrAction::Tombstone or ClrAction::Restore with undo_next = rec.prev_lsn (stamping the page with the CLR’s LSN); finish with an Abort record. Write this as one reusable routine — the undo pass in step 9 is the same loop; ARIES presents it once as ROLLBACK and reuses it.1 (Real-world note: production PostgreSQL skips physical undo and CLRs on ROLLBACK because MVCC visibility hides aborted tuple versions until VACUUM cleans them up — its WAL is redo-only. FerricDB runs ARIES physical undo on both live ROLLBACK and restart recovery so you build the classic Mohan et al. algorithm end to end.) Also implement TransactionManager::restore(max_txn_id, committed) in crates/txn (tested by ms9_restore_committed_txns_after_restart): mark every recovered committed id as Committed and advance next_txid past max_txn_id so post-crash transactions see recovered data and never collide with pre-crash ids.

Step 6 — Fuzzy checkpoints and BufferPoolManager::dirty_pages

A checkpoint exists to bound how much log recovery must read; it must not stop the world. WalManager::checkpoint(active, dirty) appends CheckpointBegin, then CheckpointEnd carrying the ATT (each active transaction with its lastLSN) and the DPT (each dirty page with its recLSN), flushes through CheckpointEnd, and returns the CheckpointEnd LSN. Record the checkpoint’s location in a small master/metadata file (alongside the cumulative committed_txns and max_txn_id observed by WalManager up to this checkpoint, written atomically via temp-file + rename) — the analog of ARIES’ master record and of PostgreSQL’s pg_control + pg_xact, which persist the latest checkpoint location, nextXid, and durable commit status so recovery stays bounded to the last checkpoint without ever scanning from LSN 0.14 Only trust a checkpoint whose CheckpointEnd reached durable storage: an incomplete checkpoint must be ignored.1

The recLSN needs care: record it in BufferPoolManager when a clean frame first transitions to dirty, and clear it when the page is flushed or evicted — then expose the snapshot of currently dirty frames via BufferPoolManager::dirty_pages() (part of the public API in api-spec.md). Crucially, a fuzzy checkpoint forces no dirty pages1 — PostgreSQL’s checkpointer likewise dribbles dirty pages out gradually while traffic continues, on a timer that defaults to 300 seconds.4

Step 7 — Recovery I: the analysis pass

Analysis seeds committed_txns and max_txn_id from the last complete checkpoint’s metadata (if any), then starts at that checkpoint’s CheckpointBegin (or LSN 0 if none) and scans forward to the end of the log.1 Track a local ended set of transactions whose Commit or Abort record you observe during this scan, and update ATT, DPT, committed_txns, and max_txn_id from every record:

  • When passing CheckpointEnd, merge its snapshot carefully so concurrent records already seen between CheckpointBegin and CheckpointEnd are never clobbered: for each (txn, last_lsn) in active_txns, insert into ATT only if txn is neither already in ATT nor in ended (a transaction that committed or aborted mid-checkpoint must not return as a loser!); for each (page, rec_lsn) in dirty_pages, insert into DPT or keep the smaller recLSN if the page is already present.
  • Any record naming a transaction updates max_txn_id; if the transaction is not yet in the ATT, add it, and update its lastLSN.
  • Any page-touching record (PageInit/Insert/Update/Delete/Clr) whose page is not in the DPT adds it with recLSN = the record’s own LSN.
  • Commit records add the transaction to committed_txns and ended and remove it from the ATT; Abort records add it to ended and remove it from the ATT (an Abort is only written after rollback finished, so nothing remains to undo).

Whoever remains in the ATT at end of scan is a loser. The redo starting point is the minimum recLSN in the DPT; if the DPT is empty, redo can be skipped entirely.1

Step 8 — Recovery II: redo repeats history

Redo scans forward from the minimum recLSN and re-applies every missing page change — including those of loser transactions and including CLRs. This “repeating history” is the paradigm the paper is built on: first re-establish the exact state as of the crash, then roll losers back from that known state.1 The decision procedure, from ARIES Fig. 11 (pseudocode of the published algorithm — your Rust will differ):

for (lsn, _prev, rec) in wal.iter_from(min_recLSN):
    if rec touches a page
       and rec.page ∈ DPT
       and lsn ≥ DPT[rec.page].recLSN:        # filter 1: no disk read needed
        fetch the page via the buffer pool
        if page.pageLSN < lsn:                 # filter 2: is the effect present?
            re-apply the record's redo action
            page.pageLSN := lsn                # no new log records are written

Filter 1 uses only the DPT and skips records without touching the disk; filter 2 reads the page and asks whether the effect already made it out before the crash. Both are required and they are not the same test (see the pitfalls). Setting pageLSN := lsn after each application is what makes redo idempotent; nothing is logged during the redo pass.1 PostgreSQL’s recovery makes the identical comparison — a record is replayed only when its LSN beats the page’s pd_lsn, because replaying a change that is already present is not an idempotent operation.5

Step 9 — Recovery III: undo the losers

Undo rolls back all losers in one backward sweep, in reverse LSN order across transactions: repeatedly pick the loser with the largest next-LSN-to-undo and process that record.1 Adapted from ARIES Figs. 8 and 12:

undo_next[t] := lastLSN(t) for every loser t
while any undo_next[t] ≠ 0:
    t := loser with the largest undo_next[t];  rec := record at undo_next[t]
    match rec:
        Insert/Update/Delete →
            apply the inverse via HeapPage::delete / HeapPage::put_at
            clr := append Clr { txn: t, rid: rec.rid,
                                action: Tombstone | Restore { meta, tuple },
                                undo_next: rec.prev_lsn }
            page.pageLSN := clr.lsn
            undo_next[t] := rec.prev_lsn
        Clr   → undo_next[t] := rec.undo_next      # skip; CLRs are never undone
        Begin → undo_next[t] := 0
    if undo_next[t] == 0:
        append Abort { txn: t }                    # fires on Begin, prev_lsn == 0, or Clr(0)

Two things are deliberately absent. Undo never consults the DPT, and never compares pageLSNs — because history was already repeated, the page state is exactly what the log says it is, so the undo applies unconditionally.1 And when undo meets a CLR (left over from a rollback that a crash interrupted, or from a previous recovery that itself crashed), it does not undo it — it follows undo_next straight past the work that was already undone. That single pointer is what bounds logging even across repeated failures: each undoable record produces at most one CLR, ever.1 Flush the WAL and the buffer pool before returning RecoveryReport (redone, undone, loser_txns, committed_txns, max_txn_id).

One contrast worth knowing: the recovery walkthrough in interdb Ch. 9.8 is redo-only — PostgreSQL replays from the REDO point and stops,5 leaning on MVCC (your Milestone 8 machinery) to keep aborted rows invisible instead of erasing them at restart. FerricDB implements full ARIES physical undo on both normal ROLLBACK and crash recovery as a course choice: it teaches the canonical three-pass algorithm and keeps the WAL self-contained, while TransactionManager::restore restores committed MVCC state after recovery completes.

Step 10 — The kill-the-process harness

The provided sim-crash tests fake a crash: run a workload, drop the buffer pool without flushing data pages (the WAL file survives), reopen, recover, check invariants. They are fast and seeded, and they will catch most bugs. But a simulated crash only loses what you remembered to throw away. The real harness — your job here — kills an actual process at an arbitrary instruction:

  1. Give the test binary a child mode. At the top of a harness test, check an environment variable (say FERRICDB_MS9_CHILD). If set, run the child role; otherwise run the parent role. The parent re-executes its own binary via std::process::Command::new(std::env::current_exe()?) with the variable set, plus a seed and a database path — a standard libtest re-exec pattern.
  2. Child: open the database, run a seeded workload of small transactions — inserts, updates, deletes; commit some, abort others; make each row’s values derivable from (txn number, seed) so the parent can validate content, not just counts. After each successful commit, print COMMITTED <n> to stdout and flush stdout. At a seeded random operation count, call std::process::abort() — no destructors, no flushes, no goodbye.
  3. Parent: wait for the child (expect an abnormal exit), collect the COMMITTED lines, reopen the database, run recover() and txn_manager.restore(report.max_txn_id, report.committed_txns), and assert the two invariants: every transaction acknowledged before the crash is fully present with correct contents, and no rows from aborted or unfinished transactions are visible. The check is deliberately one-sided: a commit that returned but whose stdout line was lost in the crash is allowed to survive — it must never be half-present.
  4. Loop over a hundred or more seeds, and for extra credit re-kill the child during recovery (child mode: recover, then abort at a random point) and recover again — recovery must be idempotent.

Common pitfalls

Appending to the log without stamping the pageLSN

If a page change is logged but set_lsn is skipped, redo’s filter 2 sees a stale pageLSN and re-applies a change that is already present. Redo of a slotted-page mutation is not idempotent — PostgreSQL guards replay with exactly this LSN comparison for the same reason.5 Symptom: duplicate rows or doubly-applied updates after recovery, and a database that gets worse each time you recover it again.

Undoing CLRs

Never. CLRs are redo-only; when undo encounters one it follows undo_next and moves on.1 If you “undo the undo”, a crash during rollback resurrects aborted data on the next restart, and repeated crashes make the log grow without bound — the exact failure ARIES cites in older systems that compensated compensations.1 Symptom: the crash-during-recovery loop flip-flops a row between states instead of converging.

Conflating the two redo filters

“Page not in the DPT (or LSN < recLSN)” and “pageLSN ≥ record LSN” are different tests with different jobs: the first prunes log records using only in-memory tables, the second is the ground truth read from the page itself.1 Skip the second and you double-apply to pages that were flushed just before the crash; skip the first and you are merely slow — until you “optimize” by treating recLSN as the application test, which corrupts pages whose on-disk state is newer than the DPT thinks. Symptom: corruption that only appears when a checkpoint, an eviction, and a crash interleave — i.e., only under the randomized loop.

Flushing the commit record without everything before it

flush(up_to) is a prefix operation: every record with LSN ≤ up_to goes out, in order, before the fsync. If your implementation flushes selected records — say, just the commit — the durable log can hold a commit whose updates are missing, and recovery will happily declare a winner it cannot redo. The WAL guarantee is stated over the whole prefix: changes are recoverable because all records describing them reached storage first.7 Symptom: committed rows vanish, but only when the crash lands between two partial flushes.

Treating the checkpoint as a barrier

A fuzzy checkpoint promises nothing about data pages — it forces none of them.1 It is where analysis starts, not where redo starts: redo begins at the minimum recLSN, which can lie far before the checkpoint (Figure 3), and records written between begin_chkpt and end_chkpt still need scanning.1 If you start redo at the checkpoint, every page dirtied before it and never flushed silently loses its changes. Symptom: committed data missing, but only in runs where a checkpoint happened while old dirty pages were still in the pool.

Recovery that assumes it will finish

A crash during recovery must leave the system recoverable again — that is the whole design: redo is guarded by pageLSN, and CLRs written by the undo pass carry undo_next so a second undo resumes rather than repeats.1 But the property only holds if your recovery honors the WAL rule too — the buffer manager follows the usual protocol while writing pages during recovery,1 so wire the LogFlusher hook before calling recover(). Symptom: recovering once works; killing the process mid-recovery and recovering again panics or loses data.

  • Your process-kill harness (step 10) demonstrates the same two invariants across at least 100 seeded kills, including kills during recovery, and is documented in your repo so a grader can run it.
  • Recovery is idempotent: running recover() on an already-recovered database, or crashing mid-recovery and recovering again, converges to the same committed state, and TransactionManager::restore restores recovered committed transaction ids on startup.
  • The WAL rule is airtight: no code path writes a page whose pageLSN exceeds flushed_lsn() — add a debug assertion in the buffer pool’s write-back path and leave it on in tests.
  • COMMIT returns to the caller only after the log is flushed through the commit record’s LSN; no data pages are flushed at commit.
  • Checkpoints bound recovery: after a checkpoint plus more traffic, restart scans the log only from the checkpoint (analysis) and the minimum recLSN (redo) — verify by counting records scanned, not by vibes.
  • Earlier ms1_–ms8_ suites (via --include-ignored) and baseline cargo test --workspace stay green — the WAL wiring must not regress earlier milestones.
